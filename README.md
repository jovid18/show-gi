# show-gi — AI가 「언제 입을 열지」를 스스로 정한다

[![show-gi — 입을 열 때를 스스로 정하는 쇼기 상대](apps/web/public/og.png)](https://show-gi.com)

> **AI가 사람의 행동에 개입할 타이밍과 강도를 스스로 조절하는 제품.** 검증 도메인은 쇼기(将棋)다.

**https://show-gi.com** — 로그인 없이 그대로 한 판 둘 수 있다.

설계와 개발 문서는 [docs/](docs/README.md)에 있다. 하나만 읽는다면 [docs/01-core.md](docs/01-core.md).

## 1. 무엇을 하는 것인가

초심자가 **큰 실수를 두는 순간에만** 판이 멈추고, **왜 나쁜지**를 설명해 다시 두게 한다. 평소에는 최선수를 보여주지 않는다. 그리고 상대 AI의 강함은 당신이 둔 수를 보고 **한 판 안에서** 움직인다 — 스승의 指導対局처럼.

### 멈추는 데서 끝내지 않고, 「왜」를 판 위에서 보여준다

悪手를 잡으면 착수를 되돌린 뒤, 무엇이 잡히는지를 판 위의 공격선과 짧은 설명으로 보여준다. 카드에는 그 수를 되돌리지 않고 계속했을 때의 상대 후보수도 함께 선다. 숫자만으로 「악수입니다」라고 채점하는 것이 아니라, **다음에 무슨 일이 벌어지는지를 같은 국면에서 확인한 뒤 다시 두게 하는** 화면이다.

[![悪手를 멈추고 이유와 상대의 응수를 보여주는 대국 화면](docs/images/show-gi-intervention.png)](https://show-gi.com)

_▲3三角成를 되돌린 순간. 馬가 잡히는 이유와, 그대로 진행했을 때의 응수를 같은 화면에서 보여준다._

컴퓨터 쇼기는 지금도 양극단이다. 약한 설정은 있을 수 없는 자리에 駒를 버리며 자멸하고, 강한 설정은 이쪽의 작은 실수 하나로 국면이 통째로 뒤집힌다. **「사람이 결국 이기는 데까지 데려가는」 상대**가 그 사이에 하나도 없다.

## 2. 설계 원칙은 셋뿐

### ① 판단도 설명도 결정적이다

悪手인지 아닌지, 어느 카테고리인지, 무엇이 잡히는지 — **결정적 룰과 엔진의 평가치**가 정한다. 화면에 나가는 일본어도 그 사실에서 코드가 조립한다.

학습 앱에서 설명이 틀리면 초심자에게는 그것을 검증할 수단이 없다. **틀린 것을 그대로 배운다.** 그래서 「이 국면 어떻게 생각해?」라고 판을 통째로 생성 모델에 던지는 경로는 이 레포에 한 줄도 없다.

생성 모델이 도는 자리는 둘뿐이고, 둘 다 **받아 적기만 한다.** **가져온 기보의 서식을 옮겨 적는 자리**(`internal/kifunorm`)와 **판이 찍힌 그림을 읽는 자리**(`internal/boardread`)다.

어느 쪽에도 좌표를 만들게 하지 않는다. 프롬프트는 筋도 段도 한 번 말하지 않고, 그림 쪽이 듣는 말은 「위 줄부터, 왼쪽부터, 그려진 대로」 하나뿐이다. 先手인지 後手인지도 정하게 하지 않는다 — 그림에서 알 수 있는 것은 「위쪽 駒인가 아래쪽 駒인가」뿐이고, 아래쪽을 先手로 두는 것은 코드가 정한다.

옮겨 적은 표기는 한 手씩 룰 엔진의 검산을 지나야 지 수가 되므로, 기보 쪽은 지어내면 반드시 거기서 떨어지고 가져오기가 거부된다. 그림 쪽은 지 수의 나열이 없으니 국면 자체를 검산한다(二歩·玉의 수·行き所のない駒·王手放置). **그래도 안 잡히는 오독이 있다** — 銀을 成銀으로 읽은 판은 그 자체로 합법인 국면이다. 그래서 읽어 낸 국면은 반드시 당신에게 보여 주고, 고쳐 받은 뒤에 해석한다.

같은 사실에는 반드시 같은 문장이 나간다. 카테고리마다 **말해도 되는 사실**이 정해져 있고(`explain.Facts`), 거기 없는 것은 문장에 나타나지 않는다.

### ② 최선수를 가르쳐 주지 않는다

수를 대신 놓아 주는 순간, 사람은 생각하기를 멈춘다.

- 제지형(悪手 뒤) — 「왜 나쁜가」까지
- 詰み 게이지 — 수순도 手數도 안 낸다. 판의 테두리가 타오를 뿐
- 둔 뒤에 붙는 이름(囲い·戦法·戦型) — 「지금 이렇게 되어 있다」까지

수를 짚어 주는 힌트는 둘이고, **둘 다 「기댈 수 없다」가 조건**이다.

- **갇힘 힌트** — 같은 국면에서 3회 되물리면 그 駒에, 5회에 手에 표시가 붙는다. 다섯 번 실패해야 열리는 문이다
- **부르는 힌트** — 버튼으로 부른다. 같은 국면에서 1회째는 그 駒, 2회째에 그 手, 3회째는 없다. **판당 6회**라 답까지 볼 수 있는 것은 최대 3手다

부른 국면의 手는 **실력 추정에서 뺀다.** 가르쳐 준 수를 그대로 둔 것이 실력으로 기록되면 화면에 나가는 段級이 부풀기 때문이다.

**검토 화면은 이 원칙 밖에 있다.** 手合割을 골라 初手부터 놓아 보는 판이고, 거기서는 최선수 3手를 그대로 낸다 — 답을 보러 오는 화면이기 때문이다. 그래서 **대국 중에는 이 화면을 안 띄운다**: 두는 중에 열 수 있으면 이 절이 의미를 잃는다.

다만 그 벽은 **열려 있는 브라우저 탭 안에만 있다** — 다른 탭에서 여는 것을 막는 장치는 없고, 서버는 「지금 두고 있는가」를 모른다. 혼자 쓰는 학습 앱이라 그 자리는 장치가 아니라 놓는 방식의 문제로 남겨 두었다.

### ③ 탐색은 무조건 깊이로 건다. 시간으로 자르지 않는다

같은 국면을 언제나 같은 기준으로 판정하기 위해, 탐색은 시간이 아니라 깊이로 고정한다. 서버가 붐빈다고 悪手 판정이나 상대의 강함이 달라지지 않아야 하기 때문이다.

## 3. 개입 루프

<picture>
  <source media="(prefers-color-scheme: dark)" srcset="docs/images/intervention-loop.dark.svg">
  <img alt="개입 루프 — 착수마다 승률의 낙폭을 재고, 임계치를 넘으면 제지해 다시 두게 한다" src="docs/images/intervention-loop.svg" width="900">
</picture>

판정식은 평가치를 그대로 쓰지 않고, **승률로 옮긴 뒤 낙폭**을 본다. cp의 차는 언제나 같은 무게가 아니다. 호각에 가까운 국면의 300cp와, 이미 크게 벌어진 국면의 300cp는 이길 가망의 변화가 전혀 다르기 때문이다.

$$WR(cp) = \frac{1}{1 + e^{-cp/K}}, \qquad \Delta = WR(\text{최선수 뒤}) - WR(\text{실제로 둔 수 뒤})$$

종반에서는 이 식이 포화한다(+2000cp에서 詰み까지 Δ 3.5%p). 그래서 **詰み까지의 거리**로 기준을 바꾼다 — 詰将棋 solver가 詰み을 찾은 순간부터가 이 제품의 「종반」이고, 5手 이하의 詰み을 놓치는 수만 멈춘다. 11手詰め를 못 본 것은 8급에게 실수가 아니기 때문이다.

## 4. 지금 실제로 도는 것

| 기능              | 내용                                                                                                                                      |
| ----------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| **대국과 개입**   | 룰 엔진·엔진 판정·일본어 기보. 悪手는 이유를 짚어 다시 둘 수 있다                                                                         |
| **힌트와 待った** | 갇혔을 때의 계단식 힌트, 부르는 힌트(판당 6회), 待った(판당 3회)                                                                          |
| **적응형 상대**   | 지 수의 질에서 강함을 대국 중에 조절한다. 안전하지 않은 후보수는 고르지 않는다                                                            |
| **되짚기와 총평** | 평가치 그래프, 국면에서의 분기, 종국 뒤 총평, 같은 한 판에서 만드는 퀴즈                                                                  |
| **학습의 실마리** | 詰み 게이지, 囲い·戦法·戦型·手筋 태그, 무너지기 쉬운 곳                                                                                   |
| **기록과 로그인** | 로그인 없이 대국 가능. 로그인하면 실력의 변화와 중단한 판을 이어받는다                                                                    |
| **친구와 대국**   | 초대 링크로 일대일. **들어갈 수 있는 것은 두 명뿐**, 지 시간은 한 手 60초. 개입은 나오지 않는다                                           |
| **검토**          | 手合割을 골라 初手부터 직접 놓으며 형세와 **최선수 3手**를 확인한다. 대국 중에는 안 띄운다                                                |
| **설명과 표시**   | 설명은 카테고리와 국면의 사실에서 결정적으로 조립한다. 판은 three.js로 그린다                                                             |
| **기보 가져오기** | 다른 데서 둔 자기 기보를 붙이면 여기서 둔 한 판과 같은 해석·퀴즈·실력 추정까지 지난다. KIF·KI2·CSA·USI를 읽고, 못 읽는 서식만 AI가 옮긴다 |
| **판 사진 읽기**  | 판이 찍힌 그림을 올리면 국면을 읽어 낸다. 사람이 확인해 고친 뒤에 검토 화면으로 넘어간다                                                  |
| **놀이법 안내**   | 개입의 흐름, 悪手의 종류, 힌트 횟수를 대국 전에 확인할 수 있다                                                                            |

### 한 판을, 두고 끝내지 않는다

되짚기에서는 평가치 그래프가 그대로 국면의 이동 장치가 된다. 빨간 점은 개입이 일어난 자리이고, 고르면 그 시점의 판과 후보수가 열린다. 총평으로 한 판 전체를 읽고, 마음에 걸린 국면에서는 **다른 수를 그 판에서 실제로 둬 보며** 앞을 확인할 수 있다.

[![평가치 그래프, 총평, 후보수를 한 국면에서 확인하는 되짚기 화면](docs/images/show-gi-review.png)](https://show-gi.com)

_평가치의 궤적, 총평, 후보수, 판을 한 화면에 두었다. 그래프 위의 36手째에서 다른 수순을 두고 있는 참이다._

### 끝난 한 판이, 그대로 문제가 된다

일반 문제를 푸는 것이 아니라, **자기가 방금 둔 한 판**에서 詰み 1문과 최선수 3문까지를 만든다. 詰み 문제는 맞힐 때까지 답을 내지 않고, 판 위에서 王手를 이어 간다. 채점할 때마다 엔진을 부르는 것이 아니라, 종국 시점에 마련해 둔 정답 수순으로 판정한다.

_98手째에 있던 7手詰め. 남은 手數와 「王手가 되는 수만」이라는 조건까지 보여 주고, 수순 자체는 감춘다._

### 3D로 만들어도 판독성은 떨어뜨리지 않는다

판은 3D지만 **원근법이 아니다.** 쇼기의 駒는 전부 같은 오각형이고, 한자로만 구별하며, 방향으로 先後를 나타낸다. 원근 투영을 넣는 순간 안쪽 한자가 뭉개지고, 상대 駒는 뒤집힌 채 세로로 눌리고, 앞이 뒤를 가린다. **학습 앱에서 판독 부하를 올리면 앱이 자기 목적과 싸우게 된다.**

  <source media="(prefers-color-scheme: dark)" srcset="docs/images/architecture.dark.svg">
  <img alt="브라우저 · Go API 의 여덟 패키지 · USI 엔진 · PostgreSQL 의 구성" src="docs/images/architecture.svg" width="900">
</picture>

| 구분   | 내용                                                                                        |
| ------ | ------------------------------------------------------------------------------------------- |
| 서버   | Go 단일 서비스. 대국 상태는 세션마다 직렬로 관리하고, 탐색만 병행 실행한다                  |
| 엔진   | やねうら王 9.40 + 水匠5. 詰み 탐색에는 전용 solver를 쓴다                                   |
| 프론트 | React + TypeScript + Vite + three.js. 합법수 판정은 전부 서버 쪽                            |
| DB     | PostgreSQL 17. 대국과 해석(국면별 평가치 캐시)을 저장                                       |
| 인프라 | AWS ECS on EC2 스팟(c6g.large / ARM64) + ALB + RDS + Route53. Terraform, GitHub OIDC로 배포 |

**EC2 티어가 둘이고, 가르는 것은 `SERVER_ROLE` 하나다.** 대국(상호작용) 대는 1대 고정이다 — 대인전 방이 짝지은 프로세스의 메모리에 있어서, 두 대가 되면 초대와 매칭이 절반 확률로 깨진다. 늘어나는 것은 **해석 대**뿐이고, 밀린 手 지표를 CloudWatch 알람이 보고 ECS 서비스의 대수를 계단식(StepScaling)으로 움직인다. 용량 공급자가 미배치 태스크를 보고 EC2를 따라 올리며, 새 대가 일을 받기까지 실측 3분이다. 목표 추적을 안 쓰는 이유는 이 층의 임계치가 이미 부하 회차의 실측으로 잡혀 있어서다 — 그것을 다시 짓는 것은 두 번째 진실이 된다.

**대국 상태는 세션 goroutine 하나가 소유한다.** 다시 두는 중에 낡아진 해석 결과는 버려서, 판과 설명이 어긋나지 않게 한다.

## 6. 개발

```sh
pnpm install
docker compose up -d          # api + db
pnpm dev                      # http://localhost:5173
```

**엔진이 arm64 Debian 바이너리라 macOS에서는 직접 안 돈다.** api는 반드시 컨테이너로 띄운다.

```sh
# 검증
pnpm lint && pnpm typecheck && pnpm test && pnpm build
cd apps/server && gofmt -l . && go vet ./... && go test -race ./...
terraform -chdir=infra fmt -check && terraform -chdir=infra validate
```

> `go test` 만으로는 다 안 돈다. DB·엔진 테스트는 환경변수가 없으면 **조용히 skip 되고 초록으로 보인다.** 무엇이 필요한지는 [apps/server/README.md](apps/server/README.md)에 표로 있다.

자세한 구성은 [apps/server/README.md](apps/server/README.md)와 [apps/web/README.md](apps/web/README.md)에, 배포 절차는 [deploy/README.md](deploy/README.md)에 있다.
