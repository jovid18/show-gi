## 1. 프로젝트 목표

초심자가 큰 실수를 두는 순간에만 판을 멈추고, 왜 나쁜지를 판 위에서 보여준 뒤 다시 두게 하는 쇼기 상대. 평소에는 최선수를 알려주지 않고, 상대 AI의 강함은 플레이어가 둔 수를 보고 한 판 안에서 이동 — 指導対局에 가까운 형태.

기존 컴퓨터 쇼기가 비워 둔 자리:

- 약한 설정 — 있을 수 없는 자리에 駒를 버리며 자멸
- 강한 설정 — 작은 실수 하나로 국면이 통째로 뒤집힘
- 그 사이, 「사람이 결국 이기는 데까지 데려가는 상대」가 없음

### 핵심 기능 — 悪手 개입

悪手를 잡으면 착수를 되돌리고, 무엇이 잡히는지를 판 위의 공격선과 짧은 설명으로 제시. 카드에는 되돌리지 않고 진행했을 때의 상대 응수도 함께. 채점이 아니라 같은 국면에서 다음 수순을 확인하고 다시 두는 화면.

[![悪手를 멈추고 이유와 상대의 응수를 보여주는 대국 화면](docs/images/show-gi-intervention.png)](https://show-gi.com)

_▲3三角成를 되돌린 순간. 馬가 잡히는 이유와, 그대로 진행했을 때의 응수를 한 화면에._

## 2. 아키텍처

Go 한 프로세스 안의 여덟 패키지가 역할을 나누고, 엔진은 파이프 건너편의 별도 프로세스.

<picture>
  <source media="(prefers-color-scheme: dark)" srcset="docs/images/architecture.dark.svg">
  <img alt="브라우저 · Go API 의 여덟 패키지 · USI 엔진 · PostgreSQL 의 구성" src="docs/images/architecture.svg" width="900">
</picture>

| 구분   | 내용                                                                                      |
| ------ | ----------------------------------------------------------------------------------------- |
| 서버   | Go 단일 서비스. 대국 상태는 세션마다 직렬, 탐색만 병행                                    |
| 엔진   | やねうら王 9.40 + 水匠5. 詰み 탐색은 전용 solver                                          |
| 프론트 | React + TypeScript + Vite + three.js. 합법수 판정은 전부 서버                             |
| DB     | PostgreSQL 17. 대국과 해석(국면별 평가치 캐시)                                            |
| 인프라 | AWS ECS on EC2 스팟(c6g.large / ARM64) + ALB + RDS + Route53. Terraform, GitHub OIDC 배포 |

규약 셋:

- **대국 상태는 세션 goroutine 하나가 소유.** 롤백이 있는 이상 상태 변경 순서가 곧 제품 정합성이라, HTTP 핸들러는 상태를 직접 읽지 않음. 다시 두는 중에 낡아진 해석 결과는 폐기
- **패키지마다 모르는 것이 고정.** 개입 판정(`intervene`)의 입력은 평가치와 詰み 거리뿐이라 상수 조정에 엔진이 불필요. 실력 추정(`skill`)은 엔진 · DB · 판을 모름
- **모든 탐색은 데이터로 잔존.** `archive` 가 국면과 깊이별 값을 적재하고, 여섯 자리(상대 수 · 개입 판정 · 가정 수순 · 검토 · 부르는 힌트 · 되짚기 퀴즈)가 그 한 겹을 통과. 같은 국면 재질의가 1.54s → 27ms(로컬 실측), 詰み 캐시는 프로덕션 8판 동시에서 90.8%

### 오토 스케일링 — 늘어나는 것은 해석 티어뿐

대국은 대기 시간이 곧 체감, 종국 뒤 해석은 늦어도 무관. 그래서 EC2 티어 둘, 가르는 것은 `SERVER_ROLE` 하나.

<picture>
  <source media="(prefers-color-scheme: dark)" srcset="docs/images/autoscaling.dark.svg">
  <img alt="오토 스케일링 — 밀린 手를 알람이 보고 ECS 대수를 계단식으로 조절" src="docs/images/autoscaling.svg" width="900">
</picture>

| 구분         | 내용                                                                |
| ------------ | ------------------------------------------------------------------- |
| 신호         | 밀린 手 `AnalysisBacklogPlies` 하나. EMF 로그가 매분 한 점          |
| 스케일 아웃  | 5분 연속 100手 초과 → StepScaling +1. cooldown 5분, 상한 2대        |
| 스케일 인    | 30분 연속 0 → −1. cooldown 10분                                     |
| 새 대의 준비 | 용량 공급자가 미배치 태스크를 보고 EC2 기동. 일을 받기까지 실측 3분 |

목표 추적 대신 StepScaling — 이 층의 임계치가 부하 회차 실측으로 이미 고정돼 있고, 밀린 手가 대수에 반비례하지 않아 「용량 한 단위당 부하」 꼴이 아니기 때문.

스케일 인의 신호는 임계 100의 반대쪽이 아니라 「30분 내내 비어 있음」. 밀린 手는 포화 신호라서, 여유 있는 상태와 일이 없는 상태를 가르는 기준이 연속 시간.

### 되짚기 — 평가치 그래프가 국면의 이동 장치

그래프를 눌러 국면 이동. 빨간 점이 개입이 일어난 자리이고, 고르면 그 시점의 판과 후보수. 총평으로 한 판 전체를 읽고, 마음에 걸린 국면에서는 다른 수를 그 판에서 직접 둬 보기.

_평가치의 궤적 · 총평 · 후보수 · 판을 한 화면에. 그래프 위의 36手째에서 다른 수순을 둬 보는 중._

### 퀴즈 — 방금 둔 한 판에서 출제

일반 문제가 아니라 자기가 둔 판에서 詰み 1문과 최선수 3문. 詰み 문제는 맞힐 때까지 답을 내지 않고 판 위에서 王手를 이어감. 채점은 종국 시점에 저장한 정답 수순으로 — 매번 엔진을 부르지 않음.

## 4. 개입 판정 — 판단과 표현 모두 결정적

悪手 여부, 카테고리, 무엇이 잡히는지 — 모두 결정적 룰과 엔진 평가치로 결정. 화면 문구도 그 사실에서 코드가 조립하므로 같은 사실이면 같은 문장. 카테고리별로 쓸 수 있는 사실은 `explain.Facts` 에 고정.

<picture>
  <source media="(prefers-color-scheme: dark)" srcset="docs/images/intervention-loop.dark.svg">
  <img alt="개입 루프 — 착수마다 승률의 낙폭을 재고, 임계치를 넘으면 제지 후 다시 두기" src="docs/images/intervention-loop.svg" width="900">
</picture>

판정식은 평가치를 그대로 쓰지 않고 승률로 옮긴 뒤 낙폭을 봄. 같은 cp 차이의 무게가 국면마다 다르기 때문 — 호각인 국면의 300cp와 이미 벌어진 국면의 300cp는 이길 가망의 변화가 전혀 다름.

$$WR(cp) = \frac{1}{1 + e^{-cp/K}}, \qquad \Delta = WR(\text{최선수 뒤}) - WR(\text{실제로 둔 수 뒤})$$

종반에는 이 식이 포화(+2000cp에서 詰み까지 Δ 3.5%p). 그래서 기준을 詰み까지의 거리로 교체 — 詰将棋 solver가 詰み을 찾은 순간부터가 이 제품의 종반이고, 5手 이하의 詰み을 놓치는 수만 제지. 11手詰め는 8급 기준에서 실수가 아님.

탐색은 깊이 고정(`go depth`), 시간 미사용. 같은 국면이면 항상 같은 기준으로 판정되고, 서버 부하가 悪手 판정과 상대의 강함을 흔들지 않음. 지연은 캐시와 선행 계산으로 처리.

### 최선수를 알려주지 않는 선

각 표시가 말하는 범위를 고정.

| 표시                               | 어디까지                             |
| ---------------------------------- | ------------------------------------ |
| 제지형 (悪手 뒤)                   | 왜 나쁜가                            |
| 詰み 게이지                        | 판 테두리의 불꽃. 수순도 手数도 없음 |
| 둔 뒤에 붙는 이름 (囲い·戦法·戦型) | 지금 이렇게 되어 있다                |

수를 짚어 주는 힌트는 둘. 조건은 「기댈 수 없어야 한다」.

| 힌트        | 문이 열리는 조건               | 무엇이 붙나                          |
| ----------- | ------------------------------ | ------------------------------------ |
| 갇힘 힌트   | 같은 국면에서 3회 되물림 → 5회 | 3회에 그 駒, 5회에 그 手             |
| 부르는 힌트 | 버튼. 판당 6회                 | 1회째 그 駒, 2회째 그 手, 3회째 없음 |

부르는 힌트는 판당 6회라 답까지 볼 수 있는 것이 최대 3手. 힌트를 부른 국면의 手는 실력 추정에서 제외 — 알려준 수를 그대로 둔 것이 실력으로 남으면 화면의 段級이 부풀기 때문.

## 5. LLM — 「받아 적는 일」 두 자리

판을 통째로 생성 모델에 던지고 「이 수 어때?」를 묻는 경로 없음. 학습 앱에서 설명이 틀리면 초심자에게 검증 수단이 없으므로, 판단과 표현은 전부 결정적 코드가 담당. 생성 모델이 도는 자리는 둘, 둘 다 받아 적는 일.

<picture>
  <source media="(prefers-color-scheme: dark)" srcset="docs/images/llm-pipeline.dark.svg">
  <img alt="LLM 계층 — 기보 정규화와 사진 읽기. 두 갈래 모두 룰 엔진의 검증을 통과" src="docs/images/llm-pipeline.svg" width="900">
</picture>

경계는 「좌표를 안 시킨다」. 프롬프트에 筋 · 段 · 「5五」가 한 번도 없음. 사진 쪽이 받는 지시는 「위 줄부터, 왼쪽부터, 그려진 대로」 하나이고, 그 순서가 SFEN 판 칸의 순서와 같아서 옮기는 코드에 좌표 계산이 없음. 先手 · 後手도 시키지 않음 — 사진에서 알 수 있는 것은 위쪽 편인지 아래쪽 편인지뿐이고, 아래쪽을 先手로 두는 것은 코드의 결정.

검증자는 계층마다 다름.

| 계층               | 검증자                                                                                     |
| ------------------ | ------------------------------------------------------------------------------------------ |
| 기보 (`kifunorm`)  | 룰 엔진의 한 手씩 검증(`shogi.ValidateMove`). 출력에 믿는 부분 없음                        |
| 사진 (`boardread`) | 국면 검사(`shogi.Faults` — 二歩 · 玉의 수 · 行き所のない駒 · 王手放置) 뒤 사람의 확인 화면 |

결정적 파서가 하나라도 성공하면 이 계층은 호출되지 않음. 같은 기보가 항상 같은 결과를 주는 것이 기본값이고, 정규화는 그 기본값이 성립하지 않는 자리에서만 동작.

### 기보 가져오기 — 파서가 먼저

KIF · KI2 · CSA · USI는 결정적 파서가 그대로 읽고, 읽힌 手는 한 手씩 룰 엔진을 통과. 화면은 手数 · 양쪽 이름 · 결과와 수순 앞뒤를 먼저 제시하고, 어느 편이었는지만 사람에게 질문 — 段級을 어느 쪽으로 셀지가 그 답으로 정해짐.

[![붙여 넣은 KIF를 읽어 手数와 결과를 보여주는 기보 가져오기 화면](docs/images/show-gi-import.png)](https://show-gi.com)

_KIF 한 벌을 붙여 넣은 직후. 15手 · 先手の勝ち까지 파서가 읽었고, LLM은 호출되지 않음._

### 판 사진 읽기 — 사람이 확정

올린 사진과 읽어 낸 판을 나란히 두고, 칸을 눌러 駒를 고치고 持ち駒를 맞춤. 확정 전에 룰 엔진이 국면을 검사하므로 성립하지 않는 판은 해석으로 넘어가지 않음.

[![올린 사진과 읽어 낸 판을 나란히 두고 사람이 확정하는 확인 화면](docs/images/show-gi-position.png)](https://show-gi.com)

_왼쪽이 올린 사진, 오른쪽이 읽어 낸 판. 龍(成駒)과 양쪽 持ち駒까지 이 화면에서 확정한 뒤 검토로._
