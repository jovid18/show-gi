将棋の対局サービスを個人で作っています。プレイヤーが悪手を指した瞬間に割り込んで、指し直させるアプリです。

割り込むかどうかは、エンジンが返す**評価値の落差**で決めます。だから同じ局面には同じ評価値が返ってきてほしい。ところが、素直に書くと返ってきません。

同じ局面・同じコマンドで四回探索させた結果です。

```
go movetime 500     depth 14   score cp -48
                    depth 17   score cp -41
                    depth 14   score cp -48
                    depth 16   score cp -41
```

誰も触っていない、同じマシンの、同じ局面です。

この記事で扱うのは「探索をどこで打ち切るか」の選び方と、その選択が**何を巻き添えにするか**です。将棋エンジン固有の話に見えますが、外部プロセスの結果をキャッシュする設計なら同じ形の問題が出ます。

想定読者は、外部のソルバーや推論プロセスを叩いて、その結果をキャッシュしたことがある方です。将棋の強さの知識は要りません。

## 1. 何が困るのか

このアプリは、プレイヤーが一手指すたびに探索を二回走らせます。

1. **指す前**の局面を読む → いちばん良い手の評価値
2. **指した後**の局面を読む → プレイヤーが実際に指した手の評価値 (手番が入れ替わるので符号を反転して揃える)
3. 二つの落差が大きければ割り込む

**3 の比較が成立するには、評価値が安定していなければなりません。** 同じ局面を二度計算して -48 と -41 が出るなら、7cp はエンジンの都合であってプレイヤーの責任ではありません。しかも探索は一手につき二回走るので、**揺れも二か所から入ります。** 閾値の近くにいる手は、運で割り込まれたり割り込まれなかったりします。

しかも困るのは判定だけではありません。**同じ局面の結果をキャッシュしている**なら、保存した値は「たまたまその時に出た値」になります。次に同じ局面が来たとき、キャッシュを引くか計算し直すかで答えが変わる。

## 2. 探索をどこで打ち切るか

ここが本題です。

### 2.1 二つの止め方

将棋エンジンは USI というプロトコルで喋ります[^usi]。探索の開始は `go` で、**どこで止めるか**を一緒に伝えます。

[^usi]: UCI (チェス) の将棋版にあたるテキストプロトコルです。標準入出力で行をやりとりします。

| コマンド          | 意味                                     |
| ----------------- | ---------------------------------------- |
| `go movetime 500` | **500 ミリ秒**考えたら答えを返せ         |
| `go depth 14`     | **14 手先**まで読んだら答えを返せ        |
| `go infinite`     | 止めるまで考え続けろ (`stop` で打ち切る) |

対局時計のあるソフトなら `movetime` が自然です。持ち時間から今回の予算を決めて渡す。エンジン側も、時間内で行けるところまで深く読んでくれます。

**この記事の結論は「`movetime` を使わない」です。** 理由はここから先です。

### 2.2 「同じ答えが返る」とは何か

まず言葉を決めます。**同じ入力に同じ出力を返すことを、ここでは決定的 (deterministic) と呼びます。**

将棋エンジンの探索は、原理的には決定的にできます。局面が同じで、読む深さが同じで、枝刈りの判断材料も同じなら、通る道が同じになるからです。最後の「判断材料」がいちばん厄介で、そこで一度つまずきます (2.6)。

問題は、**「読む深さ」を時間で指定した瞬間に、深さが実行環境の関数になる**ことです。

```
速いマシン・空いている  →  500ms で depth 17 まで行けた
遅いマシン・混んでいる  →  500ms で depth 14 で終わった
```

深さが変われば評価値も変わります。つまり `movetime` は、**評価値にマシンの都合を混ぜ込む**指定です。

### 2.3 手元で確かめる

理屈は分かっても、実際どれくらい揺れるのかは測らないと分かりません。エンジンさえあれば手元で確かめられます。

:::message alert
USI エンジンにコマンドをパイプで流し込むとき、**探索の途中で標準入力が閉じると、エンジンはそこで終了します。** `printf '...' | engine` と書くと `go` の直後に EOF が来て、探索が始まった瞬間に打ち切られた答えが返ります (`depth 1`, `nodes 0` が出たらこれです)。**答えが返るまで標準入力を開けておく**必要があります。
:::

`ENGINE` を手元の USI エンジンのパスに置き換えれば、そのまま動きます。

```sh
ENGINE=/path/to/your/usi-engine

cat > /tmp/usi-cmds <<'EOF'
usi
setoption name Threads value 1
setoption name USI_Hash value 128
setoption name PvInterval value 0
setoption name FV_SCALE value 24
setoption name USI_OwnBook value false
isready
position startpos moves 7g7f 3c3d 2g2f
go depth 14
EOF

(cat /tmp/usi-cmds; sleep 25) | "$ENGINE"
```

最後の `(cat ...; sleep 25) |` が上の注意点への対処です。`sleep` は答えが返るまで標準入力を開けておくためだけのもので、探索時間とは関係ありません。

`PvInterval 0` は、深さごとの `info` 行を間引かせないための指定です。やねうら王の既定値は 300 (ミリ秒) で、その間隔でしか PV を出しません。上のような軽い探索はそれより速く終わるので、**既定値のままだと最後の深さの一行しか残りません。**

これは手元用の設定ではありません。深さごとの行が残るおかげで **`depth 12` 一回が depth 1〜12 の評価値を丸ごとくれる**ので、このアプリは「浅く見ると得に見えるが深く読むと悪い手」を、別の探索を走らせずに見分けられます。

`FV_SCALE 24` は、**評価関数の出力を最後にいくつで割って整数にするか**という除数です — やねうら王の公式ドキュメントの言葉で、既定値は 16 です。正しい値は評価関数ごとに決まっていて、下に書いた水匠5では 24 です。**これが違うと cp の尺度ごと変わります。** 手元で既定値の 16 のまま同じ局面を読ませたら `score cp -134` で、24 なら `score cp -57` でした。別の評価関数を使うなら、その評価関数の値に置き換えてください。

`USI_OwnBook false` は定跡を切る指定です。やねうら王の既定値は `true` で、下で使う `7g7f 3c3d 2g2f` は定跡のど真ん中です。定跡ファイルが入っている環境だと、**探索せずに定跡手が返ってきます** — `nodes 0` で `bestmove` だけが出て、`depth 14` の行は一行も出ません。

見るのは `bestmove` の直前に出る `info` 行です。

```
info depth 14 seldepth 25 multipv 1 score cp -57 nodes 65644 ... pv 8c8d ...
bestmove 8c8d ponder 2f2e
```

`score cp` が評価値、`nodes` が調べた局面数です。`seldepth` は規格で「選択的に読んでいる手の探索深さ」とされている値で、有望な変化だけは `depth` の先まで伸ばして読むため、指定した 14 より大きくなります。**`nodes` まで一致していれば、同じ道を通ったということです。**

### 2.4 三通り測った

同じ局面 (`startpos moves 7g7f 3c3d 2g2f`、後手番) に、条件を変えて繰り返し聞きました。

**① `go movetime 500`、1 スレッド**

```
depth 14   score cp -48   nodes  98852
depth 17   score cp -41   nodes 112241
depth 14   score cp -48   nodes 101998
depth 16   score cp -41   nodes 108127
```

冒頭に出したのはこの四回で、`nodes` の列を省いたものです。

**到達した深さが 14 から 17 まで揺れています。** 誰も使っていないマシンでこれです。本番では探索用のエンジンを 3 つ、それとは別に詰み探索用をもう 1 つ、同じ 4 vCPU の上で走らせます。空きを奪い合うぶん、揺れはさらに大きくなります。

**② `go depth 14`、4 スレッド**

深さを固定しました。これで決まるはずです。

```
score cp -125   nodes 142137
score cp -112   nodes 314444
score cp -145   nodes 412940
score cp -106   nodes 348220
```

**決まりません。** 評価値は 39cp の幅で散り、`nodes` は 3 倍近く違います。

**③ `go depth 14`、1 スレッド**

```
score cp -57   nodes 65644
score cp -57   nodes 65644
score cp -57   nodes 65644
```

**`nodes` まで完全に一致します。** (この三回は毎回エンジンを起動し直しています。それがなぜ効くのかは次の節です)

### 2.5 固定深さだけでは足りない

②が本題の半分です。**深さを固定しても、マルチスレッド探索は決定的になりません。**

置換表 (探索した局面を覚えておく表) は**エンジン全体で一つ**あり、スレッドはそれを共有します。しかもやねうら王が取り込んでいる Stockfish の実装は、そこへのアクセスに鍵をかけません。ソースのコメントがそう明言しています。

> There is only one global hash table for the engine and all its threads. (…) For chess in particular, we even allow racy updates between threads to and from the TT, as taking the time to synchronize access would cost thinking time and thus elo. (…) Probes and reads are racy and non-atomic, possibly resulting in inconsistent data.

「for chess in particular」とあるとおり元はチェス側のコメントですが、やねうら王はこの実装をそのまま将棋で使っています。②の実測がその結果です。

同期しないので、どのスレッドがどの順で書き込むかはその時のスケジューリング次第です。書き込まれた順で枝刈りの判断が変わり、**同じ `depth 14` でも通る道が変わります。**

条件は二つ、のつもりでした。

### 2.6 三つめの条件 — 置換表は前の探索を覚えている

③と同じ 1 スレッド・固定深さのまま、**エンジンを立ち上げ直さずに**同じ局面を三回続けて聞くと、こうなります。

```
score cp  -57   nodes 65644
score cp -107   nodes 63958
score cp  -98   nodes 11337
```

50cp 動いて、`nodes` は 5.8 倍違います。1 スレッドで、深さも固定で、です。

犯人は同じ置換表です。**前の探索が書き残したものを、次の探索が読みます。** 各探索の前に `isready` を挟むと、同じセッションのままぴたりと揃います。

```
score cp -57   nodes 65644
score cp -57   nodes 65644
score cp -57   nodes 65644
```

ここは名前に騙されました。**表を空にするのは `usinewgame` ではなく `isready` です。** `usinewgame` だけを挟んでも三回は割れたままで、`isready` だけを挟むと揃います。エンジン自身がそう言っていて、`isready` を送るたびに `info string USI_Hash : Start clearing with 1 threads , size = 128[MB]` が流れてきます。

③が `nodes` まで一致したのは、あれが毎回エンジンを起動し直していたからでした。**空の表から測っていた**わけです。

| 条件               | 無いとどうなるか                      |
| ------------------ | ------------------------------------- |
| 深さで打ち切る     | 到達する深さが実行環境で変わる (①)    |
| 1 スレッド         | 同じ深さでも通る道が変わる (②)        |
| 置換表の状態が同じ | 前の探索の答えが次の答えを変える (③´) |

そして三つめを、このアプリはまだ満たしていません。エンジンはプールに入れて使い回していて、`isready` を送るのはプロセスを立ち上げる最初の一回だけだからです。二手目以降は、前の探索が残した表の上で次を計算しています。

#### 実際の対局でも効くのか

ここまでは**まったく同じ局面を連続で聞く**という極端な条件です。本番はそうではありません。局面は毎回違うので、表に残っているのは「さっきまで読んでいた別の局面」です。

そこで実際の対局から取った 6 局面を、**一つのエンジンに `isready` を挟まず順に食べさせて** `depth 12` で読ませました。同じことを**逆順**でもやり、比較用に**毎回表を空にした**場合も取りました。同じ局面が、前に何を読んだかだけで違う答えを返すかを見ます。

| 局面     | 表を空にして | 順に読ませて | 逆順で読ませて | ばらつき |
| -------- | -----------: | -----------: | -------------: | -------: |
| A-20 手  |         -214 |         -214 |           -232 |     18cp |
| A-45 手  |        -1340 |        -1327 |          -1278 |     62cp |
| B-30 手  |           94 |          107 |            153 | **59cp** |
| B-70 手  |         1206 |         1130 |           1176 |     76cp |
| B-110 手 |         4133 |         4016 |           3896 |    237cp |
| B-150 手 |       7 手詰 |       7 手詰 |         7 手詰 |        0 |

**6 局面のうち 5 局面で答えが変わりました。** 変えたのは局面でも深さでもスレッド数でもなく、**その前に何を読んでいたか**だけです。詰みが見えている局面 (B-150 手) だけが動きませんでした — そこは読み筋が一本しかないからです。

数字の意味は 4.3 で勝率に直します。互角に近い B-30 手の 59cp は勝率で **2.4 ポイント**で、②のマルチスレッドで見た 39cp (1.6 ポイント) より大きい。つまり③´は②より小さい問題ではありません。

逆に、いちばん幅の大きい B-110 手の 237cp は勝率にすると **0.05 ポイント**しかありません。**この表は右端の列で並べ替えてはいけない**ということです — 大差がついた局面では cp が何百動いても勝敗の見込みは動かず、痛いのは互角の近くだけです。

**4.1 のキャッシュを対局ループにつなぐ前に、ここを決める必要があります** — 毎回表を空にして速さを捨てるのか、「同じ局面 = 同じ結果」を捨てて別の条件でキャッシュするのか。

捨てることになる速さは測れます。本番と同じ 128MB の表を `isready` で空にするのに、手元で **130〜250 ミリ秒**かかりました。§1 の判定は一手に二回探索するので、その一回ごとに空にすると、**探索をもう一回足すのに近い**負担になります。ただ乗りできる選択肢ではありません。

「固定深さにしたから再現する」で止めていたら、②を見落としたまま「同じ局面 = 同じ結果」を前提にしたコードを書いていました。②で安心していたら、今度は③´で同じことをするところでした。**「決定的だ」は、条件を数え終えたときにしか言えません。**

そして③´は、探索に固有の話ですらありません。**借りて使い回すプロセスには、前の仕事の跡が残ります。** 消し方を知っているかどうかだけが違いです。

## 3. できない API は置かない

決めたことをコードに落とします。この探索クライアントには、**時間で打ち切る関数がありません。**

```go:apps/server/internal/usi/client.go
// SearchDepth は固定深さまで探索させる。
//
// **このパッケージに時間ベースの探索 (go movetime) は意図的に無い。** 時間ベースは
// 同じ局面が同じ答えを返さないので、局面キャッシュ (「同じ局面 = 同じ結果」) も
// バンド制御 (候補の cp を信じられる必要がある) も成立しない。
// 遅延はキャッシュ・先行計算・深さを下げることで吸収する。
func (e *Engine) SearchDepth(ctx context.Context, startSFEN string, moves []string, depth int) (SearchResult, error) {
	return e.search(ctx, startSFEN, moves, "go depth "+strconv.Itoa(depth), 0)
}
```

コメントで「使うな」と書く手もありますが、**関数が無ければ書けません。** レビューを通り抜ける可能性がゼロになります。

最初からこうだったわけではありません。USI クライアントを書いた最初のコミットには `Search(ctx, sfen, moves, movetimeMs)` があって `go movetime` を投げていましたし、対局相手はそれを既定 500 ミリ秒で呼んでいました — 冒頭で測ったのと同じ値です。エンジンを載せ替えるコミットで、この二つを消しました。**「使わない」と決めただけなら、関数はそこに残ります。**

### 途中で切った結果は捨てる

探索に自前の制限時間はありません。終わるのは局面が決めます。ただし `context` で外から切れるようにしてあります。プールに入れて使う以上、終わらない探索一つがスロットを永久に占有すると困るからです。

**切ったときは結果を捨てます。**

途中まで読んだ結果は `depth 14` の結果ではありません。それを `computed_depth = 14` としてキャッシュに書いたら、**キャッシュが嘘をつきます。** そして嘘をついていることは、次に誰かが同じ局面を引いたときにも分かりません。時間で切るのを避けた理由がそのまま、途中結果を使わない理由になります。

## 4. 再現性が支えているもの

「同じ局面が同じ答えを返す」は、それ自体が目的ではありません。**三つのものが同時にこれに乗っています。**

### 4.1 局面キャッシュ

計算済みの局面を保存しておいて、次に同じ局面が来たら計算を省きます。**キーは局面の文字列だけ**です — 手数を抜いた SFEN で、抜くことで別の手順から合流した同じ形 (転置) が一行にまとまります。深さはキーではなく列に持たせて、**浅く計算した結果が深い結果を上書きしないため**だけに使います。

これが成立するのは、**「同じ局面を同じ深さで計算したなら同じ値」が本当のときだけ**です。②や③´の状態でキャッシュを入れると、保存された値は「その時たまたま出た値」になります。しかも保存した後は、それが正しいかどうか確かめる方法がありません。

正直に書くと、**このキャッシュはまだ対局ループにつながっていません。** テーブルと読み書きはありますが、探索する側から呼ぶ場所がまだ無い。つまりこの節は「今こう効いている」ではなく、**この前提を先に決めたからテーブルをこう作れた**という話です。前提のほうを後から差し替えると、作り直すのはテーブルではなく保存済みの中身です。

### 4.2 相手の強さ

このアプリの対局相手は、**わざと最善手を外して**プレイヤーに近い強さで指します。候補手を 10 個出させて、評価値が**狙った幅にいちばん近いもの**を選ぶ仕組みです。幅に入るものが一つも無ければ、いちばん近いものがそのまま選ばれます — 相手が大きく負けている局面では候補が全部幅の外 (上側) に出るので、これは自動的に「最善を尽くす」になります。

候補の評価値が揺れると、**選ぶ基準そのものが揺れます。** 順位が入れ替われば選ぶ手も入れ替わる。同じ局面で、あるときは狙い通りの手を選び、あるときは強すぎる手を選ぶ。プレイヤーからは「相手の強さが安定しない」と見えます。

サーバが混んでいるときだけ相手が弱くなる、という挙動は説明のしようがありません。

### 4.3 割り込みの判定

冒頭の話です。ただし比べているのは cp そのものではありません。cp はいったん勝率に直してから引き算します — 優勢な側では cp の意味が圧縮されて、同じ差でも局面ごとに違う意味になるからです。閾値のほうも勝率の落差で持っていて、既定 (いちばん初心者向け) で 25 ポイントです。

この変換は、形勢が離れるほど鈍くなります — それが「圧縮」の中身です。裏を返すと**いちばん速く動くのは互角付近**なのですが、その一番きついところですら、②で見た 39cp の散らばりは勝率にして 1.6 ポイントにしかなりません。大差の局面ならもっと小さい。つまり揺れで裏返るのは**閾値のすぐ際にいる手だけ**です。ただしそこは、割り込まれた側がいちばん納得しにくい場所でもあります — 同じ手をもう一度指したら今度は何も言われなかった、が起きるのはここです。

**この三つが、一つの性質にぶら下がっています。** だから `movetime` は「今回はやめておく」ではなく「入れない」になりました。

### 4.4 詰み探索 — 手数で切る理由と、「分からない」の扱い

詰みを探す探索は別のバイナリで、`go mate` を使います。これも**時間ではなく手数**で打ち切ります。

```go:apps/server/internal/usi/client.go
// 探索の限界はプールを作るときに DepthLimit (詰み手数の上限) で渡す。
// 時間 (go mate <ms>) ではなく手数で切る理由は他の探索と同じ
// — 同じ局面が同じ答えを返さないとキャッシュできない。
```

そして詰み探索には、キャッシュに関してもう一段の区別があります。詰将棋 solver が返す答えは四種類です。

| 返事                | 意味                                 | キャッシュ     |
| ------------------- | ------------------------------------ | -------------- |
| `checkmate <手順>`  | その手数の中に詰みがある。手順はこれ | してよい       |
| `checkmate nomate`  | **その手数の中には詰みが無い**       | してよい       |
| `checkmate timeout` | **時間内には分からなかった**         | してはいけない |
| `checkmate none`    | **エンジンの限界で解けなかった**     | してはいけない |

規格にはもう一つ `notimplemented` がありますが、これは詰将棋機能を持たないエンジンに `go mate` を送ったときの返事なので、solver からは出ません。

前の二つは証明なので、何度やっても同じです。ただし二つめは「詰みは無い」ではありません。**限界より長い詰みも `nomate` として返ってきます** — 5 手詰のある局面に `DepthLimit 3` で聞くと `checkmate nomate` でした。公式ドキュメントにも「3 を設定すると 3 手詰めまでを発見し、5 手詰めは不詰め扱いとなる」とそのままの例が載っています。それでも保存してよいのは、**これが局面についての言明だから**です。「3 手では詰まない」は、いつどのマシンで聞いても 3 手では詰まない。何手までを見たかは呼ぶ側が決めた値なので、呼ぶ側が覚えていれば足ります。

後ろの二つは違います。`checkmate timeout` は「間に合わなかった」という、**局面ではなくマシンについての言明**です。**これを「詰みは無い」として保存すると、ある詰みを見落としたまま終盤の判定が動きます。**

そして `timeout` は、手数で切っているかぎり返ってきません。これは実測というより定義で、規格が「**制限時間ありで**詰将棋解答を開始した場合、制限時間内に結論が出なければ `checkmate timeout` を返す」と書いています。手元でも `go mate infinite` に `DepthLimit` を添えたときは `checkmate <手順>` か `nomate` しか出ず、`timeout` が出たのは `go mate 50` と時間で聞いたときだけでした。

問題は四つめです。`checkmate none` は規格には無く、やねうら王が足したものです。公式ドキュメントいわく「探索ノード数制限で解けなかった時や、詰将棋用のメモリ (`USI_Hash` で指定している) がリミットに達した場合」に返ります。意味は `timeout` と同じ側 — 「詰みは無い」ではなく「**解けなかった**」です。

白状すると、これはこの記事を書くまで見落としていました。コードは `nomate` と `timeout` と `notimplemented` を名指しし、**それ以外は手順とみなします。** `none` はどれにも当たらないので手順として読まれ、手順として不正なので「手順は空」、つまり **「詰みは無いと証明できた」という顔で残ります。**

救いはあります。この「証明できたか」のフラグを読んでいるコードは、まだテストしかありません — 4.1 のキャッシュと同じで、置いただけでつながっていない段階です。**間違った値のほうが、それを信じるコードより先に見つかった**わけで、順番が逆なら、見つかるのは「なぜか詰みを見落とす」という形になっていたはずです。時間で切るのをやめても、「分からなかった」を返す口はもう一つ空いていました。

判定の軸は最初から出ていたのに、コードのほうがそれを文字列の一覧として書いてしまっていた、というのがこの見落としの正体です。**キャッシュしてよいかどうかは、返事の綴りではなく「これは局面についての言明か、マシンについての言明か」で決まります。**

## 5. 払っている代償

正直に書くと、この選択は**待ち時間を人間に押し付けています。**

深さを固定するということは、重い局面では素直に重いということです。実際の対局から取った 6 局面で候補手を 10 個ぶん `depth 14` で読ませたところ、**いちばん重い局面で 8.4 秒**かかりました。これがいちばん痛いのは、下に挙げる**先行計算** — プレイヤーが考えている間に次の局面を読んでおく — の側です。プレイヤーが 8.4 秒より早く指してしまえば、そこで狙っている「遅延ゼロ」は成立しません。同じ 6 局面を `depth 12` にすると、いちばん重い局面でも 2.0 秒です。

この「10 個」は**相手が指す手を選ぶための候補数**です (§4.2)。先行計算のほうも 8〜10 個を読みますが、並べているものが違います — あちらは**プレイヤーが指しそうな手**で、外しても着手後の単発の計算で埋まります。§1 の判定はそのどちらでもなく、候補 1 個で足ります — 同じ 6 局面・同じ `depth 12` で最長 400 ミリ秒、一手に二回走らせても 1 秒に届きません。候補数を変えただけで 400 ミリ秒が 2 秒になるので、**深さと候補数は別の予算として持っています。**

時間で切ればこの問題は消えます。**消えるのは問題ではなく、問題が見えなくなるだけ**ですが。

なので遅延は別の手で削ります。

- **キャッシュ** — 同じ局面を二度計算しない。4.1 が効くのはここ
- **先行計算** — プレイヤーが考えている間に、来そうな局面を読んでおく
- **深さを下げる** — 設計に 14 と書いてあったものを 12 にした。**評価の精度を落とす、という正面からの判断**

**今そこにあるのは三つめだけです。** 前の二つは置き場所を作った段階で、まだ対局ループにつながっていません。その三つめも全部が決着したわけではなく、12 で確定しているのは相手の手を選ぶ探索のほうです — 先行計算をどの深さで回すかはまだ開いています。本番環境で測り直したら手元より速くて (`depth 12` × 候補 1 個で 400 ミリ秒に対し 308 ミリ秒)、14 のままでいける余地が出てきました。**ただし比べたのは候補 1 個の一点だけ**です。先行計算が読むのは 8〜10 個のほうなので、この一点をもって 14 を選ぶことはできません。測り直しが要ります。

それでも三つめが本命です。深さを下げるのは品質を落とす決定で、**時間で切るのはそれを「たまたまそうなった」に変えてしまう**からです。落とすなら、落としたと分かる形で落とすほうがいい。

## 6. まとめ

- **時間で打ち切る探索は、評価値に実行環境を混ぜ込む。** 空いているマシンで depth 17、混んでいるマシンで depth 14 なら、返ってくる数字は別物になる
- **深さを固定しただけでは決定的にならない。** マルチスレッド探索は同じ深さでも通る道が変わり、置換表は前の探索を覚えている。`nodes` まで一致させたいなら、1 スレッドにしたうえで**表を空にしてから**測る
- **やってはいけないことは、コメントではなく API から消す。** 関数が無ければ、レビューを通り抜けようがない
