# Review Criteria — self-review 지식코어

심각도·Never Review·finding 형식의 정본은 이 파일이다. `docs/`에 같은 내용을 두지 않는다.

## 리뷰 권위 체인 (충돌 시 위가 이긴다)

1. `CLAUDE.md` — 레포 규칙 전체. 그중 「이 프로젝트의 요점」은 제품의 불변식이다. 최상위 권위.
2. `docs/01-core.md` — 개입 엔진의 설계 정본. 판정식·블런더 온톨로지·적응형 상대·힌트·실력 추정.
3. 서버: `docs/02-architecture.md` + `apps/server/README.md`(특히 「코드를 고치기 전에」와 「스키마를 바꿀 때」).
4. 웹: `docs/03-frontend.md` + `apps/web/README.md`.
5. 변경된 코드가 `journal §NN`으로 가리키는 저널 절. 실측 표와 결정의 정본이다. 상수·임계치·깊이를 바꾸는 diff는 그 값을 정한 절을 읽고 대조한다.
6. 선언에 붙은 doc 주석이 정한 계약. 예: `explain.Facts.used`(카테고리별로 문장에 쓸 수 있는 사실), 잠금 규약, goroutine 소유권.

문서끼리 충돌하면 번호가 낮은 쪽이 이긴다. 가이드와 요구사항 정본(PR 본문·`WORKTREE.md`)이 충돌하면 어느 쪽도 기각하지 말고 양쪽을 병기해 🟡 finding으로 올린다.

`docs/spec/`(API·ERD·아키텍처 그림)은 권위가 아니라 코드의 사본이다. `docs/spec/README.md`: 「어긋나면 언제나 코드가 맞다」. 같은 README의 「어디가 정본인가」 표가 코드를 고치면 같은 PR에서 고칠 spec 자리를 정한다. 그 자리를 고치지 않은 것이 finding이다.

`docs/06-status.md`도 결과 요약이다. diff와 어긋나면 finding이지 권위가 아니다.

## 가이드 해석 규칙

- **예시가 아니라 조항이 규칙이다.** 문서의 사례는 조항의 표본이다. 위반 여부는 조항 문장으로 판정한다. 코드가 사례와 겉모습이 다르다는 이유로 통과시키지 않는다.
- **정상 판정에도 근거를 요구한다.** 보고서의 「검증된 정상 항목」은 finding과 같은 증거 기준을 따른다. 어떤 조항에 비추어 정상인지 원문을 인용한다. 인용 없는 정상 판정은 누락 finding이 숨는 자리이고 verifier의 반박 대상이다.
- 「하지 않는다」·「쓰지 않는다」로 끝나는 CLAUDE.md 문장은 MUST NOT이다. 이 레포는 RFC 키워드를 쓰지 않는다. 금지형 평서문을 금지 조항으로 읽는다.

## 심각도 판정 (순서대로 적용)

1. **기준 목록**:
   - 🔴 정상 흐름에서 틀린 결과를 내는 버그. 「이 프로젝트의 요점」 불변식 위반(판단·표현의 비결정화, 시간 기반 탐색, 판단·설명에 생성 모델 사용, 덜 끝난 탐색 결과의 캐시 저장, 세션 goroutine 밖의 상태 읽기·쓰기). CLAUDE.md 「언어」 절이 허용하지 않은 언어가 화면에 나감. 비밀이 커밋됨. 요구사항 미구현
   - 🟡 엣지 케이스에서만 틀리는 버그. 요구사항 일부 미충족·scope creep. 「어디가 정본인가」 표가 요구한 spec 갱신 누락. 새 사실과 모순되는 옛 문장이 문서에 남음. 생성물(`internal/store/db/`)과 스키마·질의의 불일치. 되돌릴 수 없는 마이그레이션 규칙 위반. 서버 테스트가 `-race`를 빠뜨림
   - 🟢 주석·문서 문체 규칙 위반(CLAUDE.md 「문서」), 명명, 추출 기회, 테스트 보강

   목록은 표본이다. 판정은 조항 문장으로 한다.

2. **하한**: CLAUDE.md의 금지 조항 위반이 성립하면 🟡 이상이다. 단, 「문서」 절의 문체 규칙(주석 길이·`—` 반복·굵게 위치·경위 서술)은 🟢 하한이다.
3. **상한**: 🔴은 동작·요구·불변식·보안에 닿는 finding에만 쓴다. 닿는다고 자동으로 🔴이 되지는 않는다.
4. **영향 범위가 모호하면** 하한 안에서 낮은 쪽을 고르고 판단 근거를 병기한다. 🔴을 남발하면 리뷰를 믿지 않게 된다.

**심각도는 우선순위이지 수정 여부가 아니다.** finding은 범위 규칙상 전부 이번 diff가 만든 것이다. 고칠지는 성격으로 정한다.

- **결함**: diff가 만든 상태가 틀렸거나 무언가를 빠뜨렸다. 동작 오류, 요구 미충족, 가이드 위반, 문서 서술이 코드와 다름, 기존 규칙·정보의 유실. 심각도와 무관하게 고친다.
- **개선**: diff가 만든 상태는 옳지만 나아질 수 있다. 명명 다듬기, 추출 기회, 테스트 보강. 작성자 재량이다.

🔴·🟡은 항상 결함이다. 🟢은 둘 중 하나로 반드시 표기한다(경량 형식). 🟢을 「안 고쳐도 된다」로 읽으면 diff가 만든 작은 부정확이 그대로 머지된다.

## Never Review (finding으로 올리지 않는다)

CI·`pre-commit`이 이미 막는 것이다. 다시 보고하면 노이즈다.

- 포맷: oxfmt(TS·마크다운), gofmt, terraform fmt
- `go vet`, `tsc`(`pnpm typecheck`)가 잡는 것
- oxlint error 레벨(`correctness`). CI의 `pnpm lint`가 실패시킨다
- `tools/prose/bold.py`(굵게 위치)와 `tools/prose/phrase.py`(주석의 금지 맺음 문구)가 잡는 것. 둘 다 CI에서 돈다
- 마크다운 표 파이프 정렬(CLAUDE.md 「포맷」: oxfmt가 CJK 폭을 1칸으로 센다)
- 생성물 본문: `apps/server/internal/store/db/`, `docs/images/`(drawio 내보내기). 단 원본과 생성물의 불일치는 리뷰 대상이다
- 이미 적용된 마이그레이션 파일의 주석(CLAUDE.md: 고치지 않는다)

### 예외: 자동 게이트를 통과하는 린트

oxlint의 `suspicious`·`perf` 카테고리는 warn이다. warn은 `pnpm lint`의 종료 코드를 바꾸지 않고 `pre-commit`은 `--quiet`로 숨긴다. 어떤 자동 단계도 막지 않으므로 리뷰가 유일한 방어선이다. diff가 수정한 블록에서 나온 warn은 finding으로 올린다. 근거란에 규칙 이름과 「warn → 자동 게이트 미포착」을 쓴다.

`.oxlintrc.json`에 react-hooks 플러그인이 없다. 훅 의존성 배열(`exhaustive-deps`)과 훅 호출 규칙은 린터가 전혀 보지 않는다. 웹 축이 손으로 본다.

스코프는 「경고가 앵커된 라인이 `+`인가」가 아니라 「위반을 만든 블록을 diff가 수정했는가」로 판정한다. 훅 본문을 고쳐 새 참조를 들여와도 deps 배열 라인은 미변경으로 남는 경우가 흔하다. 블록 전체가 diff와 무관한 기존 위반이면 「범위 외 관찰」로만 남긴다.

심각도는 기본 🟡, 잘못된 런타임 동작(stale closure로 옛 값이 화면에 나감 등)을 만들면 🔴.

## Finding 형식 (🔴·🟡은 4필드, 🟢은 경량 3필드. 필드가 빠지면 검증에서 기각된다)

```markdown
### {ID} {🔴|🟡|🟢} {한 줄 요약}

- **위치**: `path/to/file.go:123` — `{그 줄의 원문}` (리뷰 트리 `root`의 실제 라인 번호. patch offset 아님)
- **근거**: {위반한 문서·절 + `path:line` + 조항 원문 인용} 또는 {요구사항 ID (R1, AC-2 등) + 정본 원문 인용} 또는 {재현 시나리오 — 발생 가능한 입력·상태 → 잘못된 결과}
- **문제**: {코드가 실제로 무엇을 하는지 기준으로 왜 위반·불일치인지}
- **제안**: {구체적 수정 방향. 코드를 직접 고치지 않고 제안만}
```

- ID: 요구사항 `REQ-n`, 서버 `SV-n`, 웹 `WB-n`, 로직 `LG-n`, 불변식 `INV-n`, 문서·주석 `DOC-n`, Codex `CDX-n`. verifier가 CONFIRM한 finding은 `VF-n`으로 다시 매기고 원 ID를 병기한다(병합 시 원 ID 전부).
- **위치는 실제 파일을 Read로 열어 확인한 라인 번호**다. Read·Grep·라인 확정은 스폰 프롬프트와 `meta.md`의 `root` 기준이다. 세션의 체크아웃이 아니다. 경로는 `root` 기준 상대 경로로 쓴다.
- **인용은 원문 그대로 옮긴다.** 위치의 대상 줄과 근거의 조항 모두. 요약·의역한 인용은 기각된다.
- **근거 없는 finding은 finding이 아니다.** 「일반적으로 좋지 않다」 같은 취향 지적은 올리지 않는다. 권위 체인의 조항, 요구사항 항목, 재현 시나리오 중 하나에 연결한다.
- **제안은 생략할 수 없다.** 최종 리포트까지 그대로 간다.

### 🟢 경량 형식

```markdown
- 🟢 [결함|개선] {한 줄 요약} — `path:line` `{그 줄의 원문}` / 근거: {조항 출처 path:line 또는 R-id} "{원문 한 구절}" / {제안}
```

🟡 이상으로 올라갈 여지가 보이면 경량 형식을 쓰지 말고 4필드로 쓴다.

## 요구사항 축 분류

| 분류           | 정의                                                                                                 | 기본 심각도                     |
| -------------- | ---------------------------------------------------------------------------------------------------- | ------------------------------- |
| 미구현         | 정본의 요구 항목이 diff 어디에도 없음                                                                | 🔴                              |
| 부분 구현      | 구현됐으나 정본의 조건·분기·엣지가 빠짐                                                              | 🟡                              |
| 검증 누락      | 요구에 대응하는 테스트나 측정이 없음. 측정으로 정해야 하는 상수(CLAUDE.md: 「실측으로 정한다」) 포함 | 🟡                              |
| scope creep    | 어떤 요구 항목에도 연결되지 않는 hunk                                                                | 🟡 (행위 변경) / 🟢 (구조 정리) |
| 상태 문서 누락 | 상태가 바뀌었는데 `docs/06-status.md`를 같은 PR에서 갱신하지 않음(CLAUDE.md)                         | 🟡                              |

## 리뷰 범위 규칙

diff에 직접 연결된 위반만 보고한다. 변경되지 않은 인접 코드의 기존 문제는 보고서 끝 「범위 외 관찰」에 한 줄로만 남긴다.

예외는 문서 모순이다. diff가 새 사실을 더했는데 diff 밖의 옛 문장이 그 사실과 모순되면 finding이다. CLAUDE.md가 「같은 PR에서 고친다」고 정했으므로 그 옛 문장을 남긴 것이 이번 diff의 결함이다.
