# 기사 리뷰 — 두 에이전트 교대

에이전트 **A**와 **B**가 번갈아 같은 기사를 리뷰하고 고친다. **둘 다 「고칠 것이 없다」고 판단했을 때** 끝난다.

혼자 돌리면 자기가 방금 쓴 문장을 검증 없이 지나간다. 실제로 그렇게 됐다 — 한 세션에서 3·4·5패스의 오류가 **전부 직전 패스에서 스스로 추가한 문장**이었다. 남의 눈이 필요한 이유가 이것이다.

## 규칙 — 이것부터 읽는다

### ① 근거 축을 새로 하나 들고 온다

**같은 글을 눈으로 다시 훑는 패스는 두 번째부터 수확이 없다.** 매 라운드는 아직 안 쓴 근거를 하나 들고 들어간다.

| 축               | 무엇을 하나                                                             |
| ---------------- | ----------------------------------------------------------------------- |
| 원본 대조        | 인용한 코드가 **실제로 그 분기인가**. 파일을 열어 한 줄씩 맞춘다        |
| 실행             | 주장을 돌려본다. `docker run`·`go test`·`curl`                          |
| git 히스토리     | 「왜 지금까지 멀쩡했나」는 여기서만 나온다. `git log -S`·`git show`     |
| 렌더 화면        | `pnpm zenn:preview` → 브라우저. 독자가 보는 것                          |
| 공식 문서        | WebFetch. API가 정말 그 값을 주는가                                     |
| 리포 런북·도움말 | `deploy/README.md`, `<cmd> help`. 기사가 인용한 문서가 그 말을 하나     |
| 실물 인프라      | `aws ... --profile show-gi`. **`--profile`을 빼면 회사 default를 탄다** |

**들고 올 축이 떨어졌으면 그것 자체가 「고칠 것 없음」의 정당한 사유다.** 억지로 짜내지 않는다.

### ② 상대가 방금 추가한 문장을 먼저 본다

**가장 잘 나오는 자리다.** 상대가 고치면서 넣은 문장은 원전을 다시 열지 않고 기억으로 메워진 경우가 많다. 새 문장과 **같은 기준으로** 검증한다.

### ③ 무엇이 「고칠 것」인가

카운터를 리셋하는 것은 이 다섯뿐이다.

1. **사실 오류** — 코드·문서·실물과 다르다
2. **검증 불가** — 근거를 못 대는 단정. 고치거나 `[미확정]`으로 낮춘다
3. **내부 모순** — 앞 절과 뒤 절이 어긋난다. 앞 라운드의 수정이 만든 것 포함
4. **근거 없음** — 맞는 것 같은데 원전 인용이 없다. 링크·실측을 붙인다
5. **렌더 깨짐** — 프리뷰에서 안 나오거나 다르게 나온다

**문체·표현 취향은 여기 없다.** 고쳐도 되지만 **보고할 때 「수정 사항」으로 세지 않는다.** 이걸 세면 두 에이전트가 서로의 문장을 맞바꾸며 영원히 안 끝난다.

### ④ 상대의 수정을 조용히 되돌리지 않는다

되돌리려면 **근거를 대야 한다** — 「원래가 나았다」는 근거가 아니다. 사실이 틀렸다면 근거와 함께 되돌리고, 취향 차이면 그냥 둔다.

### ⑤ 동시에 쓰지 않는다

같은 파일을 고친다. **한 번에 한 에이전트만 돈다.** 상대가 보고를 끝낸 뒤에 다음이 시작한다.

### ⑥ 지어내지 않는다

확인 못 한 것은 [CLAUDE.md](../../../CLAUDE.md)대로 추정으로 메우지 않는다. 기사는 밖으로 나가서 고칠 기회가 없다.

## 종료

**연속 두 보고가 모두 「수정 사항 0」이면 끝난다.** A가 0을 냈고 이어서 B도 0을 내면, B는 A가 마지막에 손댄 것까지 본 뒤 0을 낸 것이므로 교차 판단이 성립한다.

하나라도 나오면 카운터는 0으로 돌아간다.

**8라운드에서 무조건 멈춘다.** 거기까지 갔으면 수렴하지 않는 것이고, 그 사실을 사용자에게 그대로 보고한다 — 「끝났다」고 하지 않는다.

## 진행 순서

### 준비

1. 대상 파일 확인. 안 밝혔으면 `articles/`에서 가장 최근 것
2. `pnpm lint`로 기준선. 지금 깨져 있으면 먼저 알린다
3. 브랜치 확인 — `main`이면 브랜치를 판다
4. **축 원장(ledger)을 연다.** 라운드마다 누가 어느 축을 썼는지 적는다

### 루프

- **1라운드** — `Agent`로 A를 띄운다
- **2라운드** — `Agent`로 B를 띄운다. A의 보고를 넘긴다
- **3라운드부터** — `SendMessage`로 A·B를 번갈아 부른다. **새로 `Agent`를 부르지 않는다** — 컨텍스트가 날아가면 자기가 이미 확인한 축을 또 돈다

각 보고를 받으면 원장을 갱신하고, 0 카운터를 세고, 사용자에게 **한 줄로** 진행을 알린다.

### 프롬프트 (그대로 쓴다)

```
너는 리뷰 에이전트 <A|B>다. 대상: <파일 경로>

<1라운드가 아니면> 직전에 <상대>가 이렇게 보고했다:
<상대의 보고 전문>

할 일:
1. 아직 안 쓴 근거 축을 하나 고른다. 이미 쓴 축: <원장>
2. 그 축으로 기사를 검증한다. 읽기만 하지 말고 실제로 명령을 돌린다
3. **상대가 방금 추가·수정한 문장을 특히 본다** — 원전을 다시 열어 확인한다
4. 찾은 것을 고친다. 고친 뒤 `pnpm lint`
5. 상대의 수정을 되돌릴 때는 근거를 댄다

보고 형식 (이대로):
- 쓴 축:
- 수정 사항: N건   ← 사실오류·검증불가·모순·근거없음·렌더깨짐만 센다
  1. <무엇이 틀렸나> / <근거> / <어떻게 고쳤나>
- 문체만 손댄 것: (있으면 한 줄. 개수에 안 넣는다)
- 다음 에이전트가 볼 만한 곳:

수정 사항이 0이면 그렇게 보고한다. 억지로 만들지 않는다.
```

### 끝난 뒤

1. 누적 diff를 보여준다 — `git diff main...HEAD -- <파일>`
2. 라운드별 수확을 표로 요약한다
3. **커밋은 한 번에 한다.** 루프 전체를 한 커밋으로. Conventional Commits, 영어
4. PR은 `/create-pr`

## 하지 않는 것

- **`published: true`로 바꾸지 않는다.** 공개는 별도 PR이다([기사 계획 §11](../../../docs/07-articles.md))
- **머지하지 않는다.** PR을 여는 데까지가 끝이다
- 코드 diff 리뷰에 쓰지 않는다 — 그건 `/code-review`
