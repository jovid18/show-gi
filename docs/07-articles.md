## 2. 어디에 무엇이 있나

```
articles/   기사 마크다운. 파일 하나가 기사 하나
images/     스크린샷·그래프. 아직 없다 — 첫 이미지가 생길 때 만든다
```

`images/`를 미리 만들지 않는 이유는 **Zenn이 확장자를 검사**하기 때문이다. 빈 디렉터리를 유지하려고 `.gitkeep`을 넣으면 배포에서 걸릴 수 있다.

```sh
pnpm zenn:new        # articles/ 에 새 기사. --slug --title --type --emoji
pnpm zenn:preview    # localhost:8000 (잡혀 있으면 8001), 라이브 리로드
pnpm lint            # oxfmt가 articles/ 도 포맷한다 (§4)
```

`zenn-cli`는 루트 `devDependencies`에 고정했다. `npx`로 매번 받으면 버전이 안 정해진다.

## 3. Zenn 사양 — 공식 문서로 확인한 것

출처: [CLI](https://zenn.dev/zenn/articles/zenn-cli-guide) · [Markdown](https://zenn.dev/zenn/articles/markdown-guide) · [GitHub 연동](https://zenn.dev/zenn/articles/connect-to-github) · [이미지](https://zenn.dev/zenn/articles/deploy-github-images)

### front matter

```yaml
---
title: 'デプロイは緑なのに対局だけできなかった'
emoji: '🩺' # 1자. 썸네일이 된다
type: 'tech' # tech | idea
topics: ['aws', 'ecs', 'go']
published: false
published_at: '2026-08-15 10:00' # 선택. JST
---
```

### 제약

| 항목     | 값                                                         |
| -------- | ---------------------------------------------------------- |
| **slug** | 파일명이 곧 URL. **`a-z0-9`·`-`·`_`로 12~50자**            |
| 디렉터리 | `articles/`·`images/` 둘 다 **리포 루트**                  |
| 이미지   | 본문에서 **`/images/...` 절대경로**. 상대경로 금지         |
| 이미지   | **3MB 상한**, `.png .jpg .jpeg .gif .webp` 만              |
| 연동     | 계정당 **리포 최대 2개**. 등록 브랜치에 push하면 자동 배포 |
| Mermaid  | 블록당 **2000자**, 체인 연산자(`&`) 최대 10개              |

**[미확정]** `topics` 최대 개수. **본(book)에는 「5つまで」가 명시돼 있는데 기사에는 그 문장이 없다**([CLI 가이드](https://zenn.dev/zenn/articles/zenn-cli-guide)). 그리고 **로컬 CLI는 검증하지 않는다** — 6개를 넣어도 `zenn list:articles`도 `zenn preview`도 통과했다. 서버 쪽에서만 걸리므로 **5개로 두고** 동기화가 실제로 돌 때 확인한다.

## 4. oxfmt는 Zenn 문법을 안 망가뜨린다 — 실측

`.oxfmtrc.jsonc`가 `**/*.md`를 전부 포맷하므로 `articles/`도 대상이다. 기사를 다 쓰고 나서 알면 늦어서 **미리 시험했다.**

Zenn 고유 문법을 한 파일에 다 넣고 `oxfmt`를 돌린 결과, **본문에서 바뀐 것은 표 정렬 한 곳뿐이었다.** 그건 [CLAUDE.md](../CLAUDE.md)에 이미 정상 동작으로 적혀 있다.

살아남은 것: `![](x.png =400x)` 폭 지정 · `:::message` 와 `::::details` 중첩 · `@[card]` · `@[gist]` · GitHub URL 임베드 · ` ```go:파일명 ` · ` ```diff go ` · ` ```mermaid ` · KaTeX `$$` 와 인라인 `$K = 600$` · 각주.

**그래서 `articles/`를 `ignorePatterns`에 넣지 않았다.** 표는 손으로 맞추지 않는다.

### 다만 front matter의 따옴표는 바뀐다

`zenn new:article`이 만드는 템플릿은 큰따옴표인데 **oxfmt가 작은따옴표로 바꾼다**(`singleQuote: true`).

```diff yaml
- title: "【テスト】GitHub 連携と記法の動作確認"
+ title: '【テスト】GitHub 連携と記法の動作確認'
```

둘 다 유효한 YAML이고 zenn-cli도 정상 파싱한다. **고칠 것이 아니라 알고 있으면 되는 동작**이다 — 새 기사를 만들면 첫 `pnpm lint`에서 한 번 바뀌고 그 뒤로는 안 바뀐다.

### 물결표는 본문에서 쓰지 않는다 — 이건 진짜 함정이다

`~`가 한 문단에 두 개 있으면 마크다운이 **취소선으로 짝짓는다.** oxfmt는 그걸 정규 형태인 `~~`로 굳혀버려서, 범위 표기가 조용히 취소선이 된다.

```diff md
- 전법 선택은 50~200cp(Δ 2~8%p)라
+ 전법 선택은 50~~200cp(Δ 2~~8%p)라
```

**이미 `docs/06-status.md`에서 벌어져 있었다**(이 PR에서 고쳤다). 저장하면 굳어지므로 사람 눈으로는 거의 못 잡는다.

범위는 `50-200cp`처럼 붙임표로 쓴다. 일본어 본문에서는 애초에 전각 물결표 `〜`를 쓰므로 걸리지 않는다.

### 한 편의 구조 — 개념부터 친절하게 쓴다

**읽는 사람이 그 개념을 처음 본다고 가정한다.** 검색으로 들어온 독자는 우리 프로젝트를 모르고, 그 개념도 모른다. 「아는 사람만 읽는 글」은 첫 화면에서 독자를 잃는다.

| 순서                      | 내용                                               | 비중        |
| ------------------------- | -------------------------------------------------- | ----------- |
| ① 무엇이 곤란한가         | 개념 이름을 대기 전에 **그게 없을 때 겪는 일**부터 | 짧게        |
| ② **개념 설명**           | 그림과 최소 예제로. **여기가 본문의 절반이다**     | **가장 큼** |
| ③ 어떻게 쓰는가           | 복사해서 돌아가는 최소 코드                        | 중간        |
| ④ 이 프로젝트에서 물린 것 | 남의 글과 갈리는 자리. 클라이맥스                  | 중간        |
| ⑤ 정리                    | 세 줄                                              | 짧게        |

**②를 줄이고 ④로 달려가지 않는다.** ④는 ②를 읽은 사람에게만 값이 있다.

### 친절함의 기준

- **용어는 처음 쓸 때 반드시 푼다.** 다만 EC2·React처럼 널리 알려진 것은 설명하지 않는다 — 그건 친절이 아니라 늘어짐이다. 기준은 **「이 개념을 일본어로 검색해서 좋은 해설이 바로 나오는가」**
- **결론을 먼저, 근거를 뒤에.** 「왜 그런지는 마지막에 알려드리겠습니다」로 끌지 않는다
- 코드는 **그 블록만 복사해도 돌아가는 최소 단위**로 쓴다. 우리 코드에서 잘라온 조각은 문맥이 없어서 독자 환경에서 안 돈다
- **그림을 아끼지 않는다.** Mermaid는 이미지 파일이 없어서 비용이 거의 0이다(§5)
- 전제 지식이 필요하면 **첫머리에 링크로 밝힌다.** 중간에서 갑자기 요구하지 않는다
- 쇼기 용어(持ち駒·成り·詰み)는 일본 독자에게 설명이 필요 없다. **반대로 USI·SFEN·NNUE는 쇼기를 알아도 모른다**

## 9. 쓰면 거짓말이 되는 것

[상태 §5](06-status.md)와 같은 목록이지만, 기사는 **밖으로 나가므로** 여기 다시 적는다.

- **LLM이 한 줄도 안 붙었다.** `ORCA_API_KEY`는 SSM에 `unset` 자리표시자고, 개입 문구는 전부 카테고리별 고정 일본어 템플릿이다. **「AIが説明してくれる」는 현재 사실이 아니다.** B1은 「こう設計した」까지만 쓴다
- 상수 K(600)·레벨별 임계치·상대 밴드가 전부 초기값이고 실측 전이다
- **「적응형 상대」가 사람에게 적응하지 않는다.** 고정 밴드에 국면을 맞출 뿐이고, 판정 결과를 쌓아 사람으로 만드는 코드가 없다. 실시간 조절은 설계만 있다 — E4가 바로 이 이야기다
- **카테고리가 온톨로지 전부는 아니다.** 二枚換え 손해와 정석 이탈은 안 들어갔다 — 앞은 여러 수에 걸친 교환을 봐야 하고 뒤는 정석 북이 있어야 한다. 「모든 블런더를 분류한다」고 쓰면 거짓말이 된다
- **개입이 여전히 사람을 가둔다.** 반박 수순이 「왜 나쁜가」를 채웠어도 한 국면에서 89%가 튕기는 것은 그대로다. 「개입이 학습을 돕는다」를 결과로 쓸 근거가 아직 없다
- 국면 캐시를 쓰는 곳이 없다 / 詰み 게이지 없음 / Google 로그인 없음(익명 대국만) / three.js 없음(2D 보드만) / 리뷰 화면 없음 / 정석 북 없음
- 반박 수순은 **DB에 안 남는다.** `interventions`는 카테고리와 Δ승률까지다

### 동기화 브랜치 — 확인 완료, `main`으로 확정

확인할 때만 동기화 브랜치를 작업 브랜치(`docs/zenn-article`)로 옮겨서, 머지 없이 대시보드에 下書き가 뜨는 것을 봤다. **확인이 끝나고 `main`으로 되돌렸다.**

`main`으로 두는 것이 맞다. [CLAUDE.md](../CLAUDE.md)상 `main` 머지는 사람이 GitHub PR 화면에서 하므로, 작업 브랜치에 걸어두면 그 브랜치가 머지되어 사라진 뒤 **동기화가 조용히 멈춘다.** 에러가 안 나서 알아채기 어렵다.

### 그래서 기사가 Zenn에 닿는 경로는 이렇다

```
브랜치 작업 → PR → 사람이 main 머지 → Zenn이 main을 보고 동기화
```

**머지가 곧 공개는 아니다.** `published: false`인 채로 머지되면 下書き로만 들어간다. 공개는 그 값을 `true`로 바꾸는 **별도 PR**이고, 그래서 초안을 안심하고 쌓을 수 있다.

머지 전 확인은 `pnpm zenn:preview`가 맡는다. **이미지도 로컬 프리뷰가 `/images`를 그대로 서빙**하므로 머지 없이 볼 수 있다.

> 등록 브랜치에서 사라진 기사는 Zenn에서도 지워진다. 테스트 기사가 `main`에 없으므로 되돌린 시점에 정리됐다.

### 브랜치를 바꾸기 전에 한 push는 소급되지 않는다

처음엔 아무것도 안 떴다. 원인은 순서였다.

```
① push (docs/zenn-article)      ← 등록 브랜치가 아직 main이라 웹훅이 안 뜬다
② Zenn 설정에서 브랜치 변경     ← 지나간 push를 가져오지 않는다
```

**설정을 저장해도 과거 커밋을 끌어오지 않는다.** `git commit --allow-empty`로 push를 한 번 더 일으키자 바로 떴다. 브랜치를 옮긴 뒤에는 **새 push가 한 번 필요하다.**

## 12. 소재가 계속 바뀐다 — 낡지 않게 쓰는 법

기사의 재료인 코드가 마감까지 계속 갱신된다. **D5·D6이 남아 있다** — LLM 계층, 리뷰 화면, three.js. 적응형 상대는 일정보다 먼저 들어왔다. 오늘 쓴 문장이 사흘 뒤에 거짓이 될 수 있고, **기사는 밖으로 나가서 고칠 기회가 없다.**

### ① 「지금 이렇다」가 아니라 「그때 이렇게 판단했다」

축을 **판단과 근거**에 두면 코드가 바뀌어도 글이 안 틀린다. 사고 기록(C)과 전략(B)은 원래 이 형태다. 반대로 「현재 이렇게 동작한다」는 반드시 낡는다.

### ② 부재를 단정하지 않는다 — 대신 범위를 긋는다

이것이 가장 위험한 자리다.

| 쓰지 않는다                    | 쓴다                           |
| ------------------------------ | ------------------------------ |
| 現在 LLM は 1 行も入っていない | この記事が扱うのは判定層までだ |
| 詰み ゲージはまだ無い          | 詰み 探索の話は別稿にする      |

**없다고 말하지 않으면 생겨도 안 틀린다.** §9의 「쓰면 거짓말이 되는 것」이 여기서 함께 풀린다 — 사실이 아닌 것을 안 쓰는 동시에, 사실이 될 것을 미리 부정하지도 않는다.

### ③ 검증 시점과 커밋 SHA를 말미에 박는다

실측 숫자는 엔진이나 `nn.bin`이 바뀌면 달라진다. 어느 시점 값인지가 안 붙으면 나중에 대조할 수가 없다.

### ④ GitHub 임베드는 SHA 퍼머링크로만

브랜치 링크는 코드가 바뀌면 **글이 조용히 틀려진다.** SHA는 GitHub가 영구 보존하므로 링크가 죽지도 않는다.

### ⑤ 영향 추적 — 남은 D5·D6이 들어올 때 손볼 기사

| 무엇이 들어오면    | 손봐야 하는 기사                                            |
| ------------------ | ----------------------------------------------------------- |
| LLM 계층 (D5)      | B1 — 「설계」까지만 쓴 부분을 다시 본다                     |
| 상수·밴드 실측     | A11 · B9 · B15 — 초기값이 아니게 된다                       |
| 엔진·`nn.bin` 교체 | A5 · A7 · B2 · C11 — 실측 표를 다시 돌린다                  |
| 실시간 실력 추정   | **E4가 통째로 바뀐다** — 「국면에 적응한다」가 끝난다       |
| 갇힘 해소          | C10 · C11 — 89%가 줄면 그 숫자가 그 국면의 것이 아니게 된다 |
| 詰み 게이지 · 리뷰 | D4 — 「무엇을 말하지 않는가」의 목록이 바뀐다               |

**이 표가 §12 ②(부재를 단정하지 않는다)와 짝이다.** 여기 있는 글은 「아직 없다」를 쓰면 반드시 틀려진다.

> **초안으로 쌓는 것이 여기서 값을 한다.** `published: false`로 모아뒀다가 공개 시점에 한 번 훑을 기회가 생긴다. 쓰는 족족 공개하면 못 하는 일이다.

## 13. 재싱크와 제외 목록

### 재싱크

[상태](06-status.md)가 갱신될 때마다 §8의 목록을 훑는다. 새 소재가 나오면 더하고, 근거 강도가 올라가면 고친다. **이 문서는 계획이 아니라 살아 있는 목록이다.**

돌린 뒤에는 문서 맨 위의 **「마지막 재싱크」**를 갱신한다. 그게 없으면 다음 사람이 어디까지 반영됐는지 알 수 없어 처음부터 다시 읽게 된다.

### 제외 목록은 재싱크보다 강하다

**한 번 빼기로 한 주제는 되살리지 않는다.**

재싱크를 돌리면 같은 소재가 다시 「좋은 주제」로 발견된다. 근거가 새로 생겼거나 실측이 붙었으면 더 그렇다. **그래도 안 된다.** 아래 표에 있는 것은 새로 발견되더라도 §8에 다시 올리지 않는다.

되살리는 유일한 길은 **사용자가 명시적으로 그렇게 말하는 것**이다. 근거가 좋아졌다는 것은 이유가 못 된다.

| 주제 | 뺀 날 | 이유 |
| ---- | ----- | ---- |

> 비어 있다. 뺄 주제가 나오면 여기에 적고 §8에서 지운다. **표에 적는 것이 먼저다** — 목록에서 지우기만 하면 다음 재싱크에서 그대로 돌아온다.

## 14. 첫 편에서 고정한 형식

`articles/showgi-green-deploy-broken-game.md`(C1). §8의 5단 구조를 실제로 한 편에 태워 보고 정한 것들이다. **다음 편부터 이대로 쓴다.**

②(개념 설명)가 본문의 약 4할을 먹었다. 「ECS의 태스크 정의가 이미지의 `ENV`를 덮어쓴다」 하나를 설명하는 데 그만큼 든다 — ④로 바로 달려갔으면 세 문단으로 끝났을 글이다.

### 코드 인용 — 주석은 일본어로 옮긴다

§5는 「퍼블릭 리포라 실제 소스를 그대로 박는다」였는데, 실제로 임베드해 보니 **레포의 코드 주석이 한글**이라([CLAUDE.md](../CLAUDE.md) 언어 규칙) 일본 독자에게 안 읽히는 덩어리가 그대로 나간다.

| 무엇               | 어떻게                                                             |
| ------------------ | ------------------------------------------------------------------ |
| 본문의 코드        | ` ```go:경로 ` 라벨을 붙인 **발췌.** 주석은 일본어로 옮긴다        |
| 실제 소스          | **말미에 SHA 링크 목록.** 마크다운 링크로 건다 — 임베드는 안 쓴다  |
| 독자가 돌려볼 코드 | 그 블록만 복사해서 돌아가는 최소 예제. 우리 코드에서 자르지 않는다 |

**번역했다고 밝히지 않는다.** 임베드를 안 쓰므로 원문이 화면에 같이 뜨지 않고, 어긋나 보일 자리가 없다. 「원문은 한국어입니다」는 기사 주제와 상관없는 데다 일본 독자에게 질문 하나를 더 만든다. 주석을 옮기는 것은 긴 부분을 `// ...`로 줄이는 것과 같은 층위의 손질이고, 원본 대조는 말미의 SHA 링크가 보장한다.

### 초안은 끝이 아니다 — 수확 0이 나올 때까지 리뷰한다

C1은 초안 뒤에 **세 패스**를 돌았고 매번 나왔다.

| 패스 | 새로 들여온 근거       | 수확                                 |
| ---- | ---------------------- | ------------------------------------ |
| 1    | 원본 코드·설정과 대조  | 기술적 오류 1, 부정확 3              |
| 2    | 1패스 수정이 만든 균열 | 논리 결함 1, 모순 2                  |
| 3    | **git 히스토리**       | 글의 요점에 해당하는 **내용 누락 1** |

**매 패스는 새 근거를 하나 들고 들어온다.** 같은 글을 눈으로만 다시 훑는 패스는 두 번째부터 수확이 급락하고, 고친 것을 또 고치는 낭비가 된다. 순서는 ① 원본 대조 ② 주장을 실행해서 확인 ③ git 히스토리 ④ 렌더된 화면 ⑤ 공식 문서.

3패스의 수확이 그 증거다 — 「왜 지금까지는 멀쩡했나」는 **교체 전 Dockerfile을 열어봐야** 나왔다. 다시 읽어서는 안 나온다.

**앞 패스의 수정이 다른 곳과 모순을 만들지 않았는지**를 매번 같이 본다. 2패스 수확은 전부 이것이었다.

### 최소 예제는 실제로 돌려서 출력을 붙인다

C1의 `docker run -e` 3줄은 정말로 실행해서 나온 출력이다. 특히 **「빈 문자열로 덮어써진다」는 머리로 짚으면 반대로 쓰기 쉬운 자리**였다 — 지운 것이 아니라 빈 값으로 덮인다.

### 태그는 검색으로 들어오는 독자를 우선한다

§7은 공통 4개(`将棋`·`Go`·`AWS`·`個人開発`)를 깔라고 했는데, C1에서는 `将棋`를 빼고 `docker`를 넣었다.

**Zenn에 시리즈 개념이 없어서 태그가 글을 묶어주지 않는다.** 태그의 유일한 일이 검색이고, 「ECS 環境変数 上書き」로 들어올 사람에게 `将棋`는 다섯 칸 중 한 칸을 버리는 것이다. 쇼기가 본론인 편에서는 당연히 넣는다.

### 렌더 확인은 브라우저로 한다 — 로컬 프리뷰가 실물과 같다

`pnpm zenn:preview`를 띄우고 **브라우저로 연다.** C1에서 확인된 것: mermaid · `:::message` · `:::message alert` · ` ```diff hcl ` · 코드 파일명 라벨 · 표 · 목차. 전부 실제로 그려진다.

**mermaid도 로컬에서 그대로 그려진다.** `embed.zenn.studio` iframe으로 나가는데, 프리뷰 페이지가 `listen-embed-event.js`를 같은 곳에서 불러오기 때문에 **온라인이면 로컬에서도 Zenn과 같은 것이 보인다.** 다이어그램 문법이 맞는지도 여기서 확인된다.

| 방법                                | 무엇을 보나                                                                |
| ----------------------------------- | -------------------------------------------------------------------------- |
| **브라우저로 프리뷰**               | **실물.** 사람이 읽고 고칠 때는 이것만 쓴다                                |
| `/api/articles/<slug>`의 `bodyHtml` | 특정 문법이 인식됐는지 기계로 확인할 때. 임베드는 iframe 태그까지만 보인다 |

> 포트 8000이 이미 잡혀 있으면 `zenn preview`가 조용히 **8001로 올라간다.** 로그의 `👀 Preview:` 줄을 보고 들어간다.

### GitHub 파일 임베드는 이 레포에서 못 쓴다

§5는 이것을 주력 무기로 잡았지만, **실제 렌더를 보고 뺐다.** `infra/ecs.tf`를 임베드하니 **한글 주석 아홉 줄이 그대로 화면에 떴다.** 일본 독자에게는 읽히지 않는 덩어리이고, 「번역이 덜 된 것」으로 보인다.

레포의 코드 주석은 한글이 정본이다([CLAUDE.md](../CLAUDE.md) 언어 규칙). **주석을 일본어로 바꾸는 것이 아니라 임베드를 안 쓰는 쪽으로 푼다** — 코드 주석은 이 레포를 읽는 사람을 위한 것이고, 기사는 기사에서 해결한다.

| 대신                                 | 무엇을 지키나                      |
| ------------------------------------ | ---------------------------------- |
| 본문은 **번역한 발췌** + 파일명 라벨 | 일본어로 읽힌다                    |
| 말미에 **SHA 마크다운 링크 목록**    | 원본 대조가 되고, 링크가 안 죽는다 |

**URL을 한 줄에 그냥 두면 안 된다.** Zenn이 그걸 임베드로 바꿔서 소스를 통째로 그린다 — 마크다운 링크(`[텍스트](url)`)로 써야 링크로 남는다.
