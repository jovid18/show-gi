## 1. 한 줄

**개입 루프가 프로덕션에서 끝까지 돈다.** 블런더를 두면 물러지고, 왜 나쁜지가 사실로 뜨고, 상대가 어떻게 벌하는지를 한 수씩 넘겨 볼 수 있고, 같은 국면에서 계속 막히면 찾는 것을 돕는다. 그 문장을 **지금은 LLM이 쓴다** — 키가 프로덕션에 들어갔다(§3).

### 1순위(기능) — 태그를 **쓰는 쪽**을 붙인다 (감지는 §30에서 열렸다)

~~**지금 이 제품이 아는 쇼기는 룰과 엔진 평가치뿐이다.**~~ **통로는 열렸다**(§30) — `internal/tag` 이 네 축을 감지하고, 짜는 순간 판에 이름이 뜨고, `kb_chunks` 에 **47항목**이 들어갔다.

**그런데 남은 것이 목록의 크기가 아니다.** 태그가 필요했던 이유 셋(RAG 검색 키 · 제안형 힌트 게이트 · 「정석 이탈」 카테고리)에 **아직 하나도 안 이어져 있다** — 지금 태그는 화면에 이름을 띄우는 데까지다. 목록을 40개로 늘려도 그 셋은 그대로 비어 있다.

```
囲い    21 / 42     将棋ウォーズ 기준
전법     7 / 114     좌표로 표현 가능한 것은 애초에 여섯쯤이다
戦型     3 / 6
手筋     9 / 10     태그 수로는 10 (十字飛車·角による両取り는 위키백과 이름)
```

넓히는 값이 **항목마다 다르다.** 좌표를 확인할 수 있으면 싸고, 없으면 못 넣는다(§30).

## 6. D2 — 대국 루프 (완료)

배포 파이프는 끝났다. 이제부터는 **main에 머지하면 자동으로 배포된다.**

D2의 목표는 [로드맵](05-roadmap.md) 기준 **"사람 vs 엔진 한 판을 끝까지 둘 수 있다"**였고, 네 조각으로 나눠 전부 끝냈다.

```
① 룰 엔진 이식      ✅ apps/server/internal/shogi/   — 테스트 17개
② USI 클라이언트    ✅ apps/server/internal/usi/     — 테스트 18개
③ WS 대국 루프      ✅ apps/server/internal/game/ + server/ws.go — 테스트 20개
④ 프론트 보드       ✅ apps/web/src/                — 2D. three.js는 D6
```

**D2 내내 DB를 안 썼다.** 완료 기준이 "한 판을 끝까지 둘 수 있다"이지 "저장된다"가 아니라서다. 그래서 **세션이 서버 메모리에만 있고 연결에 매여 있다**(§9의 무중단 배포 항목과 같은 이야기).

D3의 첫 관문이던 DB 접근 계층은 sqlc로 정해졌다(§12).

### ① 룰 엔진에서 원본과 달라진 것

`../shogi`에서 그대로 가져오지 않은 부분만 적는다.

| 무엇                        | 왜                                                                                                                                                                                                                                                                                                                                                               |
| --------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `IllegalMoveError`의 구조   | 원본은 한국어 문구를 에러에 직접 담았다(주석에 "학습용 메시지"). 그대로면 화면에 한글이 나간다. **`Reason` 코드 + `Message()` 일본어**로 쪼갰다. 다만 이건 실력 추정용 신호가 아니다 — 클라이언트가 합법수만 고르게 할 것이라 실사용자한테서는 거의 안 나온다. **API 직접 호출과 국면 어긋남에 대한 방어이고, 후자는 우리 버그라 사유가 정확해야 원인을 찾는다** |
| Go 에러 문자열              | 파싱 실패 등 개발자용 에러는 전부 영어로 바꿨다. 로그로만 가고 화면에는 안 나간다                                                                                                                                                                                                                                                                                |
| `InventoryShortfall` 미이식 | 手筋 부분도(지면 문제 디지털화)에서 "持ち駒 残り全部"를 검증하려던 함수다. 그 기능을 안 하므로 호출자가 없다. `InventoryExcess`는 밖에서 들어온 SFEN 방어용이라 가져왔다                                                                                                                                                                                         |

테스트는 원본 14개를 옮기고 3개를 더했다 — `InventoryExcess`, `MoveJa`(棋譜 표기), 그리고 **사유 문구에 한글이 없는지 기계로 확인하는 것**. 마지막 것은 언어 규칙을 사람 눈으로 지키면 결국 새기 때문이다.

### ② USI 클라이언트에서 고친 것

| 무엇                    | 내용                                                                                                                                                                                                                                                                    |
| ----------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **깊이별 평가치**       | 원본 `parseScore`는 `depth`를 안 읽고 같은 순위를 덮어써서 **마지막 깊이만** 남겼다. `SearchLine`에 `Depth`·`MultiPV`를 넣고 `SearchResult.History`에 깊이별로 쌓는다. `EvalByDepth(수)`가 `edges.eval_by_depth`에 들어갈 배열을 준다                                   |
| **속보는 안 담는다**    | `lowerbound`/`upperbound` 라인의 점수는 확정값이 아니다. 담으면 개입 판정이 엔진이 "아직 모른다"고 말한 값 위에서 돈다                                                                                                                                                  |
| **빈 깊이를 안 메운다** | 그 수가 상위 k에 없던 깊이는 데이터가 없는 것이다. 실측에서 `4g4f`가 depth **6·8·10**에만 잡혔다 — 없는 값을 지어내면 판정이 그 위에서 돈다                                                                                                                             |
| **엔진 풀**             | `Engine`은 mutex로 탐색을 직렬화한다(프로세스 1개 = 동시 탐색 1개). `Engine`은 그대로 두고 `Pool`을 새로 썼다. **옵션은 Engine에 남으므로, 빌린 쪽이 탐색 직전에 매번 걸어야 한다** — 안 그러면 A 대국의 강함이 B 대국에 샌다                                           |
| **ctx 취소**            | 원본은 취소가 없고 `SearchDepth`는 시한조차 없었다. 끝나지 않는 탐색 하나가 풀 슬롯을 영구히 물면 교착이다. 취소 시 `stop`을 보내고 **bestmove를 반드시 삼킨다** — 안 삼키면 다음 탐색이 이전 탐색의 답을 읽는다(대국 루프에서는 상대가 엉뚱한 수를 두는 것으로 보인다) |

`go mate`는 안 넣었다. **fairy-stockfish가 지원하지 않아 지금은 검증할 방법이 없다**(§9). 엔진 교체 PR에서 함께 넣는다.

테스트 18개. 그중 `TestRealEngine`은 **진짜 엔진에 붙는 유일한 테스트**로, `SHOWGI_USI_CMD`가 없으면 건너뛴다(CI 러너에 엔진이 없다). 가짜 엔진은 우리가 적은 것만 돌려주므로 실제 출력을 읽는다는 증거가 못 된다. 컨테이너에서 한 번 돌려 확인했다:

```sh
SHOWGI_USI_CMD=fairy-stockfish go test ./internal/usi/ -run RealEngine -v
# engine: Fairy-Stockfish 11.1 LB 64
# best=4g4f cp=143 depth=10, 4g4f의 깊이별=[{6 129} {8 126} {10 143}]
```

**엔진을 갈아끼울 때 이 테스트가 첫 관문이다.**

### ③ WS 대국 루프 — 프론트가 붙일 계약

`GET /ws/game`. 연결 하나가 대국 하나다.

```
브라우저 → 서버   {"type":"move","usi":"7g7f"}
                  {"type":"resign"}

서버 → 브라우저   {"type":"snapshot","snapshot":{…}}
                  {"type":"error","reason":"nifu","message":"二歩です。…"}
```

`snapshot`은 **항상 전체 상태**다. 부분 갱신을 보내지 않는다 — 롤백(D3)이 들어오면 "무엇이 바뀌었는지"를 클라이언트가 재구성하게 두는 순간, 물러진 뒤 화면과 서버가 어긋나도 아무도 모른다.

| 필드                    | 쓰임                                                                   |
| ----------------------- | ---------------------------------------------------------------------- |
| `sfen` · `ply` · `turn` | 판 그리기                                                              |
| `legalMoves`            | **사람 차례일 때만 채워진다.** 클라이언트는 여기 있는 수만 고르게 한다 |
| `moves[]`               | `{usi, ja, by}` — `ja`가 棋譜 표기(`▲7六歩`)라 그대로 화면에 나간다    |
| `yourTurn` · `thinking` | 입력 잠금과 「考え中」 표시                                            |
| `status` · `winner`     | `playing` / `checkmate` / `stalemate` / `resigned` / `repetition`      |

`error`는 코드(`reason`, 영어)와 문구(`message`, 일본어)를 함께 준다. **문구는 그대로 띄우면 된다.**

설계상 중요한 것 셋:

- **상태는 세션 goroutine 하나가 소유한다.** 잠금이 없고, 밖에서 상태를 읽는 길도 없다 — 스냅샷 요청조차 명령이다
- **엔진 탐색은 세션 goroutine 밖에서 돈다.** 안에서 기다리면 생각하는 동안 투료도 스냅샷도 못 받는다. 국면이 바뀌면 세대 번호가 올라가고 **늦게 도착한 탐색 결과는 버려진다** — D3의 롤백이 여기에 그대로 얹힌다
- **엔진 출력을 믿지 않는다.** 돌려준 수를 룰 엔진으로 검증하고, 둘 수 없으면 기보를 깨뜨리는 대신 그 자리에서 대국을 끝낸다

`TestWSAgainstRealEngine`이 진짜 엔진과 24수를 뒀다(`SHOWGI_USI_CMD` 없으면 건너뜀). 가짜 상대로는 우리가 적은 수가 돌아오는 것뿐이라 증명이 안 된다.

> **엔진이 안 뜨면 `/ws/game`이 503을 주고 서버는 그냥 뜬다.** 프로세스를 죽이면 ECS가 재시작을 반복하며 `/healthz`까지 같이 사라져 사이트 전체가 내려간다. 대국만 막고 나머지는 살린다.

### ④ 프론트 보드 — 화면에서 정한 것

`docs/03-frontend.md`의 방침(다크 기본, 무광 판, **강조는 색이 아니라 빛으로**, 평시엔 조용하게)을 그대로 따랐고, 구현하면서 정한 것만 적는다.

| 무엇                           | 정한 것                                                                                                                                                                                                                                              |
| ------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **한자 최소 크기 먼저**        | 하한을 못 박고 칸 크기를 역산했다(`--sq`). ~~360px 화면에서 이 하한이 물려 칸이 32px가 된다~~ — **이 순서는 §14에서 뒤집혔다.** 움직임 표식이 새겨지면서 글자가 표식에 자리를 맞춘다                                                                 |
| **駒는 明朝, UI는 ゴシック**   | 붓에서 온 굵기 대비가 있어야 「버튼에 쓴 글자」가 아니라 駒로 읽힌다. 棋譜도 같은 明朝로 둬서 판과 기보가 한 서체로 이어진다                                                                                                                         |
| **판은 榧색, 기물이 더 밝다**  | `03-frontend.md`가 "오프화이트 판"이라고 지시했는데 그대로 만드니 판·기물·빛이 전부 밝은 값이 되어 대비가 1.13이었다. 실제 판은 꿀색 나무이고 기물이 그보다 밝다 — 되돌리니 1.92. **빛으로 강조하려면 판이 밝으면 안 된다.** 설계 문서도 같이 고쳤다 |
| **강조는 --light 하나**        | 착수 후보는 **칸 전체가 밝아지고**(잡는 수는 駒가 칸을 덮으므로 더 세게), 王手는 유일하게 또렷한 테. D3 개입 연출은 이걸 더 세게 쓰는 것이다. 직전 수만 빛이 아니라 색이다(§14)                                                                      |
| **새 대국은 새 연결**          | 대국이 끝나면 「もう一局」이 뜬다. 서버가 연결 하나에 대국 하나를 여니 소켓을 다시 여는 것이 곧 새 판이다 — 서버에 명령을 새로 만들지 않았다. 끊긴 연결을 다시 붙이는 것도 같은 장치다                                                               |
| **고른 駒는 들어올린다**       | 처음엔 빛으로 표시했는데 **밝은 駒 위의 밝은 빛은 대비가 없어 안 보였다.** 칸에 빛의 테를 두르고 駒를 판에서 띄우는 쪽으로 바꿨다                                                                                                                    |
| **클라이언트는 규칙을 모른다** | 서버가 준 `legalMoves`만 쓴다. 二歩도 打ち歩詰め도 클라이언트가 알 필요가 없다 — 목록에 안 들어온다. 「成りますか」를 묻는 조건도 *성·불성이 둘 다 목록에 있는가*로 판정한다                                                                         |
| **棋譜 표기는 안 만든다**      | 서버의 `ja`를 그대로 그린다. 클라이언트가 USI에서 다시 만들면 두 벌이 되고, 어긋났을 때 어느 쪽이 맞는지 알 수 없다                                                                                                                                  |

브라우저를 띄워 `▲7六歩 △3四歩`까지 두고 데스크톱·390px·360px를 눈으로 확인했다. 좁은 화면에서 가로 넘침 0.

## 9. 알아두면 시간 아끼는 것

**엔진 빌드 실측** (arm64 컨테이너, 2026-08-08)

| 조합                      | 결과                                                          |
| ------------------------- | ------------------------------------------------------------- |
| `TARGET_CPU=ARMV8` + g++  | ✅ **33초**, USI 응답 확인 (`YaneuraOu NNUE 9.70git 64ARMV8`) |
| `ARMV8_DOTPROD` + g++     | ❌ NEON 인트린식 컴파일 에러                                  |
| `ARMV8_DOTPROD` + clang++ | ❌ 링커(lld) 없음                                             |

즉 **YaneuraOu는 arm64에서 문제없이 빌드된다.** dotprod는 NNUE 추론 속도 최적화라 없어도 된다. 남은 것은 평가함수 파일(水匠, ~60MB)을 이미지에 굽는 일.

**fairy-stockfish에는 `go mate`가 없다 — 그런데 에러도 안 난다** (실측 2026-08-09)

1手詰め 국면(`4k4/9/4P4/9/9/9/9/9/8K b G 1`, 정답 `G*5b`)에 `go mate 5000`을 보낸 결과:

```
보낸 것:  go mate 5000
기대:     checkmate G*5b        (USI 규격)
실제:     bestmove G*5b         ← 일반 탐색으로 떨어진다
```

`checkmate` 응답이 한 줄도 안 온다. `mate` 토큰을 조용히 무시하고 보통 `go`처럼 도는 것이라, 시간 제한 없이 보내면 **무한 탐색**이 된다. 파싱하는 쪽은 영원히 안 오는 `checkmate`를 기다린다.

같은 프로브에서 확인된 것: USI 핸드셰이크 정상(`Fairy-Stockfish 11.1 LB 64`), `var shogi` 존재, MultiPV는 `multipv 1/2/3`이 `score cp`와 PV를 제대로 돌려준다. **즉 못 쓰는 것은 詰み 탐색 하나뿐이고, 그게 D4의 詰み 게이지다.**

> 엔진 옵션 이름은 `USI_Variant`가 아니라 **`UCI_Variant`**다. D2 ②에서 이식할 `client.go`가 두 이름을 다 보내므로 이 차이에는 안 걸린다.

**OIDC가 거부당하면 subject 형식부터 확인한다**

GitHub이 subject claim에 **불변 ID**를 넣는다. 문서에 흔히 적힌 형식이 아니다.

```
통념:  repo:jovid18/show-gi:ref:refs/heads/main
실제:  repo:jovid18@143411145/show-gi@1327659382:ref:refs/heads/main
```

에러는 `Not authorized to perform sts:AssumeRoleWithWebIdentity` 한 줄뿐이라 원인을 안 알려준다. 현재 형식을 보는 법:

```sh
gh api /repos/jovid18/show-gi/actions/oidc/customization/sub
```

신뢰 정책에는 두 형식을 목록으로 넣어뒀다(OR로 평가된다). 이걸 찾는 데 실패한 실행이 두 번 들었다.

**JMESPath에 축약 표기는 없다**

`{family, cpu}`는 문법 오류다. multi-select hash는 `{family: family, cpu: cpu}`처럼 쌍으로 적는다. AWS에 요청이 가기 전에 파싱에서 죽는다.

**apply에서 실제로 물린 것들** (2026-08-09)

| 증상                                              | 원인                                                                                                                           |
| ------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| `InvalidParameterValue: Invalid rule description` | 보안그룹 규칙 `description`에 **한글을 넣을 수 없다.** 허용 문자 집합이 정해져 있다                                            |
| SG 삭제가 ENI 분리에서 실패                       | 보안그룹 `description`은 **불변**이다. 고치면 SG 재생성을 시도하는데 RDS가 붙어 있으면 못 지운다. 문구가 낡아도 두는 편이 싸다 |
| `ssm:DescribeParameters` 거부                     | 리소스 단위 권한을 지원하지 않는 **계정 단위 API**라 `Resource: "*"`가 필요하다                                                |
| `iam:AttachRolePolicy` 거부                       | 정책을 ECS용으로 재작성할 때 해당 statement를 통째로 빠뜨렸다. **없는 Sid를 수정하는 스크립트는 조용히 아무것도 하지 않는다**  |

**로컬 8080 포트 충돌**

`../shogi` 프로젝트의 `shogi-guide` 컨테이너가 8080을 잡고 있으면 `docker compose up`이 실패한다. `cd ../shogi && docker compose down`으로 내린다.

**무중단 배포는 아직 성립하지 않는다**

ECS가 롤링 배포와 헬스체크를 해주지만, **대국 세션이 서버 메모리에 있어서 배포하면 진행 중인 대국이 끊긴다.** 세션을 DB로 빼기 전에는 어떤 인프라를 써도 같다. 데모 녹화 중에는 main에 머지하지 않는 것으로 우회한다.

**비용**

상시 가동 시 주 **~$37**(Fargate $26 + ALB $4 + RDS $6). **대회가 끝나면 `terraform destroy`** — 안 지우면 월 $150이 계속 나간다.

## 10. 엔진 교체 — やねうら王 + 水匠5

D3 전에 끝내야 했다. 블런더 임계치와 승률 상수 K는 **어느 엔진의 cp인지에 종속**이라, fairy로 튜닝한 뒤 갈아끼우면 마감 직전에 MVP 사수선의 상수를 다시 잡게 된다.

```
탐색부   YANEURAOU_ENGINE_NNUE   v9.40 소스 빌드 (arm64, 약 50초)
詰み     YANEURAOU_MATE_ENGINE   같은 소스, 다른 에디션 — 별도 바이너리
평가     水匠5 nn.bin (63MB)     릴리스에서 빌드 시 다운로드
이미지   260MB                   기동 시 3엔진 + 서버 788MB
```

### 실측으로 잡은 것 — 전부 조용히 틀렸을 것들

| 무엇                   | 그대로 뒀으면                                                                                                                                                  |
| ---------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **`PvInterval=0`**     | 기본값 300(ms) 간격으로만 PV를 찍는다. 우리 탐색이 그보다 빨라서 **깊이별 평가치가 마지막 하나만 남았다.** 개입 판정의 입력이 통째로 사라지는데 에러는 안 난다 |
| **`Threads=1`**        | 기본 4. 풀 3개면 12스레드가 4 vCPU에 몰린다. 더 중요한 건 **멀티스레드는 고정 깊이에서도 결정적이지 않아** `positions` 캐시의 "같은 국면 = 같은 결과"가 깨진다 |
| **`USI_Hash=128`**     | 기본 1024. 엔진 하나가 통째로 잡는 메모리라 3개면 **3GB**를 잡고 기동 때 그만큼 지운다                                                                         |
| **`BookFile=no_book`** | 없는 정석 파일을 찾다 매 기동 에러를 남긴다. `USI_OwnBook=false`만으로는 안 멈춘다                                                                             |
| **`FV_SCALE=24`**      | 水匠5가 요구하는 값. 틀리면 cp 척도가 통째로 달라지고 임계치가 그 위에서 잡힌다                                                                                |

`PvInterval`은 **`TestRealEngine`이 잡았다.** 엔진을 바꾸자마자 "깊이별 기록이 1개뿐"으로 떨어졌고, 그게 없었으면 D3에서 판정이 안 되는 이유를 한참 찾았을 것이다. 고친 뒤에는 깊이 1~10이 빠짐없이 들어온다 — fairy(6·8·10만)보다 촘촘하다.

`PvInterval=0`은 **배포 설정이 아니라 파서가 동작하기 위한 조건**이라 `usi` 핸드셰이크에 넣었다. 나머지는 운영 손잡이라 환경변수다(`ENGINE_HASH_MB`·`ENGINE_THREADS`·`ENGINE_FV_SCALE`).

### `go mate`는 별도 바이너리다

탐색부에 보내면 **YaneuraOu에서도 `bestmove`가 돌아온다** — fairy와 같은 함정이다. 詰将棋 solver 에디션만 규격대로 답한다.

```
탐색부      go mate 5000  →  bestmove G*5b     ❌
mate solver go mate 5000  →  checkmate G*5b    ✅
```

이미지에 `ENGINE_MATE_CMD=/opt/yaneuraou/run-mate`로 넣어뒀다. ~~아직 부르는 코드는 없다~~ — **붙었다.** `startMateEngines` 가 풀을 띄우고 `engineAnalyst` 가 매 판정마다 부른다(§29 ②). ~~아직 없는 것은 詰み 게이지 화면이다.~~ **그것도 붙었다** — 같은 풀을 세션이 사람 차례마다 한 번 더 부른다(§31).

### 라이선스

やねうら王·NNUE 모두 **GPLv3**. 水匠5는 やねうら王 릴리스에서 무료 공개된 단체 파일이다(최신 水匠은 지원자 전용이라 못 쓴다).

엔진은 **파이프 너머의 별도 프로세스라 GPL이 우리 코드로 전파되지 않는다.** 이미지에 바이너리를 담는 것은 배포에 해당하므로 빌드한 태그를 Dockerfile에 남겼고, 레포가 퍼블릭이라 소스 제공 조건도 그걸로 충족된다.

### 남은 것

**cp 척도가 fairy와 다르다.** 로드맵의 「評価関数 비교 / 밴드 적중률·레이턴시 실측」이 이제 실제로 돌릴 수 있는 상태가 됐고, **D3의 상수를 잡기 전에** 해야 한다.

### 실측 — depth × MultiPV (2026-08-09)

`internal/usi/measure_test.go`. 엔진이나 `nn.bin`을 바꾸면 다시 돌린다.

측정 국면은 **将棋ウォーズ 8급 대국 두 판**(55수·161수)에서 序盤·中盤·終盤으로 6개를 뽑았다. 손으로 쓴 SFEN이나 프로 대국을 안 쓴 이유는 §10 아래에 적었다.

**15칸 전부 쟀다** (depth 3 × k 5). 왼쪽이 최장 소요, 오른쪽이 밴드 적중(/6).

| k \ depth | 10        | 12       | 14    |     | 10    | 12    | 14    |
| --------- | --------- | -------- | ----- | --- | ----- | ----- | ----- |
| 1         | 144ms     | 400ms    | 767ms |     | 0     | 0     | 0     |
| 5         | 318ms     | 956ms    | 4.0s  |     | 4     | 4     | 5     |
| **10**    | **609ms** | **2.0s** | 8.4s  |     | **5** | **5** | **5** |
| 20        | 967ms     | 3.3s     | 23.5s |     | 5     | 5     | 5     |
| 40        | 2.3s      | 7.1s     | 48.9s |     | 6\*   | 5     | 5     |

**두 축이 서로 다른 것을 지배한다.** 밴드 적중은 **k**가 정하고(0→4→5에서 포화) **depth와는 거의 무관하다**(가로로 평평하다). 반대로 시간은 depth가 지배한다 — k=10에서 609ms → 8.4s로 14배. 그래서 **k는 후보 다양성 기준으로, depth는 평가 정확도 기준으로 따로 고를 수 있다.**

`*` depth 10 / k=40의 6/6은 개선이 아니다. 그 칸의 최대 낙폭이 `24182`로 **詰み 점수**라, 40번째 후보에서 외통이 하나 튀어나온 것이다. 잡음이다.

정해진 것과 드러난 것:

|                                       |                                                                                                                                                              |
| ------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **적응형 상대 `k=10`**                | 적중이 여기서 멈춘다. 20으로 늘려도 덮이는 국면이 안 늘고 비용만 배가 된다                                                                                   |
| **단발 개입 판정**                    | `depth 10 × k=1` = **144ms**. 설계에 적어둔 ≈150ms가 맞았다                                                                                                  |
| **선행 계산은 적어둔 대로는 안 된다** | `depth 14 × k≈10`이 **8.4초**다. 플레이어가 그 안에 두면 "지연 0"이 성립하지 않는다. depth 12면 2.0초 — 내릴지는 초반 캐시 히트율을 보고 정한다 **[미확정]** |
| **덮이지 않는 1/6**                   | 승부가 갈린 종반이라 후보 낙폭이 20~40cp에 몰린다. **고장이 아니라 조절할 여지가 없는 국면**이고, 그때는 밴드 대신 최선수를 둬야 한다                        |

> 노트북(4코어 할당)에서 잰 값이다. **Fargate가 더 빠를 것이라고는 예상 못 했다** — §11 참조. 도커 데스크톱 VM의 가상화 오버헤드가 끼어 있었던 것으로 보인다. 넓은 k에서도 그런지는 아직 안 쟀다.

## 11. 배포는 성공했는데 대국이 안 됐다 (2026-08-09)

엔진 교체(§10)를 머지했더니 **배포가 초록으로 끝나고 사이트도 200인데 대국만 안 됐다.**

```
https://show-gi.com          200
https://show-gi.com/healthz  {"ok":true}
https://show-gi.com/ws/game  503  {"error":"engine_unavailable"}
```

### 원인 — 같은 값이 두 곳에 있었다

```
Dockerfile     ENV ENGINE_CMD=/opt/yaneuraou/run
태스크 정의    ENGINE_CMD=fairy-stockfish        ← 이쪽이 이긴다
```

**태스크 정의의 `environment` 가 이미지의 `ENV` 를 덮어쓴다.** 이미지에서 fairy-stockfish를 지웠는데 태스크 정의에는 그 이름이 남아 있어서, 서버가 없는 바이너리를 실행하려다 풀을 못 띄웠다.

엔진 실행 경로는 **이미지 내부 구조라 Terraform이 알 수 없는 값**이다. 양쪽에 적어두면 이미지를 바꿀 때 조용히 어긋난다. `infra/ecs.tf`에서 뺐다 — 운영 손잡이(`ENGINE_POOL_SIZE` 등)는 이미지 안에 없는 값이라 거기 둬도 안전하다.

### 세 가지가 예상대로/예상 밖으로 동작했다

|                                |                                                                                                                                                                               |
| ------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| ✅ **엔진 없이도 서버는 산다** | 프로세스를 안 죽이기로 한 결정(§6)이 바로 값을 했다. 죽였으면 ECS가 재시작을 반복해 사이트 전체가 내려갔다                                                                    |
| ❌ **아무도 못 잡았다**        | `/healthz`가 엔진을 일부러 안 건드리니 ECS도 워크플로도 초록이었다. **`{"ok":true,"engine":false}`로 상태를 드러내고, 배포 워크플로가 `engine`을 확인해 실패시키도록 고쳤다** |
| ❌ **로그를 못 봤다**          | §7에 "곧 물린다"고 적어둔 그대로 물렸다. 결국 로그 없이 태스크 정의를 직접 읽어 찾았다                                                                                        |

### 고치는 순서 — 이 순서여야 한다

배포 워크플로는 **AWS에 있는 현재 태스크 정의를 읽어** 이미지만 갈아끼운다. 그래서 `ecs.tf`를 고치는 것만으로는 프로덕션이 안 바뀐다.

```sh
terraform -chdir=infra apply     # ① ENGINE_CMD 없는 새 리비전 등록
                                 #    plan: 태스크 정의 1개 교체뿐. 서비스는 ignore_changes
# ② 그 다음에 머지 → images.yml 이 새 리비전을 읽어 배포
```

머지를 먼저 하면 워크플로가 낡은 리비전을 읽어서 **그대로 또 깨지고**, 고치려면 apply 뒤에 워크플로를 한 번 더 돌려야 한다(3단계).

### 결과 — 고쳐졌다

```
/healthz          {"engine":true,"ok":true}
서비스 리비전     show-gi:9   (ENGINE_CMD 없는 rev8 기반)
엔진 응답         평균 196ms  최장 308ms
기보              ▲9六歩 △3四歩 … △8七歩成
```

`skip_destroy`도 확인됐다 — apply가 `1 destroyed`라고 했는데 **rev6·rev7이 여전히 ACTIVE**다. 롤백 경로가 살아 있다.

**그리고 Fargate가 노트북보다 빨랐다.** depth 12 × k=1 기준 노트북 400ms / Fargate 308ms. §10에 "Graviton은 더 느리다"고 적어뒀던 것이 틀렸다 — 노트북 측정이 도커 데스크톱 VM 안이라 가상화 오버헤드가 끼어 있었던 것으로 보인다. **선행 계산을 depth 14로 유지할 여지가 생겼지만**, 비교한 것이 k=1 한 점뿐이라 넓은 k에서도 그런지는 따로 재야 한다.

> **`skip_destroy = true` 를 같이 넣었다.** 기본값이면 apply가 새 리비전을 만들면서 옛 것을 deregister 하는데, 그러면 ① 런북의 롤백 경로("이전 리비전으로 서비스를 돌린다")가 INACTIVE를 가리키고 ② apply 직후 잠깐 서비스가 가리키는 리비전이 INACTIVE가 되어, 그 사이 태스크가 죽으면 못 살아난다. 배포 워크플로가 Terraform 밖에서 리비전을 계속 쌓으므로 여기서 정리해봐야 얻는 것도 없다.

### 실측 — 詰み 탐색 (2026-08-09)

매 수 돌아야 하는 탐색이라(종반 판정 §2 + 詰み 게이지 §7) 따로 쟀다. 대국 B의 **162국면 전부**를 훑었다.

> **매 수 한 번이 아니라 두 번이다**(§31). 판정은 착수 **전** 국면을, 게이지는 사람 차례의 **현재** 국면을 묻는다 — 같은 질문을 한 수 늦게 하는 것이라 하나로 합칠 수 없다. 대신 **두 자리가 시간상 겹치지 않아**(판정은 사람의 수 직후, 게이지는 상대의 수 직후) solver 풀은 하나로 충분하다.

```
DepthLimit=7    최장 118ms   詰みあり  9/162   미증명 0
DepthLimit=9    최장 123ms   詰みあり  9/162   미증명 0
DepthLimit=11   최장 124ms   詰みあり 10/162   미증명 0    ← 채택
DepthLimit=13   최장 439ms   詰みあり 10/162   미증명 0
DepthLimit=15   최장 833ms   詰みあり 10/162   미증명 0
```

|                             |                                                                                                          |
| --------------------------- | -------------------------------------------------------------------------------------------------------- |
| **`DepthLimit=11`**         | 11이 7·9보다 詰み을 하나 더 찾는데 비용은 같다(124ms vs 118ms). 13부터는 더 못 찾으면서 3.5배가 된다     |
| **평균 107ms, 한계와 무관** | 대부분이 탐색이 아니라 고정 비용(국면 전송·통신)이다. 매 수 **두 번** 돌려도 상대 수(2.0s)에 묻힌다      |
| **미증명 0**                | 162국면 전부 `checkmate`/`nomate`로 결론이 났다. 둘 다 증명이라 캐시할 수 있다 — `timeout`만 캐시 금지다 |
| **詰みあり 10/162**         | 실제 8급 대국에서 詰み이 사정권에 드는 국면이 약 6%                                                      |

> **결과는 결정적이고 시간은 아니다.** 두 번 돌렸을 때 詰み 개수는 한계별로 정확히 같았지만 최장 시간은 흔들렸다(限界 9에서 216ms → 123ms). 그래서 캐시 키에는 결과만 쓰고, 위 시간은 대략의 크기로만 읽는다.

### 찾는 깊이와 판정하는 깊이는 다르다

11까지 **찾는** 것은 공짜다. 그러나 8급에게 「11手詰을 놓쳤다」고 개입하는 것은 다른 문제다 — 애초에 찾을 수 없는 수순이라 배울 것이 없고, [§1](01-core.md)이 말하는 개입이 아니다.

그래서 **탐색은 11까지 하고, 판정에 쓸 手数는 레벨별로 따로 정한다.** §2의 레벨별 임계치와 같은 자리다. 엔진은 정직하게 최대한 알아내고 제품 판단은 우리 코드가 한다는, `Skill Level`을 안 쓰는 것과 같은 원칙이다.

**[미확정]** 레벨별 판정 手数. §7의 詰み 게이지가 7→5→3→1을 그린다는 것은 **표시**의 상한이 7이라는 뜻이므로 거기서 시작해 볼 만하다.

**시간이 아니라 `DepthLimit`(詰み手数)으로 자른다.** `go mate`가 원래 ms를 받지만, 그러면 같은 국면이 같은 답을 주지 않아 캐시가 성립하지 않는다 — 다른 탐색과 같은 이유다.

## 12. DB 접근 계층 — sqlc + 국면 캐시

§8의 열린 결정을 닫았다. **`DATABASE_URL`을 읽고 실제로 읽고 쓰는 경로가 처음 돌았다.**

```
internal/store/migrations/*.sql   정본
internal/store/query/*.sql        질의
internal/store/db/                생성물 (go tool sqlc generate)
internal/store/store.go           얇은 감싸개 — JSON 인코딩과 에러 변환만
```

sqlc 자체를 `go.mod`의 `tool`로 고정했으므로 **따로 설치할 것이 없다.**

### 규칙을 SQL에 두고 Go로 옮겨 적지 않았다

```sql
ON CONFLICT (sfen_key) DO UPDATE SET ...
WHERE positions.computed_depth < EXCLUDED.computed_depth
```

이 한 줄이 **「더 얕게 계산한 결과가 깊은 결과를 덮지 않는다」** 전부다. Go에서 읽고-비교하고-쓰면 경합이 생기고, 규칙이 두 벌이 된다.

덮지 않았을 때는 `stored=false`로 알려준다 — 호출 측이 "내 결과가 더 얕았다"를 알아야 조용히 버려지지 않는다.

### CI에 postgres를 띄웠다

규칙이 SQL에만 있으므로 **가짜로는 검증할 수 없다.** `server` 잡에 `pgvector/pgvector:pg17` 서비스를 붙이고 스키마를 적용한 뒤 테스트를 돌린다. 로컬은 `docker compose up -d db` 후 같은 환경변수를 준다.

### `/healthz` 에 `db` 가 붙었다

```json
{ "ok": true, "engine": true, "db": true }
```

**DB가 없어도 프로세스를 안 죽인다** — 엔진과 같은 판단이다. 캐시가 없으면 매번 계산할 뿐 대국은 된다. 엔진과 달리 매 요청 `Ping` 하는 이유는, DB는 기동 때 붙었어도 나중에 끊기기 때문이다.

**[미확정]** 아직 캐시를 **쓰는 곳이 없다.** 국면 캐시를 대국 루프에 물리는 것은 D3에서 선행 계산과 같이 붙인다 — 지금 붙이면 `candidates` 를 채울 MultiPV 탐색이 아직 대국 루프에 없어서 반쪽이 된다.

## 13. D3 ① — 개입 판정과 롤백 (서버)

**「블런더를 두면 물러지고 이유가 뜬다」의 서버 쪽이 끝났다.** 로드맵의 D3 완료 기준이자 MVP 사수선이다.

```
시작 국면   B-30手 (실제 8급 대국, 형세 팽팽)
둔 수       ▲1七香   ← 엔진이 제일 싫어하는 수를 일부러
판정        Δ승률 = 0.158  >  중급 임계치 0.12
결과        물러짐. ply 0으로 복귀, 다시 사람 차례
문구        その手は形勢を大きく損ねます。
```

### 첫 시도가 실패하면서 나온 것 — 지고 있을 때도 승률은 포화한다

처음엔 초기 국면부터 아무 수나 두게 했더니 **20수 만에 절망적인 형세가 되어 한 번도 개입하지 않았다.**

`-3000cp`에서 더 나쁜 수를 둬도 승률은 1% → 0%라 낙폭이 안 나온다. **[§2](01-core.md)가 말한 포화의 거울상**이고, 고칠 버그가 아니라 **판정이 의미를 갖는 구간이 형세가 팽팽할 때**라는 사실이다. 실제 사용자가 있는 곳도 거기다.

그래서 실엔진 테스트를 **실제 대국의 중반 국면에서 시작**하게 했다.

### 구조

|                                     |                                                                                     |
| ----------------------------------- | ----------------------------------------------------------------------------------- |
| **판정은 세션 goroutine 밖**        | 탐색과 같은 이유다. 안에서 기다리면 판정하는 동안 투료도 스냅샷도 못 받는다         |
| **판정 끝나기 전에 엔진이 안 둔다** | 물러질 수가 있는데 상대가 먼저 두면 **되돌릴 것이 둘**이 된다                       |
| **롤백은 전부 되돌린다**            | 국면·기보·표기·千日手 계수까지. 하나라도 남으면 다음 판정이 오염된 상태 위에서 돈다 |
| **판정이 고장 나도 대국은 계속**    | 개입은 부가 기능이고 대국이 본체다. 실패는 로그로만 남긴다                          |
| **판정 중에는 착수 금지**           | 두면 물러질 수가 둘이 된다. 스냅샷의 `judging` 으로 화면이 잠근다                   |

### `intervene` 패키지는 엔진을 모른다

입력이 이미 구해진 평가치와 詰み 거리뿐이라, **상수(K·임계치)를 흔들어 보는 데 엔진이 필요 없다.** D3에서 그 상수들을 실측으로 잡아야 하므로 그 분리가 값을 한다.

테스트가 **전제 자체를 지킨다** — 「詰み과 +2000cp의 승률 차이가 어느 임계치에도 못 미친다」를 검사하므로, K를 바꿔 그 전제가 깨지면 즉시 드러난다.

### 관측 구간을 없앴다 — 의도를 잘못 옮긴 규칙이었다

`§2`에 「초반 20수는 개입 안 함」이라고 적혀 있었는데, 지키려던 것은 **오프닝 전법 선택의 폭**이었다. 그건 *무엇을 뒀는가*의 문제라 수 번호로 자르면 **5수째의 飛 헌납을 놓치면서 25수째의 정당한 선택은 못 봐준다.**

그리고 자를 필요가 없었다. **임계치가 이미 그 일을 한다** — 전법 선택은 50-200cp(Δ 2-8%p)라 어느 레벨도 안 걸리고, 銀 이상을 공짜로 주면 입문(25%p)에서도 걸린다. 원래 예외로 적어둔 「飛/角 공짜 헌납」이 그냥 나온다.

**기본값을 0으로 바꿨다. 첫 수부터 판정한다.** 그러면 앞서 발견한 구멍(관측 구간에서 −3000까지 가버리면 그 뒤로 판정이 눈이 먼다)도 같이 사라진다.

`intervene` 에서는 수 번호를 아예 뺐다 — **"언제 두었나"는 판정의 입력이 아니다.** 언제 물을지는 세션의 정책이고, `Config.ObservePlies` 로 남아 있지만 쓰는 곳이 없다.

> **sqlc를 들이면서 취약점 경고 3건이 떴다**(grpc 1건 high, x/net·cel-go 각 1건). 셋 다 **sqlc를 통해서만 들어오는 코드 생성 도구의 전이 의존성**이라 API 바이너리에는 안 들어간다(`go mod why` 로 확인). 그래도 올렸다 — 도구 의존성이라고 방치하면 다음에 오는 진짜 경고가 묻힌다.

### 프로덕션에서도 걸린다

```
둔 수    ▲3三角成 (8h3c+)   ← 角을 공짜로 주는 수
Δ승률    0.507
결과     물러짐. 기보는 ▲7六歩 △3四歩 까지만 남고 다시 내 차례
```

**2수째에 걸렸다** — 관측 구간을 없앤 것이 바로 값을 했다. 예전 설계였다면 20수 안이라 그냥 넘어갔을 자리다.

남은 일은 §5에 모아뒀다.

## 14. D3 ② — 개입 연출 (프론트)

**되물러진 수가 판 위에서 다시 재생되고 이유가 뜬다.** 서버가 §13에서 싣기 시작한 `intervention` 을 화면이 처음으로 그린다.

```
둔 수      ▲3三角成 (8h3c+)
연출       판이 살짝 기울고 나머지가 어두워진다 → 8八의 角이 빛에 감싸이고
           유령 角이 3三까지 느리게 갔다가 되돌아온다 → 문구가 뜬다
문구       待った / ▲3三角成 を戻しました / その手は形勢を大きく損ねます。/ 勝率 −50%
입력       「わかった」를 누를 때까지 잠긴다
```

브라우저에서 실제로 확인했다 — 데스크톱(1280)과 390px 둘 다, 반상 이동(`8h3c+`)과 打(`B*5b`) 둘 다. 좁은 화면 가로 넘침 0.

### 정한 것

개입 연출은 D2의 `--light` 를 **세게 쓰는 것**이지 새 색을 꺼내는 것이 아니다. 판정 결과를 빨강으로 칠하는 순간 「경고창」이 되고, [§2](03-frontend.md)가 말하는 「슬로모션 리플레이」와 정반대가 된다.

| 무엇                       | 정한 것                                                                                                                                          |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| **시간이 멈춘다**          | 닫을 때까지 착수 금지. 판정 중(`judging`)에는 서버가 이미 `yourTurn` 을 내려두므로 화면이 더 할 일이 없다                                        |
| **카메라가 살짝 기운다**   | `rotateX(7deg)`. 더 주면 뒷줄 한자가 뭉개진다 — 원근 판을 함정이라고 적어둔([§1](03-frontend.md)) 그 이유가 여기서도 그대로 걸린다               |
| **재생은 한 번**           | 두 번 돌리면 재생이 아니라 잔소리가 된다. 대신 두 칸의 빛은 닫을 때까지 남아 숨쉰다                                                              |
| **문구는 판을 안 가린다**  | 넓은 화면에서는 옆 패널 맨 위. **판이 화면보다 길어서 화면 아래에 붙이면 반드시 겹친다.** 좁은 화면에서만 아래에 띄운다(옆 패널이 화면 밖이라서) |
| **최선수를 말하지 않는다** | 화면에 나가는 것은 물러진 수·이유·낙폭까지다. 어느 수를 뒀어야 했는지는 어디에도 없다                                                            |
| **문장을 짓지 않는다**     | `retractedJa` 도 `message` 도 서버가 준 것을 그대로 그린다. 화면이 표기를 다시 만들면 두 벌이 되고 어긋났을 때 어느 쪽이 맞는지 알 수 없다       |

### 판이 말하는 방식이 여기서 정리됐다

연출을 붙이니 평시 화면의 문제가 같이 드러났다 — **무엇이 움직였는지가 안 보이고**, 착수 후보의 흰 원은 판 위에 뜬 별개의 물건처럼 보였다. 신호를 세 채널로 갈랐다.

|               | 뜻                                  | 어떻게                                                                                                                                                                                                        |
| ------------- | ----------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **빛**        | 지금 할 수 있는 것·지금 벌어지는 것 | 착수 후보는 **칸 전체가 밝아진다.** 원으로 두면 여러 칸이 켜졌을 때 물방울로 읽힌다. 잡는 수는 駒가 칸을 덮으므로 더 세게. 王手·개입도 같은 빛을 세기만 달리해 쓴다                                           |
| **색**        | **방금** 벌어진 것                  | 직전 수의 **출발 칸과 도착 칸**을 나무색으로 덮는다. 도착만 짚으면 「저기 뭔가 있다」까지다                                                                                                                   |
| **駒의 인쇄** | 그 駒가 무엇이고 어떻게 가는가      | 한 칸은 점, 쭉 가는 곳은 화살표, **뛰는 곳은 점과 거기까지의 잔 점선**(§22), 성한 駒는 붉은 글자. 점은 **정사각 3×3 격자** — 둥글게 두면 玉처럼 여덟 방향이 다 있는 駒에서 원으로 보여 어느 칸인지가 흐려진다 |

**셋을 안 가르면 서로를 지운다.** 직전 수까지 빛이면 駒를 집어 든 순간 착수 후보와 같은 신호가 되고, 직전 수 표식을 붉은 점으로 두면 움직임 표식 사이에서 안 읽힌다(그래서 뺐다).

세 번째가 앞의 둘을 밀어냈고, 두 가지가 따라 움직였다.

- **글자가 표식에 자리를 맞춘다.** 20px·0.52 → **13px·0.40**. 「한자 크기를 먼저 정하고 칸을 역산한다」(§6 ④)가 여기서 뒤집혔다 — 초심자가 얻어야 하는 것은 「이 글자가 무엇인가」보다 「이 駒가 어떻게 가는가」이고, 후자는 글자를 못 읽어도 통한다
- **성한 銀·桂·香는 한 글자**(全·圭·杏). 두 글자를 세로로 쌓으면 32px 칸에서 한 글자가 **10.8px**까지 내려간다. 전부 「金」으로 쓰는 방식도 있지만 그러면 **잡았을 때 뭐가 손에 오는지를 판에서 못 읽는다**

### 「있다」가 아니라 「회차」로 센다

서버는 개입을 **다음 착수까지** 들고 있다. 그래서 `snapshot.intervention` 이 있는지만 보면 닫아도 다시 뜨고, 같은 수로 또 걸린 것을 「아까 그거」로 착각한다. `useGame` 이 없다가 생긴 순간마다 회차를 올리고, 화면은 **본 회차와 비교**한다.

### 물린 것 — 전부 화면을 띄워야만 보이는 것들

| 증상                           | 원인                                                                                                                                                                                                                                                          |
| ------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **판이 한 칸씩 밀렸다**        | 유령 駒에 `grid-column` 으로 자리를 줬더니 81칸이 그것을 피해 밀렸다. **명시 배치는 DOM 순서보다 먼저 처리된다.** 격자에 얹지 않고 띄우는 것으로 고쳤다                                                                                                       |
| **장막이 판까지 덮었다**       | `z-index` 를 1·2로 붙여 썼는데, 판이 3D 변형으로 합성 레이어가 되는 순간 `position: fixed` 인 장막과 순서가 뒤집혔다. 40·50·60으로 벌려 놓았다                                                                                                                |
| **駒에 두른 테가 안 그려졌다** | `clip-path` 오각형은 **`filter`·`box-shadow` 를 먼저 그리고 그 다음에 자른다.** 오각형이 사각형에 닿는 곳은 아랫변뿐이라 밑줄 하나만 남는다. **세 번 물렸다**(직전 수 테 · 그 대안 `drop-shadow` · 駒의 `border-top`) — 윤곽선은 잘리지 않는 바깥 요소에 건다 |

전부 타입도 테스트도 통과한 상태에서 판이 통째로 어긋나 있었다.

### 그때 못 한 것 — 상대 공격선

[§2](03-frontend.md)는 「위험 기물과 **상대 공격선**을 광선으로」라고 적어뒀는데, 이 시점에는 위험 기물까지만 했다.

**어느 적 기물이 그 수를 벌하는지가 페이로드에 없었다.** 클라이언트가 계산하려면 규칙 엔진을 한 벌 더 갖는 것이고, 그건 D2에서 「클라이언트는 규칙을 모른다」로 정해둔 것과 정면으로 어긋난다(§6 ④). 판정할 때 서버는 이미 반박 수순을 알고 있으므로 **그 한 수를 실어 보내면 화면이 그린다.**

**§20에서 그렇게 했다.**

## 15. D3 ③ — 블런더 카테고리

**문구가 「その手は形勢を大きく損ねます。」 하나뿐이던 자리에 이유가 붙었다.** [§3](01-core.md)의 온톨로지가 코드로 내려온 것이고, ⑤ 약점 프로파일이 이 값 위에 쌓인다.

```
둔 수        ▲3三角成 (8h3c+)
카테고리     hangs_piece
문구         その駒は取り返せない場所に置かれています。相手の利きを確かめてみてください。
```

### 세 층으로 갈랐다 — `intervene` 은 판도 엔진도 안 받는다

|                    |                                                                             |
| ------------------ | --------------------------------------------------------------------------- |
| `shogi`            | 利き을 **센다**(`AttackCount`·`Neighbors8`). 룰만 안다                      |
| `game/features.go` | 판과 엔진 결과에서 **스칼라 사실**을 뽑는다. 여기가 판을 읽는 유일한 자리다 |
| `intervene`        | 그 스칼라로 카테고리를 정한다. **`shogi` 를 import 하지 않는다**            |

`intervene` 이 엔진을 모른다는 성질을 카테고리도 지켜야 했다(CLAUDE.md). 그래서 `Input.Features` 가 숫자와 참거짓뿐이고, **임계치를 흔들어 보는 데 국면을 만들 필요가 없다.** 판을 넘겼으면 그 성질이 조용히 사라졌을 자리다.

**그 결정이 CI 커버리지로 돌아왔다.** 분류 규칙 테스트 14개(`category_test.go` 6 + `features_test.go` 8)에 `t.Skip` 이 하나도 없다 — 환경변수를 전부 지우고 돌려도 skip이 0이다. 이 레포에서 제일 흔한 함정이 「환경변수가 없으면 조용히 skip 되고 초록으로 보인다」인데, **분류 로직은 거기 안 걸린다.** 실엔진 테스트는 진짜 국면에서 한 번 더 확인하는 것이고, 규칙 자체는 CI가 매번 지킨다.

### 순서가 규칙의 일부다

한 수가 여러 조건에 걸리는 것은 예외가 아니라 보통이다. **프로덕션 재현 수 `▲3三角成`이 王手이면서 タダ捨て다** — 馬가 3三에서 4二를 지나 5一玉에 닿는다. 그때 무엇을 말해줄지가 곧 제품의 판단이라, 위에서부터 **눈으로 확인할 수 있는 것**을 앞에 둔다.

| 순  | 카테고리         | 룰                                                     |
| --- | ---------------- | ------------------------------------------------------ |
| 0   | `missed_mate`    | 종반 판정으로 걸렸다 — 다른 축이라 맨 앞               |
| 1   | `unpromoted`     | 최선수와 같은 이동인데 成 여부만 다르다 (§24)          |
| 2   | `hangs_piece`    | 놓인 칸에 상대 利き 有 · 내 利き 無 · 딴 것보다 비싸다 |
| 3   | `shallow_trap`   | 얕게(depth 2) 이득 · 깊게 손해 · 반전 폭 ≥ 300cp       |
| 4   | `greedy_capture` | 駒는 땄는데 형세가 나빠졌다                            |
| 5   | `idle_check`     | 이득 없는 王手                                         |
| 6   | `king_exposed`   | 玉 주변 방어 利き 감소 **그리고** 상대 利き 증가       |
| —   | `other`          | 미분류                                                 |

`king_exposed` 가 **양쪽을 같이** 요구하는 이유는 한쪽만 보면 玉을 자기 진영으로 옮기는 정상적인 수까지 걸리기 때문이다. 실측으로 `▲5八玉`이 `ShieldLoss = -1`(방어가 오히려 늘었다)로 나온다.

### 利き으로 세는 곳과 합법수로 묻는 곳이 갈린다

같은 「노린다」가 자리마다 다른 뜻이어야 했다. **셀프리뷰가 잡았다.**

| 무엇                         | 어떻게              | 왜                                                                      |
| ---------------------------- | ------------------- | ----------------------------------------------------------------------- |
| 玉 주변 압력 (`AttackCount`) | 利き — 핀을 안 본다 | 압력의 크기를 재는 것이라 묶인 駒도 압력이다                            |
| 착수 칸 (`LandsAttacked`)    | **합법수**          | 「その駒は取り返せない場所に置かれています」라는 **화면의 단언**이 된다 |

`IsAttacked` 로 착수 칸을 물으면 **핀에 묶여 못 움직이는 駒도 「노린다」로 센다.** 실제로 재현된다 — `4k4/9/4r4/9/9/9/9/9/4R3K b G 1` 에서 `G*4c` 는 5三飛가 노리지만 그 飛는 5一玉과 5九飛 사이에 묶여 있어 **4三을 딸 수 있는 합법수가 0개**다. 그런데 화면은 「그 駒는 그냥 잡힙니다」라고 말한다.

**틀린 설명이 나가는 것이 이 제품에서 가장 큰 실패다**(01-core.md §3). 초심자에게는 검증할 수단이 없다. 그래서 착수 칸은 `LegalMoves()` 로 묻는다.

`LandsDefended` 도 뜻이 같이 바뀌었다 — 「내 利き이 있는가」가 아니라 **「따인 뒤에 되딸 수 있는가」**다. 상대는 되따이지 않는 쪽으로 딸 것이므로, 되딸 수 없는 따는 수가 하나라도 있으면 그 駒는 그냥 잡히는 것이다. 문구가 「取り返せない」라고 말하는 것과 계산이 같아졌다.

> 비용은 매 수 `LegalMoves()` 몇 번이다. 그 옆에서 엔진 탐색이 수백 ms를 쓰므로 정확도를 살 값으로 싸다.

### 「딴 것」만으로는 이유가 안 된다

`greedy_capture` 가 처음엔 「딴 駒가 있다」만 보고 걸렸는데, **반대쪽에서 벌어진 일 때문에 나쁜 수인데 마침 歩를 하나 공짜로 딴 경우**에 「駒는 취했지만 대가가 큽니다」라고 말하게 된다. 딴 것은 이유가 아니었다.

그래서 대가가 실제로 보이는 두 경우로 좁혔다 — **되따일 수 있거나**(그 위에서 `hangs_piece` 가 안 걸렸으니 교환 자체는 유리해 보이는 쪽이다) **玉이 더 밀리거나**. 카테고리 이름의 「옥 안전 무시」가 뒤쪽이다. 둘 다 아니면 `other` 로 떨어진다.

### `shallow_trap` 은 추가 탐색이 0이다

`PvInterval=0` 덕에 판정용 `depth 12 × k=1` 한 번이 depth 1~12를 전부 돌려준다. 「얕게 보면 이득」의 판정이 **이미 받아 둔 info 라인**에서 나온다 — [§4](01-core.md)가 적어둔 그대로다. `SearchResult.ScoreAtDepth` 가 그 자리다.

`EvalByDepth` 와 묻는 것이 다르다. 저쪽은 「이 수가 깊이별로 어떻게 평가됐나」이고 이쪽은 「이 국면을 여기까지만 읽으면 얼마로 보이나」다. **후자가 초보자의 시야다** — 얕은 깊이에서 순위 밖으로 밀린 수를 따라가면 값이 아예 없다.

### 실측 — 최악수가 늘 짚을 만한 수는 아니다

`TestRealEngineIntervention`(B-30手)에서 엔진이 제일 싫어하는 수는 **`▲1七香`** 이었다. 駒를 던지지도, 王手를 걸지도, 玉을 열지도 않고 그냥 손해인 수다.

```
카테고리   other
문구       その手は形勢を大きく損ねます。もう一度考えてみてください。
```

**이게 맞는 동작이다.** 처음엔 「최악수인데 이유를 못 짚었다」를 실패로 잡는 단언을 넣었는데, 그것이 바로 [§3](01-core.md)이 금지한 「억지로 끼워 맞추기」였다. 짚을 것이 없으면 짚지 않는다 — 초심자는 설명이 틀려도 검증할 능력이 없다.

그래서 테스트를 갈랐다. **결과가 정해진 수로 물어야 카테고리가 검증된다.**

| 테스트                       | 묻는 것                                       |
| ---------------------------- | --------------------------------------------- |
| `TestRealEngineIntervention` | 개입이 걸리는가 (카테고리는 값을 안 박는다)   |
| `TestRealEngineHangingPiece` | `▲3三角成` → `hangs_piece` + 利き을 짚는 문구 |

### 안 넣은 둘

|                   |                                                                                                             |
| ----------------- | ----------------------------------------------------------------------------------------------------------- |
| **二枚換え 손해** | 한 수가 아니라 **여러 수에 걸친 교환**을 봐야 한다. 지금 뽑는 사실은 착수 한 수의 전후뿐이다                |
| **정석 이탈**     | `edges.tags` 의 전법 태그가 있어야 하고 **정석 북이 아직 없다**([§6](01-core.md)의 오프닝 랜덤과 같은 자리) |

`idle_check` 도 원안과 다르다. 「후속 詰めろ가 없을 것」을 조건에 뒀는데 詰めろ 판정이 없어서, **이득 없는 王手**로 좁혔다. 개입이 걸릴 만큼 형세를 해친 王手는 이어지지 않았다는 뜻이라 억지는 아니지만, 詰めろ 판정이 붙으면 좁힌다. **[미확정]**

### 駒의 값은 평가치가 아니다

`game/features.go` 의 `pieceValue` 는 歩를 1로 잡은 눈금이고 **교환의 손익을 견주는 데만 쓴다.** cp로 바꾸려 들면 엔진의 평가와 두 벌이 되고, 어긋났을 때 어느 쪽이 맞는지 알 수 없다. 형세를 재는 것은 언제나 엔진이다.

## 16. D4 ① — 적응형 상대

**「지지만 던지지 않는」 상대가 들어갔다.** 바뀐 것은 `Opponent` 구현 하나이고 세션 상태머신은 안 건드렸다 — [§6](#6-d2--대국-루프-완료)에 그렇게 될 것이라고 적어둔 자리다.

### 이건 편의 기능이 아니라 개입의 전제였다

D3에서 초기 국면부터 아무 수나 두게 했더니 **20수 만에 절망적인 형세가 되어 개입이 한 번도 안 걸렸다**(§13). 승률이 포화하기 때문이고, 고칠 버그가 아니라 판정이 의미를 갖는 구간이 형세가 팽팽할 때라는 사실이다.

같은 약한 기보(늘 합법수 목록의 첫 수)를 두 상대에게 20수 두게 하고 형세를 쟀다.

```
적응형 상대   플레이어 관점  +293cp   ← 밴드([+100,+300]) 안
최선수 상대   플레이어 관점  −4782cp  ← 개입이 눈이 먼 구간
```

**초심자보다도 못 두는 쪽**을 잡아 하한을 본 것이라, 실제 플레이어에게는 더 유지된다. `TestRealEngineAdaptiveKeepsTheGamePlayable` 이 매번 이 값을 다시 잰다.

### 설계 문서와 한 곳에서 갈렸다 — 밴드 밖일 때

「밴드에 드는 후보가 없으면 그냥 최선수를 둔다」고 적혀 있었는데, **그 규칙은 필요 없을 뿐 아니라 한쪽에서 해롭다.** 거리를 최소화하면 두 경우가 저절로 갈린다.

| 상황                    | 후보 위치      | 거리 최소화가 고르는 것          |
| ----------------------- | -------------- | -------------------------------- |
| 상대가 크게 지고 있다   | 전부 밴드 위   | 제일 작은 것 = **엔진의 최선수** |
| 상대가 크게 이기고 있다 | 전부 밴드 아래 | 제일 큰 것 = 가장 너그러운 수    |

즉 **불리할 때는 저절로 최선을 다하고**(「던지지 않는다」) 유리할 때만 양보한다. 여기서 최선수로 물러서면 **이기고 있을 때 조절을 포기하는 것**이 되어, 조절이 가장 필요한 자리에서 초심자를 그대로 뭉갠다.

원문이 걱정한 「승부가 갈린 종반」은 후보들이 20~40cp에 몰려 어느 수를 골라도 같은 국면이라, 가장 가까운 것을 골라도 최선수와 사실상 같다. **근거는 맞았고 결론이 넓었다.**

### 「던진다」의 정의를 개입과 공유한다

자살수 필터는 `intervene.Features.HangsPiece()` 다 — **블런더의 タダ捨て 판정과 같은 함수**다.

정의가 두 벌이면 화면이 「その駒は取り返せない場所に置かれています」라고 가르쳐놓고 **컴퓨터가 바로 그 수를 두는** 일이 생긴다. 그 순간 방금 배운 것이 무너진다.

그리고 이 필터는 **엔진이 필요 없다.** 룰 엔진만으로 되므로 엔진에 넣기 전에 쳐내고, 그만큼 필요한 k도 줄어든다.

### MultiPV는 탐색 직전에 매번 건다

옵션은 `Engine` 에 남는다. 한 번 k=10으로 걸어두면 **그 엔진을 다음에 빌리는 쪽까지 k=10으로 돈다** — 개입 판정이 후보 1개면 될 자리에서 10개를 받아 400ms가 2초가 된다. 대국 A의 설정이 대국 B로 새는 것과 같은 문제다(§6 ②).

그래서 `Pool.SearchDepth` 도 `SearchMultiPV` 를 지나며 **1을 명시한다.** 「안 건드리면 그대로」에 기대지 않는다.

### 비용

상대 수가 `depth 12 × k=1`(400ms)에서 `depth 12 × k=10`(2.0s)이 됐다. [§4](01-core.md)의 표에 원래 그렇게 적혀 있던 값이고, **강함을 탐색이 아니라 선택에서 얻겠다는 설계가 곧 MultiPV를 요구한다.** 지연은 선행 계산으로 잡는 자리이지 k를 줄일 자리가 아니다 — k=1은 밴드 적중 0/6이다(§10).

### 남은 손잡이

`OPPONENT_BAND_LO` · `OPPONENT_BAND_HI` 로 밴드를 흔들 수 있다. **[미확정]** 값은 실측으로 잡는다. 레이팅이 붙으면 플레이어마다 달라질 자리다.

## 17. 실측 — 자연스러운 수가 거의 다 물러지는 국면

플레이 테스트에서 **「생각한 수가 전부 물러졌다」**는 보고가 나왔다.

**보고와 아래 숫자는 다른 주장이다.** 보고는 *직접 둬본 몇 수*가 전부 걸렸다는 것이고, 전수 조사가 아니다. 아래는 우리가 따로 **합법수 전부**를 판정에 돌린 결과이고, 그것이 보고를 설명한다 — 80~89%가 걸리는 국면에서는 **전부 둬보지 않아도** 자연스럽게 고른 몇 수가 전부 걸리는 것이 당연하다. 우연이 아니라 구조다.

기보는 실제로 둔 84수짜리 한 판이고, 헤맸다고 지목된 두 자리를 쟀다. `internal/game/stuck_test.go` — **기보 문자열만 갈아끼우면 어느 국면이든 같은 표가 나온다.**

|                         | 77수째        | 81수째        |
| ----------------------- | ------------- | ------------- |
| 합법수                  | 76            | 111           |
| 최선수                  | `5d5f` +537cp | `B*4a` +433cp |
| 블런더 (입문 0.25)      | **68 (89%)**  | **89 (80%)**  |
| 블런더 (초급 0.18)      | 73 (96%)      | 105 (95%)     |
| 블런더 (중급 0.12)      | 75 (99%)      | 107 (96%)     |
| 그중 `other`(이유 없음) | 44 (**65%**)  | 62 (**70%**)  |

**둘 다 이기고 있는 국면이다**(+537 / +433). 초심자가 통과하는 수를 못 찾으면 89번 튕긴다. [§2](01-core.md)에 구멍으로 기록했다.

> ~~그 우세를 지키는 수가 하나뿐이라~~ — **이 읽기는 §23에서 틀린 것으로 드러났다.** 89%만 보고 「바늘 국면」이라고 읽었는데, 후보 사다리를 찍어 보니 **상위 9수가 전부 통과선 위**였다. 괜찮은 수는 여덟 개 있고 초심자가 그걸 못 찾는 것이다 — 그 차이가 고치는 방향을 통째로 바꾼다.

### 이유를 못 대는 것이 3분의 2다

카테고리는 **착수 한 수의 전후만** 본다. 이 국면들에서 수가 나빠지는 이유는 몇 수 앞의 수순이라 하나도 안 잡힌다. 그래서 화면에는 「その手は形勢を大きく損ねます」만 나가고, **플레이어는 왜인지 모른 채 같은 실수를 반복한다.**

그걸 그대로 메우는 것이 **상대 공격선(반박 수순)**이고, **§20에서 붙었다.** 착수 후 탐색의 PV가 곧 「상대는 이렇게 벌한다」이고 **분류가 필요 없다.** §5에서 맨 위로 올렸던 이유다.

> 반박 수순을 보여주는 것은 「최선수를 짚지 않는다」에 어긋나지 않는다. 금지된 것은 **플레이어가 뒀어야 할 수**이고, 반박 수순은 **왜 나쁜가**에 속한다([§1](01-core.md)).

### `shallow_trap` 의 전제가 틀렸다

깊이 반전이 **187개 중 0건**이었다. 데이터가 없어서가 아니다 — 얕은 평가는 187/187 전부 잡혔다.

```
5b5a  shallow=-886   deep=-1143
5b6a  shallow=-1420  deep=-1915
5b4b  shallow=-555   deep=-300
```

**얕게 봐도 이미 나쁘다.** `depth 2`가 초보자의 시야를 모사한다는 전제가 틀렸고, NNUE는 2수만 읽어도 초심자보다 훨씬 잘 본다. [§7.1](01-core.md)에 적었다.

### 기보 → USI 역매칭은 손으로 하지 않는다

`kifuToUSI` 는 **합법수마다 우리 `MoveJa` 를 돌려 표기가 일치하는 것을 찾는다.** 손으로 옮기면 표기가 두 벌이 되고 어긋났을 때 어느 쪽이 맞는지 알 수 없다(§6 ④와 같은 이유).

84수 전부가 **유일하게** 일치했다 — 棋譜 표기 코드의 왕복 검증이 덤으로 따라온 셈이고, `TestKifuRoundTrips` 는 엔진 없이 CI에서 돈다.

## 18. D3 ④ — 대국 기록

**둔 판이 남기 시작했다.** 그전까지는 개입이 화면에 떴다가 다음 착수에서 지워지고 끝이었다 — 새로고침하면 사라지고, 지나간 대국은 복원할 방법이 없었다.

```
games          로그인 전에도 남는다. 시작 국면과 결과
game_moves     기보 — **확정된 수만**
interventions  물러진 수 · 카테고리 · Δ승률 · 레벨
```

### 물러진 수와 기보를 갈라 둔다

같은 ply가 두 표에 다른 값으로 들어간다. 실측으로 확인했다.

```
game_moves    ply 3 = 2g2f    ← 다시 둔 수
interventions ply 3 = 8h3c+   ← 원래 두려던 수 (hangs_piece, Δ0.494)
```

기보는 **지금 판에 남아 있는 수순**이라 물러진 수가 들어가면 롤백이 롤백이 아니게 된다. 반대로 물러진 수는 여기서만 남는다 — **개입에 오염되지 않은 유일한 실력 신호**라([§5](01-core.md)) 안 적으면 영영 사라진다.

`interventions` 의 `(game_id, ply)` 는 **유니크가 아니다.** 한 국면에서 몇 수를 시도하고 전부 물러지는 일이 실제로 있고(§17), 그 반복 자체가 「그 국면이 그 사람에게 얼마나 어려웠나」다.

### 세션 goroutine을 막지 않는다

`Recorder` 는 `Analyst`·`Opponent` 와 같은 방식으로 주입된다. `game` 은 DB를 모른다.

구현은 이벤트를 **버퍼 채널(256)에 던지고 자기 goroutine이 쓴다.** 상태를 goroutine 하나가 소유한다는 것이 이 프로젝트의 정합성이라, DB가 느리다고 그 줄을 세우지 않는다. 큐가 차면 **버리고 로그를 남긴다** — 기다리면 대국이 멈춘다.

**쓰기에는 세션 ctx 를 안 쓴다**(`context.WithoutCancel`). 연결이 끊기면 세션 ctx 가 먼저 취소되는데, 대국이 끝나는 순간이 곧 마지막 이벤트가 몰리는 순간이라 그때 전부 실패하면 제일 아깝다.

### 끝나지 않은 판은 `abandoned`

빈 `result` 로 두면 **「아직 두는 중인 판」과 구별이 안 된다.** 나중에 기록을 훑을 때 그 둘이 섞이면 어느 것이 실제 대국인지 셀 수 없다.

### 로그인 전에도 남긴다 — `002_anonymous_games.sql`

`games.user_id` 가 NOT NULL이라 **Google 로그인(D5)이 붙기 전에는 한 판도 못 남겼다.** 그동안 둔 판을 버리면 실력 추정의 원본이 통째로 사라지고, 되살릴 수 없다. nullable로 풀었다.

`start_sfen` 도 같이 넣었다. `root_key` 는 `positions` 참조라 캐시에 없는 국면은 못 적는데, 기보만으로는 어디서 시작했는지 알 수 없어 **기록이 그것만으로 완결되지 않는다.**

### 물린 것 — 「연결을 끊었는데 abandoned 가 안 찍힌다」

**버그가 아니었다.** 브라우저는 5173(Vite)에 붙고 **Vite가 8081로 프록시**하는데, 탭을 닫아도 Vite가 상류 소켓을 붙들고 있어서 서버에서는 대국이 계속 살아 있었다. Vite를 내리자 즉시 찍혔다.

로컬에서 세션 종료를 확인할 때는 **브라우저가 아니라 프록시를 봐야 한다.** 프로덕션은 Caddy가 그 자리라 같은 현상이 아니다.

> `pingInterval`(45초)이 죽은 상대를 알아채는 장치인데, 이 경우 Vite가 살아서 pong을 돌려주므로 걸리지 않는다.

### CI가 마이그레이션을 전부 적용한다

`server.yml` 이 `001_init.sql` 만 적용하고 있었다. 새 마이그레이션이 CI에서 안 돌면 **로컬은 통과하는데 CI만 깨진다.** `migrations/*.sql` 을 번호 순서대로 전부 돌리도록 고쳤다.

### 棋譜 복사

화면의 棋譜에 복사 버튼을 붙였다. **개발 도구다** — 이 문자열 하나로 국면이 완전히 복원되므로(§17), 「이 국면에서 헤맸다」는 보고를 그대로 조사에 넣을 수 있다. 실제로 84수를 손으로 옮겨야 했던 적이 있다.

## 19. 프로덕션 DB에 직접 붙는다

**일회용 ECS 태스크로 스키마를 넣던 방식을 걷어냈다.** 그 방식은 넣는 것은 되는데 **보는 것이 안 됐다** — 결과가 CloudWatch로만 나가고 운영자 정책에 로그 읽기 권한이 없다(§7). 기록을 붙여놓고 못 보면 반쪽이다.

```
publicly_accessible = true                 # 엔드포인트를 공개한다
aws_vpc_security_group_ingress_rule        # 누가 닿는지는 여기가 정한다
  cidr_ipv4 = var.admin_cidr → 5432
```

### NAT도 bastion도 필요 없었다

RDS가 **default VPC의 default 서브넷**에 있고, 그건 이미 IGW가 붙은 퍼블릭 서브넷이다(Fargate를 `assignPublicIp=ENABLED` 로 띄우는 것과 같은 이유). 막고 있던 것은 스위치 하나와 방화벽 규칙 하나뿐이었다.

**NAT는 방향이 반대다** — 프라이빗 서브넷의 **아웃바운드**용이라 인바운드 접근과 무관하다. 여기서 헷갈리면 안 만들어도 되는 것을 만들게 된다.

### 감수한 것과 그 근거

**실질 방어선은 보안그룹이다.** 등록된 주소 외에는 포트에 닿지도 못하고, 비밀번호는 그 다음 겹이다.

|           |                                               |
| --------- | --------------------------------------------- |
| 접근      | 단일 IP(`admin_cidr`) + 태스크 보안그룹       |
| 전송      | `rds.force_ssl` 로 TLS 강제 — 끄면 거부당한다 |
| 담기는 것 | 본인 대국 기록. 개인정보 없음                 |
| 기간      | 대회가 끝나면 `terraform destroy`             |

운영 서비스라면 반대로 둔다.

### IP는 레포에 안 들어간다

`admin_cidr` 은 기본값이 `null` 이고 값은 `infra/terraform.tfvars` 에 둔다. `.gitignore` 가 `*.tfvars` 를 막는다 — **퍼블릭 레포라 집 IP를 커밋하면 그대로 공개된다.**

비우면 규칙이 아예 안 생긴다. **값을 안 주고 apply 하면 있던 규칙이 지워진다** — 통로가 조용히 남아 있지 않게 하려는 것이다. 공인 IP가 바뀌면 tfvars를 고치고 apply 한다(수십 초).

### 비밀번호는 URL 인코딩되어 있다

`rds.tf` 가 접속 문자열을 만들 때 `urlencode()` 를 건다. `&`·`:` 같은 문자가 그대로 들어가면 파서가 필드를 끊기 때문이다.

**GUI 클라이언트에는 디코딩된 값을 넣어야 한다.** `psql` 은 접속 문자열을 그대로 받는다(libpq가 디코딩한다). 한 줄로 뽑는 명령은 [런북](../deploy/README.md)에 있다.

> `terraform output` 에 접속 문자열을 통째로 내보내지 않았다. 비밀번호가 들어가면 `output` 한 번이 터미널 기록과 스크롤백에 남는다. 대신 그때그때 SSM에서 꺼내는 명령만 값으로 둔다.

### 확인

DataGrip에서 PostgreSQL 17.10, Ping 12ms, SSL yes. `002_anonymous_games.sql` 을 그 자리에서 적용했다 — 컨테이너도 raw URL도 종료 코드 확인도 없다.

## 20. 반박 수순 — 「왜 블런더인지 모르겠다」의 답

**물러진 수를 그대로 뒀을 때 상대가 어떻게 벌하는지가 화면에 나온다.** §5의 맨 위였고, 플레이 테스트에서 나온 유일한 내용 있는 불만이었다.

```
둔 수      ▲3三角成 (8h3c+)
카테고리   hangs_piece
수순       △同角          ← 되따는 한 수로 이유가 끝난다
판 위      2二角 → 3三 으로 광선 하나
```

### 새 탐색이 없다

판정은 이미 착수 **후** 국면을 `depth 12 × k=1`로 읽고 있고, **그 탐색의 PV가 곧 반박 수순이다.** 비용이 0이고 분류도 필요 없다 — 카테고리가 이유를 못 대는 3분의 2(§17)가 통째로 설명을 갖는 것이 이 값이 싼 이유다.

### `Verdict` 에 싣지 않았다

§14에 한때 거기라고 적어뒀는데, 싣는 순간 `intervene` 이 착수 수(USI 문자열)를 받게 되어 **「입력은 이미 구해진 숫자뿐」이 깨진다** — 카테고리를 스칼라로 받게 만든 것과 같은 이유다(§15).

반박 수순은 판정의 입력도 출력도 아니고 **화면에 그릴 재료**다. 그래서 `analyst` 가 `Judgement{Verdict, Refutation}` 로 감싸 넘기고, `intervene` 은 이 기능이 있는지도 모른다.

### 최선수를 말하는 것이 아니다

금지된 것은 **플레이어가 뒀어야 할 수**이고 반박 수순은 **왜 나쁜가**에 속한다([§1](01-core.md)). 그리고 이 수순이 시작하는 국면은 되물러서 **이미 판에서 사라졌다** — 여기 있는 어느 수도 「지금 이렇게 두라」가 되지 않는다.

### 길이는 상수가 아니라 국면이 정한다

처음엔 4수로 박아뒀는데 **첫 플레이 테스트에서 바로 걸렸다.** 角을 던지면 되따는 한 수로 이유가 끝나는데, 거기에 세 수가 더 붙는다.

```
▲3三角成  →  △同角 ▲8八飛 △4五角 ▲5八玉
              └ 여기서 끝 ┘ └── 잡음 ──┘
```

반대로 §17처럼 몇 수 앞에서 벌어지는 국면에서는 같은 상수가 이유가 나오기 전에 끊는다. **한쪽에 맞추면 다른 쪽이 틀리는 것이라 상수로는 안 된다.**

**駒를 따거나 王手를 거는 첫 수에서 시작해, 같은 칸에서 주고받는 동안까지 보여준다.** 그 전까지는 판 위에서 아직 아무 일도 안 일어나서 준비 수순으로 필요하고, 교환이 닫힌 뒤는 이미 벌어진 손해 위에서 두는 이어지는 수다. 판단에 엔진이 필요 없다 — 룰 엔진으로 재생하면서 공짜로 알 수 있어서 **개입 판정에 비용이 안 붙는다.**

### 실측 — 자르는 규칙을 두 번 고쳐 잡았다 (2026-08-10)

§17의 두 국면에서 입문 임계치에 걸리는 수 **전부**의 수순 길이를 쟀다(`stuck_test.go`). 아래는 81수째 89개다.

| 어디서 자르나                | 1~2수  | 3~5수 | 6수 이상 |
| ---------------------------- | ------ | ----- | -------- |
| ① 마지막 따는 수까지         | 3      | 13    | **73**   |
| ② 처음 따는 수까지           | **65** | 23    | 1        |
| ③ 같은 칸 교환이 닫힐 때까지 | 47     | 35    | 7        |

**① 「마지막」은 그 앞을 전부 끌고 온다.** 조용한 수도 마지막 교환보다 앞에 있으면 딸려 오고, 날카로운 중반은 PV 끝 어딘가에서 반드시 따므로 사실상 **항상 상한까지** 간다.

**② 「처음」은 교환을 반쪽만 보여준다.** 길이는 좋아졌는데 `△7六飛成` 에서 끊으면 飛가 馬를 그냥 딴 것으로 읽힌다 — 실제로는 `▲同角` 으로 되딴다. **화면에 나가는 단언이라 반쪽이 틀린 것보다 한 수 긴 편이 낫다.**

**③ 「같은 칸」이 조건이다.** 그냥 「따는 수가 이어지는 동안」으로 두면 다른 자리의 별개 교환까지 붙어서 ①과 같아진다 — 실제로 두 규칙이 아래 8수짜리를 똑같이 냈다. 쇼기에서 교환은 **한 칸에서 주고받는 것**이다.

```
①  △5二香 ▲7六馬 △7八飛 ▲6七角 △7六飛成 ▲同角 △5八香成 ▲同角
②  △5二香 ▲7六馬 △7八飛 ▲6七角 △7六飛成
③  △5二香 ▲7六馬 △7八飛 ▲6七角 △7六飛成 ▲同角

②  △同銀            ← 상대가 그냥 딴 것으로 읽힌다
③  △同銀 ▲同馬      ← 되딸 수 있다는 것까지
```

77수째는 ③에서 **최장 4수**다(1수 26 · 2수 17 · 3수 3 · 4수 22). 81수째에만 6~7수가 7개 남는데, 준비 수순이 실제로 네 수 필요한 국면이다.

`RefutationPlies = 8` 은 길이가 아니라 **상한**이다. 그 안에 따는 수도 王手도 없으면 벌하는 첫 수만 남긴다 — 조용한 수를 늘어놓아 봐야 「왜 나쁜가」가 거기 없기는 마찬가지이고, **모르는 것을 길이로 메우지 않는다.**

> 상한을 더 좁히면 안 된다. 이 규칙에서 상한을 넘기는 것은 **긴 설명**이 아니라 **설명 없음**(1수)이 된다.

### 한 판에 겹쳐 긋지 않고 **한 수씩 넘겨 본다**

처음엔 수순의 상대 수를 **전부** 광선으로 되돌아온 판 위에 그렸는데, 브라우저에서 보고 뺐다.

```
수순(당시)  △同角 ▲9八飛 △4五角 ▲7八金
2번째       △4五角  ← 지금 상대의 持ち駒에 角이 없다
```

두 번째 상대 수부터는 **사이에 오지 않을 응수를 전제**한다. 그것을 지금 판 위에 그리면 연출이 아니라 국면에 대한 거짓말이고, 실제로 「아직 손에 없는 駒를 놓는 수」가 나왔다. 화면에서는 빈 칸에 뜬 얼룩으로 보인다.

**넘겨 보게 만들면 그 문제가 통째로 사라진다.** 판이 수순을 따라 실제로 진행하므로 어느 장면에서도 그 수는 그 판의 사실이다. 「거짓말이라 못 그린다」가 「한 번에 하나씩 그린다」로 바뀐 것이고, 사용자 요청에서 나왔다.

```
0장면   ▲3三角成 을 둔 직후      光線 8八 → 3三
1장면   △同角                    光線 2二 → 3三 · 相手の駒台에 角
…
버튼    前へ · 次へ · 指し直す
```

**넘기는 것은 선택이다.** 유령 駒가 한 번 나고 0장면에서 멈추므로, 그냥 두던 사람은 `指し直す` 한 번으로 끝나고 궁금한 사람만 넘긴다. 자동으로 넘어가면 초심자에게 통과 의례가 된다.

### 판을 넘기는 것은 서버다 — 화면은 수를 두지 않는다

각 수에 **그 수를 둔 뒤의 SFEN**을 같이 싣는다(`RefutationMove.sfen`, 그리고 0장면용 `retractedSfen`). 화면이 스스로 두게 하면 규칙 엔진을 한 벌 더 갖는 것이고, 그건 D2에서 「클라이언트는 규칙을 모른다」로 정해둔 자리다(§6 ④).

**持ち駒도 SFEN에 들어 있으므로 駒台까지 이 한 줄로 맞는다.** 위 1장면에서 相手의 駒台에 角이 들어오는 것을 따로 계산하지 않는다.

`refutationLine` 이 이미 룰 엔진으로 재생하고 있어서 **비용은 `pos.SFEN()` 몇 번**이다.

### 화살표는 「방금 둔 수」가 아니라 **「다음에 올 수」**다

처음엔 그 장면을 만든 수의 궤적을 그렸는데, 판이 이미 그 결과를 보여주고 있으니 **같은 말을 두 번 하는 것**이었다. 알고 싶은 것은 「그래서 상대가 어떻게 하는가」다.

그래서 채널이 하나 더 갈렸다(§14의 세 채널 위에).

|                 |                  |
| --------------- | ---------------- |
| **흰빛 두 칸**  | 방금 벌어진 것   |
| **초록 화살표** | 다음에 벌어질 것 |

`次へ` 를 누르면 화살표대로 벌어진다. 그래서 물러진 수의 궤적을 따로 그릴 필요가 없어졌다 — 0장면부터 바로 상대의 다음 수를 가리킨다.

**양쪽 화살표가 같다.** 한때 사람의 수를 옅게 뒀는데 그건 되돌아온 판 위에 그리던 때의 이유였고(내 駒에서 뻗는 선이 「이렇게 두라」로 읽힐까 봐), 넘겨 보는 지금은 어느 장면이든 일어나지 않을 가정 국면이라 그 위험이 없다. 밝기 차이는 뜻이 안 읽혀서 그냥 고장으로 보인다. 누구의 수인지는 옆 문구의 ▲△가 말한다.

### 王手는 붉은 화살표로, **거는 말을 전부** 짚는다

플레이 테스트에서 `▲1七銀`에 개입이 걸렸고, 수순이 `△2八金` 한 수만 나갔다. 「同銀으로 먹으면 되는 것 아닌가」가 나왔다. **먹을 수 없다.**

```
▲1七銀 뒤    사람 관점 −29970cp (詰み)
△2八金 뒤    합법수 ▲2六玉 · ▲3六玉 · ▲同玉  — 玉을 움직이는 수뿐
```

**両王手**다. 金이 3八에서 나가는 순간 **4九馬의 대각선(4九–3八–2七)이 열려서** 金과 馬가 동시에 王手를 건다. 両王手는 玉을 움직일 수밖에 없어서 `同銀`이 애초에 합법수가 아니다.

화면이 그걸 말하지 못한 것이 문제였다. 둘을 같이 고쳤다.

**① 王手를 거는 말을 붉은 화살표로 긋는다.** 초록 화살표와 **모양은 같고 색만 다르다** — 「다음에 올 수」와 「지금 玉을 잡으러 오는 것」은 다른 사실이라 한눈에 갈려야 한다. **두 줄이면 両王手**이고, 그 그림이 곧 「먹어서 못 푼다」의 답이다.

「王手다」까지는 국면만 봐도 알지만 **어느 말이 걸고 있는지는 규칙을 알아야 한다.** 그래서 서버가 `shogi.Attackers` 로 구해 보낸다 — 클라이언트가 계산하면 규칙 엔진을 한 벌 더 갖는 것이다(D2).

**② 王手도 혼자 서지 못한다.** 응수가 강제라, 답을 빼고 던져 놓으면 화면이 「먹으면 되는 것 아닌가」를 부른다 — **교환을 반쪽만 보여주면 안 된다는 것과 같은 이야기다.** 王手가 나오면 그 응수까지, 王手가 이어지면 이어지는 동안 함께 보여준다. 위 국면은 그래서 `△2八金 ▲同玉 △2七銀` 세 수가 된다.

이 규칙이 §17 국면의 수순을 늘렸다.

| 6수 이상    | 王手 규칙 전 | 후       |
| ----------- | ------------ | -------- |
| 77수째 68개 | 0            | 10 (15%) |
| 81수째 89개 | 7            | 9 (10%)  |

```
5b6a → △4七桂成 ▲5九金引 △3八成桂 ▲同玉 △4九馬 ▲同金 △4七金 ▲同玉
```

**여덟 수가 전부 강제다.** 그 길이가 곧 설명이고, `△4七桂成` 하나만 보여주면 아무것도 안 남는다.

### 打 화살표는 **駒台의 그 駒에서** 출발한다 — 재서

打은 판 위에 출발 칸이 없다. 처음엔 도착 칸 바로 위(판 밖)에서 내려오게 했는데, 화면에서 보니 **持ち駒가 없는 자리에서 駒를 가져오는 것**으로 보였다. 그 駒가 駒台의 어디에 놓여 있는지와 아무 상관이 없는 자리였기 때문이다.

「칸 산수로는 안 나온다」는 맞지만 **「알 수 없다」는 틀렸다.** 駒台는 판 밖의 형제 요소이고 그 안의 자리는 持ち駒 종류 수·라벨 폭에 따라 달라지므로 계산으로는 안 나오지만, **재면 나온다.**

- `offsetLeft`/`offsetTop` 을 `offsetParent` 를 타고 올라가며 더한다. **`getBoundingClientRect` 를 쓰면 안 된다** — 개입 중에는 판이 3D로 기울어 있어 그쪽은 변형이 끝난 화면 좌표를 준다. 우리가 필요한 것은 변형 **전**의 배치 좌표이고, 화살표도 같은 변형 안에 있으므로 그대로 맞는다
- `--sq` 가 화면 폭을 따라 변하므로 `ResizeObserver` 로 다시 잰다
- 못 쟀으면 **안 긋는다.** 엉뚱한 자리에서 뻗는 화살표가 바로 위의 그 버그다

그리고 駒台의 그 駒도 같은 초록으로 함께 빛난다. 화살표의 출발점이 어느 駒인지가 그것으로 닫힌다.

### 회상 중에는 판이 색을 잃는다

기울기만으로는 「지금 화면이 대국이 아니다」가 약했고, **흰 광선이 榧색 나무 위에서 거의 안 보였다.** 둘을 한 번에 푼다 — 판을 탈색하고 낮추면 그 위의 빛이 저절로 또렷해진다.

|                       |                                                                                                                                            |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| **색을 안 꺼낸다**    | 초록·빨강을 쓰면 「강조는 색이 아니라 빛으로」가 무너진다. 판 위에는 이미 색이 셋 있다(성한 駒의 붉은 먹·움직임 표식·직전 수)              |
| **빨간 테는 안 쓴다** | §14에서 한 번 뒤집은 결정이고, **판 위에서 빨강은 이미 「성한 駒」의 뜻**이라 초심자가 두 신호를 섞는다                                    |
| **backdrop-filter**   | 낮추는 겹 **위에** 있는 것은 안 낮아진다. 표식·유령 駒·광선의 z-index 를 그보다 크게 뒀다. `filter` 로 판에 걸면 그 셋까지 같이 어두워진다 |

### 표기는 서버가 만들고, 엔진 출력은 검증한다

`refutationLine` 이 PV를 한 수씩 룰 엔진으로 검증하며 `MoveJa` 를 붙인다. 못 두는 수가 나오면 **거기서 끊고 그때까지만** 돌려준다 — 화면에 나가는 단언이라 틀린 것을 그리느니 짧게 그린다. 대국 루프가 상대 수를 검증하는 것과 같은 이유다(§6 ③).

되따는 수가 「同」으로 나오는 것도 여기서 온다. 물러진 수의 도착 칸을 `prevTo` 로 넘기기 때문이고, **화면이 「取り返せない」라고 말한 그 자리를 수순이 그대로 짚는다.**

### 테스트가 엔진 없이 돈다

`analyst_test.go` 7개에 `t.Skip` 이 하나도 없다. 재료가 전부 룰 엔진에서 나오므로 **이 레포에서 제일 흔한 함정**(환경변수가 없으면 조용히 skip 되고 초록으로 보인다)에 안 걸린다. 카테고리 분류를 그렇게 만든 것과 같은 판단이다(§15).

실엔진 쪽은 `TestRealEngineHangingPiece` 가 이어받아 「첫 수가 상대의 수인가」와 「그 수가 던진 駒를 되따는가(同)」를 본다.

### 확인

브라우저에서 `▲3三角成`으로 물러지게 하고 데스크톱(1280)과 390px 둘 다 봤다. 2二角에서 3三으로 광선 하나, 문구에 수순 네 수, 가로 넘침 0.

### 남은 것

- **DB에 안 남긴다.** `interventions` 는 카테고리와 Δ승률까지다. 수순은 국면에서 다시 구할 수 있는 파생 데이터이고, 약점 프로파일이 쓰는 것도 카테고리 쪽이다
- 반박 수순이 붙었다고 §17의 갇힘이 풀리지는 않는다 — 89번 튕기는 것은 그대로다. **§23이 그쪽을 따로 받았다**(계단식 힌트). 이유를 대는 것과 갇히지 않는 것은 다른 일이었다

## 21. 플레이 테스트에서 나온 셋 (2026-08-10)

한 판을 끝까지 두고 나온 요구 셋이다. 하나는 그대로, 하나는 고쳐서, 하나는 뒤집어서 받았다.

### ① 상대가 너무 잘한다 — **한 판 안에서 실시간으로 조절해야 한다**

「나름 봐주는데도 끝까지 가기가 힘들었다」.

§16 실측은 **최악의 플레이어**(늘 합법수 첫 수)로 잰 것이고 +293cp가 나왔다. 즉 밴드는 지금도 형세를 지키고 있다. **그런데 어려웠다는 것은 형세가 난이도가 아니라는 뜻이다.**

+300인데 초심자가 통과하는 수를 못 찾는 국면이 §17에서 잰 바로 그것이다.

> **그래서 둘을 「같은 실패의 양쪽」으로 묶었는데, §23이 다시 갈랐다.** 갇힘은 밴드와 상관이 없었다 — 조절할 여지가 없는 국면이 아니라 **괜찮은 후보가 아홉 개나 있는** 국면이었다. 아래 「밴드만으로는 안 되는 자리」와도 다른 이야기다.

|             |                                           |
| ----------- | ----------------------------------------- |
| 갇힘 방지   | 판정이 「더 나은 선택지가 있었나」를 본다 |
| 적응형 강화 | 상대가 **애초에 그런 국면을 안 만든다**   |

#### 「적응형」이 적응하는 대상이 플레이어가 아니다

지금 `adaptiveOpponent` 는 후보 10개 중 **플레이어 관점 cp가 고정 밴드 `[+100, +300]` 에 제일 가까운 것**을 고른다. 플레이어가 잘 두든 헤매든 겨냥하는 값이 같다. 이름이 오해를 부르지만 **적응하는 대상은 국면이지 사람이 아니다.**

그리고 플레이어의 수는 매 수 판정되는데(`Analyst.Judge`, depth 12 × 2), 그 값이 가는 곳은 「이 한 수를 물릴까」와 DB 기록 둘뿐이다. **쌓아서 사람으로 만드는 코드가 없다.**

#### 목표 — 한 판 안에서, 실시간으로

**대국이 끝난 뒤 평가해서 다음 판에 반영하는 것으로는 늦다.** 이번 판에서 흥미를 잃은 사람에게 다음 판은 없다. 조절은 **두는 동안** 일어나야 한다.

그리고 **쉽게 해주는 것과 던지는 것은 다르다.** 조절은 **밴드를 움직이는 것이지 자살수 필터를 끄는 것이 아니다** — 화면이 「その駒は取り返せない場所に置かれています」라고 가르쳐놓고 컴퓨터가 바로 그 수를 두면 방금 배운 것이 무너진다(§16). 「지지만 던지지 않는다」는 그대로 두고 지는 폭만 넓힌다.

#### 구조는 비동기여야 한다 — 그리고 그 구조가 이미 있다

추정기가 롤링 통계면 인라인으로 끝나지만, **모델이나 LLM으로 레이팅을 매기려면 상대 수가 추정기 속도에 묶인다.** 그래서 갈라야 한다.

`Recorder` 가 이미 그 모양이다(§18) — 이벤트를 **버퍼 채널에 던지고 자기 goroutine이 소비하며, 큐가 차면 버린다.** 레이팅 worker는 **같은 이벤트 흐름의 두 번째 소비자**다.

```
세션 goroutine ──(판정 결과, 논블로킹)──┬──> Recorder ──> Postgres
                                        │
       ^                                └──> Rating worker  (느려도 된다)
       │                                          │
       └────────(준비되면 명령으로 돌려준다)───────┘

maybeThink → Choose(ctx, start, moves, skill)   ← 세션이 들고 있는 최신 값. 기다리지 않는다
```

**읽는 쪽을 세션이 소유해야 한다.** worker가 공유 변수를 직접 쓰면 「상태는 goroutine 하나가 소유한다」가 깨진다. 명령으로 돌려주면 그대로 남는다.

지연 예산은 넉넉하다 — 상대 수가 `depth 12 × k=10` = **2.0초**라 worker는 그 사이에 돈다. 한 수 늦게 반영돼도 **한 판 안에서 서너 번은 조절된다.**

그리고 이 구조의 진짜 이득은 **추정기를 갈아끼워도 루프가 안 바뀐다**는 것이다. 롤링 통계(µs) → 모델(수백 ms) → LLM(초)로 올라가도 생산자·소비자 배선이 그대로다. 인라인으로 만들면 그 자리를 잃는다.

> 인프로세스 버퍼 채널이면 지금은 충분하다(ECS 태스크 1개). 외부 브로커가 필요해지는 것은 worker가 프로세스 재시작을 넘어 살아야 하거나 API 인스턴스가 여러 개가 될 때이고, **그때도 생산자 쪽은 안 바뀐다.**

> **추정기에 LLM을 쓴다면 판을 넣지 않는다.** 넣을 것은 이미 결정적으로 구해 둔 것들 — Δ승률 시퀀스·카테고리 분포·착수까지 걸린 시간·블런더율. LLM이 쇼기를 판단하는 것이 아니라 **우리 측정치 위에서 사람을 요약**하는 것이라 CLAUDE.md의 선 안에 있다.

#### 밴드만으로는 안 되는 자리

**후보 10개가 20~40cp 안에 몰리는 국면에서는 밴드를 아무리 넓혀도 도달할 수 없다**(§10에서 6개 중 1개가 그랬다). 승부가 갈린 종반이 그렇다.

그래서 손잡이를 하나 더 둔다: **이기고 있을 때 강제수를 피한다**(王手·따는 수). 신호도 밴드도 필요 없고 룰 엔진만으로 되며, 후보가 몰려 있어도 듣는다. **[미확정]** 실제로 얼마나 듣는지는 안 쟀다.

### ② 블런더 화면에서 자유롭게 둬 보기 — **물러진 수는 고정이다**

「이렇게 두면 어떻게 되지」를 그 자리에서 해보게 한다. 피요쇼기가 리뷰에서 하는 것이고, 우리는 **블런더 화면에서도** 한다.

핵심은 뿌리다.

```
P        물러진 국면            ← 탐색에 들어오지 않는다. 바로 다음에 두는 그 국면이다
P+B      물러진 수를 둔 직후    ← 여기가 뿌리
P+B+…    자유롭게              ← 최선수를 봐도 된다
```

**물러진 수 B가 고정이라는 것이 곧 안전장치다.** 여기서 도달할 수 있는 국면은 전부 B를 둬야만 생기는 것들이고, B는 되물러졌으므로 판에 오지 않는다.

> 처음에는 이 절을 「블런더 화면에서 최선수는 안 된다」로 적었는데, **P에서의 최선수로 잘못 읽었기 때문**이었다. P를 열면 「블런더 → 답 → 그대로 두기」가 되어 블런더에 보상이 붙는다. 뿌리를 P+B로 두면 그 경로가 없다.

남는 위험은 하나뿐이고 좁다 — **블런더가 手番만 버린 수였을 때**(`▲1七銀` 류) 두 수 앞의 최선수가 P의 최선수와 같을 수 있다. 날카로운 블런더에서는 안 통한다(角을 던진 뒤의 최선수는 角이 없는 국면의 것이다). 그리고 여러 수를 직접 둬 보며 도달한 것은 [§1](01-core.md)이 걱정한 「가만히 있어도 뜨는 답」과 결이 다르다. **[미확정]** 실사용에서 이 구멍이 실제로 쓰이는지는 봐야 안다.

비용은 작지 않다 — WS 명령 하나, 노드마다 엔진 탐색 ~400ms, 대국 중 풀 경합. **리뷰 화면([§3](03-frontend.md))과 같은 장치이므로 그때 함께 만든다.** 거기서 이미 「네 방향 전부 클릭해서 분기로 들어가고, 되돌아가면 분기가 다시 보인다」로 설계돼 있다.

### ③ 공격할 때인가 수비할 때인가 — **단언하지 않고 답한다**

「지금은 수비할 때입니다」는 **틀릴 수 있는 문장**이다. 玉의 危険度 비교 같은 휴리스틱으로는 반드시 틀리는 국면이 나오고, 그건 [§3](01-core.md)이 금지한 그것이다 — 초심자는 검증할 수단이 없다.

~~**대신 상태를 그린다.** 詰み 게이지를 **양쪽 다** 그리면 「누가 詰み에 가까운가」가 곧 공격/수비이고, 아무것도 단언하지 않는다.~~ — **이 부분은 접혔다**(§31). 게이지는 상대 玉 쪽 하나만 그린다.

**틀린 것은 「단언하지 않는다」가 아니라 그것을 실을 자리였다.** 두 값을 같은 테두리에 그리면 불이 붙었을 때 이기는 중인지 지는 중인지가 정반대로 읽힌다. 공격/수비를 단언 없이 답하는 일 자체는 여전히 유효하고, **다른 장치가 필요하다** — 지금은 없다.

요청자는 「꼭 필요하지는 않다」고 했지만 **셋 중 제일 쌌고, 실제로 그랬다.** mate solver는 이미 이미지에 있었고(`ENGINE_MATE_CMD`), `DepthLimit=11` 도 실측돼 있었으며(최장 124ms·미증명 0), 게이지 디자인도 [§1](03-frontend.md)에 있었다.

> **그리고 그 뒤로 solver가 실제로 붙었다**(§29 ②) — 종반 판정이 매 수 詰み을 묻고 있다. ~~그래서 게이지에 남은 것은 이미 구해진 거리를 스냅샷에 실어 테두리에 그리는 일뿐이다.~~ **그 줄이 틀렸다** — 판정이 묻는 것은 착수 **전** 국면이라 한 수 낡았고, 게이지는 **지금** 국면을 따로 물어야 했다(§31). 「solver는 수번 측의 詰み을 답한다」는 것만 그대로 값을 했다 — 그것이 곧 상대 玉까지의 거리다.

## 22. 桂가 대각선으로 가는 駒로 그려져 있었다 (2026-08-10)

§5 맨 위에 있던 항목이다. **판이 규칙을 틀리게 가르치고 있었다.**

```
그리던 것   nne → (COL.east, ROW.north)   = ne 와 같은 자리
            nnw → (COL.west, ROW.north)   = nw 와 같은 자리
읽히는 것   桂 = 앞의 대각선 한 칸        ← 銀과 같은 그림
```

「격자 밖이지만 뜻은 같은 칸에 실린다」고 주석까지 적어두고 넘어간 자리다. **빠진 것은 자리가 아니라 길이었다** — 점 하나로는 「두 칸 앞」을 말할 수 없고, 화살표는 「지나간다」라서 桂가 하지 않는 일을 가르친다.

### 도착은 점, 거기까지는 길

```
점            한 칸        銀·金·玉
화살표        쭉           香·角·飛
점 + 잔 점선  뛴다          桂뿐
```

**도착 칸은 다른 駒와 똑같은 점이다.** 「점 = 그 칸」이라는 어휘를 桂에서만 버릴 이유가 없고, 격자보다 바깥에 놓일 뿐이다. 桂를 桂로 만드는 것은 그 옆에 함께 그려지는 **길**이다 — 굵기가 도착점의 1/3이라 「여기가 도착, 저건 지나가는 길」로 갈리고, **길이 끊겨 있는 것**이 사이 칸을 밟지 않는다는 뜻이다.

### 뿌리가 하나라 Y가 된다

줄기가 갈래에서 둘로 나뉜다. **「한 駒가 두 곳으로 뛴다」가 그 모양에 실려 있다** — 두 길을 각자 그으면 V가 되고, 그러면 표식 둘이 우연히 같은 곳을 향하는 것처럼 보인다.

그래서 줄기는 방향마다가 아니라 **한 번만** 그린다. 두 번 그리면 같은 자리에 겹쳐 그 부분만 진해진다(먹이 0.88이라 겹치면 0.99가 된다). 점 간격은 줄기와 갈래가 똑같이 **3**이라 길이가 달라도(6과 9) 한 줄기에서 갈라진 것으로 읽힌다.

将棋ウォーズ의 桂가 정확히 이 그림이다. ぴよ将棋도 桂만 선으로 그린다 — 둘 다 뜀에는 **자리만으로 부족하다**고 본 것이다.

### 타입이 桂를 유일한 예외로 못 박는다

```ts
type Mark =
  | { reach: 'step' | 'slide'; direction: GridDirection } // 3×3 격자
  | { reach: 'jump'; direction: JumpDirection }; // nne · nnw
```

이렇게 갈라 두면 `SPOT` 이 격자 방향만 받으므로 **뛰는 자리에 점을 찍는 코드가 애초에 컴파일되지 않는다.** 원래 버그가 정확히 그것이었다. 테스트도 5개 붙였고 환경변수를 안 탄다.

### 양끝은 재서 잡았다 — letterbox를 빼먹으면 어긋난다

브라우저에서 자를 대고 세 번 고쳤다. **셋 다 에러가 안 난다.**

| 물린 것                         | 원인                                                                                                                                                                                    |
| ------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **글자가 첫 점을 먹었다**       | 줄기를 글자 상자 안(viewBox 37)에서 시작했다. 글자가 표식 위에 오므로 그대로 가려진다. 글자 상자가 끝나는 **30.2**에서 시작하게 고쳤다 — 桂는 木과 土 사이가 벌어져 있어 그 틈에 앉는다 |
| **오각형 어깨가 15가 아니다**   | 駒는 0.8×0.84라 세로가 길고, SVG가 `meet` 로 맞추면서 viewBox 100칸이 **가로에만** 꽉 찬다. `clip-path` 의 %는 駒 상자 기준이라 어깨는 viewBox 자로 **13.3**이다                        |
| **갈래마다 점이 하나씩 없었다** | `stroke-dasharray: 0.01 4` 는 주기가 **4.01**이다. 길이 8인 선에서 세 번째 점이 8.02에 떨어져 선 밖으로 밀려나고 그냥 안 그려진다. **마디 길이를 빼서 `0.01 3.99`** 로 맞췄다           |

마지막 것은 눈으로 두 번 넘겼다. 갈래가 갈리는 꼭짓점이 비어 있는 것을 사람이 짚어줘서 알았고, 그 뒤로는 세지 않고 안 넘어간다 — `getTotalLength() / 주기`로 점 수를 세어 확인한다.

숫자는 전부 맞물려 있다. 간격 **4**, 줄기 8.2(3점), 갈래 8.3(3점), 도착점은 오각형 안에 반지름 5가 온전히 드는 (68, 13)이다. 갈래의 마지막 점과 도착점 사이는 1.6이 남아 붙어 보이지 않는다.

데스크톱(1280)과 360px 둘 다 브라우저에서 확인했다. 32px 칸에서도 桂와 銀이 갈린다.

## 23. 갇힘 — 판정을 느슨하게 하는 대신 찾는 것을 돕는다 (2026-08-10)

§17의 「생각한 수가 전부 물러졌다」에 대한 답이다. **§21이 걸어둔 방향은 실측에서 틀렸다.**

### 먼저 잰 것 — 바늘 국면이 아니었다

§21은 「판정이 **더 나은 선택지가 있었나**를 본다」고 적었다. 그 말대로면 기준을 최선수에서 N위 후보로 내리면 되는데, **후보 사다리를 처음 찍어 보고 기각했다.**

```
77수째 (depth 12 × k=10)          통과선 = −96cp
   1위  5d5f  +530     8위  P*6i   +14
   2위  5d5g  +368     9위  5b4b   −71
   3위  P*5i  +282    10위  1f1e  −182
   5위  P*6e  +186
```

**상위 9수가 전부 통과선 위**다. 「우세를 지키는 수가 하나뿐」이라던 §17의 문장이 틀렸다 — 아홉 개 있다.

그래서 기준을 5위(+186)로 내려도 바가 −96 → −433으로만 내려가는데, **탈락한 68수는 −500~−2400에 몰려 있다.** 바를 네 배 내려도 거의 아무도 안 들어온다. 81수째도 같다(1위 `B*4a` +465, 8위 −2).

즉 문제는 기준이 아니다. **76수 중 8수가 괜찮은데 그 8수를 못 찾는 것**이고, 그러면 판정을 느슨하게 할 것이 아니라 찾는 것을 도와야 한다. 밴드(§16)와도 상관이 없다 — 조절할 여지가 없는 국면이 아니었다.

> 이 사다리는 `k=10` 탐색 한 번이면 나온다. **그런데 D3 내내 한 번도 안 찍어 봤다.** 89%라는 숫자만 보고 「바늘」이라고 읽었고, 그 위에 판정 규칙을 고칠 계획을 세워뒀다.

### 계단식 힌트

같은 국면에서 연속으로 물러진 횟수로 문이 열린다.

```
1·2회  지금 그대로 (이유 + 반박 수순)
3·4회  그 駒에 파란 테          판 위면 그 칸, 打면 駒台
5회~   그 수를 파란 화살표로
```

**횟수는 국면 단위다.** 한 판 누적으로 세면 40수에 걸쳐 서로 다른 이유로 실수한 사람에게 엉뚱한 힌트가 열린다. 갇힘은 국면의 문제다 — 통과하는 수 하나로 0으로 돌아간다.

[§1](01-core.md)의 「최선수를 보여주지 않는다」에 어긋나지 않는 것은 **문이 다섯 번 실패해야 열리기 때문**이다. 기댈 수 있는 힌트가 아니고, 3회 단계는 어디로 갈지를 여전히 플레이어가 찾는다. **발동 조건이 곧 설계다**([§7](01-core.md)).

비용은 0이다 — 판정이 이미 착수 전 국면을 탐색하므로 최선수가 손에 있다. 추가 탐색이 없다.

### 3회 단계가 얼마나 듣는가

|                      | 그냥 둘 때         | 그 駒만 움직일 때 |
| -------------------- | ------------------ | ----------------- |
| 77수째 `5d5f` (龍)   | 8/76 = **10.5%**   | 3/11 = **27%**    |
| 81수째 `B*4a` (角打) | 16/111 = **14.4%** | 6/49 = **12%**    |

판 위의 수는 **2.6배**가 된다. 통과가 `5d5e` `5d5f` `5d5g` 셋이고 전부 5筋을 따라 내려가는 수라, 사람이라면 그중 하나를 고를 만하다.

**打의 12%는 균등 확률이라 사람을 모사하지 못한다.** 49칸을 같은 확률로 고른다고 본 값인데, 사람은 角을 아무 데나 놓지 않는다 — 통과한 자리가 `4a` `5c` `5e` `6e`로 상대 진영을 노리는 줄에 몰려 있다. 그리고 숫자보다 중요한 것은 **질문이 바뀐다**는 것이다. 「76수 중 뭘 두지」는 초심자가 답할 수 없고 「角을 어디에 놓지」는 답할 수 있는 쇼기 질문이다. 그래서 打에 특례를 두지 않았다.

**[미확정]** 3과 5는 초기값이다. 3회에서 27%면 한 번에 맞히기를 기대하는 값이 아니라 두 번을 준 뒤 수를 보여주는 값이다.

### 페이로드도 계단이어야 한다

3회 시점에 최선수를 통째로 내려보내고 화면이 출발 칸만 그리면, **계단이 화면에만 있고 답은 devtools에 그대로 있다.**

```
3회  { hint: { square: "5d" } }   또는 { hint: { drop: "B" } }
5회  { hint: { square: "5d", usi: "5d5f" } }
```

그래서 자르는 일을 서버가 한다(`buildHint`). 테스트가 **3회에 `usi` 가 비어 있는 것**을 지킨다 — 이 성질은 사람 눈으로는 안 보인다.

### 파랑은 비어 있었다

판 위 색 예산을 세어 보니 초록(다음 수)·빨강(王手)·붉은 먹(駒의 인쇄)·나무색(직전 수)·흰빛(후보·선택·개입)·보라(詰み 게이지, 테두리)였고 **파랑이 비어 있었다.**

그리고 여기서는 **빛을 쓸 수 없다.** 힌트가 뜨는 순간이 정확히 플레이어가 駒를 고르는 순간인데, 고른 駒는 이미 흰빛 테를 두르고 들어올려진다 — 빛을 하나 더 얹으면 「내가 고른 駒」와 「골라야 할 駒」가 같은 신호가 된다.

화살표는 초록·빨강과 **모양이 같고 색만 다르다.** 굵기와 촉을 같이 두는 것은 「한 수를 잇는 선」이라는 뜻이 같아서이고, 색을 가르는 것은 **가리키는 쪽이 반대**라서다 — 저 둘은 상대가 무엇을 하는가이고 이쪽은 네가 무엇을 두면 되는가다.

### 물린 것 셋 — 전부 브라우저에서만 보인다

| 증상                         | 원인                                                                                                                                                                                                               |
| ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **駒에 테가 안 그려진다**    | §14에서 세 번 물린 그것이다. `clip-path` 오각형이 `border`·`box-shadow` 를 그린 다음에 자르고, 사각형 테와 오각형이 만나는 곳은 아랫변뿐이라 밑줄만 남는다. **같은 오각형을 조금 크게 그린 요소를 駒 뒤에 깔았다** |
| **화살표가 압정처럼 보인다** | 자루 끝이 `border-radius: 999px` 의 둥근 마구리라 촉의 뾰족한 끝보다 두껍다. 촉 끝을 도착 칸 한가운데에 맞춰 두니 그 마구리가 촉 위로 반원처럼 삐져나왔다. **촉을 0.09칸 앞으로 내보내 덮었다**                    |

두 번째는 **§20부터 계속 그랬던 것**이고, 힌트 화살표를 붙이면서 확대해 보고서야 보였다. 초록·빨강도 같이 고쳐졌다.

### 힌트가 駒台에 초록 링을 같이 켰다

셀프리뷰가 잡았다. 打 화살표의 출발점을 **재야 하는 駒**와 **초록 링이 켜지는 駒**를 한 값으로 쓰고 있었다 — `dropping` 을 `<Hand>` 에 그대로 넘겼더니 힌트가 `data-dropping` 을 켰고, 그 CSS가 `--ray`(초록)로 링을 그린다.

그래서 3회 단계에서 駒台 駒에 **파란 테와 초록 링이 동시에** 걸렸다. 초록은 이 PR이 스스로 「상대가 무엇을 하는가」로 예약한 색이고, 게다가 그 단계에는 화살표가 없으니 **화살표 없는 초록 링**만 남는다. §23이 잰 두 국면 중 하나가 打이므로 흔한 길이다.

**재는 것과 빛나는 것을 갈랐다**(`measure` prop). 빛이 채널이라는 것이 이 레포의 규칙인데, 편의로 한 값을 두 뜻에 쓰면 그 규칙이 조용히 깨진다.

### 그리고 화면이 통째로 하얘졌다 — 打 힌트에서만

**실제 대국에서 계단이 열리는 순간 화면이 죽었다.** 서버는 정상이고 로그도 깨끗했다.

```
Maximum update depth exceeded
 > GameScreen.tsx  setDropFrom({...})
```

打 화살표의 출발점은 재서 얻으므로(§20) `useLayoutEffect` 가 돈다. 그 의존성인 `dropping` 에 힌트를 얹으면서 **매 렌더마다 새 객체**가 되게 만들었다 — 효과 재실행 → `setDropFrom(새 객체)` → 리렌더 → 또 새 객체 → 무한이다. 회상 쪽은 `scenes` 의 `useMemo` 에서 와서 원래 안정적이었고, **그 성질에 기대고 있다는 것이 코드에 안 적혀 있었다.**

두 겹으로 막았다 — `dropping` 을 `useMemo` 로 고정하고, `measureDrop` 이 **같은 값이면 상태를 안 건드리게** 했다. 뒤쪽은 위쪽 의존성이 또 흔들리는 날에 흰 화면 대신 아무 일도 안 일어나게 하는 것이다.

> **이건 타입도 테스트도 빌드도 전부 통과한다.** 웹 테스트는 순수 함수만 돌리고 렌더는 안 하므로, 렌더 루프는 브라우저를 띄우지 않으면 못 본다. 그리고 **打 힌트에서만** 터지므로 판 위의 수로 눌러 보는 동안에는 안 나온다 — §14가 「화면을 띄워야만 보이는 것들」이라고 적어둔 목록에 한 줄이 더 붙었다.

데스크톱(1280)에서 직선·대각선·파랑·초록·빨강을 모두 확인했고, **실제 대국에서 3회에 파란 테가, 5회에 파란 화살표가 뜨는 것까지 봤다.** 루프를 고친 뒤다.

## 24. 不成을 「잡는 것이 문제」라고 가르쳤다 (2026-08-10)

[플레이 기록 §8](08-playtest.md)이 잡은 것이다. **이 제품이 틀린 것을 가르친 유일한 자리**라 다른 항목과 급이 다르다.

```
둔 수     7c8d   ▲同銀不成      개입, greedy_capture, Δ승률 1.000
최선수    7c8d+  ▲8四銀成       from·to가 같다. 差는 成하느냐뿐
나간 문구 駒は取れますが、払う代償のほうが大きくなります。
```

**잡는 것이 문제가 아니었다. 잡는 것이 정답이었다.** 銀이 `7三`(敵陣)에서 나오므로 성할 수 있고, 成銀은 金처럼 움직여 옆칸 `9四`의 玉을 노린다. 不成은 그 자리를 못 본다 — 하나는 詰めろ이고 하나는 즉패다.

그런데 화면은 「잡는 대가가 크다」고 말했다. 기록자는 그 문장을 **「飛를 잡으면 안 되는구나」로 읽고** 다음 후보로 `▲7五歩`을 뒀다. 그것도 Δ1.000, 그다음 `▲7七玉`도 1.000. **문구가 세 수를 틀린 방향으로 끌고 갔다.**

초심자는 이 설명을 검증할 수단이 없다. [§1](01-core.md)이 이 레포의 존재 이유로 삼은 실패가 실측으로 한 번 일어난 것이다.

### 고친 것 — 칸 하나와 순서 하나

```
game.UnpromotedOnly(played, bestUSI)   같은 from·to, 成 여부만 다른가 → bool
intervene.Features.UnpromotedOnly      그 참거짓만 건너간다
classify                               맨 앞. missed_mate 다음이다
```

**엔진이 필요 없다.** USI 두 개를 견주면 결정적으로 갈린다. 그리고 **판정을 `intervene` 밖에서 한다** — 저쪽에 USI 문자열을 넘기면 「입력은 이미 구해진 숫자뿐」이 깨진다(§15에서 카테고리를 스칼라로 받게 만든 것과 같은 이유).

**타다스테보다도 앞이다.** 이동이 최선수와 같다면 배울 것은 「成れた」쪽이고, 不成으로 놓인 駒가 마침 잡히는 자리여도 그건 성하지 않은 결과다.

### 문구가 순서를 뒤집는다

```
その一手で合っていますが、成っていません。敵陣から出る手も成れます。
```

**맞은 것을 먼저 말한다.** 「その手は」로 시작하면 플레이어는 이동 자체를 의심하고, 실제로 그렇게 세 수를 헤맸다. 그리고 놓친 규칙을 한 줄 붙였다 — 기록자가 몰랐던 것이 **「敵陣에서 나오는 수도 成れる」**였다(§6-6). 도착 칸만 보고 성이 안 된다고 판단한 것이다.

### 거울상은 안 본다

成하지 **말아야** 했던 수(成らずの妙手)는 이 카테고리에 넣지 않았다. 초심자의 실수 모양이 아니고 문구도 「成れます」로 끝낼 수 없다 — 한 카테고리에 둘을 넣으면 다시 뭉뚱그린 설명이 된다. **[미확정]** 실제로 나오는지는 표본이 더 필요하다.

### 그 국면에서 다시 판정한다

`TestRealEngineUnpromotedIsNotGreed` 가 games.id=84의 **102수를 그대로 놓고** `7c8d`를 판정한다.

```
최선수=7c8d+  카테고리=unpromoted  Δ승률=1.000
```

기보에 물러진 수가 남지 않으므로(§18) 테스트가 102수까지만 두고 그 한 수를 직접 넣는다. **최선수가 `7c8d+`라는 것이 이 테스트의 전제**여서 그것도 같이 단정한다 — 엔진이 바뀌어 전제가 깨지면 조용히 통과하지 않고 거기서 멈춘다.

엔진 없이 도는 테스트도 둘 붙였다. `TestUnpromotedOnly` 가 打·도착 칸 차이·최선수 불명 같은 경계를 보고, `TestUnpromotedBeatsEveryOtherReason` 은 **칸을 내리면 옛 오분류가 그대로 돌아오는 것**까지 단정한다 — 그 줄이 있어야 무엇을 막고 있는지가 코드에 남는다.

## 25. 반박 수순은 최선 수순이지 교훈이 아니다 (2026-08-10)

[플레이 기록 §7](08-playtest.md)이 「69手 `▲2五飛`의 반박이 한 수로 끊겨 왜 나쁜지 안 보인다」고 적었고, `△8九香成 ▲同金 △同馬`까지 가야 보인다고 했다. **잘못 잘린 것을 찾으러 갔는데 그게 아니었다.**

`internal/game/refutation_measure_test.go` 가 그 국면을 다시 잰다.

### 자른 것은 옳았다

```
PV: 8f8i+  P*3d  8i7i  3d3c+ …
     △8九香成  ▲3四歩
```

엔진은 **8九를 되잡지 않는다.** `trimRefutation` 은 「같은 칸에서 주고받는 동안」만 이어 붙이므로 교환이 이어지지 않는 여기서 1수에 끊는 것이 규칙대로다.

### 그런데 사람의 수순도 옳았다

```
도망   7i7h    내 관점  -593    ← 엔진의 최선수
되잡기 7i8i    내 관점 -2292    ← 합법인데 1699cp 더 나쁘다
       그 뒤   8e8i+           8五의 飛가 잡고 龍이 된다
```

되잡는 수는 실재하고 실제로 그만큼 나쁘다. 「공격 2 대 수비 1」이라는 읽기도 맞다 — 9九馬와 8五飛가 8九를 보고 7九金 하나가 지킨다. 엔진이 `△同馬` 대신 `△同飛成` 를 고르는 것은 龍이 되는 쪽이 세기 때문이고 **결론은 같다.**

### 두 세션이 서로 다른 것을 「반박 수순」이라고 불렀다

|              | 무엇을 보여주나                                                     |
| ------------ | ------------------------------------------------------------------- |
| 사람이 쓴 것 | **되잡으면** 이렇게 된다 — 두고 싶어했을 수를 둬 보고 실패하는 변화 |
| 엔진 PV      | **최선으로 두면** 이렇게 된다 — 桂는 포기하고 金을 살리는 정리      |

PV는 수번이 번갈아 오고, **가르치는 내용은 상대 수 쪽에만 있다.** `△8九香成` 다음 PV의 두 번째 수는 내 수이며 최선의 내 수는 `▲7八金`(도망)이라 왜 나쁜지를 하나도 안 가르친다 — 이미 손해를 인정한 뒤의 정리이기 때문이다.

[§20](#20-반박-수순--왜-블런더인지-모르겠다의-답)이 「착수 후 PV가 곧 상대는 이렇게 벌한다」로 둘을 같은 것으로 놨는데, **첫 수 뒤로는 그 동일시가 깨진다.**

### 그래서 PV를 늘리는 것은 틀린 처방이다

한 번 더 탐색해 두 번째 수를 붙이면 `▲7八金` 이 나온다 — 400ms를 내고 설명력 0을 얻는다. 게다가 PV 꼬리는 신뢰할 수 없다: PV의 두 번째 수가 `P*3d` 인데 그 국면을 새로 재면 `P*3d` 는 3위(-1025)이고 1위는 `7i7h`(-593)다. **430cp 어긋난 수를 화면에 그리게 된다.** `RefutationPlies` 주석의 「PV는 뒤로 갈수록 확실하지 않다」가 실측으로 확인됐다.

실제로 가르치는 것은 **「되잡으면 어떻게 되나」**이고 그것은 최선 수순이 아니라 **플레이어가 두려 했을 수의 변화**다. 그건 [§21 ②](#21-플레이-테스트에서-나온-셋-2026-08-10)의 「가정 수순을 직접 둬 보기」와 같은 장치다 — **이번 재현이 §5의 두 항목을 하나로 이었다.**

즉 `other` 66.7%의 설명 부족은 반박을 늘려서 풀리지 않는다. 분기를 둬 볼 수 있게 해야 풀린다. **그때까지 남는 싼 수단은 「무엇을 잃었는지 말하기」뿐이다** — 탐색이 필요 없고, 이 국면에서 플레이어가 놓친 것(8九를 둘이 보고 하나가 지킨다)을 정면으로 겨냥한다. **[미확정]** 아직 안 했다.

## 26. 평가치 궤적을 기보에 남긴다 (2026-08-10)

[플레이 기록 §11](08-playtest.md)이 잡은 것이다. 109수 한 판이 기록됐는데 **`game_moves.eval_cp` 가 109행 전부 NULL**이었다. 스키마에는 처음부터 있던 칸이고 넘길 길이 없었다 — `Recorder.Moved(ply, usi, by)` 에 평가치 인자가 없다.

없으면 막히는 것이 셋이다.

|                      |                                                                                     |
| -------------------- | ----------------------------------------------------------------------------------- |
| **평가치 궤적**      | 한 판의 형세가 어떻게 흔들렸는지 사후에 못 그린다. 리뷰 화면 스파크라인의 원본이다  |
| **밴드 검증**        | 적응형 상대가 겨냥하는 `+100~+300cp`(§16)가 **실제 대국에서 지켜졌는지 알 수 없다** |
| **K를 다시 잡는 일** | 아래                                                                                |

세 번째가 이 항목의 순서를 앞으로 당긴 이유다. 개입 판정은 cp를 승률로 바꿔 쓰고(`WinRate(cp) = 1/(1+exp(-cp/K))`, K=600 **[미확정]**) `interventions.delta_win` 은 그 **파생값**이다. **cp를 원본으로 남겨두면 K를 바꿔 지난 대국을 다시 채점할 수 있다** — 엔진을 다시 돌리지 않고. 승률만 남기면 그 길이 닫히고, §5의 「상수 실측」이 이 칸 위에서 돈다.

### 추가 탐색이 없다 — 판정이 이미 두 국면을 재고 있다

`Opponent.Choose` 는 자기가 고른 수의 평가치를 돌려주지 않는다. 인터페이스를 넓히는 대신 **판정이 이미 손에 든 값**을 쓴다.

```
사람이 두면 판정이 두 번 탐색한다
  착수 전 국면  = 직전 상대 수 뒤의 국면   → 그 手数의 평가치
  착수 후 국면                              → 이 手数의 평가치
```

그래서 **상대 수의 평가치는 한 수 늦게 채워진다.** 그리고 **마지막 수는 안 채워진다** — 그 뒤에 사람의 수가 없으면 판정도 없다. 둘 다 구조상 그런 것이라 기록해 둔다.

`Moved` 와 `Evaluated` 를 가른 것도 그 때문이다. 값을 아는 시점이 다르고, 한 메서드로 묶으면 수를 다시 쓰게 된다 — SQL도 `UPDATE ... SET eval_cp` 로 따로 두어 **수를 덮을 길을 없앴다.** upsert로 두면 물러진 수로 기보를 덮는 경로가 생긴다.

### 관점은 先手로 고정한다

`edges.eval_by_depth` 와 같은 규약이다([§4](02-architecture.md)). 「플레이어 관점」으로 적으면 **색이 다른 두 판을 나란히 못 놓는다** — 뒤집는 일은 질의하는 쪽이 `games.my_color` 로 한다.

**부호는 사람 눈으로 안 보인다.** 뒤집혀 들어가면 궤적이 상하로 뒤집힌 채 그려지고 「밴드가 지켜졌나」에 정확히 반대 답이 나온다. 그래서 테스트가 **사람이 後手인 판까지** 본다. `senteCp` 가 뒤집지 않게 고쳐 보면 그 쪽만 실패한다 — 확인했다.

### 배선을 세 곳에서 지킨다

한 곳만 비어도 칸이 조용히 NULL로 남는다. 실제로 그렇게 한 판이 기록됐다.

| 테스트                               | 지키는 것                                                |
| ------------------------------------ | -------------------------------------------------------- |
| `TestEvalsAreRecordedFromSentesSide` | 세션이 두 手数를 채운다 · **부호**가 先手 관점이다       |
| `TestSetMoveEvalFillsOnlyTheEval`    | SQL이 수를 덮지 않는다 · 없는 ply에 행을 만들지 않는다   |
| `TestRecordFillsEvalTrajectory`      | **dbRecorder 가 이벤트를 흘리지 않는다** — WS부터 DB까지 |

마지막 것이 없으면 앞의 둘이 다 초록인데 칸은 계속 NULL이다. `evEvaluated` 를 흘리게 고쳐 보면 그것만 실패한다.

**마이그레이션은 없다.** 칸은 `001_init.sql` 에 처음부터 있었다.

## 27. 설명 계층 — 문장을 만드는 일을 세션에서 떼어냈다 (2026-08-11)

`internal/explain`. [LLM 계층](04-llm.md)의 Tier 0·1·2가 코드가 됐다.

**두 가지가 한 자리에서 풀렸다.** 플레이 기록이 잡은 최대 결함(`other` 16회가 전부 같은 문장이고 정보량이 0)과, 「판단은 엔진, 표현만 LLM」의 LLM 쪽이 0줄이던 것이다. 앞은 사실을 문장에 넣는 일이고 뒤는 그 사실을 누가 문장으로 바꾸느냐라, **같은 구조의 앞뒤였다.**

### 결정적 문구가 먼저다 — LLM은 그 위에 얹힌다

순서를 뒤집으면 LLM이 없을 때 정보가 같이 사라진다. 그래서 `Render` 가 사실을 전부 담고, LLM은 **같은 사실을 더 좋은 문장으로** 바꾸는 일만 한다.

```
그전   その駒は取り返せない場所に置かれています。相手の利きを確かめてみてください。
지금   その銀を取れる相手の駒が2枚あり、取り返す駒がありません。

그전   その手は形勢を大きく損ねます。もう一度考えてみてください。          (16회 전부 이것)
지금   その手は形勢を大きく損ねます。相手は桂を取れます。
```

플레이 기록이 요구한 것 그대로다 — 「어느 駒인지, 몇 개가 노리는지를 숫자로」([§7](08-playtest.md)), 그리고 「무엇을 잃었는지 말하기」([§25](#25-반박-수순은-최선-수순이지-교훈이-아니다-2026-08-10)의 `[미확정]` 항목).

**「取り返せない」의 주어 모호함도 여기서 고쳤다.** 내가 되딸 駒가 없다는 뜻이었는데 상대가 못 잡는다고도 읽혔다. `取り返す駒がありません` 은 그렇게 안 읽힌다.

### 매수를 센다 — 수를 세면 거짓말이 된다

`legalCapturesOn` 이 돌려주는 것은 **수**다. 같은 銀이 成·不成으로 두 수를 내므로 그대로 세면 화면이 「2枚あります」라고 말하는데 판에는 한 장뿐이다.

**에러가 안 나는 종류의 거짓말이라 기계로만 잡힌다.** `TestFactsCountPiecesNotMoves` 가 그 국면을 놓고 「따는 수는 2개, 매수는 1」을 단정한다. 전제(수가 정말 2개인가)까지 같이 단정해서, 국면이 바뀌면 조용히 통과하지 않는다.

그리고 이 값은 「노리는 매수」가 아니라 **실제로 딸 수 있는 매수**다 — 핀에 묶인 駒는 안 센다(§15에서 `LandsAttacked` 를 합법수로 물은 것과 같은 이유다. 화면에 나가는 단언이라 그렇다).

### 판정과 설명이 **같은 자리에서** 사실을 센다

`moveFacts` 하나가 `intervene.Features`(판정용 값)와 `explain.Facts`(설명용 이름·매수)를 함께 낸다. 갈라서 두 번 세면 카테고리는 タダ捨て가 아니라고 판정했는데 문장은 「2枚が取れます」라고 말하는 일이 생긴다.

### 칸도 Δ승률도 문장에 안 넣는다 — 둘 다 캐시 때문이 아니다

```
칸      판이 빛으로, 카드가 棋譜(▲8四銀)로 이미 말한다.  문장은 「その銀」까지면 된다
Δ승률   카드에 「勝率 −N%」 막대가 따로 있다
```

Δ승률을 프롬프트에 주면 LLM이 문장에 옮겨 적어 **막대와 두 벌**이 되고, 어긋났을 때 어느 쪽이 맞는지 알 수 없다. 칸을 빼면 캐시 키가 81배로 안 늘어나는 것은 그 결정의 **결과**이지 이유가 아니다.

### 카테고리마다 말해도 되는 것이 다르다

`Facts.used()` 가 그 목록이고, **키·프롬프트·결정적 문구가 전부 그 함수를 지난다.**

|                  |                                                         |
| ---------------- | ------------------------------------------------------- |
| `hangs_piece`    | 움직인 駒 · 노리는 매수 · 되딸 수 있는가                |
| `greedy_capture` | 딴 駒                                                   |
| `other`          | 잡히는 駒 하나. **이유는 모른다고 프롬프트에 적는다**   |
| 나머지 다섯      | 없음 — 카테고리 자체가 이미 구체적이라 붙일 자리가 없다 |

갈라두면 두 가지가 조용히 어긋난다. 문장에 안 쓰는 사실로 캐시가 갈려 히트율이 떨어지고(비용), 프롬프트에만 있는 사실은 언젠가 문장으로 샌다(거짓). `unpromoted` 에 아무것도 안 붙인 것은 [#26](#24-不成을-잡는-것이-문제라고-가르쳤다-2026-08-10)이 그 문장의 **순서**로 오분류를 고쳤기 때문이다 — 거기에 매수를 얹으면 다시 이동을 의심하게 만든다.

### 카드가 뜨기 **전**에 문장이 손에 들어와야 한다

판정 goroutine 안에서 부른다. 나중에 올려 보내 갈아끼우는 쪽이 지연은 없지만, **플레이어가 읽는 도중에 글자가 바뀐다.**

```
판정      depth 12 × 2   ≈ 800ms   ← 이미 기다리는 시간
설명      최대 5초 (§28에서 실측)   ← 넘기면 안 기다리고 결정적 문구로 간다
캐시 히트  HTTP가 안 나간다          ← 두 번째부터는 이 지연이 없다
```

**통과한 수에는 안 부른다.** 109수 대국에서 개입은 8국면이었다([§5](08-playtest.md)) — 매 수 부르면 비용이 열 배인데 그 문장이 나갈 자리조차 없다.

### LLM 출력을 믿지 않는다

엔진이 돌려준 수를 룰 엔진으로 검증하는 것([§6 ③](#6-d2--대국-루프-완료))과 같은 자리다. 빈 문장·120자 초과·**한글 혼입**은 버리고 결정적 문구로 간다.

**자르지 않고 버린다.** 중간에서 자른 일본어는 뜻이 바뀌고 초심자는 그것을 검증할 수단이 없다. 버려도 대가가 없는 것은 결정적 문구가 언제나 준비돼 있기 때문이다.

한글 검사는 런타임에도 돈다. 프롬프트가 전부 일본어라 올 일이 없지만, **사람이 매번 읽고 확인할 수 없는 출력**이라 규칙을 코드가 지켜야 한다. 테스트는 프롬프트·문구·카테고리 사전 전부를 기계로 훑는다.

### 비용은 헤더에 없었다 — 라우터 소스를 읽고 알았다

[04-llm.md §3](04-llm.md)에 옮겨 적었다. 요점만:

- `x-orca-*` 헤더는 **캐시 여부와 모델 이름까지**다. 비용 헤더는 없다
- 원당 비용은 본문 `usage.cost_usd`(또는 `_orca_meta.cost_usd`), **USD**
- **없으면 0으로 적는다.** 토큰 × 가격표로 되메우면 발표의 「1회당 ○엔」이 우리가 만든 숫자가 된다
- `x-orca-cache: HIT` 이면 0이다. 그때 본문의 `usage` 는 원래 호출의 것이라 그대로 곱하면 **같은 돈을 두 번 센다**

필드 이름을 짐작해서 적었으면 전부 조용히 0이 됐을 것이다. 문서가 아니라 `app/routes/chat.py` 를 읽었다.

### `explain_tier` 는 안 거쳤으면 NULL이다

0으로 적으면 「캐시 히트」와 같은 값이 되는데 **뜻이 정반대다** — 히트는 부를 것을 아껴서 0엔이고, NULL은 애초에 안 부른 것이다. 섞이면 「호출을 구조적으로 줄였다」는 발표의 주장이 「LLM을 안 붙였다」와 구별되지 않는다.

`explain_cache.hits` 는 조회 질의가 `UPDATE ... RETURNING` 이라 **찾으면서 센다.** 앞에 메모리 캐시를 두지 않은 것도 그 때문이다 — 거기서 맞으면 이 숫자가 조용히 낮아지고, 그게 곧 발표의 히트율이다.

### 배선을 네 곳에서 지킨다

[§26](#26-평가치-궤적을-기보에-남긴다-2026-08-10)과 같은 이유다. 한 곳만 비어도 화면은 옛 문구를 그대로 보여주고 **아무 에러도 안 난다.**

| 테스트                                         | 지키는 것                                    |
| ---------------------------------------------- | -------------------------------------------- |
| `TestFactsCountPiecesNotMoves`                 | 매수가 매수다 · 그 숫자가 그대로 문장이 된다 |
| `TestPromptCarriesOnlyWhatTheSentenceMayUse`   | 프롬프트가 말해도 되는 사실만 싣는다         |
| `TestInterventionMessageComesFromTheExplainer` | **카드 문장이 설명 계층에서 온다**           |
| `TestRecordFillsExplainTierAndCost`            | WS부터 DB까지 — 계층과 비용이 칸에 들어간다  |

마지막 것을 확인했다. `r.explanation` 대신 빈 값을 넘기게 고쳐 보면 그것만 실패한다.

## 28. 실키로 재보니 넷이 틀렸다 (2026-08-11)

`ORCA_API_KEY` 가 들어왔다. §27이 「키가 없어서 못 쟀다」로 남긴 것을 전부 쟀고, **네 가지가 문서와 달랐다.**

`internal/explain/real_router_test.go` 가 그 측정이다. `ORCA_API_KEY` 가 없으면 건너뛴다 — `usi` 의 `TestRealEngine` 과 같은 자리이고, **프롬프트를 고치면 여기가 첫 관문이다.** 가짜 라우터는 우리가 적은 것을 돌려주므로 「모델이 지시를 지키는가」의 증거가 못 된다.

### ① `auto` 는 이 라우터의 모델 이름이 아니다

```
model=auto              →  503  model_not_found: No available channel for model auto
model=orcarouter/auto   →  200
```

호스팅 쪽 모델 이름에는 **네임스페이스가 붙는다**(`GET /v1/models` 에 182개). 그리고 이 에러는 401이 아니라서 **키는 처음부터 정상이었다** — 인증과 모델 이름을 에러 하나로 구별할 수 있었던 것은 본문을 에러에 붙여 뒀기 때문이다.

### ② 그런데 `orcarouter/auto` 를 기본값으로 두면 안 된다

라우터는 「요구 능력을 충족하는 가장 싼 모델」을 고르는데, **우리 요구는 능력이 아니라 짧고 빠른 것**이라 그 기준과 어긋난다. 실제로 추론 모델로 갔다.

| 모델                             | 지연(카테고리 8개) | 결과                                       |
| -------------------------------- | ------------------ | ------------------------------------------ |
| **`anthropic/claude-haiku-4.5`** | **1.7 ~ 3.2초**    | ✅ 사실을 다 싣고 지시를 지킨다            |
| `google/gemini-3.5-flash-lite`   | 1.9 ~ 6.7초        | 흔들린다                                   |
| `orcarouter/fusion-mini`         | 15 ~ 23초          | `qwen3.7-flash` — 추론 모델                |
| `orcarouter/auto`                | 같다               | `qwen3.7-plus`. 한 문장에 추론 토큰 1036개 |

한 문장 각색에 추론 토큰 1000개를 쓰는 것이 이 라우팅의 실제 모습이다. 그래서 **기본값을 실측한 모델로 박았다.**

### ③ 원당 비용을 얻을 길이 없다 — 계획된 발표 슬라이드가 하나 사라진다

§27에 「비용은 본문 `usage.cost_usd` 에 있다(라우터 소스에서 확인)」고 적었는데, **그건 Lite 소스이고 호스팅은 다르다.**

```
응답 헤더    x-orca-request-id · x-orca-resolved-model · x-orca-router · x-orca-version
             ← x-orca-cache 조차 없다
usage        prompt_tokens · completion_tokens (+reasoning_tokens).  cost_usd 없음
/v1/analytics/spend · recent · savings   →  전부 404
```

즉 **`interventions.cost_yen` 은 이 프로바이더에서 언제나 0이다.** [LLM 계층 §5](04-llm.md)의 「개입 1회당 평균 ○엔」과 「savings 위젯 스크린샷 한 장으로 끝」은 **API로는 못 만든다.**

**토큰 수와 가격표로 추정해 채우지 않는다.** 그 순간 발표의 숫자가 우리가 만든 숫자가 되고 근거가 사라진다. 남은 길은 셋이고 전부 [미확정]이다 — 라우터 웹 대시보드 스크린샷(사람이 로그인), Lite 자체 호스팅(analytics 가 소스에 있다), 또는 토큰 수만 사실로 기록하고 비용은 말하지 않는 것.

> 소스를 읽은 것은 옳았지만 **읽은 소스가 우리가 쓰는 것이 아니었다.** Lite(MIT, 자체 호스팅)와 호스팅 서비스가 같은 표면일 것이라고 가정했다.

### ④ 실모델이 **틀린 것을 두 개 가르쳤다** — 그리고 원인이 같았다

제일 값비싼 발견이다. 지연·비용은 숫자가 틀린 것이고, 이쪽은 **제품이 하지 않기로 한 일**이다.

```
missed_mate   나간 문장:  終盤で相手に詰みがある局面です。
              틀린 곳:    詰み을 가진 쪽은 **나**다. 내가 상대를 詰ませる 수를 놓친 것인데
                          내가 詰まされる 것으로 읽힌다 — 방향이 반대인 설명

unpromoted    나간 문장:  敵陣に入ったときに成ることができます。
              틀린 곳:    이 카테고리가 생긴 이유가 **「敵陣から出る手も成れる」**를 놓친
                          실수였는데(08-playtest.md §6-6), 그 오해를 그대로 남긴다
```

**원인은 모델이 아니라 프롬프트다.** 두 자리 모두 `categoryJa` 가 결정적 문구보다 사실을 적게 들고 있었고(주체가 없었고, 「出る」가 없었고), **모델이 그 빈 곳을 채우면서 틀렸다.**

그래서 규칙이 하나 나온다 — **프롬프트는 결정적 문구와 같은 사실을 들고 있어야 한다.** 「사실을 문장으로 바꾼다」는 프롬프트가 그 사실을 실제로 줄 때만 성립하고, 덜 주면 그 자리를 모델이 메운다. 결정적 문구에 지식이 박혀 있으면 그것도 프롬프트로 옮겨야 한다.

고친 뒤:

```
missed_mate  相手を詰ませられる手がありました。その手を指さずに別の手を指すと、詰ませるチャンスを逃してしまいます。
unpromoted   その駒は敵陣から出る時に成ることができます。成らずに動かすと、損をしてしまいます。
```

테스트가 그 둘을 `mustNotMention`·`mustMention` 으로 고정했다. **사람 눈으로는 두 번 넘긴 종류의 오류다** — 문장이 자연스럽고 문법도 맞아서, 쇼기를 아는 사람이 뜻을 따져야만 보인다.

### 그리고 문장은 실제로 템플릿보다 낫다

`hangs_piece` 를 나란히 놓으면 이렇다.

```
결정적   その銀を取れる相手の駒が2枚あり、取り返す駒がありません。
LLM      銀を動かすと、相手の駒2枚に取られてしまいます。取り返す駒がないので、銀を失ってしまいます。
```

**같은 사실을 말하는데 인과로 풀어 준다.** 입문자(`levelJa` 가 「駒の動きを覚えたばかり」로 준다)에게는 뒤쪽이 읽기 쉽다. 사실이 같으므로 틀릴 여지가 늘지 않은 것이 요점이다 — 늘어난 것은 문장력뿐이다.

### 실측으로 바뀐 상수

|                | 그전   | 지금                         | 왜                                                       |
| -------------- | ------ | ---------------------------- | -------------------------------------------------------- |
| `Deadline`     | 1.5초  | **5초**                      | 실측이 1.7~4.7초다. 1.5초면 **전부 템플릿으로 떨어진다** |
| `DefaultModel` | `auto` | `anthropic/claude-haiku-4.5` | ②                                                        |

**5초가 관대한 것이 아니라, 이 제품에서 기다림이 손실이 아니다.** 쇼기 상대가 몇 초 생각하는 것은 자연스럽고 화면이 이미 「判定中」을 띄우고 있어서, 그 시간이 **고민으로 읽힌다.** 같은 값이 다른 종류의 앱에서는 고장으로 보일 것이다 — 그래서 이 상수는 실측이 아니라 **제품의 성격**이 정한다.

판정 800ms에 더해지므로 카드가 최대 5.8초까지 늦어질 수 있고, 넘는 국면은 결정적 문구로 떨어진다 — 그래서 카드는 언제나 뜬다. 테스트도 지연을 단정하지 않고 기록만 한다(두 배를 넘으면 그때 실패한다).

**[미확정]** 어디까지가 「고민」이고 어디부터 「멈췄다」인지는 브라우저에서 사람이 보고 정할 값이다.

**남은 것: Tier 1을 미리 만들어 두는 것.** 키가 24가지뿐이라(카테고리 8 × 레벨 3) 한 번 생성해 `explain_cache` 에 넣어두면 그 절반은 런타임에 0초가 된다. §27에서 「Tier 2가 대부분이라 사전 생성은 이득이 적다」고 적었는데, **2초라는 실측이 그 판단을 뒤집었다.**

### 부수적으로 — 임베딩은 있다

`google/gemini-embedding-001` 이 모델 목록에 있고 `POST /v1/embeddings` 가 200을 준다. **차원이 3072**인데 `kb_chunks.embedding` 은 `vector(1536)` 이라 그대로는 안 들어간다.

그런데 RAG에 이게 꼭 필요한지가 먼저다 — **우리 검색 키는 자유 문장이 아니라 태그**이고(「이 국면에 `mino` 태그가 붙었으니 美濃囲い 항목을 꺼낸다」), 그건 `kb_chunks.tags` + 이미 있는 GIN 인덱스로 결정적으로 된다. 벡터가 필요해지는 것은 플레이어가 자유롭게 묻는 대화형이 붙을 때다. **[미확정]** 차원을 맞출지(1536으로 잘라 요청) 칸을 바꿀지는 그때 정한다.

원인은 같다. **새 사실을 절 하나로 덧붙이고 그 사실이 무효화한 옛 문장을 안 찾았다.** §28은 정확했고 §5를 안 고쳤을 뿐이다.

> **그리고 같은 실패에 종류가 하나 더 있다** — [§31](#31-詰み-게이지--갈려-있던-것은-결정이-아니라-말이었다-2026-08-11)이 그것이다. 위 넷은 **사실**이 갈렸지만, 게이지 쪽은 두 절이 **같은 낱말(「내」)을 다른 뜻으로** 쓰면서 갈렸다. 이쪽이 더 오래 안 잡힌다 — 문장을 나란히 놓아도 서로 모순으로 안 보이고, 각자 자기 문맥에서는 맞는 말이기 때문이다. **말이 두 뜻으로 쓰이는 것을 발견하면 그 말을 버린다**(「내 것/상대 것」 → 「상대 玉까지의 거리」).

### 그래서 이 문서의 읽는 순서를 바꿨다

§1에 **「지금 실제로 도는 것」 표**를 넣었다. §5(남은 일)보다 먼저 오고, **「무엇이 없나」를 읽기 전에 「무엇이 있나」를 알게 한다** — ②가 정확히 그 실패였다. 「부르는 코드가 없다」를 믿고 이미 있는 것을 다시 만들 뻔했다.

§9~§28은 **손대지 않았다.** 그것들은 「지금 이렇다」가 아니라 **「그때 이렇게 판단했다」**의 기록이라 낡지 않는다 — [07-articles.md §12](07-articles.md)가 기사에 대해 말하는 것과 같은 성질이다. 대신 사실이 뒤집힌 자리에는 취소선과 함께 어느 절이 뒤집었는지를 적었다.

> **`[미확정]` 은 지울 때 지워야 한다.** ③이 그 예다 — 코드가 값을 정하면서 주석에는 근거까지 적었는데, 설계 문서의 `[미확정]` 은 그대로 남았다. 이 표시는 **모르는 것의 목록**이라, 아는 것이 섞이면 목록 전체가 안 믿긴다.

## 30. 판에 이름이 붙는다 — 좌표에서, 해설문에서가 아니라 (2026-08-11)

`internal/tag`. §5의 1순위였던 「囲い·전법 태그 + `kb_chunks`」다.

**이 제품이 아는 쇼기가 룰과 엔진 평가치뿐이던 자리**에 이름이 들어왔다. 美濃囲い인지, 四間飛車인지를 판이 알고, 그 이름에 해설이 붙어 있다.

### 정의를 좌표 집합으로 두면 2차 자료가 필요 없다

[04-llm.md §4](04-llm.md)가 적어둔 방식 그대로다. 囲い를 「이렇게 두면 美濃다」라는 서술이 아니라 **필수 칸의 집합**으로 두면, 판정이 룰 엔진 조회 몇 번이 되고 저작권도 신뢰성도 걸리지 않는다.

```go
{2, 8, King}, {3, 8, Silver}, {4, 8, Gold}, {5, 8, Gold}   // 本美濃囲い
```

**그런데 좌표 자체는 지어낼 수 없다.** 囲い 이름은 화면에 그대로 나가는 단언이고, 틀리면 판이 규칙을 틀리게 가르친다 — §22와 같은 실패다. 그래서 칸마다 **일본어 위키백과 본문의 배치 서술**을 읽고 옮겼고, 출처 URL을 정의 표에 달았다. `TestCastlesCarryTheirSource` 가 그것이 비면 실패한다.

### 後手를 두 벌 적지 않는다

180° 회전으로 파생시킨다 — `(筋, 段) → (10-筋, 10-段)`.

두 벌로 적으면 한쪽만 고치는 버그가 나고, **그 버그는 에러를 내지 않는다.** 後手 국면에서 태그가 조용히 안 뜨는 것으로만 보인다.

### 「플레이어 쪽만」을 지키는 테스트가 처음엔 아무것도 안 봤다

제일 값비싼 발견이다. 스냅샷에 **플레이어 쪽 태그만** 실어야 하는데(01-core.md §7 — 상대의 계획을 알려주지 않는다), 그것을 재는 테스트를 이렇게 적었다.

```
국면       양쪽 다 本美濃
기대       사람이 先手면 hon_mino, 後手면 hon_mino
```

**`HumanColor` 를 `shogi.Black` 으로 박아도 통과했다.** 양쪽의 답이 같아서 어느 색을 재는지 구별할 수 없었다.

양쪽을 **다른** 囲い로 바꿨다 — 先手 本美濃, 後手 金矢倉. 그러면 색을 잘못 넘기는 순간 後手 케이스만 실패한다. 확인했다.

> 테스트가 초록인 것과 무언가를 재고 있는 것은 다르다. **「고쳐 보면 그것만 실패한다」를 실제로 해 봐야** 그 둘이 갈린다(§26·§27과 같은 자리).

### 居飛車를 뺐다 — 정의가 初期配置와 같다

飛が2八のまま가 居飛車의 정의인데, 2八은 平手の初期配置다. 넣으면 **첫 수를 두기도 전에 「居飛車」가 뜬다** — 플레이어가 아직 하지 않은 선택에 이름을 붙이는 것이다.

振り飛車 넷(中·四間·三間·向かい)은 전부 飛를 실제로 옮겨야 성립하므로 이 문제가 없다. `TestStartPositionHasNoTags` 가 이 결정을 지킨다.

우리는 囲い 9 · 전법 4다. [04-llm.md §4](04-llm.md)의 신뢰 계층 3이 「将棋ウォーズ의 태그명은 **이름만** 참고한다」고 허용한 그대로, 이름 목록만 조사해 옮긴다.

넓히는 데 걸리는 것이 둘이고, **둘 다 이름 수집이 아니라 좌표 확인이다.**

| 막힌 것        | 무엇                                                                                                                                                                       |
| -------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| ~~**穴熊**~~   | 위키백과 본문에 배치 서술이 없어 한 번 보류했는데, **계층을 바꿔 넣었다** — 신뢰 계층 1(자체 엔진 재검증)이다. 아래 참조                                                   |
| **전법 107종** | 대부분 **좌표로 정의되지 않는다.** 棒銀·藤井システム·早石田은 수순이고, 좌표로 흉내내면 「이 배치면 棒銀」이라는 틀린 것을 가르친다. 그래서 飛의 筋으로 되는 일곱만 넣었다 |

### 전법 106종을 실제로 훑어봤다 — 대부분이 수순이다

숫자만 인용하고 목록을 안 봤던 자리라 이름을 전부 확인했다. **좌표로 안 되는 것이 압도적이다.**

```
수순으로 정의되는 것   藤井システム · 早石田 · 鬼殺し · 棒銀 · ゴキゲン中飛車 · 塚田スペシャル
                       雀刺し · 森下システム · カニカニ銀 · 丸山ワクチン · 超速 …
筋 하나로 되는 것      中飛車(5) · 四間飛車(6) · 三間飛車(7) · 向かい飛車(8) · 袖飛車(3) · 右四間飛車(4)
```

즉 **좌표로 표현할 수 있는 전법은 애초에 여섯쯤**이고, 106 중 100은 「이 배치면 그 전법」이라고 말할 수 없다. 106분의 4가 부끄러운 것처럼 보이지만 **분모가 잘못된 비교였다.**

### 목록을 보다가 지금 구현이 좁은 것을 찾았다

袖飛車와 右四間飛車를 넣으려고 정의를 읽었더니 둘 다 **段이 아니라 筋으로** 적혀 있었다.

```
袖飛車      「先手ならば飛車を3筋に、後手ならば飛車を7筋に振る」
            ▲3八飛 에서 ▲3五飛 까지 段은 움직인다 — 筋만 3이면 袖飛車다
右四間飛車  「先手ならば飛車を4筋に」
```

**우리 정의는 八段에 고정이다**(`{6, 8, Rook}`). 그러면 四間飛車를 짜고 飛를 6五로 올린 순간 이름이 사라진다 — 전법은 그대로인데 라벨만 꺼진다. 지금 잡고 있는 것은 전법이 아니라 **전법을 짜는 순간**이다.

그래서 **袖飛車·右四間飛車를 넣지 않았다.** 3八·4八로 적으면 출처가 筋이라고 말한 것을 段으로 좁혀 적는 것이고, 그건 좌표를 지어내는 것과 같은 종류의 거짓이다.

고치는 방향은 「飛가 그 筋에 있는가」인데 **느슨하게 하면 다른 거짓이 생긴다** — 종반에 飛가 우연히 6筋을 지나가는 국면까지 四間飛車라고 부른다. 그래서 이것은 **실측으로 정할 문제**다: 기록된 대국(§18)에서 筋 기준과 段 고정 기준이 각각 몇 수 동안 켜지는지를 세면 답이 나온다. **[미확정]**

### 배치 서술이 없으면 **둬 보면 된다** — 계층을 바꿨다

穴熊에서 막혀 있던 자리다. 위키백과 본문에 배치 서술이 없고 그림밖에 없는데, 그림을 읽히니 좌표가 깨져 나왔다. 그래서 「다른 출처가 필요하다」로 남겼는데, **출처의 계층을 바꾸는 것이 답이었다.**

[04-llm.md §4](04-llm.md)의 신뢰 계층이 이미 그렇게 적혀 있었다.

```
계층 1  수순·국면   공개 정석 파일·프로 기보    →  자체 엔진으로 재검증
계층 2  용어·개념   위키백과·連盟 공식          →  사람이 읽고 확인
```

**囲い의 좌표는 계층 2가 아니라 계층 1의 것이었다.** 배치는 개념이 아니라 국면이고, 국면은 사람 글로 확인하는 것보다 **엔진으로 확인하는 쪽이 강하다.**

그래서 平手에서 합법수만으로 그 배치까지 실제로 둬 보는 테스트를 붙였다. 좌표가 틀리면 도중에 반칙이 나거나 마지막에 태그가 안 뜬다.

**실제로 좌표를 두 번 고쳐 줬다.** 玉을 7九로 보내려 했는데 거기엔 初形의 銀이 서 있었고, 香를 9八로 올리지 않으면 9九에 들어갈 수 없었다 — 둘 다 사람이 세지 않고 룰 엔진이 반칙으로 잡았다. 「穴」이 왜 穴인지가 그 두 반칙에 그대로 들어 있다.

이 길이 열린 뒤 囲い가 **9종에서 21종**이 됐다. 그리고 병목이 바뀌었다 — 「배치 서술을 찾을 수 있나」에서 **「수순을 만들 수 있나」**로. 후자가 훨씬 넓어서, 위키백과가 특징만 적어둔 美濃 파생형들도 이 길로 들어올 수 있다.

### 이름을 사이드바에 상시 띄웠더니 무엇을 가리키는지 알 수 없었다

**브라우저에서 보고 고친 자리다.** 처음에는 옆 패널에 라벨로 상시 띄웠는데, 실제로 띄워 보니 「中飛車」가 상태 문구 아래에 홀로 떠서 **무엇에 대한 말인지 알 수 없었다** — 棋譜의 소제목처럼도 읽혔다.

이름 옆에 「戦法」 같은 분류를 붙여 고칠 수도 있었지만, 그건 사이드바에 설명을 하나 더 얹는 일이다. **사건으로 만들면 설명이 필요 없어진다** — 짜는 순간 판 가운데에 잠깐 뜨고 사라지면 위치와 타이밍이 그 말을 대신한다. 将棋ウォーズ가 하는 그것이고, [03-frontend.md](03-frontend.md)의 「평시엔 조용하게」와도 맞는다: 지나가면 화면에 아무것도 안 남는다.

**회차를 기억한다.** 囲い는 깨졌다가 다시 짜이므로 코드를 기억하지 않으면 같은 이름이 여러 번 뜬다. 한 대국에서 이름 하나는 한 번이다.

### 길이가 두 벌이면 조용히 안 보인다

애니메이션(CSS)과 언마운트(JS 타이머)의 길이를 각각 2200ms로 적어뒀다. **두 값이 서로 맞아야 하는데 그걸 아무것도 강제하지 않는다.**

실제로 어긋나게 해 보니 이렇게 됐다.

```
JS 타이머  60초   요소가 DOM에 남는다
CSS        2.2초  animation-fill-mode: forwards 가 마지막 프레임(opacity 0)을 붙잡는다
결과            요소는 있고 화면에는 없다 — 에러도 안 난다
```

그래서 **타이머를 없앴다.** `onAnimationEnd` 로 지우면 길이의 주인이 CSS 하나가 된다. 브라우저를 안 띄웠으면 이 결합을 못 봤을 것이고, 나중에 애니메이션 길이만 고치는 날 라벨이 조용히 사라졌을 것이다.

> 이 절이 §14·§22와 같은 자리다 — **화면은 눈으로 재야 한다.** 저기서는 자를 대고 세 번 고쳤고, 여기서는 스냅샷까지 왔다는 테스트가 초록인데 화면이 전달하지 못했다.

### 棋譜가 매 수 페이지를 아래로 끌어당기고 있었다 — 태그와 무관한 버그를 같이 잡았다

화면을 띄운 김에 좁은 화면을 눌러 보다 나왔다. **수를 둘수록 판이 화면 위로 밀려 올라간다.**

원인이 「목록이 자란다」가 아니었다 — 상한(`max-height`)은 이미 있었다.

```
scrollIntoView({ block: 'nearest' })
  목적이 「이 요소가 보이게」라 **가장 가까운 스크롤 가능한 조상**을 움직인다
  목록이 아직 넘치지 않으면 그 조상이 페이지다
  좁은 화면에서 棋譜는 판 아래 화면 밖 → 매 수마다 페이지가 끌려간다
```

**넓은 화면에서는 안 나온다.** 棋譜가 판 옆에 있어 이미 보이므로 아무 일도 안 일어난다 — 데스크톱만 보고 있으면 영원히 못 만나는 버그다.

목록의 `scrollTop` 을 직접 움직이면 페이지를 안 건드린다. 그리고 좁은 화면에서는 높이를 **고정**했다 — 상한만 두면 0에서 상한까지 자라며 `投了` 와 페이지 길이가 매 수 흔들린다.

되돌려서 재보고 확인했다.

| 수   | `scrollY` 전 | 후  | 페이지 높이 전 | 후  |
| ---- | ------------ | --- | -------------- | --- |
| 시작 | 0            | 0   | 817            | 817 |
| 2수  | 54           | 0   | 931            | 975 |
| 5수  | **233**      | 0   | 1111           | 975 |

그 시점 판의 위치가 `top: -107` 이었다 — **판 윗부분이 화면 밖**이다. 고친 뒤 `126`.

### 코퍼스는 **뜨는 태그에만** 붙였다

[04-llm.md §4](04-llm.md)가 「50항목」이라고 적었는데 **47항목**이다. 숫자가 비슷해진 것은 우연이고, **범위를 태그에 맞춘 결과**다 — 뜨는 태그 39개 + 블런더 카테고리 8개다.

手筋 15~20항목이 빠진 이유가 같은 문서 안에 이미 있다 — 「코퍼스를 먼저 만들어도 붙일 곳이 없다」. 手筋에는 감지기가 없어서 **꺼내올 검색 키가 없다.** 넣으면 검색에 안 걸리는 행이 20개 쌓인다.

`source_url` 이 `NOT NULL` 인 것을 두 갈래로 채웠다.

|                  |                                                                                               |
| ---------------- | --------------------------------------------------------------------------------------------- |
| `CC-BY-SA-4.0`   | 囲い 9항목. 배치 서술을 위키백과에서 읽고 옮겼으므로 저작자 표시가 필요하다                   |
| `engine-derived` | 전법·블런더 카테고리 12항목. 정의가 우리 코드 안에 있다 — 남의 글이 아니라 그 파일을 가리킨다 |

**이것이 §8의 「RAG 코퍼스 출처」를 절반 닫는다.** 위키백과 인용 범위는 「배치 서술만, 항목마다 URL을 박고」로 정해졌다. 정석 파일 선정은 **아직 열려 있다** — 정석 오프닝 랜덤이 그것을 요구하고, 이번 작업은 안 건드렸다.

### 초안에 키릴 문자가 두 군데 섞여 있었다

일본어 본문을 쓰다가 `серьез攻め`·`серьез読み`가 들어갔고, 제목 하나에는 영어(`naked`)가 남았다. **일본어 사이에 낀 한두 글자는 사람 눈으로 그냥 안 보인다.**

`TestCorpusIsJapaneseOnly` 가 한글과 키릴을 함께 본다. 그리고 **DB 테스트로 두지 않았다** — `SHOWGI_TEST_DATABASE_URL` 이 없으면 조용히 skip 되고 초록으로 보이는데(CLAUDE.md), 코퍼스에 다른 언어가 섞이는 것은 화면과 프롬프트로 그대로 새면서 에러가 안 나는 종류다. 그래서 **마이그레이션 파일을 텍스트로 읽는다.**

### 실물로 확인한 것

| 무엇           | 결과                                                                    |
| -------------- | ----------------------------------------------------------------------- |
| 마이그레이션   | 로컬 Postgres에 `ON_ERROR_STOP=1` 로 적용해 exit 0. **21행**            |
| 멱등성         | 두 번 돌려도 21행 (앞에 `DELETE` 를 둔다 — 사람이 손으로 돌린다)        |
| 한글           | `body ~ '[가-힣]'` 이 0행                                               |
| `verified_by`  | 21/21 이 `'engine'`. 비면 검색에 걸려도 프롬프트에 안 붙는다            |
| 좌표 ↔ 룰 엔진 | 손으로 적은 SFEN 하나로 끝까지 확인 (`TestDetectsFromAHandWrittenSFEN`) |

마지막 것이 없으면 앞의 테스트들이 전부 `squareFor` 로 판을 만들어 재므로, **그 함수가 통째로 틀려도 자기 일관성만으로 다 통과한다.**

### 남은 것

- **화면을 브라우저에서 안 봤다.** 라벨이 뜨는 것은 테스트가 스냅샷까지만 확인했고, 좁은 화면에서의 줄바꿈과 明朝 대비는 눈으로 재야 한다
- 태그를 **`edges.tags` 에 적는 쪽이 없다.** 「정석 이탈」 카테고리가 그 칸을 요구한다
- 태그를 **설명 프롬프트에 붙이는 쪽이 없다.** `kb_chunks` 조회 질의와 `explain.Facts.used()` 갱신이 남았다 — 이번에는 코퍼스를 넣는 데까지다

## 31. 詰み 게이지 — 갈려 있던 것은 결정이 아니라 말이었다 (2026-08-11)

**판정은 §29 ②부터 돌고 있었고, 남은 것은 화면이었다.** 그런데 만들기 전에 닫아야 할 것이 하나 있었다 — 「몇 쪽을 그리나」가 §8에 열려 있었고, 두 문서가 서로 다른 답을 적어 두고 있었다.

### 갈린 이유

[01-core.md §7](01-core.md)은 「**내 詰み만**」, [§21 ③](#21-플레이-테스트에서-나온-셋-2026-08-10)은 「**양쪽 다**」였다. 대조하면 모순인데, 실제로는 **같은 「내」를 서로 다르게 읽고 있었다.**

|                     | 「내」가 무엇이었나                     |
| ------------------- | --------------------------------------- |
| §7의 「내 詰み」    | **내가 거는 詰み** = 상대 玉까지의 거리 |
| §21 ③이 더하자던 것 | **내 玉이 詰まされる 쪽**               |

§7 안에 이미 「테두리에 불이 붙으면 **언제나 「내가 가까워졌다」는 뜻**」이 적혀 있었는데, 절 이름이 「내 것만」이라 반대로 읽혔다. **[§29](#29-문서가-코드와-갈려-있던-자리-2026-08-11)가 말하는 그 종류의 갈림이고, 이번에는 사실이 아니라 대명사에서 났다.**

그래서 **말을 바꿨다.** 「내 것 / 상대 것」은 두 번 갈렸으므로 문서에서 쓰지 않는다 — **「상대 玉까지의 詰み 거리」**로 적는다.

### 정한 것 — 상대 玉 쪽 하나만

요청자가 근거를 그 자리에서 정리했다: **내 玉이 詰まされる 것은 개입이 이미 막는다.** 詰まされる 수를 두면 승률 낙폭이 멀쩡히 움직여 §2의 제지형이 그 수를 물리므로, 게이지로 한 번 더 그릴 이유가 없다.

「양쪽 다」의 목적(§21 ③의 「공격할 때인가 수비할 때인가에 **단언 없이** 답한다」)은 여전히 유효하지만, **그 답이 한 표면에 안 실린다.** 같은 테두리에 둘을 그리면 불이 붙었을 때 이기는 중인지 지는 중인지가 정반대로 읽힌다. 그 일은 다른 장치를 기다린다.

### 판정의 詰み을 게이지로 돌려쓸 수 없다

§21 ③이 「이미 구해진 거리를 스냅샷에 실으면 된다」고 적어뒀는데 **그 줄이 틀렸다.**

```
사람의 수 직후   Judge → SearchMate(착수 前 국면)   ← 판정용. 게이지에는 한 수 낡았다
상대의 수 직후   게이지 → SearchMate(지금 국면)      ← 사람 차례의 현재 국면
```

같은 질문이지만 **한 수 늦게 묻는다.** 그래서 세션이 따로 부른다 — 매 수 solver 호출이 **한 번에서 두 번**이 됐다. 대신 두 자리가 시간상 겹치지 않아(하나는 사람의 수 직후, 하나는 상대의 수 직후) **풀은 그대로 1개**다.

`maybeGauge` 가 `maybeThink` 와 **정확히 반대 조건**(사람 차례 / 엔진 차례)인 것이 그 보장이다. 둘을 같은 자리마다 나란히 부르므로 한쪽을 빠뜨리기도 어렵다.

### 「수번 측의 詰み」이 곧 상대 玉까지의 거리다

solver는 `go mate` 를 받은 국면의 **수번 측**이 詰ますことができるか를 답한다. 사람 차례에 물으면 그것이 정확히 「내가 상대 玉을 몇 手로 詰ますか」다 — **그리기로 한 쪽이 공짜로 나온다.**

거꾸로, 상대 차례에 물으면 그리지 않기로 한 쪽이 나온다. 그래서 `maybeGauge` 는 사람 차례에서만 묻고, **그 전제를 실 solver로 확인했다**(`TestMateGaugeAgainstRealMateEngine`). 가짜로는 안 잡히는 자리다 — 전제가 뒤집혀 있으면 게이지는 내 玉이 위험할 때 켜지는, 정확히 반대의 물건이 된다.

손으로 만든 1手詰 국면(`mateInOneSFEN`)이 **정말 1手詰인지**를 엔진 없이 먼저 못박아 둔다. 없으면 게이지가 안 켜졌을 때 배선이 틀린 건지 국면이 틀린 건지를 못 가른다 — 囲い 좌표를 룰 엔진으로 재검증하는 것과 같은 자리다([09-tags.md §1](09-tags.md)). **실제로 그 확인이 국면을 한 번 고쳐 줬다**: 처음에 5筋의 香로 金을 받쳤는데 그 香가 玉에게도 닿아 「先手 차례인데 後手가 이미 王手를 받는」 국면이었다.

### 手数는 화면에 안 나간다 — 서버가 세기로 자른다

게이지는 「수순도 手数도 알려주지 않는다」인데, 페이로드에 手数가 있으면 **그리지 않아도 이미 알려준 것**이다. 그래서 서버가 `mateHeat` 1~5로 잘라서 보낸다 — 갇힘 힌트의 단계를 서버가 자르는 것과 같은 자리다([§23](#23-갇힘--판정을-느슨하게-하는-대신-찾는-것을-돕는다-2026-08-10)).

구간은 §7의 「11→7→5→3→1」이 그대로다. `DepthLimit=11` 이라 手数는 홀수 1·3·5·7·9·11 중 하나로만 오지만, 그 한계가 환경변수라 더 큰 값에도 답이 있게 둔다.

### 낡은 불꽃을 남기지 않는 법

국면이 움직이면 그 세기는 그 자리에서 무효다. 지우는 코드를 착수·롤백·종료에 흩어 두는 대신, **스냅샷이 `mateGen == searchGen` 을 대조**한다 — 세 곳 중 하나를 빠뜨리면 낡은 불꽃이 새 국면에 남고, 그건 「지금 판 위의 사실」이 아니게 된다. `StyleTags` 를 매번 다시 세는 것과 같은 판단이다.

**회상 중에도 끈다.** 그때 판은 물러진 수의 국면이라, 지금 국면의 게이지를 거기 얹으면 그 순간 거짓말이 된다.

### 화면에서 잰 것

브라우저에서 세기 1·3·5를 눈으로 재고 값을 한 번 고쳤다.

- **세기를 알파와 번짐 두 축으로 나눈다.** 하나만 키우면 다섯 단계가 한 축에 몰려 3과 4가 안 갈린다
- **안쪽 그림자를 얕게 내렸다.** 세기 5에서 판 가장자리 칸이 보라로 물들었는데, **테두리가 판과 다른 표면이라는 것이 여기서 색을 쓰는 근거**라([01-core.md §7](01-core.md)) 색이 판 안으로 번지면 그 근거가 사라진다
- `prefers-reduced-motion` 에서는 흔들림을 지우고 세기만 남긴다 — 흔들림은 분위기이지 정보가 아니다

### 남은 것

- **詰み 국면을 브라우저에서 못 봤다.** 서버가 平手에서만 시작해서, 실제로 불이 붙는 장면은 한 판을 끝까지 둬야 나온다. 불꽃 자체는 세기를 넣어 눈으로 쟀고, 엔진까지의 배선은 실 solver 테스트가 덮는다
- **레벨별 표시 상한이 그대로다.** §11의 `[미확정]`(판정 手数)과 같은 자리인데, 게이지는 지금 레벨을 안 본다 — 8급에게 11手詰의 불꽃을 보여주는 것이 맞는지는 안 쟀다

## 32. 병렬로 나눠 일한다 — 갈리는 것은 api 하나뿐이었다 (2026-08-11)

마감이 **8/15 15:00**인데 §5의 남은 일이 한 줄로 처리하기엔 많다. 그래서 워크트리를 나눠 세션을 여러 개 열고 각자 PR을 내는 쪽으로 바꿨다. `/worktree` 스킬이 그 판을 깐다.

**이 결정이 옛 규칙 하나를 무효로 만들었다.** CLAUDE.md의 「작업 브랜치를 여러 개 만들지 않는다」는 근거가 *「아직 머지되지 않은 `.gitignore`가 다른 브랜치에 없어서 `git add -A`가 무시돼야 할 파일을 커밋한다」*였다. 그 근거는 **한 워크트리에서 브랜치만 갈아탈 때**의 것이고, 워크트리는 각자 `origin/main`에서 분기하므로 해당하지 않는다. 문장을 지우지 않고 조건을 붙여 남겼다 — 근거가 아직 살아 있기 때문이다.

### 실제로 부딪히는 것은 넷이었고, 셋은 이미 공유였다

띄워 보고 잰 것이다.

|                  |                                                                                                                                                     |
| ---------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| 엔진 빌드        | **다시 안 돈다.** Dockerfile이 같으면 やねうら王 컴파일 스테이지의 레이어 캐시가 맞는다. 다시 도는 것은 Go 빌드뿐 — 워크트리 하나 세우는 데 **9초** |
| `pnpm install`   | **1.1초.** store가 공유이고 하드링크로 깔린다                                                                                                       |
| Go 모듈 캐시     | 공유. `go test`가 셋업 없이 바로 돈다                                                                                                               |
| **api 컨테이너** | 여기만 갈린다. 이름과 포트가 `docker-compose.yml`에 하드코딩돼 있었다                                                                               |

### db를 왜 안 나눴나

**엔진이 arm64 Debian 바이너리라 macOS에서 직접 못 돈다** — `go run ./cmd/api`로는 대국이 안 되므로 api는 무조건 컨테이너다. 그런데 db까지 워크트리마다 띄우면 마이그레이션을 새 워크트리마다 전량 재적용해야 하고, 문서·스킬에 적힌 `docker exec -i show-gi-db psql ... -d showgi`가 워크트리마다 달라진다.

그래서 **db 컨테이너 하나와 데이터베이스 `showgi`를 전부가 같이 쓴다.** 값은 그 대신 제약 하나다 — **되돌릴 수 없는 마이그레이션(`DROP`·`RENAME`·`NOT NULL` 추가)을 병렬로 돌리지 않는다.** 컬럼·테이블 추가는 다른 워크트리의 서버가 모른 채 그냥 돌지만, 저 셋은 남의 서버를 그 자리에서 깨뜨린다.

### 컨테이너명으로 붙는다, 서비스명이 아니라

`DATABASE_URL`이 `@db:5432`였는데 **서비스명은 같은 compose 프로젝트 안에서만 풀린다.** 워크트리의 api는 다른 프로젝트라 메인이 띄운 db를 못 찾는다. `@show-gi-db:5432`로 바꿨다 — 컨테이너명은 네트워크 전체에서 풀린다. 다른 프로젝트에서 실제로 붙는 것을 확인하고 넣었다.

네트워크 이름도 고정했다(`show-gi-net`). 기본값이 `<디렉터리명>_default`라 워크트리마다 갈리고, 그러면 api와 db가 다른 네트워크에 떨어져 이름이 안 풀린다.

> 워크트리에서 `a network with name show-gi-net exists but was not created for project ...` 경고가 뜬다. 네트워크를 메인이 만들고 워크트리가 얹는 구조라 나오는 것이고 붙는 데는 지장이 없다. `external: true`로 지울 수 있지만 그러면 **메인이 맨 처음 뜰 때 네트워크가 없어 실패**한다 — 경고 한 줄이 그것보다 싸다.

### db 이름은 일부러 안 갈랐다

api는 `${SHOWGI_API_NAME}`으로 갈리는데 db의 `container_name: show-gi-db`는 고정으로 뒀다. 갈랐다면 워크트리에서 `--no-deps`를 빠뜨렸을 때 **두 번째 postgres가 자기 볼륨을 들고 조용히 뜬다** — 같은 스키마를 본다고 믿는 두 서버가 서로 다른 데이터를 보게 된다. 고정해 두면 컨테이너명 충돌로 그 자리에서 실패한다. **시끄럽게 실패하는 쪽을 골랐다.**

### 나누는 기준은 주제가 아니라 파일이다

주제가 달라도 같은 파일을 고치면 나눈 것이 아니고, 나중에 머지되는 PR이 리베이스에 시간을 다 쓴다 — 병렬로 번 것보다 크다. 이 레포에서 잘 겹치는 자리는 `internal/game/session.go`(세션이 상태를 소유해서 거의 모든 기능이 지난다), `apps/web/src/components/GameScreen.tsx`, 그리고 이 문서다.

그래서 스킬은 **분담안을 내기 전에 기존 워크트리의 `git status`(커밋 안 된 것)와 열린 PR의 파일 목록까지 걷어 「점유된 파일 집합」을 만든다.** `git diff origin/main...HEAD`만 보면 아직 커밋 안 한 작업이 통째로 안 보인다.

### 남은 것

- **문서 절 번호 충돌은 못 막았다.** 두 워크트리가 이 문서에 절을 붙이면 §33이 둘 생긴다. 스킬이 미리 번호를 배정해 주는 것으로 갈음했고, 자동으로 막히지는 않는다
- **워크트리 몇 개까지가 실익인지 안 쟀다.** 기본을 2~3으로 뒀지만 api 컨테이너가 각자 엔진 프로세스를 물고 있어 상한은 머신이 정한다

## 33. 리뷰 화면 — 기록은 쌓이고 있었고, 없던 것은 꺼내는 쪽이었다 (2026-08-11)

**D6에서 제일 큰 조각을 붙였다.** 대국이 끝난 뒤 그 판을 手数마다 되짚고, 어디서 몇 번 막혔는지가 보이고, **물러진 수를 그 국면 위에 다시 그린다.**

`/api/games` · `/api/games/{id}` 둘이 생겼다. **이 레포에서 `/api` 아래에 무언가가 생긴 것은 처음이다** — 그전까지 라우트는 `GET /healthz`와 `GET /ws/game` 둘뿐이었다.

### 없던 것은 데이터가 아니었다

`games`·`game_moves`·`interventions`에는 §18·§26 이후로 계속 기록이 쌓이고 있었다. **읽는 코드가 하나도 없었을 뿐이다** — `internal/store/query/games.sql`의 질의가 전부 쓰기와 `Count*`뿐이었다. 그래서 이 작업은 「기능을 만드는 일」이 아니라 **이미 있는 것을 꺼내 오는 일**이었고, 스키마를 한 줄도 안 고쳤다(마이그레이션 없음 — 공유 DB에서 병렬로 일하는 동안 이게 값이다, §32).

### 기보만으로는 판을 못 그린다

DB에 있는 것은 USI 문자열뿐이다. 그것만으로는 **판을 그릴 수도(국면이 없다) 읽을 수도(棋譜 표기가 없다) 없다.**

그래서 서버가 한 판을 **처음부터 다시 둔다.** `start_sfen`에서 시작해 手数마다 `MoveJa`로 표기를 만들고 `Apply`로 국면을 밀며, 王手가 걸린 玉의 칸까지 같이 붙인다. 화면은 그 SFEN을 그대로 그린다.

**클라이언트가 두게 하지 않는 것이 요점이다.** 그쪽이 편해 보이지만 룰 엔진을 한 벌 더 갖는 것이고, 어긋났을 때 어느 쪽이 맞는지 알 수 없다 — D2에서 「화면은 규칙을 모른다」로 정해 둔 그 자리이고, 반박 수순이 `sfen`을 실어 보내는 이유와 같다.

### 기록은 깨질 수 있고, 깨진 자리에서 멈춘다

`dbRecorder`는 큐가 차면 이벤트를 **버린다**(대국이 본체이므로). 그러면 手数에 구멍이 난 기보가 남는다.

구멍을 무시하고 이어 두면 **없던 국면을 그린다** — 3手目를 2手目 자리에 두는 셈이라 그 뒤가 전부 거짓이 된다. 그래서 `ply != i+1`이거나 수가 합법이 아니면 **거기서 재현을 멈추고**, 그 뒤의 手数는 표기도 국면도 없이 나간다. 수 자체는 목록에서 빼지 않는다 — **둔 것은 둔 것이고, 판을 못 그릴 뿐이다.**

실측: 109手 대국에서 재현이 끊긴 자리가 0이었고, 개입 24건의 물러진 수에도 전부 표기가 붙었다.

### 물러진 수는 기보에 없다 — 그래서 한 수 앞에서 그린다

`interventions.ply`는 **물러진 수의 手数**인데 그 수는 확정되지 않았으므로 `game_moves`에 없다. 그 국면을 보려면 **`ply - 1` 手目의 판**을 그려야 한다. 개입을 고르면 화면이 거기로 가서 판을 낮추고(회상), 물러진 수를 초록 화살표와 흰빛 두 칸으로 긋는다.

**대국 중의 회상과 같은 장치를 쓴다** — 같은 판이 두 화면에서 다른 모양이면 어느 쪽이 진짜인지 헷갈린다. `Board`·`Hand`·`Koma`를 props 하나 안 고치고 그대로 썼다(board-three가 그 파일 안을 갈아엎는 중이라 시그니처를 건드리면 양쪽이 깨진다).

> **打은 화살표가 안 나간다.** 판 위에 출발 칸이 없어 駒台에서 자리를 재야 하는데(§20) 그 측정은 대국 화면 쪽 장치다. 두 칸 표식이 도착점을 짚으므로 「어디에 놓으려 했나」는 남는다.

### 문구는 다시 만든다, 지어내지 않고

**그때 화면에 나갔던 문장은 어디에도 저장되지 않는다** — 남는 것은 카테고리뿐이다(LLM이 썼든 아니든). 그래서 리뷰는 문장을 다시 만들어야 하는데, 새로 짓지 않고 `explain.Render`가 **사실 없이 낼 때와 같은 문장**(`BaseMessage`)을 쓴다. 두 벌이 되면 같은 수가 대국 중과 리뷰에서 다른 이유로 나쁜 것이 된다.

사실(어느 駒가 몇 장에게 노려지는가)은 그때 국면에서만 구해지는 것이라 기록에 없다. **없는 것을 지어내지 않는 쪽을 골랐다.**

카테고리의 **짧은 이름**(`タダ捨て`·`追う手`)은 새로 필요했다 — 목록 한 줄에 문장이 안 들어간다. `explain.CategoryJa` 하나에 두었고, 화면은 코드(`hangs_piece`)를 일본어로 바꾸지 않는다.

### 평가치는 여기서 뒤집는다

`game_moves.eval_cp`는 **先手 관점**이다(두 판을 나란히 놓기 위한 규약, §26). 리뷰는 「내가 어디서 무너졌나」를 보는 화면이라 **플레이어 관점**으로 뒤집어 내보낸다 — 後手로 둔 판에서 안 뒤집으면 **진 판이 이긴 판으로 보인다.**

`null`을 0으로 채우지 않는다. 평가치는 수보다 늦게 오므로 끊긴 판의 마지막 몇 수는 비어 있고, **0은 호각이라는 다른 사실이다.**

### 한 수도 안 둔 판은 목록에 없다

ws 핸들러는 연결이 붙는 즉시 `CreateGame`한다. 그래서 탭만 열었다 닫은 판이 그대로 남는데, 개발 DB에서 그런 줄이 스무 개 넘게 목록 위쪽을 차지했다. **되짚을 것이 없는 줄이 진짜 대국을 아래로 민다.** 질의에서 `EXISTS (game_moves)`로 거른다 — 세는 쪽과 거르는 쪽이 같은 조건이라 둘이 어긋나지 않는다.

정렬은 `id` 하나로 한다. `started_at`은 `now()`라 같은 초에 여러 판이 들어가면 순서가 흔들린다.

### 대국 화면은 감추기만 한다

탭을 옮길 때 `GameScreen`을 내리면 **WebSocket이 끊기고 그 판이 `abandoned`로 닫힌다.** 두던 판을 두고 지난 판을 보러 갔다가 돌아오면 판이 사라져 있는 것이 된다. 그래서 대국 쪽은 `hidden`으로 감추기만 하고, 리뷰 쪽만 열 때마다 새로 붙는다(방금 끝난 판이 목록 맨 위에 있어야 한다).

### 곁다리로 잡은 것 — `max(id)`로 자기 대국을 찾던 테스트

`recorder_test.go`가 「방금 연 대국」을 `SELECT max(id) FROM games`로 찾고 있었다. **DB는 워크트리끼리 공유이고**(§32) `go test ./...`는 패키지마다 다른 프로세스를 **동시에** 돌린다 — 이번에 `internal/store`에 대국을 만드는 테스트를 더했더니 그쪽 판을 집어 와서, result가 영영 안 찍히는 것을 10초 기다리다 죽었다.

`id > before` **와 시작 국면**으로 함께 거르게 고쳤다. 세션은 평수 초기 국면을 `shogi.StartSFEN` 그대로 적고 다른 패키지의 테스트는 자기 이름을 적으므로 그 자리에서 갈린다.

### 남은 것

- **[03-frontend.md §3](03-frontend.md)의 「네 방향 분기」는 아직 없다.** 지금은 한 줄(실제로 둔 수순)을 앞뒤로 넘기는 데까지다 — 분기로 들어가려면 노드마다 엔진 탐색이 필요하고, 그건 「가정 수순을 직접 둬 보기」와 같은 장치다(§21 ②)
- **이동 애니메이션이 없다.** 판이 SFEN으로 통째로 바뀐다. 같은 문서가 「말이 갑자기 바뀌면 초심자는 무엇이 변했는지 못 본다」고 적어 둔 자리다
- **평가치 스파크라인이 없다.** 숫자로만 나온다. 원본(`eval_by_depth`)은 아직 대국 루프가 안 쓴다(§12)
- 목록이 최근 20판이다. 커서는 안 만들었다 — 「방금 둔 판」을 보러 오는 화면이라 깊은 페이지네이션이 필요해지면 그때 판다
- **누구의 판인지를 안 본다.** 지금은 대국이 전부 익명이라(`games.user_id` NULL) 가릴 주인이 없지만, **Google 로그인이 붙는 순간 이 자리가 위협이 된다** — `user_id` 가 채워지기 시작하면 남의 기보와 「그 사람이 어디서 막혔나」가 그대로 열린다([02-architecture.md §7](02-architecture.md) 위협 2와 같은 자리다). 로그인을 붙이는 PR이 **같이** 목록을 세션의 user_id 로 거르고 상세를 소유자 아닌 요청에 404로 닫아야 한다

## 34. 이름은 룰이, 이득은 엔진이 — 그리고 실측이 셋을 뒤집었다 (2026-08-11)

[09-tags.md §5](09-tags.md)가 「다음 PR」로 못박아 둔 것을 넣었다. `internal/tag` 은 **형태와 이름**만 내고, 「그래서 得인가」는 `internal/game/tesuji.go` 의 게이트가 개입 판정이 이미 구해 온 평가치로 답한다. **추가 탐색이 없다** — 매 수 도는 `Analyst.Judge` 의 두 값을 그대로 쓴다.

지운 것은 `forkSurvives` 다. 상대가 그 駒를 딸 수 있나 → 되딸 수 있나를 값 표로 비교하던 **손으로 쓴 1수 읽기**이고, 桂로 金 둘을 노렸지만 그 桂가 歩에 잡히는 자리였던 국면을 통과시킨 자리다.

### 자리를 나누니 테스트가 갈렸다

| 층              | 무엇을 정하나          | 어떻게 재나                                               |
| --------------- | ---------------------- | --------------------------------------------------------- |
| `tag`           | 형태와 이름            | 엔진 없이 돈다. SFEN 하나와 칸 하나                       |
| `game` (게이트) | 이득인가               | 평가치 둘을 손으로 만들어 넣는다. 여기도 엔진이 필요 없다 |
| `game` (실엔진) | **둘이 실제로 갈리나** | `SHOWGI_USI_CMD` 가 있을 때만. 이 PR의 첫 관문이었다      |

`intervene` 이 엔진을 모르는 것과 같은 구조다. **판정을 붙였는데 테스트가 조용히 skip 되는 경로가 안 생겼다**는 것이 이 나눔의 실제 값이다.

### ① 인공 국면의 평가치는 못 쓴다

처음에 판을 몇 개만 놓고 「桂가 살아 있는 両取り」를 만들어 쟀다. **엔진의 최선수가 그 수인데도 낙폭이 +620cp로 나왔다.** 玉 둘과 駒 넷뿐인 국면은 NNUE가 본 적 없는 판이고, 거기서 나온 cp로 임계치를 고르면 임계치가 그 이상함을 흡수한다.

그래서 **게이트를 통과하는 쪽의 테스트는 전부 실전 기보(games.id=84)의 도중 국면으로 옮겼다.** 인공 국면은 「떨어지는 쪽」에만 남겼다 — 桂를 歩에 그냥 주는 국면은 어느 판에서도 떨어지고, 그것이 이 PR이 되살리면 안 되는 그 국면이다.

### ② 같은 국면·같은 깊이가 같은 값을 주지 않는다

임계치를 고르려고 「엔진 최선수를 그대로 뒀을 때의 낙폭」을 쟀다. 실전 11개 국면에서 **−30 ~ +99cp**였고(한 자리만 +633), 0이 아니다. 그다음 같은 국면을 여러 번 물었더니 이렇게 나왔다.

| 국면 (games.id=84) | 처음 | 같은 프로세스에서 다시 | 다른 국면을 먼저 태운 뒤 |
| ------------------ | ---- | ---------------------- | ------------------------ |
| 27수 `▲5五角`      | +48  | +31                    | −16                      |
| 79수 `▲2二飛成`    | +363 | +427                   | +263                     |
| 85수 `6g6f`        | +179 | +29                    | −16                      |
| 91수 `▲6二成銀`    | +203 | +51                    | −67                      |

**해시가 남기 때문이다.** 깊이로 거는 것이 시간으로 거는 것보다 훨씬 안정적이라는 CLAUDE.md의 근거는 그대로지만, 「같은 국면 = 같은 결과」는 **캐시가 비어 있을 때의 이야기**다. 앞선 탐색이 남긴 치환표가 있으면 같은 depth에서도 값이 ±150cp쯤 흔들린다.

이것이 곧 **cp 한 값에 좁은 임계치를 거는 판정은 못 만든다**는 뜻이다. 게이트가 견딜 수 있는 이유는 실제로 가르는 두 무리가 멀리 떨어져 있어서다(아래).

### ③ 임계치는 歩 한 장 — `TesujiLossCp = 100`

### ④ 게이트가 실제로 무엇을 껐나 — 실 기보 102수

**꺼진 넷이 전부 던지는 수였다** — `▲2二角成`(+440cp) · `▲2三歩`(+489cp) · `△8三香`(+323cp) · `▲5五角`(4四에서 옮긴 쪽, +267cp). 룰만 있었으면 이 넷에 「角による両取り」「叩きの歩」「田楽刺し」가 떴다.

**남은 둘은 한계선 근처다** — `▲5五角`(打, +24cp) · `▲4四銀打`(+91cp). 흔들림이 ±150cp이므로(②) 판마다 0~4쯤으로 봐야 하고, **한 판에서 2라는 값을 그대로 믿으면 안 된다.**

「서로 다른 이름」이 곧 화면에 뜨는 횟수다 — 클라이언트가 한 대국에 이름 하나를 한 번만 띄운다([§30](#30-판에-이름이-붙는다--좌표에서-해설문에서가-아니라-2026-08-11)의 `useTagAnnounce`). [01-core.md §7.1](01-core.md)의 빈도 상한 초기값 「대국당 3회」와 같은 크기이지만 **다른 것이다** — 저쪽은 착수 前에 알리는 제안형의 상한이고 이쪽은 사후 명명의 실측이다.

### ⑤ 실측이 이름 버그를 둘 잡았다 — 둘 다 **成った 駒**였다

빈도를 재다가 나왔고, 손으로 만든 테스트로는 안 나올 종류였다. 테스트는 銀을 놓고 銀을 물었기 때문이다 — **실전 기보를 통과시키는 것이 다른 질문**이라는 것이 §30의 도달 확인과 같은 이야기다.

|                              |                                                                                                                                                                 |
| ---------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `▲6二成銀` 에 「腹銀」       | `BellySilver` 가 `Base()` 로 물어 **成銀도 銀으로 셌다.** 成銀은 金의 움직임이라 「그 자리가 그 자리인 이유」가 통째로 다르다 — 붙일 이름이 있다면 腹金이다     |
| `▲5二成銀` 에 「割打ちの銀」 | 両取り 쪽도 `Base()` 였다. 같은 표에서 **成桂가 「ふんどしの桂」**를 받는 것도 같은 줄이었다 — 둘 다 金이 되어 「桂가 둘로 뛴다」가 성립하지 않는다             |
| 龍·馬에 「十字飛車」         | 「둘 이상을 노린다」만 봤더니 **龍·馬가 덤으로 얻은 한 칸**으로 만든 형태에 이름이 붙었다. 「十字」는 縦과 横이 교차한다는 뜻이고, 같은 段의 둘도 十字가 아니다 |

**기준은 하나다: 이름이 말하는 성질이 남아 있는가.** 成桂·成銀은 뺀다 — 움직임이 金이 되어 이유가 사라진다. 龍·馬는 든다 — 飛의 縦横과 角의 斜め가 그대로 남아 있다. 대신 **방향을 요구한다**: 덤으로 얻은 한 칸은 그 이름의 방향이 아니다.

이 판에서 방향 조건이 여섯을 껐고 **그 여섯이 전부 龍(2二)과 馬(9九)**였다. `Base()` 조건이 하나를 더 껐다(`▲5二成銀`).

> **`Base()` 를 세 군데서 물었고 세 군데가 다 틀렸다.** 腹銀·桂頭の銀을 고치고 나서 両取り 쪽 표를 안 본 것이 이 절이 길어진 이유다 — 같은 표현을 grep 했으면 한 번에 나왔다.

### ⑥ 게이트로는 `玉の早逃げ` 가 안 열렸다 — 09-tags가 틀렸던 자리

[09-tags.md](09-tags.md)가 「엔진 게이트가 붙으면 된다」고 적어둔 항목이 넷인데, 실제로 들어온 것은 **打 기반 둘**(`叩きの歩`·`垂れ歩`)이다. 그 둘은 판에 안 남는 사실(打った 것인가)이 이름을 정해서 시그니처만 따로 있으면 됐다.

`玉の早逃げ` 는 다르다. 게이트가 거르는 것은 **평가치가 떨어지는 수**인데 玉을 옮기는 수는 囲い를 짜는 수도 안 떨어지므로, 기하를 「玉을 옮겼다」로 두면 **초반의 모든 玉 이동에 이름이 붙고 게이트는 하나도 안 거른다.** 필요한 것은 「위험이 오고 있었다」는 사실이고, 그건 `features.go` 의 `kingPressure` 쪽에 있다. `遠見の角` 도 같은 이유로 남았다.
