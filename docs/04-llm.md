# LLM 계층 — 심사 기준 6번에서 이긴다

## 1. 대원칙

> **LLM에게 판단을 맡기지 않고 표현만 맡긴다.**

학습 앱에서 설명이 틀리면 초심자는 검증할 능력이 없어 틀린 것을 그대로 배운다. 그래서 분석은 **엔진 기반**이고, LLM은 그 분석 결과를 **말로 바꾸는 역할만** 한다. 그러려면 데이터 저장 방식과 쇼기 도메인 조사가 선행되어야 한다 — 그게 [카테고리 온톨로지](01-core.md#3-블런더-카테고리-온톨로지--진짜-승부처)와 [`edges` 스키마](02-architecture.md#4-데이터-모델--그래프-db를-쓰지-않는-이유)다.

**LLM 입력은 항상 구조화 데이터다** — 카테고리, 잡히는 말, 利き 수, Δ승률, 사용자 레벨, 이미 아는 개념. 판을 그대로 던지고 "평가해줘"라고 하지 않는다.

**프롬프트도 출력도 일본어다.** 사용자가 일본인이라 당연하지만, 실무적으로도 그렇다 — 프롬프트에 한글이 섞이면 출력이 한글로 새고, `temperature=0` 캐시 키가 갈라져 [Tier 0](#2-비용-계층)이 안 맞는다. 쇼기 용어는 애초에 일본어가 원전이라 번역 손실도 없다.

**LLM이 하는 일:** 게임 중간중간 "이걸 써먹으면 좋겠다" 싶은 지점에서 코멘트를 준다. 그 판단 자체는 엔진과 [힌트 게이트](01-core.md#7-힌트--남발하지-않기-위한-게이트)가 하고, LLM은 그 사람 수준에 맞는 문장을 만든다.

**부르는 자리가 둘이다** — 개입 문구(수마다)와 **대국 후 총평**(판마다 한 번, [06-status.md §49](06-status.md)). 둘이 같은 캐시·같은 검증·같은 결정적 폴백을 쓴다. 총평 쪽은 **숫자를 프롬프트에 안 넣는다**: 手数와 횟수는 화면의 표가 그리고, LLM에는 등급(`一度だけ`·`数回`·`何度も`)만 준다.

## 2. 비용 계층

```
Tier 0  explain_cache 히트                → 0엔
Tier 1  카테고리 + 레벨 조합 각색          → 소형 모델
Tier 2  이 국면 고유 사정                  → 대형 모델
```

캐시 키 = `hash(kind, category, level_bucket, piece, 국면특징 버킷)`.
`kind`가 키에 들어가는 이유는 제지형과 제안형의 문장이 아예 다르기 때문이다 — 「なぜ悪いか」와 「ここに何かある」를 같은 키로 묶으면 캐시가 엉뚱한 문장을 돌려준다.
**블런더 카테고리는 유한하므로 설명의 대부분은 사전 생성 + 캐싱으로 덮인다.**

### 구현된 것 — `internal/explain` (2026-08-11)

계층 셋이 그대로 코드가 됐다. 구현하면서 정해진 것만 적는다.

| 무엇                      | 정한 것                                                                                                                                                                                                                                                                                                  |
| ------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **입력**                  | `explain.Facts` — 이미 결정된 사실만. 판·SFEN·cp가 이 패키지에 안 들어간다. `intervene` 이 엔진을 모르는 것과 같은 방식이다                                                                                                                                                                              |
| **칸을 안 싣는다**        | 문장이 「その銀」까지만 말한다. 어느 칸인지는 판이 빛으로, 카드가 棋譜(`▲8四銀`)로 이미 말하고 있다. 칸을 키에 넣으면 **81배로 늘어 캐시가 사실상 안 듣는다**                                                                                                                                            |
| **Δ승률을 안 싣는다**     | 카드에 「勝率 −N%」 막대가 따로 있다. 숫자를 프롬프트에 주면 LLM이 문장에 옮겨 적어 **막대와 두 벌**이 되고, 어긋났을 때 어느 쪽이 맞는지 알 수 없다                                                                                                                                                     |
| **카테고리별 허용 목록**  | `Facts.used()` 가 「이 카테고리의 문장이 말해도 되는 사실」만 남기고, **키와 프롬프트와 결정적 문구가 전부 그 함수를 지난다.** 갈라두면 안 쓰는 사실로 캐시가 갈리거나(히트율이 조용히 떨어진다) 프롬프트에만 있는 사실이 문장으로 샌다                                                                  |
| **부르는 자리**           | 판정 goroutine 안, 카드가 뜨기 **전**이다. 나중에 올려 보내 갈아끼우면 플레이어가 읽는 도중에 글자가 바뀐다. 대신 시한(**5초**, §3)을 걸고 넘기면 결정적 문구로 간다                                                                                                                                     |
| **통과한 수는 안 부른다** | 한 판 109수 중 개입은 8국면이었다(08-playtest.md §5). 매 수 부르면 비용이 열 배인데 그 문장이 나갈 자리가 없다                                                                                                                                                                                           |
| **출력을 안 믿는다**      | 빈 문장·120자 초과·**한글 혼입**·**지어낸 칸이나 수**·**`max_tokens` 에서 잘린 답**은 버리고 결정적 문구로 간다. `Facts` 에 칸도 수도 없으므로 문장에 나타났다면 모델이 만든 것이다 — 자르지 않고 버리는 이유는 반쪽 일본어 문장이 뜻이 바뀌기 때문이고, **잘린 답은 짧아서 길이 검사에 안 걸린다**(§38) |

**결정적 문구가 사실을 담는다는 것이 이 설계의 전제다.** LLM이 없어도 「その銀を取れる相手の駒が2枚あり、取り返す駒がありません」이 나간다. 그래야 LLM은 「같은 사실을 더 좋은 문장으로」만 하게 되고, 라우터가 죽어도 제품이 그대로 선다.

### 그래서 Tier는 모델 크기가 아니라 **재사용성**이다

`ORCA_MODEL_SMALL`·`ORCA_MODEL_LARGE` 의 기본값이 둘 다 같은 모델이다(§3의 실측). 계층을 가르는 것은 **키의 넓이**다.

```
Tier 1   카테고리 × 레벨 → 키 21가지     한 번 만들면 계속 재사용된다
Tier 2   + 駒·매수·잡히는 駒            국면마다 갈리지만 문장이 국면을 짚는다
```

실측 후에도 이 성질은 그대로다 — 문장 품질에 모델을 키울 이유가 안 보였다. **[미확정]** Tier 2에 더 큰 모델이 필요한 국면이 있는지.

**Tier 1은 미리 만들어 뒀다** — `internal/store/migrations/004_explain_cache_tier1.sql` 의 21행이고, 그 층의 개입은 이제 런타임에 LLM을 안 부른다(06-status.md §38). 처음에는 「Tier 2가 대부분이라 이득이 적다」고 봤는데, **2초라는 실측이 그 판단을 뒤집었다**(§28).

**24가 아니라 21이다.** 8×3은 (카테고리, 레벨) 쌍의 수이지 키의 수가 아니었다 — `hangs_piece` 와 `greedy_capture` 는 **분류 조건이 곧 Tier 2 조건**이라 이 층에 오지 않고, `other` 는 판을 읽었는가로 키가 둘로 갈린다(§38).

> **「그 절반이 0초가 된다」고 적어 뒀던 것은 근거가 없다.** 위의 이유로 가장 흔한 두 카테고리가 Tier 2로 가므로, 실제 비율은 **5%와 65% 사이**이고 그 폭 전부가 `other` 하나에 달려 있다. 아직 안 쟀다 — `explain_tier` 가 그 답을 기록하므로 플레이테스트 한 판이면 나온다.

## 3. OrcaRouter

OpenAI 호환 메타 라우터 / AI 게이트웨이. 해커톤 요구사항이기도 하다.

**아래 목록은 광고된 것이고, 그중 절반이 호스팅에 없다** — 실측은 바로 다음 절이다. 이 목록은 **무엇을 기대하고 골랐는지의 기록**으로 남긴다.

- 200+ 모델을 엔드포인트 하나로, 토큰 마크업 0
- `model="auto"` → 요구 능력(tools/vision/JSON)을 충족하는 **가장 싼 모델** 자동 선택
- LinUCB 컨텍스추얼 밴딧 + 오프라인/온라인 하이브리드 학습. RouterArena 정확도 75.5%
- 가드레일, 에이전트 방화벽, 자동 failover, 관측성

실제로 우리가 보내는 것은 이렇다.

```js
const r = await client.chat.completions.create({
  model: "google/gemini-3.5-flash-lite", // 실측으로 고른다. "auto" 는 503이고
  temperature: 0,                        // "orcarouter/auto" 는 15~23초다 (아래)
  messages: [...],
});
```

> 서버는 Go지만 OrcaRouter는 OpenAI 호환 **HTTP**라 그냥 POST하면 된다. 위 JS는 참고용.

**우리에게 특히 유용한 2가지:**

1. **크로스 프로바이더 프롬프트 캐시** — `temperature=0` 또는 seed 고정 시 반복 요청은 캐시에서 나온다. `x-orca-cache: HIT`, **비용 0.** → §2의 Tier 0을 우리가 직접 다 구현할 필요가 없다.
2. **`GET /v1/analytics/savings?baseline=gpt-4o&days=7`** — "항상 GPT-4를 썼다면 vs 실제" 비교를 대시보드 타일로. → **심사 기준 6번 슬라이드에 스크린샷 한 장으로 끝.**

**응답 헤더로 확인:**

- `x-orca-resolved-model` — 실제 선택된 모델
- `x-orca-cache` — HIT / MISS

### 위의 절반은 호스팅에 없다 — 실키로 확인 (2026-08-11)

**Lite(자체 호스팅, MIT)와 호스팅 서비스의 표면이 다르다.** 처음에 `OrcaRouter-Lite` 의 `app/routes/chat.py` 를 읽고 필드 이름을 잡았는데, 실제 키로 `api.orcarouter.ai` 에 보내 보니 그중 절반이 안 온다. 자세한 실측은 [06-status.md §28](06-status.md).

| 무엇             | Lite 소스                         | **호스팅 실측**                                                            |
| ---------------- | --------------------------------- | -------------------------------------------------------------------------- |
| 모델 이름        | `auto`                            | **`orcarouter/auto`** — 네임스페이스가 붙는다                              |
| 캐시 헤더        | `x-orca-cache: HIT/MISS`          | **없다**                                                                   |
| 원당 비용        | `usage.cost_usd` / `_orca_meta`   | **없다.** `usage` 는 토큰 수까지                                           |
| 총액 API         | `/v1/analytics/spend` · `savings` | **404**                                                                    |
| 실제로 오는 헤더 | —                                 | `x-orca-request-id` · `x-orca-version` — **다음 날 둘이 더 사라졌다**(§38) |

그래서 **`interventions.cost_yen` 은 이 프로바이더에서 언제나 0이다.** 아래 §5의 「1회당 ○엔」과 「savings 위젯 스크린샷」은 **API로는 못 만든다.**

**토큰 수와 가격표로 추정해 채우지 않는다.** 그 순간 발표의 숫자가 우리가 만든 숫자가 되고 근거가 사라진다. 남은 길 셋은 전부 **[미확정]**이다 — 라우터 웹 대시보드 스크린샷(사람이 로그인), Lite 자체 호스팅(analytics 가 소스에 있다), 또는 토큰 수만 사실로 남기고 비용을 말하지 않는 것.

코드에는 `usage.cost_usd` 를 읽는 경로가 남아 있다. 오면 쓰고, 안 오면 0이다 — 그리고 `x-orca-cache: HIT` 이면 0으로 적는다(그때 `usage` 는 원래 호출의 것이 실려 오므로 곱하면 같은 돈을 두 번 센다). `cost_yen` 이 `numeric(10,4)` 라 0.0001엔 미만은 어차피 0으로 떨어진다.

환율은 `ORCA_USDJPY`(기본 150 **[미확정]**)다. 칸 이름이 엔이라 어딘가에서 한 번은 곱해야 하고, 실시간 환율을 받아오는 것은 이 제품의 일이 아니다.

### 모델은 실측으로 고른다 — 그리고 **하루 만에 다시 골랐다**

`orcarouter/auto` 는 **추론 모델로 라우팅되어 한 문장에 추론 토큰 1000개 이상을 쓰고 15~23초가 걸렸다.** 라우터는 「능력을 충족하는 가장 싼 모델」을 고르는데 우리 요구는 능력이 아니라 **짧고 빠른 것**이라 기준이 어긋난다.

그래서 `anthropic/claude-haiku-4.5` 로 박았는데, **다음 날 그 채널이 우리 프롬프트 앞에 2만 2천 토큰짜리 시스템 프롬프트를 끼워 넣기 시작했다**(06-status.md §38). 우리 지시가 그 밑에 깔려 400~550자 해설문이 돌아오고, `clean` 이 전부 버려서 **설명이 100% 템플릿으로 떨어졌다.**

```
google/gemini-3.5-flash-lite   1.0~1.3초   프롬프트 193토큰   ← 지금 기본값
openai/gpt-4.1-mini            1.0~2.7초                      다음 후보
google/gemini-3.6-flash        2.1~2.4초                      추론 토큰에 잘려서 온다
anthropic/claude-haiku-4.5     11~17초     프롬프트 23,275토큰 ← 어제의 기본값
orcarouter/fusion-mini · auto  15~23초
```

**라우터가 채널에 무엇을 얹는지는 우리가 정하지 못한다.** 그러니 이 값은 고정이 아니라 실측의 스냅샷이고, `TestRealRouter` 가 그것을 지키는 자리다 — 실패하면 프롬프트가 아니라 **채널을 먼저 의심한다.** 그리고 **잘린 답은 짧아서 `clean` 을 통과하므로** `finish_reason == "length"` 를 따로 버린다.

`Deadline` 도 1.5초에서 **5초**로 올렸다. 1.5초면 실측값이 전부 그것을 넘어 **문장이 하나도 안 나간다.**

그리고 이 제품에서는 **기다림이 손실이 아니다.** 쇼기 상대가 몇 초 생각하는 것은 자연스럽고, 화면이 이미 「判定中」을 띄우므로 그 시간이 **고민으로 읽힌다.** 그래서 예산을 실측(최대 4.7초)을 덮을 만큼 잡았다 — 다른 종류의 앱이라면 같은 값이 고장으로 보일 것이다.

## 4. RAG — 코퍼스는 처음부터 새로 만든다

7일 안에 제대로 된 RAG 파이프라인은 무리다. 대신 **pgvector 지식 테이블**로 좁힌다. `kb_chunks`에 임베딩해서 Tier 1/2 프롬프트에 근거로 붙이고, **검색 결과가 없으면 붙이지 않는다**(환각 방지).

> **검색은 벡터가 아니라 태그로 시작한다** (2026-08-11).
>
> 우리 검색 키가 자유 문장이 아니다 — 「이 국면에 `mino` 태그가 붙었으니 美濃囲い 항목을 꺼낸다」이고, 그건 `kb_chunks.tags` + 이미 있는 GIN 인덱스로 **결정적으로** 된다. 임베딩 유사도는 그보다 부정확한 방법으로 같은 답을 구하는 것이다.
>
> 벡터가 필요해지는 것은 **플레이어가 자유롭게 묻는 대화형**이 붙을 때다. 라우터에 임베딩은 있다(`google/gemini-embedding-001`, `POST /v1/embeddings` 200) — 다만 차원이 **3072**이고 `kb_chunks.embedding` 은 `vector(1536)` 이라 그대로는 안 들어간다. **[미확정]** 1536으로 잘라 요청할지 칸을 바꿀지는 그때 정한다.
>
> 그래서 **태그가 RAG의 전제다.** 코퍼스를 먼저 만들어도 붙일 곳이 없다.

### `../shogi`의 데이터는 한 줄도 쓰지 않는다

세 가지 이유가 각각 독립적으로 결정적이다.

1. **출처를 신뢰할 수 없다.** 저쪽 콘텐츠의 원전은 개인 블로그 강좌다. 취미 학습용으로는 충분했지만, **틀린 설명이 초심자에게 그대로 전달되는 제품**의 근거로 쓸 수는 없다. 이 제품의 존재 이유가 "설명이 틀리면 초심자는 검증할 수 없다"인데 코퍼스가 검증 안 된 글이면 자기모순이다.
2. **저작권.** `tesuji.ts` 208문은 시판 서적을 디지털화한 것이다. **이 레포는 퍼블릭이다.** 신뢰성 이전에 옮기면 안 된다.
3. **언어.** 설명문이 전부 한국어다. 일본어 질의로 검색하는데 코퍼스가 한국어면 임베딩 유사도가 무너지고, 근거로 붙여도 출력이 한글로 샌다.

### 신뢰 계층 — 사실은 사람 글에서 가져오지 않는다

| 계층             | 무엇                              | 출처                                                                                                                                | 검증                                                      |
| ---------------- | --------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------- |
| **1. 수순·국면** | 정석 수순, 囲い 완성형, 手筋 국면 | 공개 **정석 파일**(やねうら王 등)과 프로 기보 DB                                                                                    | **자체 엔진으로 재검증.** 합법성 + 평가치가 주장과 맞는지 |
| **2. 용어·개념** | 囲い/전법 이름, 정의, 장단점      | **日本将棋連盟 공식** 용어·규칙 페이지, **일본어 위키백과**(CC BY-SA — 출처 표기하면 퍼블릭 레포에 실을 수 있는 유일한 서술형 소스) | 사람이 읽고 확인. 근거 URL을 chunk에 박는다               |
| **3. 태그 체계** | 태그 목록과 이름                  | 将棋ウォーズ의 전법·囲い 태그명                                                                                                     | 이름만 참고. 콘텐츠는 가져오지 않는다                     |

**핵심은 계층 1이다.** 수순의 신뢰성은 사람이 쓴 글보다 **엔진 정석 파일 + 자체 검증**이 압도적으로 높다. 囲い는 "이렇게 두면 美濃다"라는 설명이 아니라 **최종 배치의 좌표 집합**으로 정의하고, 엔진으로 도달 가능성을 확인한다. 그러면 블로그가 필요 없어진다.

**쓰지 않을 것:** 개인 블로그·번역 경로가 불분명한 2차 자료, 서적 스캔/디지털화, 유료 서비스의 해설 콘텐츠.

### 출처를 스키마에 박는다

```sql
kb_chunks (
  id, title, body,               -- body는 일본어
  tags text[],
  source_url text,               -- 없으면 프롬프트에 붙이지 않는다
  source_license text,           -- 'CC-BY-SA-4.0' | 'official-reference' | 'engine-derived'
  verified_by text,              -- 'engine' | 'human' | null
  embedding vector(1536)
)
```

`verified_by`가 비면 검색에 걸려도 **프롬프트에 붙이지 않는다.** 미검증 지식이 조용히 설명으로 새는 경로를 코드가 아니라 스키마에서 막는 것이다. 발표에서 "판단은 엔진"을 말할 때 이 컬럼이 근거가 된다.

### 규모

태그 수만큼만 있으면 된다 — 囲い 10–14 + 전법 8–10 + 手筋 15–20 + [블런더 카테고리](01-core.md#3-블런더-카테고리-온톨로지--진짜-승부처) 7 ≈ **50개 항목 × 일본어 1–2문단.** 양을 늘리는 것보다 **전부 출처가 붙어 있는 것**이 먼저다.

> **첫 적재는 47항목이다** ([06-status.md §30](06-status.md) · [09-tags.md](09-tags.md)). 50과 비슷해진 것은 우연이고, **뜨는 태그에만 붙인 결과**다 — 태그 39개 + 블런더 카테고리 8개. 감지기가 없는 이름에는 항목을 넣지 않았다. 넣어도 꺼내올 검색 키가 없고, 그건 이 절이 위에서 이미 적은 이유(「코퍼스를 먼저 만들어도 붙일 곳이 없다」)가 그대로 적용된 것이다.
>
> 그리고 **50이라는 숫자 자체가 작다.** 将棋ウォーズ 기준으로 囲い가 42종·전법이 106종이다. 태그 목록을 넓히는 것이 코퍼스를 넓히는 것보다 먼저다.

**정석 파일은 안 고르기로 정했다** ([06-status.md §48](06-status.md)). 진형 4종의 수순을 직접 적고 룰 엔진이 검증하므로 2차 자료가 필요 없고, `kb_chunks` 와도 무관하다 — 북은 상대가 둘 수순이고 코퍼스는 설명에 넣는 글이다.

**위키백과 인용 범위는 정해졌다** ([06-status.md §30](06-status.md)): **배치 서술만** 옮기고, 항목마다 `source_url` 에 그 문서를 박고 `source_license` 를 `CC-BY-SA-4.0` 으로 둔다. 해설문을 옮기지 않는 이유는 계층 1이 이미 그것을 대신하기 때문이다 — 좌표는 룰 엔진이 검증한다.

## 5. 계측 — 발표 자료가 되는 숫자

`interventions` 테이블의 `explain_tier` · `cost_yen`에서 집계한다.

- **개입 1회당 평균 ○엔**
- 캐시 히트율 (Tier 0 비율 + `x-orca-cache: HIT` 비율)
- savings 위젯 스크린샷

> **위 셋 중 앞의 둘은 지금 만들 수 없다** — 호스팅 라우터가 원당 비용도, 총액 API도 주지 않는다(§3의 실측). 남는 것은 `explain_tier` 분포와 `explain_cache.hits` 이고, 그 둘은 **호출을 얼마나 아꼈는가**는 말해도 **얼마를 아꼈는가**는 말하지 못한다.

**`explain_tier` 는 LLM을 안 거쳤으면 NULL이다.** 0으로 적으면 「캐시 히트」와 같은 값이 되는데, 그 둘은 정반대의 뜻이다 — 히트는 **부를 것을 아껴서** 0엔이고 NULL은 **애초에 안 부른 것**이다. 섞이면 「호출을 구조적으로 줄였다」는 이 절의 주장이 「LLM을 안 붙였다」와 구별되지 않는다.

`explain_cache.hits` 가 히트율의 분자다. 조회 질의가 `UPDATE ... RETURNING` 이라 **찾으면서 센다** — 세는 것을 잊을 자리가 없다. 그래서 앞에 메모리 캐시를 두지 않았다: 그쪽에서 맞으면 이 숫자가 조용히 낮게 나온다.

> **절감을 2단계로 보여주는 것이 핵심이다.** 라우터만 쓴 팀은 많을 것이다. **"구조적으로 호출 자체를 줄인 뒤, 남은 것만 최적 모델로 라우팅"** 하는 팀은 드물다.
