## 82. Fargate에서 EC2 스팟 한 대로 옮겼다 (2026-08-17)

**0으로 내려둔 서비스가 CI를 상시 빨간불로 만들고 있었다.** 해커톤이 끝나고 `desired_count` 를 0으로 내렸는데(#93), 배포 워크플로의 마지막 스텝이 `https://show-gi.com/healthz` 를 확인한다 — 태스크가 0개면 ALB가 503이라 **머지마다 `Images` 가 실패한다.** 상시 빨간 CI는 안 보는 CI이고, 그때 진짜 배포 실패를 놓친다.

내려둔 이유는 값이었다.

| 구성                                   | 월 (추정) |
| -------------------------------------- | --------- |
| Fargate ARM 4 vCPU / 8 GiB (상시)      | ~$115     |
| **EC2 t4g.small 스팟 1대 + EBS 30GiB** | **~$8**   |

### 네 가지가 같이 움직여야 했다

**하나만 바꾸면 안 뜬다.** 각각이 다른 것을 강제한다.

| 바꾼 것                                          | 왜 강제되나                                                                                                                            |
| ------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------- |
| `network_mode` `awsvpc` → **`host`**             | EC2에서 `awsvpc` 태스크 ENI에는 공인 IP를 못 붙인다(그 옵션은 Fargate 전용). 밖으로 나갈 길이 NAT뿐인데 월 $40이라 인스턴스보다 비싸다 |
| 타깃 그룹 `target_type` `ip` → **`instance`**    | 태스크가 자기 IP를 안 갖는다                                                                                                           |
| `deployment_minimum_healthy_percent` 100 → **0** | 인스턴스가 태스크 하나에 맞춰진 한 대라 두 개가 동시에 못 올라간다. 그대로 두면 새 태스크가 배치되지 않고 서킷 브레이커가 롤백한다     |
| 엔진 풀 3+2 → **2+1**, 해시 128 → **64MB**       | 기본값이 2 GiB에 안 들어간다 (아래)                                                                                                    |

**`bridge` 는 후보가 아니었다.** Caddy가 `reverse_proxy localhost:8080` 으로 api 를 부르는데(`apps/web/Caddyfile`) bridge 는 컨테이너마다 네임스페이스를 갈라서 그 한 줄이 깨진다. `host` 는 둘이 인스턴스의 네임스페이스를 같이 쓰므로 그대로 닿는다 — awsvpc 에서 성립했던 것과 같은 이유다.

### 메모리는 실제로 예약된다

**Fargate와 가장 다른 점이다.** 태스크의 `memory` 가 「상한」이 아니라 인스턴스에서 빼는 예약이라, 넘게 적으면 태스크가 아예 배치되지 않는다.

| 항목                                        | 값                      |
| ------------------------------------------- | ----------------------- |
| t4g.small                                   | 2048 MiB                |
| OS + ECS 에이전트가 먹는 것                 | ~300 MiB                |
| 태스크가 쓸 수 있는 것                      | ~1750 MiB               |
| **기본값(엔진 5개 × (NNUE 63 + 해시 128))** | **~955 MiB**            |
| \+ Go 힙 · Caddy                            | ~280 MiB                |
| **기본값 합계**                             | **~1.3 GiB**            |
| 줄인 뒤(엔진 3개 × (63 + 64))               | ~380 MiB                |
| **줄인 뒤 합계 · `task_memory`**            | **~710 MiB · 1536 MiB** |

**1536으로 태스크가 배치됐다**(2026-08-17 apply). 위의 「OS + 에이전트 ~300 MiB」는 추정이었는데, 그 값이 틀렸다면 태스크가 `PENDING` 에 머물렀을 것이다 — 배치됐다는 것이 그 추정의 유일한 검증이다. **남는 여유가 실제로 얼마인지는 아직 안 쟀다** `[미확정]`.

**풀을 줄여도 되는 근거는 사람이 한 명이라는 것이다.** 세 풀이 동시에 필요한 것은 상대 수·선행 계산·mate 탐색이 겹칠 때인데, 한 사람이 한 수를 두는 동안 그 셋은 순서대로 온다. 탐색 2 + mate 1이면 개입 판정과 상대 수가 겹치는 것까지 덮는다.

### apply 뒤 실측 (2026-08-17)

| 확인                  | 결과                                                                     |
| --------------------- | ------------------------------------------------------------------------ |
| `/healthz`            | `{"db":true,"engine":true,"ok":true}` — **엔진이 떴다**(메모리가 맞았다) |
| `/` (Caddy 정적)      | 200 · 4,125 bytes                                                        |
| `/api/openings`       | JSON — Caddy → `localhost:8080` 이 `host` 모드에서 그대로 닿는다         |
| `/api/me`             | `{"enabled":true,"user":null}` — SSM의 Google 자격증명이 실렸다          |
| `/api/resumable`      | `{"game":null}` — RDS 읽기가 인스턴스에서 된다                           |
| `/ws/game` 업그레이드 | **`101 Switching Protocols`** — ALB → instance 타깃을 지나 WS가 선다     |
| apply 직후 첫 요청    | 503 (약 20초) → 200. 스팟 확보·에이전트 등록·이미지 pull·엔진 기동의 합  |

> **`/ws/game` 은 HTTP/1.1로 확인해야 한다.** curl 이 HTTP/2로 붙으면 `Connection: Upgrade` 헤더가 규격상 벗겨져서 서버가 426을 준다 — 서버 문제가 아니다. `--http1.1` 을 붙인다.

### 무엇을 내주었나

- **배포마다 1~2분 내려간다.** 옛 태스크를 내리고 새 것을 띄우는 순서라서다. 무중단을 되찾으려면 인스턴스를 두 대로 늘리거나(값 2배) 태스크를 반으로 줄여야 한다
- **스팟 회수 시 2~3분 내려간다.** `ECS_ENABLE_SPOT_INSTANCE_DRAINING` 이 2분 전 통보에 태스크를 내리고 ALB가 타깃을 빼므로 죽은 인스턴스로 요청이 가지는 않는다. 대국 중이었으면 그 판은 `aborted` 로 닫히고 이어하기가 살린다([§51](41-60.md))
- **T 계열이라 CPU가 크레딧으로 돈다.** `cpu_credits = "standard"` 로 뒀다 — 넘기면 느려지는 대신 청구가 예측 가능하다. `unlimited` 은 엔진 탐색이 크레딧을 태우기 쉬운 모양(한 수에 CPU를 몰아 쓴다)이라 놀라운 청구서가 될 수 있다

### 정한 것

- **용량 공급자(capacity provider)를 안 만든다.** 하는 일이 태스크 수를 보고 인스턴스를 늘리는 것인데 태스크도 인스턴스도 1로 고정이다. 서비스가 `launch_type = "EC2"` 로 등록된 인스턴스에 바로 얹는다
- **ASG는 스케일링을 안 한다.** 1/1/1 고정이고, 하는 일은 「스팟이 회수되면 새 인스턴스를 받아 온다」 하나다
- **ASG의 헬스체크는 `EC2` 다(ALB가 아니다).** 배포 중에 태스크가 잠깐 내려가는데 ALB 기준으로 보면 ASG가 그것을 인스턴스 고장으로 읽고 멀쩡한 인스턴스를 죽인다 — 그러면 배포마다 인스턴스가 새로 뜬다
- **`show-gi-migrate` 태스크는 Fargate로 남긴다.** 인스턴스가 앱 태스크 하나에 맞춰져 있어 얹을 자리가 없다 — EC2로 바꾸면 배치가 안 돼서 `PROVISIONING` 에 머문다
- **타깃 그룹은 `name` 이 아니라 `name_prefix` 다.** `target_type` 이 변경 불가 속성이라 값을 고치면 교체되는데, 이름이 고정이면 terraform 이 「지우고 만들기」로 잡아서 리스너가 참조 중인 옛 것을 못 지우고 apply 가 교착한다

### 남은 비용 구조

컴퓨트가 더 이상 가장 큰 항목이 아니다 — 월 약 $42 중 **ALB(약 $18)와 RDS(약 $15)가 8할**이다. 더 줄일 곳을 찾는다면 그 둘이고, ALB는 TLS 종료·ACM 자동 갱신·WebSocket 유지가 얹혀 있어 그냥 빼면 인증서가 스팟의 휘발성 디스크로 내려간다([deploy/README.md](../../deploy/README.md) 「비용과 정리」).

### 운영자 정책이 v5가 됐다

`terraform apply` 가 시작 템플릿과 ASG를 만들어야 하는데 `show-gi-operator` 에 `ec2:Describe*` 만 있었다. **정책은 사람이 admin 자격으로 올린다** — 운영자는 자기 권한을 못 올린다([06-status.md](../06-status.md) §7).

**apply 가 세 번 막혔고, 막힌 순서가 그대로 목록이다.** 미리 다 예측하지 못했다는 것이 이 절에 남길 사실이다 — 이 정책은 Fargate 시절에 만들어져서 **인스턴스 프로파일을 한 번도 만들어 본 적이 없었다.**

| 회차 | 막힌 곳                  | 모자랐던 것                                                                                                                                           |
| ---- | ------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| 0    | (예상해서 미리 넣음)     | `ec2:*LaunchTemplate*` · `autoscaling:*` · 화이트리스트에 인스턴스 롤용 관리형 정책 둘 · `iam:PassRole` 에 `ec2.amazonaws.com` · ASG 서비스 링크드 롤 |
| 1    | `CreateInstanceProfile`  | **`iam:TagInstanceProfile`** — 프로바이더 `default_tags` 가 프로파일에도 붙는다. `iam:TagRole` 만 있었다                                              |
| 2    | `CreateAutoScalingGroup` | **`ec2:RunInstances`** — ASG가 시작 템플릿을 참조할 때 AWS가 RunInstances 인가를 먼저 확인한다                                                        |

`Untag`·`ListTags` 계열은 2회차에서 같이 넣었다. 아직 안 막혔지만 태그를 바꾸거나 지울 때 각각 다른 액션이고, **여기서는 실패 한 번이 정책 왕복 한 번**이라 그쪽이 더 비싸다.

`autoscaling:*` 만 와일드카드다. 좁게 적으면 terraform 이 refresh 때 부르는 `Describe` 가 계속 하나씩 빠져서 apply 가 권한 하나에 막히는 일이 반복된다 — 리전 조건이 이미 범위를 잡는다. 정책 크기는 **5,132 / 6,144자**로, 다음에 권한을 더할 때는 줄일 자리를 같이 찾아야 한다.

## 83. 사람끼리 두는 판 — 초대 링크 하나가 열쇠다 (2026-08-18)

**요청은 「사용자끼리 매칭해서 두게 하고, URL로 남이 못 들어오게, 로그인한 사람만」이었다.**

### 정한 것 다섯

|           |                                                                                                                                                                                                              |
| --------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 만나는 법 | **초대 링크만.** 대기열을 안 만든다 — 동시 접속자가 없으면 대기열은 아무도 못 두는 화면이고, 지금 이 앱의 동시 접속자는 대개 0이다                                                                           |
| 보조 기능 | **개입·힌트·待った 전부 끔.** [02-architecture.md §7](../02-architecture.md) 위협 1이 이미 정해 둔 것이고, 롤백은 상대를 기다리게 만드는 데다 「저쪽이 무슨 수를 뒀다가 물렀나」까지 그 사람 화면에 드러낸다 |
| 기록      | **`games` 행 두 개.** 각자 자기 판을 갖는다                                                                                                                                                                  |
| 手番      | **先手·後手·振り駒 셋.** 振り駒는 **서버가** 뽑는다 — 클라이언트가 뽑으면 마음에 안 드는 결과를 다시 뽑을 수 있고, 그러면 고르는 것과 같아진다                                                               |
| 평가치    | **판이 끝난 뒤에 채운다.** 두는 동안에는 엔진이 한 번도 안 돈다                                                                                                                                              |
| 시계      | **1手 60초.** 넘기면 시간패. 실측이 아니라 정한 값이다                                                                                                                                                       |

### 방에 들어가는 규칙은 셋이고, 셋이 다 필요하다

1. **로그인한 사람만.** 익명은 서로 구별할 수단이 없어서(`002_anonymous_games.sql`) 「이 방의 상대가 아까 그 사람인가」에 답할 수가 없다
2. **id 를 유추할 수 없다.** `crypto/rand` → 영숫자 8자(62^8, 약 47.6비트). `games.id` 같은 연번이면 로그인한 아무나 훑는다
3. **정원 2명.** 두 자리가 차면 그 뒤로는 링크를 알아도 **관전조차** 안 된다

하나라도 빠지면 나머지가 무너진다 — 1이 없으면 링크를 받은 누구나 남의 자리에 앉고, 2가 없으면 링크가 필요 없어지고, 3이 없으면 세 번째 사람이 판을 들여다본다.

**거절은 404 하나다.** 없는 방·만료된 방·남이 이미 찬 방·**로그인 안 한 요청**이 전부 같은 답을 받는다. 마지막 것이 요점 — 401은 「로그인하면 볼 수 있다」는 뜻이라, 그것만으로 **그 방이 있다는 사실이 로그인 없이 새어 나간다.** 이어하기가 남의 판 번호에 대해 하는 것과 같은 판단이다([§46](41-60.md)).

**한 사람이 들고 있을 수 있는 안 시작한 방은 셋까지다.** 방이 프로세스 메모리에 있으므로 상한이 없으면 로그인한 사람 하나가 30분 동안 계속 쌓을 수 있다. 넘으면 **거절이 아니라 오래된 것을 버린다** — 방을 또 만든 사람이 원하는 것은 대개 마지막 링크 하나이고, 거절은 「왜 안 되나」를 화면에 설명해야 한다. **사람이 걸려 있는 방은 절대 안 버린다** — 시작한 판은 물론이고 **손님이 앉기만 한 방**도 그렇다(걷어가면 그쪽에서 기다리던 사람이 영영 기다리고, 방 주인은 자기 방에 다시 못 들어간다).

**손님은 앉기 전에 한 번 확인한다.** WebSocket 이 붙는 순간 자리가 확정되고 시계가 돌기 시작하므로, 링크를 잘못 누른 사람이 모르는 사이에 남의 방을 닫으면 안 된다. 그래서 `GET /api/rooms/{id}` 는 **자리를 안 잡는다.**

### 시계가 있는 이유는 「빨리 두게 하려고」가 아니다

**판이 끝나게 하려고다.** 엔진 대국은 연결이 끊기면 그 판이 `abandoned` 로 닫히는데([§46](41-60.md)), 대인전은 **상대가 남아 있어서 끝낼 수가 없다.** 한쪽이 탭을 닫으면 그 판이 영원히 「두는 중」으로 남고, 그러면 되짚기에도 안 걸리고 결과도 없다.

그래서 **접속이 끊겨도 판을 안 멈춘다.** 멈추면 지고 있는 쪽이 탭을 닫아 판을 얼릴 수 있고, 시계가 있는 이유와 정면으로 어긋난다. 끊긴 사람은 같은 링크로 다시 들어와 이어 둔다 — 그동안 자기 시계는 흐른다.

**대국이 시작되는 조건은 「둘이 동시에 붙어 있을 것」이다.** 「들어온 적이 있다」로 세면, 링크를 보내고 탭을 닫은 방 주인이 손님이 여는 순간 시간패로 진다.

**방이 걷히면 기다리던 연결에 알린다.** 지우기만 하면 그쪽은 영영 「상대를 기다립니다」에 서 있고, 그동안 **이미 죽은 링크를 광고한다** — 상대가 열면 404를 받는데 방 주인은 아직 기다리는 줄 안다. 걷히는 자리가 둘(만료·상한)이라 둘 다 같은 채널로 알린다. **훑는 계기도 둘이다** — 남이 Hub 를 건드릴 때와 1분마다 도는 티커(`sweepLoop`). 티커가 없으면 혼자 기다리는 방은 아무도 안 와서 영영 안 걷힌다.

**한 수도 안 둔 채 시간이 다 되면 승패를 안 적는다.** 링크를 보내고 탭을 열어 둔 채 자리를 뜨는 것이 흔한데, 그때 승패를 적으면 **0手짜리 판**이 두 사람의 전적에 win/loss 로 남고 이긴 쪽의 「振り返り」 링크가 빈 판을 연다. 아무도 안 뒀으면 판이 없었던 것이다.

**내 연결이 끊긴 것은 화면이 크게 말한다.** 판은 서버에서 그대로 돌고 **내 시계도 그대로 흐르는데**, 화면은 마지막 스냅샷을 들고 있어서 아무 일도 없어 보인다 — 그동안 시간패로 지고 있다. 상대가 자리를 비운 것과 같은 무게로 그리면 안 되는 이유가 그것이다.

**끝난 판도 11분은 더 답한다**(`finishedGrace` = `FinishedTTL` + 1분). 投了를 받은 쪽이 그 순간 새로고침하는 것은 드문 일이 아닌데, 그때 문을 닫아 두면 결과 대신 오류가 뜬다. **1분이 일을 한다** — 방과 같은 값으로 두면 둘이 닫히는 순서가 안 정해져서, 「방은 아직 열려 있는데 테이블이 이미 닫힌」 창이 생긴다. 길게 두면 들어온 사람은 언제나 둘 중 하나를 받는다: 방이 살아 있으면 결과를, 방이 걷혔으면 404를.

### 평가치는 판이 끝난 뒤에 채운다

대인전에 엔진을 안 붙이는 것은 규약이라 `eval_cp` 가 통째로 비고, 되짚기의 평가치 궤적이 빈 채로 열린다. 그런데 그 빈 상태 문구(「評価値が残っていません」)는 `eval_cp` 가 뒤에 붙은 컬럼이라 생긴 **옛 판용**이었다 — 대인전이 그것을 매번 만나면 「이 갈래에는 원래 없다」로 읽힌다.

**판이 끝난 뒤 서버가 기보를 다시 재서 채운다.** 두는 동안이 아니라는 것이 요점이고, 그래서 위협 1(대국 중 소프트 참조)과 어긋나지 않는다.

|              |                                                                                                          |
| ------------ | -------------------------------------------------------------------------------------------------------- |
| 무엇을 쓰나  | `eval_cp` 뿐이다. 판정(`Judgement.Verdict`)은 버린다 — 개입은 대인전에 없다                              |
| 몇 번 재나   | **한 번.** `eval_cp` 는 先手 관점이고 뒤집는 것은 되짚기라, 같은 값이 두 행에 그대로 들어간다            |
| 동시에 몇 판 | **하나.** 엔진 풀이 지금 두고 있는 사람들과 공유라, 여러 판을 같이 돌리면 그쪽 상대 수가 그만큼 느려진다 |
| 상태는 어디  | **서버 메모리.** 배포하면 하던 분석이 끊기고 그 판은 평가치 없이 남는다 — 방과 같은 성질이다             |
| 기보는       | **안 기다린다.** 수는 둘 때 이미 들어갔고, 채우는 것은 평가치뿐이다                                      |

화면은 분석 중일 때 「評価値を分析しています…」를 그리고 5초마다 다시 묻는다. 「분석 중」과 「남지 않았다」를 갈라 두지 않으면, 판이 끝나자마자 들어온 사람이 기다리면 되는 것을 없는 것으로 안다.

### 기록 — 행 하나가 아니라 둘인 이유

소유 검사를 타는 질의가 다섯이다(`ListGamesForOwner`·`GetGameForOwner`·`CountGameResultsForOwner`·`CountInterventionCategoriesForOwner`·`CountGameStyleTagsForOwner`). 각자 자기 행을 가지면 **그 다섯이 한 줄도 안 바뀐다.**

한 행에 `opponent_user_id` 를 더하는 쪽도 재 봤는데, 그러면 다섯 질의를 전부 `OR` 로 고쳐야 하고 **`my_color` 가 소유자 기준이라 상대가 열면 先手·後手가 뒤집힌다** — 화면에 나가는 cp가 전부 「플레이어 관점」이라는 규약이 두 갈래로 갈린다. 부호 뒤집기는 [§33](21-40.md)에서 이미 한 번 물린 자리라, 아끼는 것(디스크 몇 KB)보다 무는 것이 크다.

값은 **기보가 두 벌 저장되는 것**과, 두 행을 다시 묶을 열쇠가 필요한 것 하나(`games.match_id`, 마이그레이션 `012`).

### 그 대신 닫아야 할 자리가 셋이었다

대인전 판에는 **엔진 판정이 없어서 `eval_cp` 가 비고 `interventions` 가 0건이다.** 그것을 그대로 두면 화면이 「블런더 없이 잘 둔 판」이라고 말하는데, 사실은 **재지 않았다**이고 그 둘이 초심자에게 정반대다.

| 자리              | 그대로 두면                             | 닫는 법                              |
| ----------------- | --------------------------------------- | ------------------------------------ |
| 총평              | 「一度も止められませんでした」가 나간다 | `/api/games/{id}/summary` 가 404     |
| 되짚기 퀴즈       | 「아직 만드는 중」에서 영영 안 벗어난다 | `ready:true` · 링크 자체를 안 그린다 |
| 마이페이지의 집계 | 「崩れやすいところ」의 비율이 희석된다  | 세 질의에 `match_id IS NULL`         |

**전적은 갈라 센다.** 되짚기 목록에는 그대로 뜨고(「対人」 표식이 붙는다) 마이페이지의 집계에서만 빠진다 — 목록은 「무엇을 뒀나」이고 집계는 개입 비율이 뜻을 갖는 자리라, 모집단이 달라야 하는 쪽은 뒤다.

### 왜 `internal/game` 을 안 늘렸나

그쪽은 `HumanColor` 하나 + `Opponent`(엔진) 하나가 전제이고, 개입·판정·힌트·무르기·실력 추정이 그 위에 얹혀 있다. 사람 둘을 그 안에 넣으면 **그 다섯을 전부 「사람 상대면 끄기」로 감싸게 되고**, 개입 쪽을 고칠 때마다 이쪽이 안 깨졌는지 매번 확인해야 한다.

`internal/match` 는 `internal/shogi`(룰)와 시계뿐이다 — **`usi` 를 import 하지 않는다.** 엔진 없는 배포에서도 대인전이 도는 것이 그 사실의 증거이고, 실제로 그 테스트가 엔진 없이 돈다.

갈라 둔 자리가 하나 더 있다: **`game.Side`(human/engine)를 못 쓴다.** 사람이 둘이라 절대 이름을 쓰면 같은 기보가 두 화면에서 같은 색으로 그려진다 — 그래서 스냅샷을 **보는 사람마다** 펴서 보낸다(`you`/`opponent`).

### 실측

로컬에서 사람 하나(브라우저)와 스크립트 하나로 한 판을 끝까지 돌렸다.

| 확인한 것                            | 결과                                                           |
| ------------------------------------ | -------------------------------------------------------------- |
| 방 id                                | 영숫자 8자, 500개 중 중복 0                                    |
| 세 번째 사람의 `GET /api/rooms/{id}` | 404 — 없는 방과 **응답 본문까지 같다**                         |
| 대국이 시작되는 시점                 | 둘이 동시에 붙은 그 자리. 한쪽만 붙어 있으면 시작되지 않는다   |
| 착수 왕복                            | ▲7六歩 → △9二香, 두 화면의 棋譜가 같고 `by` 만 반대            |
| 시계                                 | 60초에서 내려가고, 착수마다 다시 60초                          |
| 시간패                               | 넘긴 쪽이 패. 「持ち時間がなくなりました」                     |
| 기록                                 | `games` 행 두 개(1081 `w`/`win`, 1082 `b`/`loss`), 기보 각 2수 |
| 마이페이지                           | 그 판이 전적에서 빠짐(5판 중 4판)                              |

**`summaryOf` 가 `match_id` 를 안 옮기고 있었다.** 그러면 `isMatch` 가 언제나 false 라 위의 「닫아야 할 자리 셋」이 하나도 안 닫힌다 — 실물로 돌리기 전까지 안 보였고, 끝까지 도는 테스트(`TestTwoPeoplePlayAMatch`)가 그것을 잡았다.

### 두 갈래가 만나는 자리를 네 번 막았다

대인전 판이 `games` 에 섞여 들어가므로, **엔진 대국의 장치가 그 행을 집는 자리**를 전부 찾아야 했다. 소유 조건을 안 건드린 대신 이쪽이 늘었다.

| 자리                 | 그대로 두면                                                                                    |
| -------------------- | ---------------------------------------------------------------------------------------------- |
| 마이페이지의 집계 셋 | 개입 0건인 판이 분모에 들어가 「崩れやすいところ」 비율이 희석된다                             |
| 총평                 | 「一度も止められませんでした」가 나간다 — 사실은 **재지 않았다**이다                           |
| 되짚기 퀴즈          | 「아직 만드는 중」에서 영영 안 벗어난다                                                        |
| **이어하기**         | **사람과 두던 수순이 엔진 세션으로 이어진다** — 그 판의 두 행이 갈라져 같은 대국이 아니게 된다 |

마지막 것이 제일 위험하고 제일 늦게 보였다. 배포가 대국 중에 끼면 테이블이 접히면서 **수가 있는 행이 `abandoned` 로 닫히는데**, 그것이 정확히 이어하기 목록의 조건이다. 조건은 목록과 점유 **양쪽**에 넣었다 — 목록에서만 빼면 번호를 직접 넣어 그대로 열린다.

### 남은 것

- **방은 프로세스 메모리다.** 배포하면 열려 있던 방이 사라진다 — 두는 중에 배포가 끼면 엔진 대국도 지금 그 자리에서 끊기므로 대인전만 더 잃는 것은 없다
- **持ち時間(총 시간)과 秒読み은 없다.** 화면에 시계 둘이 필요하고, 그 전에 「끝나기는 하는가」를 먼저 세웠다
- **대기열이 없다.** 링크를 보낼 상대가 있어야 둘 수 있다

## 84. 접쇼기(駒落ち) — 판은 이미 섰고 판정식이 안 섰다 (2026-08-19)

「말을 떼고 둔다」를 열었다. 香落ち · 角落ち · 飛車落ち · 飛香落ち · 二枚落ち · 四枚落ち · 六枚落ち 일곱 종이다.

### 배선은 이미 있었다

`StartSFEN` 이 끝에서 끝까지 이미 흐르고 있었다 — `game.Config` → `usi`(언제나 `position sfen`, `startpos` 를 안 쓴다) → `games.start_sfen` → 이어하기 · 되짚기 · 가정 수순 · 퀴즈. 룰 엔진도 駒 수를 안 세고, `positions` 캐시 키는 手数 뺀 SFEN이라 국면이 겹치지도 않는다. **그래서 「판을 세우는 일」은 쿼리 하나(`?handicap=`)였다.**

**마이그레이션이 없다.** 手合割을 되짚는 값이 `games.start_sfen` 하나로 충분해서다 — 이름을 따로 저장하면 그 칸과 실제 판이 갈릴 수 있고, 갈리면 화면이 「二枚落ち」라고 적어 둔 판에 飛車가 서 있게 된다. 목록 세 질의에 그 칸을 더한 것이 전부다.

### 문제는 판정식이었다 — 승률이 판 전체에서 포화한다

[01-core.md §2](../01-core.md)가 이미 적어 둔 구멍이다: 「양쪽 끝에서 포화한다. 실전에서 문제가 안 되는 이유는 거기까지 가는 길목의 `0 → -800`이 먼저 걸리기 때문이고, **판정을 건너뛰는 구간이 있으면 그 보호가 사라진다**」. **駒落ち는 판 전체가 그 구간이다.**

실측(水匠5 · depth 14 · `FV_SCALE=24` · Threads=1 · Hash=128). 「발화선」은 입문 임계치 0.25를 넘기는 최소 낙폭이다.

| 手合     | 초기 cp | WR(K=600) | 발화선(기준점 없이) | 기준점을 빼면 |
| -------- | ------: | --------: | ------------------: | ------------: |
| 平手     |      91 |    0.5378 |                 635 |   635(그대로) |
| 香落ち   |     270 |    0.6106 |                 614 |           660 |
| 角落ち   |     756 |    0.7790 |                 687 |           660 |
| 飛車落ち |     741 |    0.7747 |                 682 |           660 |
| 飛香落ち |     865 |    0.8087 |                 724 |           660 |
| 二枚落ち |    1490 |    0.9230 |            **1058** |           660 |
| 四枚落ち |    1834 |    0.9551 |            **1312** |           660 |
| 六枚落ち |    2011 |    0.9662 |            **1456** |           660 |

**平手 줄의 두 칸이 같은 것이 요점이다** — 기준점이 0이라 그 판의 판정은 한 비트도 안 바뀐다. 갈리는 것은 아래뿐이다.

**二枚落ち에서 銀을 공짜로 줘도(약 1000cp, [§2](../01-core.md)) 안 걸린다.** 六枚落ち면 그보다 1.5배를 흘려야 한다 — 초심자가 가장 필요로 하는 手合에서 개입이 조용해진다. 같은 압축이 `internal/skill` 의 낙폭에도 걸리므로, 그 판들은 사람을 실제보다 잘 두는 것으로 추정하고 그 값이 `skill_profile` 에 남아 **다음 平手 판까지 옮겨 간다.**

### 정한 것 — 기준점 하나가 셋을 고친다

`intervene.Input.BaselineCp` 한 칸을 더하고 두 항에서 같이 뺀다.

```
Δ = WR(best - baseline) - WR(after - baseline)
```

- **판정** — 「아직 아무것도 안 흘렸다」가 다시 승률 0.5에 오므로 어느 手合에서도 660cp 언저리에서 걸린다
- **밴드**(`game.adaptiveOpponent`) — 절대 좌표의 원점이 같이 옮겨 간다. 안 옮기면 첫 수부터 `now` 가 상단 위라 상대 좌표 분기로만 가고, 그러면 상대가 **핸디캡을 되돌려 주는 일을 아예 안 한다**: 사람이 +1490을 +500까지 흘려도 「지금 형세에서 100~300 더」만 겨냥한다. [§55](41-60.md)가 고친 것의 **거울상**이다
- **총평의 「이기고 있었다」**(`explain.StandingAheadRate`) — 二枚落ち에서 +1100으로 끝난 판은 핸디캡의 절반을 잃은 판인데, 기준점을 안 빼면 「圧倒的に有利でした」가 나간다
- **되짚기의 형세 그래프**(`EvalGraph`) — 축이 승률이라 곡선이 판 내내 천장에 붙는다. 「어디서 흘렸나」가 안 보이는 것보다 나쁜 것은 **50% 선이 핸디캡을 다 잃은 자리에 그려지는 것**이다
- **후보 줄의 색**(`evalTone`) — ±800cp에서 포화하므로 六枚落ち의 후보는 **한 줄도 빠짐없이 최대 파랑**이 된다. 방금 물러진 수까지 그렇게 칠하고, 빨강은 아예 안 나온다
- **`shallow_trap` 카테고리**(`intervene.classify`) — 「얕게는 좋아 보이고 깊게는 나쁘다」를 절대 부호로 읽던 유일한 규칙이다. 안 옮기면 앞 조건이 언제나 참이고 뒤 조건이 거의 언제나 거짓이라, 판정은 걸리는데 이름이 `other` 로 떨어진다 — **개입은 살아 있고 설명만 조용히 나빠지는** 모양이라 눈으로는 안 잡힌다. 하필 「이 목록에서 가장 교육적인」 카테고리다([01-core.md §3](../01-core.md))

**밖으로 나가는 것은 마지막 둘 때문이다** — 화면이 색을 칠하려면 값을 알아야 해서 `Snapshot.baselineCp` 와 `GameDetail.baselineCp` 둘이 생겼다. 판정·밴드·총평은 서버 안에서 끝난다.

`Verdict` 의 `BestCp`·`AfterCp` 는 **기준점을 안 뺀 원본으로 남긴다.** 재채점이 그 두 칸에서 도는 자리이고([§39 ⑥](21-40.md) · `005`), 기준점은 `games.start_sfen` 에서 언제든 다시 구할 수 있다.

**平手의 기준점은 0으로 못 박았다.** 실측은 +91이지만, 지금까지의 상수가 전부 0을 좌표로 잡혔다 — 265시도 재채점([§39](21-40.md))이 그 위에서 나왔고, 91을 넣는 순간 그 측정이 다른 기준의 것이 된다. 두 좌표의 차이는 발화선 635 vs 660으로 4%다.

### 처음 잰 값이 1.5배였다 — `FV_SCALE` 을 안 걸었다

컨테이너에서 엔진에 바로 `position sfen` → `go depth 14` 를 넣어 표를 만들었는데, 그 값이 전부 1.5배였다(二枚落ち 2288, 平手 163). **`setoption name FV_SCALE value 24` 를 안 보냈기 때문이다** — 프로덕션은 `Dockerfile` 의 `ENGINE_FV_SCALE=24` 로 돌고, 그 값이 곧 cp 척도다([§10](06-20.md)).

그 표로 상수를 박았다면 개입 임계치가 1.5배 척도 위에 앉는다. **잡은 것은 측정 테스트였다** — `internal/handicap/baseline_measure_test.go` 가 프로덕션과 같은 옵션으로 `usi.Pool` 을 띄우고 표와 나란히 찍는다. 지금은 여덟 줄 전부 차이 0이다.

> **엔진에 직접 넣어 잰 값은 프로덕션의 값이 아니다.** 재는 코드가 `usi.Pool` 을 지나가야 그 옵션들이 걸린다.

### 八枚落ち·十枚落ち는 아직 안 넣었다

기준점을 옮기면 판정은 거기서도 돈다(실측 +3258 · +4010). 뺀 이유는 다른 쪽이다 — **上手에 攻め駒가 하나도 없어 판이 개입이 아니라 詰め 연습이 된다.** 그건 기준점이 고쳐 주는 종류의 문제가 아니고, 넣을지는 플레이테스트가 답한다.

## 85. 검토 화면 — 뿌리가 셋이 됐고, 벽은 둘이 필요했다 (2026-08-19)

**사람이 직접 판을 움직여 가며 형세와 최선수 셋을 읽는 화면**이 들어왔다. 平手와 手合割 일곱 종 전부에서 0手目부터 열린다.

**새로 만든 것은 뿌리 하나와 화면 하나다.** 계산부는 [§37](21-40.md)의 `whatifNodeOf` 를 그대로 쓴다 — 국면 하나를 묻고 「국면 · 手番 · 합법수 · 값 · 후보 셋 · 여기까지의 줄」을 받는 그 장치다.

### 뿌리가 셋이 됐다

| 표면                              | 뿌리를 얻는 곳                     |
| --------------------------------- | ---------------------------------- |
| 되짚기 (`/api/games/{id}/whatif`) | DB 기록                            |
| 대국 중 (`ws` 의 `whatif`)        | 세션이 방금 보낸 스냅샷            |
| **검토 (`/api/explore`)**         | **手合割 표**(`internal/handicap`) |

깊이도 후보 수도 대국과 같다(`DefaultDepth`=12 · MultiPV 3). **다르게 두면 `positions` 가 서로 못 쓰는 무리로 갈리고**, 「탐색할수록 빨라진다」가 검토 안에서만 성립한다.

### 판을 안 받는 규약은 그대로다 — 그런데 이 표면이 그 문에 가장 가깝다

받는 것은 手合割 id와 수순뿐이고 서버가 매번 되짚어 한 수씩 룰 엔진에 검증시킨다. §37이 SFEN을 거절한 이유가 「아무 국면이나 깊이 12로 재 주는 공개 엔진이 된다」였는데, **뿌리가 0手目라 합법적으로 도달하는 국면이면 무엇이든 물을 수 있다.** 그래서 벽을 둘 세웠다.

|              |                                                                                                                                 |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------- |
| **로그인**   | 이 표면만 요구한다. 되짚기·대국은 뿌리가 자기 판이라 로그인이 자격을 정하지 않는데, 여기서 막는 것은 기록이 아니라 **엔진**이다 |
| **슬롯 1개** | 풀은 대국과 같은 3개다. 검토가 동시에 하나만 잡으므로 **대국에 언제나 둘이 남는다.** 넘치면 3초만 기다리고 「まだ読んでいます」 |

### 실측 (로컬, 치환표가 더워진 상태)

| 처음 보는 국면(端歩 6手)     | **534ms → 17ms** (같은 자리 두 번째)                                                  |
| ---------------------------- | ------------------------------------------------------------------------------------- |
| 二枚落ち 0手目               | **18ms** — 駒落ち 대국이 이미 쌓아 둔 행이다                                          |
| 二枚落ち 3手目               | 215ms → 15ms                                                                          |
| §54의 그 국면(`▲3三角成` 뒤) | `△同角 +2062` · `△同桂 +2008` · `△5二玉 +94` — **[§54](41-60.md)에 적힌 숫자와 같다** |

마지막 줄이 이 절에서 값진 자리다. 검토가 **되짚기가 쌓아 둔 행을 그대로 꺼내 썼다**는 뜻이고, 캐시가 표면을 가로질러 한 무리라는 것이 그것으로 확인된다.

### 手合에서 갈린 것 — 값을 옮기지 않고 **기준선을 말한다**

二枚落ち 0手目가 **+1525**이고 기준점이 +1490이다([§84](82-100.md)). 그 둘을 나란히 두지 않으면 초심자는 `+1525` 를 「압승 중」으로 읽는다.

**뺀 값을 보내는 쪽을 안 골랐다.** 빼면 같은 국면의 cp가 되짚기 그래프와 검토에서 다른 숫자가 되고, 그건 자가 둘이 되는 일이다. 대신 응답에 `baselineCp`·`handicapJa` 를 얹고 화면이 **「二枚落ちの互角は +1490 あたりです」** 를 한 줄로 말한다 — 후보 목록의 색도 그 값을 기준으로 칠한다(`evalTone` 의 base).

### 줄의 정본은 **주소**다

`?h=nimaiochi&m=7g7f,8c8d`. 화면이 상태로 안 들고 있어서 새로고침·뒤로 가기·링크 공유가 그대로 살아나고, **줄을 든 자리가 하나뿐이라 판과 주소가 어긋날 수 없다.**

- **`URLSearchParams` 로 읽으면 안 된다.** 폼 인코딩이라 `+` 를 공백으로 풀어서 `2b3c+`(成)가 `2b3c ` 가 되고, 모양 검사에서 그 한 수가 떨어지면서 줄 전체가 버려진다. 손으로 가르고 `decodeURIComponent` 로 풀면 `+` 도 `%2B` 도 맞는다
- **한 토큰이라도 모양이 아니면 줄 전체를 버린다.** 절반만 살리면 링크를 받은 사람이 보는 판과 준 사람이 본 판이 달라진다
- 수는 `replaceState`, **手合割은 `pushState`** 다. 手合을 바꾸면 줄이 통째로 없어지는데 이력에 남으므로 **뒤로 가기 한 번으로 돌아온다** — 「정말 버립니까」를 묻지 않는 이유다

### 대국 중에는 안 연다

아무 국면에서나 최선수 셋을 답하는 화면이라, 두는 중에 열리면 「평소엔 최선수를 보여주지 않는다」([01-core.md §1](../01-core.md))가 탭 하나로 뚫린다. **헤더가 그 탭을 안 그리고, 화면도 링크로 들어온 요청을 거절한다** — 벽이 둘인 것은 개입 카드의 `floor` 와 같은 이유다([§37](21-40.md) ②).

**서버는 이 벽을 모른다.** 두는 중인지를 알려면 그 사람에게 살아 있는 세션이 있는지를 봐야 하는데, 안 끝난 판은 「이어하기」로 오래 남으므로 DB로는 갈라지지 않는다.

**그래서 벽은 「열려 있는 탭 하나」 안에만 있다.** `playing` 은 그 탭의 모듈 상태이므로(`libs/game/playing.ts`) 탭 A에서 두면서 탭 B에서 `/explore` 를 열면 둘 다 안 걸린다. **ws 세션을 유저별로 등록해 두면 서버가 가를 수 있다** — 검토가 로그인을 요구하므로 익명 판은 애초에 이 물음의 대상이 아니고, 즉 등록부 하나로 완전해진다. 안 한 이유는 **빠뜨린 감소 하나가 사람을 검토에서 영구히 잠근다**는 것이고, 그 고장이 지금 구멍보다 나쁘다. 대외용 README는 그래서 단언을 안 한다.

### 판의 겹이 늘 50이었다 — 스크롤하면 헤더를 덮는다

`.game-board` 가 `z-index: 50` 으로 **박혀** 있었다. 그 값은 개입 때 판만 장막(40) 위에 남기기 위한 것인데(§14), sticky 헤더가 30이라 **판이 화면보다 길면 스크롤하는 동안 駒台와 판이 헤더를 덮었다.**

**검토가 만든 버그가 아니다** — 되짚기에서 「盤を反転」이 「あそびかた」를 가리고 있었고, 검토는 手合割 줄이 맨 위에 서서 그것을 눈에 띄게 했을 뿐이다.

**올려야 하는 것은 장막이 떠 있는 동안뿐이고, 그 상태는 이미 표시돼 있다** — `.game[data-intervening]`. 조건부로 바꾸자 세 화면이 함께 고쳐졌다. 확인은 양쪽이다: 개입 국면에서 판이 여전히 장막 위에 밝게 남고(계산값 50), 되짚기·검토는 헤더 아래로 지나간다.

### 안 만든 것

- **打 화살표의 출발점.** 최선수가 打이면 도착 칸만 찍힌다 — 駒台에서 자리를 재는 코드가 대국·되짚기에 이미 두 벌이고, 세 벌로 늘리는 대신 목록의 첫 줄이 어느 駒인지를 말하게 뒀다
- **지나온 자리의 cp.** 링크로 받은 줄은 마지막 수에만 값이 붙는다. 앞자리를 채우려면 手数마다 탐색을 하나씩 더 걸어야 하고(§37이 스크럽에서 막은 그 일이다), 안 가 본 자리는 빈칸이 맞다

## 86. 메인 화면 — 헤더 탭 다섯을 세로 메뉴 하나로 내렸다 (2026-08-20)

**탭 무리가 원래 하던 말과 다른 말을 하고 있었다.** 처음에는 배너에 기능이 없어서 화면 전환을 거기 얹었는데, 갈래가 늘면서 다섯이 됐고(対局·振り返り·検討·マイページ + あそびかた 알약 + 로그인 알약) 좁은 화면에서는 **줄 하나가 옆으로 스크롤되는 트랙**이 됐다. 값은 그것보다 다음 하나가 크다 — **두는 중에도 「지난 판 목록」이 판 위쪽에 늘 떠 있었다.** 판 위에서 생각하는 사람에게 「지금 갈 수 있는 다른 곳」을 계속 보여 주는 자리다.

이동을 화면 하나로 내렸다.

| 전                                          | 후                                                 |
| ------------------------------------------- | -------------------------------------------------- |
| `/` 가 대국. 이동은 헤더 탭 넷 + 알약 둘    | `/` 가 메뉴. **대국은 `/play`**                    |
| あそびかた — 로고 옆 알약, **새 탭**        | 메뉴의 한 줄, **같은 탭**                          |
| ログイン·ログアウト — 헤더 오른쪽 끝에 상시 | 로그인은 메뉴 마지막 줄, **로그아웃은 마이페이지** |
| 「対局中」 — 탭 이름 옆의 점 하나           | 헤더 오른쪽 끝의 알약. **누르면 그 판으로 간다**   |

### 주소를 하나 더 만들지 않고 `/` 를 내줬다

`/home` 을 새로 파고 대국을 `/` 에 두는 쪽이 링크가 안 깨져서 싸다. 그런데 **`/` 를 가리키는 것이 셋 있다** — 로그인이 끝나면 서버가 `/` 로 되돌려보내고(`auth.go`), `canonical` 과 `sitemap.xml` 의 첫 줄이 `/` 다. 메뉴를 만들고도 그 셋이 판을 가리키면 「메인 화면」이 사람이 실제로 도착하는 자리가 아니게 된다. 그래서 `/` 를 내주고 `sitemap` 에 `/play` 를 한 줄 더했다 — 「将棋 対局」으로 들어오는 사람이 닿아야 할 곳은 메뉴가 아니라 판이다.

**못 읽는 주소가 떨어지는 곳도 대국에서 홈으로 옮겼다.** 404 화면이 없는 앱이라 그 자리는 원래 대국이었는데, 길을 잃은 사람에게 갈 곳을 전부 세워 놓은 화면이 판보다 맞다.

### `<a href>` 를 그대로 둔 링크가 셋 있었다

**대국 화면은 라우트 밖에 상시 마운트다.** 그래서 브라우저가 문서를 통째로 새로 받는 링크는 그 화면이 들고 있던 것 — 방금 끝난 판의 총평 — 을 지운다.

전에는 그런 링크가 헤더 로고 하나였고 그것은 `/`(=대국) 자기 자신이라 눌릴 일이 없었다. 홈이 `/` 가 되면서 **로고가 처음으로 자기 화면이 아닌 곳을 가리키게** 됐고, 안내가 같은 탭이 되면서 그쪽의 「対局をはじめる」와 마이페이지의 「対局する」까지 셋이 됐다. 셋 다 `navigate` 를 타게 했다.

### 두는 중에는 판만 — 그래서 「감춰진 채 살아 있는 판」이 없어졌다

처음엔 지금까지처럼 **판을 감춰 두고** 헤더에 「対局中」 알약을 세워 돌아오게 했다. 만들고 보니 그 알약이 **자기가 만든 문제를 자기가 메우는 장치**였다 — 판이 살아 있는데 안 보이는 상태가 있어서 「내 판이 날아갔나」가 생기고, 표식은 그 하나를 위해 있는 것이다. **그 상태를 없애면 표식도 필요 없다.**

두는 중에 다른 주소로 들어오면 판으로 되돌린다(`replace`). 지난 판 목록을 판 위에서 여는 것이 이 앱에서 뜻이 없다 — 「지금 이 수」에 답하는 도구인데, 그 자리에서 다른 판을 펼치는 길을 열어 두면 판 위에서 생각하는 사람에게 「지금 갈 수 있는 다른 곳」이 계속 보인다.

같이 없어진 것: 헤더의 「対局中」 알약, 대국 중의 돌아가기 화살표, 홈 메뉴의 「指しかけの対局にもどる」. **두는 동안 헤더는 누를 것이 하나도 없는 이름표다**(로고도 링크가 아니다 — 눌러도 되돌아오는 링크는 고장으로 읽힌다).

- **`replace` 다.** 이력에 쌓으면 뒤로 가기가 두 자리를 오가고, 「판을 벗어날 수 없다」가 「뒤로 가기가 고장 났다」로 읽힌다
- **주소를 무시하고 판만 그리는 방법은 안 썼다.** 주소창이 `/reviews` 인데 판이 떠 있으면 새로고침과 링크 복사가 다른 화면을 가리킨다
- **연결이 끊기면 잠금이 풀려야 한다.** 마지막 스냅샷은 `playing` 인 채로 남으므로 「두는 중인가」를 그것만으로 세면 **소켓이 죽은 뒤에도 잠금이 걸려 있다** — 사람이 「接続が切れました」 화면에서 메뉴로 나갈 길을 잃는다. 판이 돌고 있다는 사실을 밖으로 내보내는 자리에서 연결 상태를 같이 본다(`GameScreen`)
- **그래도 대국 화면은 라우트 밖에 남는다.** 되돌리는 것은 그리고 난 뒤라 한 틱 동안 감춰지는데, **감춰지는 것과 내려가는 것은 다르다** — 내려갔다면 그 한 틱에 판이 닫힌다. 끝난 판의 총평이 거기 있는 것도 이유다(`playing` 이 내려가면 되돌리기가 풀리고, 그때 되짚기를 보러 갔다 오는 것은 정상적인 길이다)

### あそびかた를 새 탭에서 같은 탭으로 되돌렸다

[§79](61-81.md)가 새 탭으로 정한 근거는 「안내를 보고 싶어지는 때가 대국 중이고, 같은 탭이면 판이 화면에서 사라진다」였다. **위에서 그 전제를 없앴다** — 두는 중에는 안내 화면 자체가 안 열린다. 안내는 두기 전에 읽는 것이 됐고, 입구는 홈 메뉴 한 줄과 시작 화면 각주 둘이며 **둘 다 같은 탭**이다.

**잃은 것을 적어 둔다.** 「지금 무슨 일이 일어났나」를 대국 중에 안내로 확인하는 길이 없어졌다. 그 자리를 원래 맡는 것은 개입 카드 자신이고(그 순간의 사실을 그 자리에서 말한다), `/guide` 는 여전히 주소가 있어 사람이 손으로 탭을 하나 더 열 수는 있다. **플레이테스트에서 초심자가 대국 중에 막히면 그때 다시 연다** — 그때 여는 것은 메뉴가 아니라 판 옆의 작은 물음표 하나여야 한다.

### 안 만든 것

- **중단한 판의 알림을 홈에.** 「つづきから指しますか」는 `/play` 에 그대로 있다. 홈에 올리려면 `useResumable` 을 한 벌 더 부르거나 `playing.ts` 같은 모듈 상태를 하나 더 만들어야 하는데, 묻는 자리가 답하는 자리(판)와 붙어 있는 편이 낫다고 봤다
- **대국 중의 안내 입구.** 위 「잃은 것」 참조 — 여는 조건을 플레이테스트로 정한다
- **로그인 후 원래 자리로.** 서버는 여전히 `/` 로 되돌려보낸다. 메뉴가 그 자리라 전보다 덜 어색하고, 상태를 왕복시키는 값보다 크지 않다
