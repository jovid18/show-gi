## 82. Fargate에서 EC2 스팟 한 대로 옮겼다 (2026-08-17)

**0으로 내려둔 서비스가 CI를 상시 빨간불로 만들고 있었다.** 해커톤이 끝나고 `desired_count` 를 0으로 내렸는데(#93), 배포 워크플로의 마지막 스텝이 `https://show-gi.com/healthz` 를 확인한다 — 태스크가 0개면 ALB가 503이라 **머지마다 `Images` 가 실패한다.** 상시 빨간 CI는 안 보는 CI이고, 그때 진짜 배포 실패를 놓친다.

내려둔 이유는 값이었다.

| 구성                                   | 월 (추정) |
| -------------------------------------- | --------- |
| Fargate ARM 4 vCPU / 8 GiB (상시)      | ~$115     |
| **EC2 t4g.small 스팟 1대 + EBS 30GiB** | **~$8**   |

### 네 가지가 같이 움직여야 했다

**하나만 바꾸면 안 뜬다.** 각각이 다른 것을 강제한다.

| 바꾼 것                                          | 왜 강제되나                                                                                                                            |
| ------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------- |
| `network_mode` `awsvpc` → **`host`**             | EC2에서 `awsvpc` 태스크 ENI에는 공인 IP를 못 붙인다(그 옵션은 Fargate 전용). 밖으로 나갈 길이 NAT뿐인데 월 $40이라 인스턴스보다 비싸다 |
| 타깃 그룹 `target_type` `ip` → **`instance`**    | 태스크가 자기 IP를 안 갖는다                                                                                                           |
| `deployment_minimum_healthy_percent` 100 → **0** | 인스턴스가 태스크 하나에 맞춰진 한 대라 두 개가 동시에 못 올라간다. 그대로 두면 새 태스크가 배치되지 않고 서킷 브레이커가 롤백한다     |
| 엔진 풀 3+2 → **2+1**, 해시 128 → **64MB**       | 기본값이 2 GiB에 안 들어간다 (아래)                                                                                                    |

**`bridge` 는 후보가 아니었다.** Caddy가 `reverse_proxy localhost:8080` 으로 api 를 부르는데(`apps/web/Caddyfile`) bridge 는 컨테이너마다 네임스페이스를 갈라서 그 한 줄이 깨진다. `host` 는 둘이 인스턴스의 네임스페이스를 같이 쓰므로 그대로 닿는다 — awsvpc 에서 성립했던 것과 같은 이유다.

### 메모리는 실제로 예약된다

**Fargate와 가장 다른 점이다.** 태스크의 `memory` 가 「상한」이 아니라 인스턴스에서 빼는 예약이라, 넘게 적으면 태스크가 아예 배치되지 않는다.

| 항목                                        | 값                      |
| ------------------------------------------- | ----------------------- |
| t4g.small                                   | 2048 MiB                |
| OS + ECS 에이전트가 먹는 것                 | ~300 MiB                |
| 태스크가 쓸 수 있는 것                      | ~1750 MiB               |
| **기본값(엔진 5개 × (NNUE 63 + 해시 128))** | **~955 MiB**            |
| \+ Go 힙 · Caddy                            | ~280 MiB                |
| **기본값 합계**                             | **~1.3 GiB**            |
| 줄인 뒤(엔진 3개 × (63 + 64))               | ~380 MiB                |
| **줄인 뒤 합계 · `task_memory`**            | **~710 MiB · 1536 MiB** |

**1536으로 태스크가 배치됐다**(2026-08-17 apply). 위의 「OS + 에이전트 ~300 MiB」는 추정이었는데, 그 값이 틀렸다면 태스크가 `PENDING` 에 머물렀을 것이다 — 배치됐다는 것이 그 추정의 유일한 검증이다. **남는 여유가 실제로 얼마인지는 아직 안 쟀다** `[미확정]`.

**풀을 줄여도 되는 근거는 사람이 한 명이라는 것이다.** 세 풀이 동시에 필요한 것은 상대 수·선행 계산·mate 탐색이 겹칠 때인데, 한 사람이 한 수를 두는 동안 그 셋은 순서대로 온다. 탐색 2 + mate 1이면 개입 판정과 상대 수가 겹치는 것까지 덮는다.

### apply 뒤 실측 (2026-08-17)

| 확인                  | 결과                                                                     |
| --------------------- | ------------------------------------------------------------------------ |
| `/healthz`            | `{"db":true,"engine":true,"ok":true}` — **엔진이 떴다**(메모리가 맞았다) |
| `/` (Caddy 정적)      | 200 · 4,125 bytes                                                        |
| `/api/openings`       | JSON — Caddy → `localhost:8080` 이 `host` 모드에서 그대로 닿는다         |
| `/api/me`             | `{"enabled":true,"user":null}` — SSM의 Google 자격증명이 실렸다          |
| `/api/resumable`      | `{"game":null}` — RDS 읽기가 인스턴스에서 된다                           |
| `/ws/game` 업그레이드 | **`101 Switching Protocols`** — ALB → instance 타깃을 지나 WS가 선다     |
| apply 직후 첫 요청    | 503 (약 20초) → 200. 스팟 확보·에이전트 등록·이미지 pull·엔진 기동의 합  |

> **`/ws/game` 은 HTTP/1.1로 확인해야 한다.** curl 이 HTTP/2로 붙으면 `Connection: Upgrade` 헤더가 규격상 벗겨져서 서버가 426을 준다 — 서버 문제가 아니다. `--http1.1` 을 붙인다.

### 무엇을 내주었나

- **배포마다 1~2분 내려간다.** 옛 태스크를 내리고 새 것을 띄우는 순서라서다. 무중단을 되찾으려면 인스턴스를 두 대로 늘리거나(값 2배) 태스크를 반으로 줄여야 한다
- **스팟 회수 시 2~3분 내려간다.** `ECS_ENABLE_SPOT_INSTANCE_DRAINING` 이 2분 전 통보에 태스크를 내리고 ALB가 타깃을 빼므로 죽은 인스턴스로 요청이 가지는 않는다. 대국 중이었으면 그 판은 `aborted` 로 닫히고 이어하기가 살린다([§51](41-60.md))
- **T 계열이라 CPU가 크레딧으로 돈다.** `cpu_credits = "standard"` 로 뒀다 — 넘기면 느려지는 대신 청구가 예측 가능하다. `unlimited` 은 엔진 탐색이 크레딧을 태우기 쉬운 모양(한 수에 CPU를 몰아 쓴다)이라 놀라운 청구서가 될 수 있다

### 정한 것

- **용량 공급자(capacity provider)를 안 만든다.** 하는 일이 태스크 수를 보고 인스턴스를 늘리는 것인데 태스크도 인스턴스도 1로 고정이다. 서비스가 `launch_type = "EC2"` 로 등록된 인스턴스에 바로 얹는다
- **ASG는 스케일링을 안 한다.** 1/1/1 고정이고, 하는 일은 「스팟이 회수되면 새 인스턴스를 받아 온다」 하나다
- **ASG의 헬스체크는 `EC2` 다(ALB가 아니다).** 배포 중에 태스크가 잠깐 내려가는데 ALB 기준으로 보면 ASG가 그것을 인스턴스 고장으로 읽고 멀쩡한 인스턴스를 죽인다 — 그러면 배포마다 인스턴스가 새로 뜬다
- **`show-gi-migrate` 태스크는 Fargate로 남긴다.** 인스턴스가 앱 태스크 하나에 맞춰져 있어 얹을 자리가 없다 — EC2로 바꾸면 배치가 안 돼서 `PROVISIONING` 에 머문다
- **타깃 그룹은 `name` 이 아니라 `name_prefix` 다.** `target_type` 이 변경 불가 속성이라 값을 고치면 교체되는데, 이름이 고정이면 terraform 이 「지우고 만들기」로 잡아서 리스너가 참조 중인 옛 것을 못 지우고 apply 가 교착한다

### 남은 비용 구조

컴퓨트가 더 이상 가장 큰 항목이 아니다 — 월 약 $42 중 **ALB(약 $18)와 RDS(약 $15)가 8할**이다. 더 줄일 곳을 찾는다면 그 둘이고, ALB는 TLS 종료·ACM 자동 갱신·WebSocket 유지가 얹혀 있어 그냥 빼면 인증서가 스팟의 휘발성 디스크로 내려간다([deploy/README.md](../../deploy/README.md) 「비용과 정리」).

### 운영자 정책이 v5가 됐다

`terraform apply` 가 시작 템플릿과 ASG를 만들어야 하는데 `show-gi-operator` 에 `ec2:Describe*` 만 있었다. **정책은 사람이 admin 자격으로 올린다** — 운영자는 자기 권한을 못 올린다([06-status.md](../06-status.md) §7).

**apply 가 세 번 막혔고, 막힌 순서가 그대로 목록이다.** 미리 다 예측하지 못했다는 것이 이 절에 남길 사실이다 — 이 정책은 Fargate 시절에 만들어져서 **인스턴스 프로파일을 한 번도 만들어 본 적이 없었다.**

| 회차 | 막힌 곳                  | 모자랐던 것                                                                                                                                           |
| ---- | ------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| 0    | (예상해서 미리 넣음)     | `ec2:*LaunchTemplate*` · `autoscaling:*` · 화이트리스트에 인스턴스 롤용 관리형 정책 둘 · `iam:PassRole` 에 `ec2.amazonaws.com` · ASG 서비스 링크드 롤 |
| 1    | `CreateInstanceProfile`  | **`iam:TagInstanceProfile`** — 프로바이더 `default_tags` 가 프로파일에도 붙는다. `iam:TagRole` 만 있었다                                              |
| 2    | `CreateAutoScalingGroup` | **`ec2:RunInstances`** — ASG가 시작 템플릿을 참조할 때 AWS가 RunInstances 인가를 먼저 확인한다                                                        |

`Untag`·`ListTags` 계열은 2회차에서 같이 넣었다. 아직 안 막혔지만 태그를 바꾸거나 지울 때 각각 다른 액션이고, **여기서는 실패 한 번이 정책 왕복 한 번**이라 그쪽이 더 비싸다.

`autoscaling:*` 만 와일드카드다. 좁게 적으면 terraform 이 refresh 때 부르는 `Describe` 가 계속 하나씩 빠져서 apply 가 권한 하나에 막히는 일이 반복된다 — 리전 조건이 이미 범위를 잡는다. 정책 크기는 **5,132 / 6,144자**로, 다음에 권한을 더할 때는 줄일 자리를 같이 찾아야 한다.

## 83. 사람끼리 두는 판 — 초대 링크 하나가 열쇠다 (2026-08-18)

**요청은 「사용자끼리 매칭해서 두게 하고, URL로 남이 못 들어오게, 로그인한 사람만」이었다.**

### 정한 것 다섯

|           |                                                                                                                                                                                                              |
| --------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 만나는 법 | **초대 링크만.** 대기열을 안 만든다 — 동시 접속자가 없으면 대기열은 아무도 못 두는 화면이고, 지금 이 앱의 동시 접속자는 대개 0이다                                                                           |
| 보조 기능 | **개입·힌트·待った 전부 끔.** [02-architecture.md §7](../02-architecture.md) 위협 1이 이미 정해 둔 것이고, 롤백은 상대를 기다리게 만드는 데다 「저쪽이 무슨 수를 뒀다가 물렀나」까지 그 사람 화면에 드러낸다 |
| 기록      | **`games` 행 두 개.** 각자 자기 판을 갖는다                                                                                                                                                                  |
| 手番      | **先手·後手·振り駒 셋.** 振り駒는 **서버가** 뽑는다 — 클라이언트가 뽑으면 마음에 안 드는 결과를 다시 뽑을 수 있고, 그러면 고르는 것과 같아진다                                                               |
| 평가치    | **판이 끝난 뒤에 채운다.** 두는 동안에는 엔진이 한 번도 안 돈다                                                                                                                                              |
| 시계      | **1手 60초.** 넘기면 시간패. 실측이 아니라 정한 값이다                                                                                                                                                       |

### 방에 들어가는 규칙은 셋이고, 셋이 다 필요하다

1. **로그인한 사람만.** 익명은 서로 구별할 수단이 없어서(`002_anonymous_games.sql`) 「이 방의 상대가 아까 그 사람인가」에 답할 수가 없다
2. **id 를 유추할 수 없다.** `crypto/rand` → 영숫자 8자(62^8, 약 47.6비트). `games.id` 같은 연번이면 로그인한 아무나 훑는다
3. **정원 2명.** 두 자리가 차면 그 뒤로는 링크를 알아도 **관전조차** 안 된다

하나라도 빠지면 나머지가 무너진다 — 1이 없으면 링크를 받은 누구나 남의 자리에 앉고, 2가 없으면 링크가 필요 없어지고, 3이 없으면 세 번째 사람이 판을 들여다본다.

**거절은 404 하나다.** 없는 방·만료된 방·남이 이미 찬 방·**로그인 안 한 요청**이 전부 같은 답을 받는다. 마지막 것이 요점 — 401은 「로그인하면 볼 수 있다」는 뜻이라, 그것만으로 **그 방이 있다는 사실이 로그인 없이 새어 나간다.** 이어하기가 남의 판 번호에 대해 하는 것과 같은 판단이다([§46](41-60.md)).

**한 사람이 들고 있을 수 있는 안 시작한 방은 셋까지다.** 방이 프로세스 메모리에 있으므로 상한이 없으면 로그인한 사람 하나가 30분 동안 계속 쌓을 수 있다. 넘으면 **거절이 아니라 오래된 것을 버린다** — 방을 또 만든 사람이 원하는 것은 대개 마지막 링크 하나이고, 거절은 「왜 안 되나」를 화면에 설명해야 한다. **사람이 걸려 있는 방은 절대 안 버린다** — 시작한 판은 물론이고 **손님이 앉기만 한 방**도 그렇다(걷어가면 그쪽에서 기다리던 사람이 영영 기다리고, 방 주인은 자기 방에 다시 못 들어간다).

**손님은 앉기 전에 한 번 확인한다.** WebSocket 이 붙는 순간 자리가 확정되고 시계가 돌기 시작하므로, 링크를 잘못 누른 사람이 모르는 사이에 남의 방을 닫으면 안 된다. 그래서 `GET /api/rooms/{id}` 는 **자리를 안 잡는다.**

### 시계가 있는 이유는 「빨리 두게 하려고」가 아니다

**판이 끝나게 하려고다.** 엔진 대국은 연결이 끊기면 그 판이 `abandoned` 로 닫히는데([§46](41-60.md)), 대인전은 **상대가 남아 있어서 끝낼 수가 없다.** 한쪽이 탭을 닫으면 그 판이 영원히 「두는 중」으로 남고, 그러면 되짚기에도 안 걸리고 결과도 없다.

그래서 **접속이 끊겨도 판을 안 멈춘다.** 멈추면 지고 있는 쪽이 탭을 닫아 판을 얼릴 수 있고, 시계가 있는 이유와 정면으로 어긋난다. 끊긴 사람은 같은 링크로 다시 들어와 이어 둔다 — 그동안 자기 시계는 흐른다.

**대국이 시작되는 조건은 「둘이 동시에 붙어 있을 것」이다.** 「들어온 적이 있다」로 세면, 링크를 보내고 탭을 닫은 방 주인이 손님이 여는 순간 시간패로 진다.

**방이 걷히면 기다리던 연결에 알린다.** 지우기만 하면 그쪽은 영영 「상대를 기다립니다」에 서 있고, 그동안 **이미 죽은 링크를 광고한다** — 상대가 열면 404를 받는데 방 주인은 아직 기다리는 줄 안다. 걷히는 자리가 둘(만료·상한)이라 둘 다 같은 채널로 알린다. **훑는 계기도 둘이다** — 남이 Hub 를 건드릴 때와 1분마다 도는 티커(`sweepLoop`). 티커가 없으면 혼자 기다리는 방은 아무도 안 와서 영영 안 걷힌다.

**한 수도 안 둔 채 시간이 다 되면 승패를 안 적는다.** 링크를 보내고 탭을 열어 둔 채 자리를 뜨는 것이 흔한데, 그때 승패를 적으면 **0手짜리 판**이 두 사람의 전적에 win/loss 로 남고 이긴 쪽의 「振り返り」 링크가 빈 판을 연다. 아무도 안 뒀으면 판이 없었던 것이다.

**내 연결이 끊긴 것은 화면이 크게 말한다.** 판은 서버에서 그대로 돌고 **내 시계도 그대로 흐르는데**, 화면은 마지막 스냅샷을 들고 있어서 아무 일도 없어 보인다 — 그동안 시간패로 지고 있다. 상대가 자리를 비운 것과 같은 무게로 그리면 안 되는 이유가 그것이다.

**끝난 판도 11분은 더 답한다**(`finishedGrace` = `FinishedTTL` + 1분). 投了를 받은 쪽이 그 순간 새로고침하는 것은 드문 일이 아닌데, 그때 문을 닫아 두면 결과 대신 오류가 뜬다. **1분이 일을 한다** — 방과 같은 값으로 두면 둘이 닫히는 순서가 안 정해져서, 「방은 아직 열려 있는데 테이블이 이미 닫힌」 창이 생긴다. 길게 두면 들어온 사람은 언제나 둘 중 하나를 받는다: 방이 살아 있으면 결과를, 방이 걷혔으면 404를.

### 평가치는 판이 끝난 뒤에 채운다

대인전에 엔진을 안 붙이는 것은 규약이라 `eval_cp` 가 통째로 비고, 되짚기의 평가치 궤적이 빈 채로 열린다. 그런데 그 빈 상태 문구(「評価値が残っていません」)는 `eval_cp` 가 뒤에 붙은 컬럼이라 생긴 **옛 판용**이었다 — 대인전이 그것을 매번 만나면 「이 갈래에는 원래 없다」로 읽힌다.

**판이 끝난 뒤 서버가 기보를 다시 재서 채운다.** 두는 동안이 아니라는 것이 요점이고, 그래서 위협 1(대국 중 소프트 참조)과 어긋나지 않는다.

|              |                                                                                                                                                      |
| ------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| 무엇을 쓰나  | 이때는 `eval_cp` 뿐이었다. 판정(`Judgement.Verdict`)은 버렸다 — 개입이 대인전에 없어서다. **[§95](82-100.md)가 그 판정으로 실력 추정도 쌓게 바꿨다** |
| 몇 번 재나   | **한 번.** `eval_cp` 는 先手 관점이고 뒤집는 것은 되짚기라, 같은 값이 두 행에 그대로 들어간다                                                        |
| 동시에 몇 판 | **하나.** 엔진 풀이 지금 두고 있는 사람들과 공유라, 여러 판을 같이 돌리면 그쪽 상대 수가 그만큼 느려진다                                             |
| 상태는 어디  | **서버 메모리.** 배포하면 하던 분석이 끊기고 그 판은 평가치 없이 남는다 — 방과 같은 성질이다                                                         |
| 기보는       | **안 기다린다.** 수는 둘 때 이미 들어갔고, 채우는 것은 그 뒤에 붙는 값들이다([§95](82-100.md))                                                       |

화면은 분석 중일 때 「評価値を分析しています…」를 그리고 5초마다 다시 묻는다. 「분석 중」과 「남지 않았다」를 갈라 두지 않으면, 판이 끝나자마자 들어온 사람이 기다리면 되는 것을 없는 것으로 안다.

### 기록 — 행 하나가 아니라 둘인 이유

소유 검사를 타는 질의가 다섯이다(`ListGamesForOwner`·`GetGameForOwner`·`CountGameResultsForOwner`·`CountInterventionCategoriesForOwner`·`CountGameStyleTagsForOwner`). 각자 자기 행을 가지면 **그 다섯이 한 줄도 안 바뀐다.**

한 행에 `opponent_user_id` 를 더하는 쪽도 재 봤는데, 그러면 다섯 질의를 전부 `OR` 로 고쳐야 하고 **`my_color` 가 소유자 기준이라 상대가 열면 先手·後手가 뒤집힌다** — 화면에 나가는 cp가 전부 「플레이어 관점」이라는 규약이 두 갈래로 갈린다. 부호 뒤집기는 [§33](21-40.md)에서 이미 한 번 물린 자리라, 아끼는 것(디스크 몇 KB)보다 무는 것이 크다.

값은 **기보가 두 벌 저장되는 것**과, 두 행을 다시 묶을 열쇠가 필요한 것 하나(`games.match_id`, 마이그레이션 `012`).

### 그 대신 닫아야 할 자리가 셋이었다

대인전 판에는 **엔진 판정이 없어서 `eval_cp` 가 비고 `interventions` 가 0건이다.** 그것을 그대로 두면 화면이 「블런더 없이 잘 둔 판」이라고 말하는데, 사실은 **재지 않았다**이고 그 둘이 초심자에게 정반대다.

| 자리              | 그대로 두면                             | 닫는 법                              |
| ----------------- | --------------------------------------- | ------------------------------------ |
| 총평              | 「一度も止められませんでした」가 나간다 | `/api/games/{id}/summary` 가 404     |
| 되짚기 퀴즈       | 「아직 만드는 중」에서 영영 안 벗어난다 | `ready:true` · 링크 자체를 안 그린다 |
| 마이페이지의 집계 | 「崩れやすいところ」의 비율이 희석된다  | 세 질의에 `match_id IS NULL`         |

**전적은 갈라 센다.** 되짚기 목록에는 그대로 뜨고(「対人」 표식이 붙는다) 마이페이지의 집계에서만 빠진다 — 목록은 「무엇을 뒀나」이고 집계는 개입 비율이 뜻을 갖는 자리라, 모집단이 달라야 하는 쪽은 뒤다.

### 왜 `internal/game` 을 안 늘렸나

그쪽은 `HumanColor` 하나 + `Opponent`(엔진) 하나가 전제이고, 개입·판정·힌트·무르기·실력 추정이 그 위에 얹혀 있다. 사람 둘을 그 안에 넣으면 **그 다섯을 전부 「사람 상대면 끄기」로 감싸게 되고**, 개입 쪽을 고칠 때마다 이쪽이 안 깨졌는지 매번 확인해야 한다.

`internal/match` 는 `internal/shogi`(룰)와 시계뿐이다 — **`usi` 를 import 하지 않는다.** 엔진 없는 배포에서도 대인전이 도는 것이 그 사실의 증거이고, 실제로 그 테스트가 엔진 없이 돈다.

갈라 둔 자리가 하나 더 있다: **`game.Side`(human/engine)를 못 쓴다.** 사람이 둘이라 절대 이름을 쓰면 같은 기보가 두 화면에서 같은 색으로 그려진다 — 그래서 스냅샷을 **보는 사람마다** 펴서 보낸다(`you`/`opponent`).

### 실측

로컬에서 사람 하나(브라우저)와 스크립트 하나로 한 판을 끝까지 돌렸다.

| 확인한 것                            | 결과                                                           |
| ------------------------------------ | -------------------------------------------------------------- |
| 방 id                                | 영숫자 8자, 500개 중 중복 0                                    |
| 세 번째 사람의 `GET /api/rooms/{id}` | 404 — 없는 방과 **응답 본문까지 같다**                         |
| 대국이 시작되는 시점                 | 둘이 동시에 붙은 그 자리. 한쪽만 붙어 있으면 시작되지 않는다   |
| 착수 왕복                            | ▲7六歩 → △9二香, 두 화면의 棋譜가 같고 `by` 만 반대            |
| 시계                                 | 60초에서 내려가고, 착수마다 다시 60초                          |
| 시간패                               | 넘긴 쪽이 패. 「持ち時間がなくなりました」                     |
| 기록                                 | `games` 행 두 개(1081 `w`/`win`, 1082 `b`/`loss`), 기보 각 2수 |
| 마이페이지                           | 그 판이 전적에서 빠짐(5판 중 4판)                              |

**`summaryOf` 가 `match_id` 를 안 옮기고 있었다.** 그러면 `isMatch` 가 언제나 false 라 위의 「닫아야 할 자리 셋」이 하나도 안 닫힌다 — 실물로 돌리기 전까지 안 보였고, 끝까지 도는 테스트(`TestTwoPeoplePlayAMatch`)가 그것을 잡았다.

### 두 갈래가 만나는 자리를 네 번 막았다

대인전 판이 `games` 에 섞여 들어가므로, **엔진 대국의 장치가 그 행을 집는 자리**를 전부 찾아야 했다. 소유 조건을 안 건드린 대신 이쪽이 늘었다.

| 자리                 | 그대로 두면                                                                                    |
| -------------------- | ---------------------------------------------------------------------------------------------- |
| 마이페이지의 집계 셋 | 개입 0건인 판이 분모에 들어가 「崩れやすいところ」 비율이 희석된다                             |
| 총평                 | 「一度も止められませんでした」가 나간다 — 사실은 **재지 않았다**이다                           |
| 되짚기 퀴즈          | 「아직 만드는 중」에서 영영 안 벗어난다                                                        |
| **이어하기**         | **사람과 두던 수순이 엔진 세션으로 이어진다** — 그 판의 두 행이 갈라져 같은 대국이 아니게 된다 |

마지막 것이 제일 위험하고 제일 늦게 보였다. 배포가 대국 중에 끼면 테이블이 접히면서 **수가 있는 행이 `abandoned` 로 닫히는데**, 그것이 정확히 이어하기 목록의 조건이다. 조건은 목록과 점유 **양쪽**에 넣었다 — 목록에서만 빼면 번호를 직접 넣어 그대로 열린다.

### 남은 것

- **방은 프로세스 메모리다.** 배포하면 열려 있던 방이 사라진다 — 두는 중에 배포가 끼면 엔진 대국도 지금 그 자리에서 끊기므로 대인전만 더 잃는 것은 없다
- **持ち時間(총 시간)과 秒読み은 없다.** 화면에 시계 둘이 필요하고, 그 전에 「끝나기는 하는가」를 먼저 세웠다
- **대기열이 없다.** 링크를 보낼 상대가 있어야 둘 수 있다

## 84. 접쇼기(駒落ち) — 판은 이미 섰고 판정식이 안 섰다 (2026-08-19)

「말을 떼고 둔다」를 열었다. 香落ち · 角落ち · 飛車落ち · 飛香落ち · 二枚落ち · 四枚落ち · 六枚落ち 일곱 종이다.

### 배선은 이미 있었다

`StartSFEN` 이 끝에서 끝까지 이미 흐르고 있었다 — `game.Config` → `usi`(언제나 `position sfen`, `startpos` 를 안 쓴다) → `games.start_sfen` → 이어하기 · 되짚기 · 가정 수순 · 퀴즈. 룰 엔진도 駒 수를 안 세고, `positions` 캐시 키는 手数 뺀 SFEN이라 국면이 겹치지도 않는다. **그래서 「판을 세우는 일」은 쿼리 하나(`?handicap=`)였다.**

**마이그레이션이 없다.** 手合割을 되짚는 값이 `games.start_sfen` 하나로 충분해서다 — 이름을 따로 저장하면 그 칸과 실제 판이 갈릴 수 있고, 갈리면 화면이 「二枚落ち」라고 적어 둔 판에 飛車가 서 있게 된다. 목록 세 질의에 그 칸을 더한 것이 전부다.

### 문제는 판정식이었다 — 승률이 판 전체에서 포화한다

[01-core.md §2](../01-core.md)가 이미 적어 둔 구멍이다: 「양쪽 끝에서 포화한다. 실전에서 문제가 안 되는 이유는 거기까지 가는 길목의 `0 → -800`이 먼저 걸리기 때문이고, **판정을 건너뛰는 구간이 있으면 그 보호가 사라진다**」. **駒落ち는 판 전체가 그 구간이다.**

실측(水匠5 · depth 14 · `FV_SCALE=24` · Threads=1 · Hash=128). 「발화선」은 입문 임계치 0.25를 넘기는 최소 낙폭이다.

> **아래 표는 下手가 先指하던 국면의 것이다.** 手番 규약이 [§88](82-100.md)에서 上手 先指로 뒤집혀 여덟 줄이 전부 옮겨 갔다 — **지금 도는 값은 그쪽이다.**

| 手合     | 초기 cp | WR(K=600) | 발화선(기준점 없이) | 기준점을 빼면 |
| -------- | ------: | --------: | ------------------: | ------------: |
| 平手     |      91 |    0.5378 |                 635 |   635(그대로) |
| 香落ち   |     270 |    0.6106 |                 614 |           660 |
| 角落ち   |     756 |    0.7790 |                 687 |           660 |
| 飛車落ち |     741 |    0.7747 |                 682 |           660 |
| 飛香落ち |     865 |    0.8087 |                 724 |           660 |
| 二枚落ち |    1490 |    0.9230 |            **1058** |           660 |
| 四枚落ち |    1834 |    0.9551 |            **1312** |           660 |
| 六枚落ち |    2011 |    0.9662 |            **1456** |           660 |

**平手 줄의 두 칸이 같은 것이 요점이다** — 기준점이 0이라 그 판의 판정은 한 비트도 안 바뀐다. 갈리는 것은 아래뿐이다.

**二枚落ち에서 銀을 공짜로 줘도(약 1000cp, [§2](../01-core.md)) 안 걸린다.** 六枚落ち면 그보다 1.5배를 흘려야 한다 — 초심자가 가장 필요로 하는 手合에서 개입이 조용해진다. 같은 압축이 `internal/skill` 의 낙폭에도 걸리므로, 그 판들은 사람을 실제보다 잘 두는 것으로 추정하고 그 값이 `skill_profile` 에 남아 **다음 平手 판까지 옮겨 간다.**

### 정한 것 — 기준점 하나가 셋을 고친다

`intervene.Input.BaselineCp` 한 칸을 더하고 두 항에서 같이 뺀다.

```
Δ = WR(best - baseline) - WR(after - baseline)
```

- **판정** — 「아직 아무것도 안 흘렸다」가 다시 승률 0.5에 오므로 어느 手合에서도 660cp 언저리에서 걸린다
- **밴드**(`game.adaptiveOpponent`) — 절대 좌표의 원점이 같이 옮겨 간다. 안 옮기면 첫 수부터 `now` 가 상단 위라 상대 좌표 분기로만 가고, 그러면 상대가 **핸디캡을 되돌려 주는 일을 아예 안 한다**: 사람이 +1490을 +500까지 흘려도 「지금 형세에서 100~300 더」만 겨냥한다. [§55](41-60.md)가 고친 것의 **거울상**이다
- **총평의 「이기고 있었다」**(`explain.StandingAheadRate`) — 二枚落ち에서 +1100으로 끝난 판은 핸디캡의 절반을 잃은 판인데, 기준점을 안 빼면 「圧倒的に有利でした」가 나간다
- **되짚기의 형세 그래프**(`EvalGraph`) — 축이 승률이라 곡선이 판 내내 천장에 붙는다. 「어디서 흘렸나」가 안 보이는 것보다 나쁜 것은 **50% 선이 핸디캡을 다 잃은 자리에 그려지는 것**이다
- **후보 줄의 색**(`evalTone`) — ±800cp에서 포화하므로 六枚落ち의 후보는 **한 줄도 빠짐없이 최대 파랑**이 된다. 방금 물러진 수까지 그렇게 칠하고, 빨강은 아예 안 나온다
- **`shallow_trap` 카테고리**(`intervene.classify`) — 「얕게는 좋아 보이고 깊게는 나쁘다」를 절대 부호로 읽던 유일한 규칙이다. 안 옮기면 앞 조건이 언제나 참이고 뒤 조건이 거의 언제나 거짓이라, 판정은 걸리는데 이름이 `other` 로 떨어진다 — **개입은 살아 있고 설명만 조용히 나빠지는** 모양이라 눈으로는 안 잡힌다. 하필 「이 목록에서 가장 교육적인」 카테고리다([01-core.md §3](../01-core.md))

**밖으로 나가는 것은 마지막 둘 때문이다** — 화면이 색을 칠하려면 값을 알아야 해서 `Snapshot.baselineCp` 와 `GameDetail.baselineCp` 둘이 생겼다. 판정·밴드·총평은 서버 안에서 끝난다.

`Verdict` 의 `BestCp`·`AfterCp` 는 **기준점을 안 뺀 원본으로 남긴다.** 재채점이 그 두 칸에서 도는 자리이고([§39 ⑥](21-40.md) · `005`), 기준점은 `games.start_sfen` 에서 언제든 다시 구할 수 있다.

**平手의 기준점은 0으로 못 박았다.** 실측은 +91이지만, 지금까지의 상수가 전부 0을 좌표로 잡혔다 — 265시도 재채점([§39](21-40.md))이 그 위에서 나왔고, 91을 넣는 순간 그 측정이 다른 기준의 것이 된다. 두 좌표의 차이는 발화선 635 vs 660으로 4%다.

### 처음 잰 값이 1.5배였다 — `FV_SCALE` 을 안 걸었다

컨테이너에서 엔진에 바로 `position sfen` → `go depth 14` 를 넣어 표를 만들었는데, 그 값이 전부 1.5배였다(二枚落ち 2288, 平手 163). **`setoption name FV_SCALE value 24` 를 안 보냈기 때문이다** — 프로덕션은 `Dockerfile` 의 `ENGINE_FV_SCALE=24` 로 돌고, 그 값이 곧 cp 척도다([§10](06-20.md)).

그 표로 상수를 박았다면 개입 임계치가 1.5배 척도 위에 앉는다. **잡은 것은 측정 테스트였다** — `internal/handicap/baseline_measure_test.go` 가 프로덕션과 같은 옵션으로 `usi.Pool` 을 띄우고 표와 나란히 찍는다. 지금은 여덟 줄 전부 차이 0이다.

> **엔진에 직접 넣어 잰 값은 프로덕션의 값이 아니다.** 재는 코드가 `usi.Pool` 을 지나가야 그 옵션들이 걸린다.

### 八枚落ち·十枚落ち는 아직 안 넣었다

기준점을 옮기면 판정은 거기서도 돈다(실측 +3258 · +4010). 뺀 이유는 다른 쪽이다 — **上手에 攻め駒가 하나도 없어 판이 개입이 아니라 詰め 연습이 된다.** 그건 기준점이 고쳐 주는 종류의 문제가 아니고, 넣을지는 플레이테스트가 답한다.

## 85. 검토 화면 — 뿌리가 셋이 됐고, 벽은 둘이 필요했다 (2026-08-19)

**사람이 직접 판을 움직여 가며 형세와 최선수 셋을 읽는 화면**이 들어왔다. 平手와 手合割 일곱 종 전부에서 0手目부터 열린다.

**새로 만든 것은 뿌리 하나와 화면 하나다.** 계산부는 [§37](21-40.md)의 `whatifNodeOf` 를 그대로 쓴다 — 국면 하나를 묻고 「국면 · 手番 · 합법수 · 값 · 후보 셋 · 여기까지의 줄」을 받는 그 장치다.

### 뿌리가 셋이 됐다

| 표면                              | 뿌리를 얻는 곳                     |
| --------------------------------- | ---------------------------------- |
| 되짚기 (`/api/games/{id}/whatif`) | DB 기록                            |
| 대국 중 (`ws` 의 `whatif`)        | 세션이 방금 보낸 스냅샷            |
| **검토 (`/api/explore`)**         | **手合割 표**(`internal/handicap`) |

깊이도 후보 수도 대국과 같다(`DefaultDepth`=12 · MultiPV 3). **다르게 두면 `positions` 가 서로 못 쓰는 무리로 갈리고**, 「탐색할수록 빨라진다」가 검토 안에서만 성립한다.

### 판을 안 받는 규약은 그대로다 — 그런데 이 표면이 그 문에 가장 가깝다

받는 것은 手合割 id와 수순뿐이고 서버가 매번 되짚어 한 수씩 룰 엔진에 검증시킨다. §37이 SFEN을 거절한 이유가 「아무 국면이나 깊이 12로 재 주는 공개 엔진이 된다」였는데, **뿌리가 0手目라 합법적으로 도달하는 국면이면 무엇이든 물을 수 있다.** 그래서 벽을 둘 세웠다.

|              |                                                                                                                                 |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------- |
| **로그인**   | 이 표면만 요구한다. 되짚기·대국은 뿌리가 자기 판이라 로그인이 자격을 정하지 않는데, 여기서 막는 것은 기록이 아니라 **엔진**이다 |
| **슬롯 1개** | 풀은 대국과 같은 3개다. 검토가 동시에 하나만 잡으므로 **대국에 언제나 둘이 남는다.** 넘치면 3초만 기다리고 「まだ読んでいます」 |

### 실측 (로컬, 치환표가 더워진 상태)

| 처음 보는 국면(端歩 6手)     | **534ms → 17ms** (같은 자리 두 번째)                                                  |
| ---------------------------- | ------------------------------------------------------------------------------------- |
| 二枚落ち 0手目               | **18ms** — 駒落ち 대국이 이미 쌓아 둔 행이다                                          |
| 二枚落ち 3手目               | 215ms → 15ms                                                                          |
| §54의 그 국면(`▲3三角成` 뒤) | `△同角 +2062` · `△同桂 +2008` · `△5二玉 +94` — **[§54](41-60.md)에 적힌 숫자와 같다** |

마지막 줄이 이 절에서 값진 자리다. 검토가 **되짚기가 쌓아 둔 행을 그대로 꺼내 썼다**는 뜻이고, 캐시가 표면을 가로질러 한 무리라는 것이 그것으로 확인된다.

### 手合에서 갈린 것 — 값을 옮기지 않고 **기준선을 말한다**

二枚落ち 0手目가 **+1525**이고 기준점이 +1490이다([§84](82-100.md)). 그 둘을 나란히 두지 않으면 초심자는 `+1525` 를 「압승 중」으로 읽는다.

**뺀 값을 보내는 쪽을 안 골랐다.** 빼면 같은 국면의 cp가 되짚기 그래프와 검토에서 다른 숫자가 되고, 그건 자가 둘이 되는 일이다. 대신 응답에 `baselineCp`·`handicapJa` 를 얹고 화면이 **「二枚落ちの互角は +1490 あたりです」** 를 한 줄로 말한다 — 후보 목록의 색도 그 값을 기준으로 칠한다(`evalTone` 의 base).

### 줄의 정본은 **주소**다

`?h=nimaiochi&m=7g7f,8c8d`. 화면이 상태로 안 들고 있어서 새로고침·뒤로 가기·링크 공유가 그대로 살아나고, **줄을 든 자리가 하나뿐이라 판과 주소가 어긋날 수 없다.**

- **`URLSearchParams` 로 읽으면 안 된다.** 폼 인코딩이라 `+` 를 공백으로 풀어서 `2b3c+`(成)가 `2b3c ` 가 되고, 모양 검사에서 그 한 수가 떨어지면서 줄 전체가 버려진다. 손으로 가르고 `decodeURIComponent` 로 풀면 `+` 도 `%2B` 도 맞는다
- **한 토큰이라도 모양이 아니면 줄 전체를 버린다.** 절반만 살리면 링크를 받은 사람이 보는 판과 준 사람이 본 판이 달라진다
- 수는 `replaceState`, **手合割은 `pushState`** 다. 手合을 바꾸면 줄이 통째로 없어지는데 이력에 남으므로 **뒤로 가기 한 번으로 돌아온다** — 「정말 버립니까」를 묻지 않는 이유다

### 대국 중에는 안 연다

아무 국면에서나 최선수 셋을 답하는 화면이라, 두는 중에 열리면 「평소엔 최선수를 보여주지 않는다」([01-core.md §1](../01-core.md))가 탭 하나로 뚫린다. **헤더가 그 탭을 안 그리고, 화면도 링크로 들어온 요청을 거절한다** — 벽이 둘인 것은 개입 카드의 `floor` 와 같은 이유다([§37](21-40.md) ②).

**서버는 이 벽을 모른다.** 두는 중인지를 알려면 그 사람에게 살아 있는 세션이 있는지를 봐야 하는데, 안 끝난 판은 「이어하기」로 오래 남으므로 DB로는 갈라지지 않는다.

**그래서 벽은 「열려 있는 탭 하나」 안에만 있다.** `playing` 은 그 탭의 모듈 상태이므로(`libs/game/playing.ts`) 탭 A에서 두면서 탭 B에서 `/explore` 를 열면 둘 다 안 걸린다. **ws 세션을 유저별로 등록해 두면 서버가 가를 수 있다** — 검토가 로그인을 요구하므로 익명 판은 애초에 이 물음의 대상이 아니고, 즉 등록부 하나로 완전해진다. 안 한 이유는 **빠뜨린 감소 하나가 사람을 검토에서 영구히 잠근다**는 것이고, 그 고장이 지금 구멍보다 나쁘다. 대외용 README는 그래서 단언을 안 한다.

### 판의 겹이 늘 50이었다 — 스크롤하면 헤더를 덮는다

`.game-board` 가 `z-index: 50` 으로 **박혀** 있었다. 그 값은 개입 때 판만 장막(40) 위에 남기기 위한 것인데(§14), sticky 헤더가 30이라 **판이 화면보다 길면 스크롤하는 동안 駒台와 판이 헤더를 덮었다.**

**검토가 만든 버그가 아니다** — 되짚기에서 「盤を反転」이 「あそびかた」를 가리고 있었고, 검토는 手合割 줄이 맨 위에 서서 그것을 눈에 띄게 했을 뿐이다.

**올려야 하는 것은 장막이 떠 있는 동안뿐이고, 그 상태는 이미 표시돼 있다** — `.game[data-intervening]`. 조건부로 바꾸자 세 화면이 함께 고쳐졌다. 확인은 양쪽이다: 개입 국면에서 판이 여전히 장막 위에 밝게 남고(계산값 50), 되짚기·검토는 헤더 아래로 지나간다.

### 안 만든 것

- **打 화살표의 출발점.** 최선수가 打이면 도착 칸만 찍힌다 — 駒台에서 자리를 재는 코드가 대국·되짚기에 이미 두 벌이고, 세 벌로 늘리는 대신 목록의 첫 줄이 어느 駒인지를 말하게 뒀다
- **지나온 자리의 cp.** 링크로 받은 줄은 마지막 수에만 값이 붙는다. 앞자리를 채우려면 手数마다 탐색을 하나씩 더 걸어야 하고(§37이 스크럽에서 막은 그 일이다), 안 가 본 자리는 빈칸이 맞다

## 86. 메인 화면 — 헤더 탭 다섯을 세로 메뉴 하나로 내렸다 (2026-08-20)

**탭 무리가 원래 하던 말과 다른 말을 하고 있었다.** 처음에는 배너에 기능이 없어서 화면 전환을 거기 얹었는데, 갈래가 늘면서 다섯이 됐고(対局·振り返り·検討·マイページ + あそびかた 알약 + 로그인 알약) 좁은 화면에서는 **줄 하나가 옆으로 스크롤되는 트랙**이 됐다. 값은 그것보다 다음 하나가 크다 — **두는 중에도 「지난 판 목록」이 판 위쪽에 늘 떠 있었다.** 판 위에서 생각하는 사람에게 「지금 갈 수 있는 다른 곳」을 계속 보여 주는 자리다.

이동을 화면 하나로 내렸다.

| 전                                          | 후                                                 |
| ------------------------------------------- | -------------------------------------------------- |
| `/` 가 대국. 이동은 헤더 탭 넷 + 알약 둘    | `/` 가 메뉴. **대국은 `/play`**                    |
| あそびかた — 로고 옆 알약, **새 탭**        | 메뉴의 한 줄, **같은 탭**                          |
| ログイン·ログアウト — 헤더 오른쪽 끝에 상시 | 로그인은 메뉴 마지막 줄, **로그아웃은 마이페이지** |
| 「対局中」 — 탭 이름 옆의 점 하나           | 헤더 오른쪽 끝의 알약. **누르면 그 판으로 간다**   |

### 주소를 하나 더 만들지 않고 `/` 를 내줬다

`/home` 을 새로 파고 대국을 `/` 에 두는 쪽이 링크가 안 깨져서 싸다. 그런데 **`/` 를 가리키는 것이 셋 있다** — 로그인이 끝나면 서버가 `/` 로 되돌려보내고(`auth.go`), `canonical` 과 `sitemap.xml` 의 첫 줄이 `/` 다. 메뉴를 만들고도 그 셋이 판을 가리키면 「메인 화면」이 사람이 실제로 도착하는 자리가 아니게 된다. 그래서 `/` 를 내주고 `sitemap` 에 `/play` 를 한 줄 더했다 — 「将棋 対局」으로 들어오는 사람이 닿아야 할 곳은 메뉴가 아니라 판이다.

**못 읽는 주소가 떨어지는 곳도 대국에서 홈으로 옮겼다.** 404 화면이 없는 앱이라 그 자리는 원래 대국이었는데, 길을 잃은 사람에게 갈 곳을 전부 세워 놓은 화면이 판보다 맞다.

### `<a href>` 를 그대로 둔 링크가 셋 있었다

**대국 화면은 라우트 밖에 상시 마운트다.** 그래서 브라우저가 문서를 통째로 새로 받는 링크는 그 화면이 들고 있던 것 — 방금 끝난 판의 총평 — 을 지운다.

전에는 그런 링크가 헤더 로고 하나였고 그것은 `/`(=대국) 자기 자신이라 눌릴 일이 없었다. 홈이 `/` 가 되면서 **로고가 처음으로 자기 화면이 아닌 곳을 가리키게** 됐고, 안내가 같은 탭이 되면서 그쪽의 「対局をはじめる」와 마이페이지의 「対局する」까지 셋이 됐다. 셋 다 `navigate` 를 타게 했다.

### 두는 중에는 판만 — 그래서 「감춰진 채 살아 있는 판」이 없어졌다

처음엔 지금까지처럼 **판을 감춰 두고** 헤더에 「対局中」 알약을 세워 돌아오게 했다. 만들고 보니 그 알약이 **자기가 만든 문제를 자기가 메우는 장치**였다 — 판이 살아 있는데 안 보이는 상태가 있어서 「내 판이 날아갔나」가 생기고, 표식은 그 하나를 위해 있는 것이다. **그 상태를 없애면 표식도 필요 없다.**

두는 중에 다른 주소로 들어오면 판으로 되돌린다(`replace`). 지난 판 목록을 판 위에서 여는 것이 이 앱에서 뜻이 없다 — 「지금 이 수」에 답하는 도구인데, 그 자리에서 다른 판을 펼치는 길을 열어 두면 판 위에서 생각하는 사람에게 「지금 갈 수 있는 다른 곳」이 계속 보인다.

같이 없어진 것: 헤더의 「対局中」 알약, 대국 중의 돌아가기 화살표, 홈 메뉴의 「指しかけの対局にもどる」. **두는 동안 헤더는 누를 것이 하나도 없는 이름표다**(로고도 링크가 아니다 — 눌러도 되돌아오는 링크는 고장으로 읽힌다).

- **`replace` 다.** 이력에 쌓으면 뒤로 가기가 두 자리를 오가고, 「판을 벗어날 수 없다」가 「뒤로 가기가 고장 났다」로 읽힌다
- **주소를 무시하고 판만 그리는 방법은 안 썼다.** 주소창이 `/reviews` 인데 판이 떠 있으면 새로고침과 링크 복사가 다른 화면을 가리킨다
- **연결이 끊기면 잠금이 풀려야 한다.** 마지막 스냅샷은 `playing` 인 채로 남으므로 「두는 중인가」를 그것만으로 세면 **소켓이 죽은 뒤에도 잠금이 걸려 있다** — 사람이 「接続が切れました」 화면에서 메뉴로 나갈 길을 잃는다. 판이 돌고 있다는 사실을 밖으로 내보내는 자리에서 연결 상태를 같이 본다(`GameScreen`)
- **그래도 대국 화면은 라우트 밖에 남는다.** 되돌리는 것은 그리고 난 뒤라 한 틱 동안 감춰지는데, **감춰지는 것과 내려가는 것은 다르다** — 내려갔다면 그 한 틱에 판이 닫힌다. 끝난 판의 총평이 거기 있는 것도 이유다(`playing` 이 내려가면 되돌리기가 풀리고, 그때 되짚기를 보러 갔다 오는 것은 정상적인 길이다)

### あそびかた를 새 탭에서 같은 탭으로 되돌렸다

[§79](61-81.md)가 새 탭으로 정한 근거는 「안내를 보고 싶어지는 때가 대국 중이고, 같은 탭이면 판이 화면에서 사라진다」였다. **위에서 그 전제를 없앴다** — 두는 중에는 안내 화면 자체가 안 열린다. 안내는 두기 전에 읽는 것이 됐고, 입구는 홈 메뉴 한 줄과 시작 화면 각주 둘이며 **둘 다 같은 탭**이다.

**잃은 것을 적어 둔다.** 「지금 무슨 일이 일어났나」를 대국 중에 안내로 확인하는 길이 없어졌다. 그 자리를 원래 맡는 것은 개입 카드 자신이고(그 순간의 사실을 그 자리에서 말한다), `/guide` 는 여전히 주소가 있어 사람이 손으로 탭을 하나 더 열 수는 있다. **플레이테스트에서 초심자가 대국 중에 막히면 그때 다시 연다** — 그때 여는 것은 메뉴가 아니라 판 옆의 작은 물음표 하나여야 한다.

### 안 만든 것

- **중단한 판의 알림을 홈에.** 「つづきから指しますか」는 `/play` 에 그대로 있다. 홈에 올리려면 `useResumable` 을 한 벌 더 부르거나 `playing.ts` 같은 모듈 상태를 하나 더 만들어야 하는데, 묻는 자리가 답하는 자리(판)와 붙어 있는 편이 낫다고 봤다
- **대국 중의 안내 입구.** 위 「잃은 것」 참조 — 여는 조건을 플레이테스트로 정한다
- **로그인 후 원래 자리로.** 서버는 여전히 `/` 로 되돌려보낸다. 메뉴가 그 자리라 전보다 덜 어색하고, 상태를 왕복시키는 값보다 크지 않다

## 87. 검토의 후보가 넷이었다 — 지워지지 않는 줄 하나 (2026-08-20)

프로덕션 제보. 「73手目 · 先手の最善手」 아래에 줄이 **넷**이고 순위가 `1 · 1 · 2 · 3` 이었다. 첫 줄만 상대 쪽 수(`△7六桂 +3001`)였고, **국면을 옮겨도 그 줄은 안 없어졌다.**

후보는 서버가 셋까지만 만든다(`whatifCandidates = 3`). 넷째 줄은 이 국면의 후보가 아니라 **옛 국면의 줄이 DOM에 남은 것**이다.

### 두 층이 겹쳤다

**① 엔진 결과에 같은 수가 두 번 들어간다.** 순위 칸은 깊이마다 덮어써지는데(`usi.parseScore`), 마지막 iteration에서 안 온 순위는 **얕은 깊이의 줄을 그대로 들고 남는다.** 그 수가 다른 순위의 수와 같으면 후보 목록에 같은 수가 둘로 선다. `Ranked` 는 빈 순위와 중복 **순위**만 걸렀고 중복 **수**는 안 봤다.

로컬 `positions` 1,485행을 셌다.

| 같은 수가 두 번 들어간 행 | 그중 상위 3 안 | 그 행들의 `computed_depth` |
| ------------------------- | -------------- | -------------------------- |
| 15행 (1.0%)               | 4행            | **전부 12**                |

깊이 12는 검토가 **캐시에서 그대로 내주는** 깊이다(`whatifDepth`). 한 번 그렇게 쌓인 행은 다시 안 재므로 그 국면은 계속 같은 목록을 낸다.

**② 화면이 그 목록을 지우지 못한다.** 줄의 열쇠가 수(`key={c.usi}`)였다. 같은 수가 둘이면 열쇠가 겹치고, React는 그 자리를 **지우지 못한 채 남긴다** — 그래서 다음 국면으로 가도 옛 줄이 1위 자리에 남고, 새로고침 전까지 안 없어진다.

프로덕션 번들에서 그대로 재현했다. `/api/explore` 응답을 가로채 중복 후보를 한 번 흘리고 다음 국면으로 옮기니 제보와 같은 그림(`1 △7六桂 / 1 ▲同銀 / 2 ▲同角 / 3 ▲同玉`)이 나왔고, 두 수 더 나아가도 첫 줄이 그대로 있었다.

### 정한 것 — 세 자리를 다 막는다

| 자리                  | 무엇을                         | 왜 여기도                                                        |
| --------------------- | ------------------------------ | ---------------------------------------------------------------- |
| `usi.Ranked`          | 같은 수는 **깊은 쪽만** 남긴다 | 후보 순서의 정본이다. 여기서 막으면 새로 재는 국면은 전부 낫는다 |
| `server.candidatesOf` | 이미 나온 수는 버린다          | 검토는 **캐시를 직접 읽어** `Ranked` 를 안 지난다(`evalOf`)      |
| `Candidates.tsx`      | 열쇠를 수에서 **순위**로       | 서버가 어떻게 뚫려도 화면에 지워지지 않는 줄이 남으면 안 된다    |

`Ranked` 에서 순위가 아니라 **깊이**로 고르는 것이 요점이다. 남는 쪽이 마지막 iteration의 값이라야 낙폭이 안 어긋난다.

같이 낫는 자리: 手筋 힌트의 게이트가 후보를 `map[수]cp` 로 되접는데(`tesuji_hint.go`), 중복이 있으면 **점수 내림차순의 뒤엣것 — 얕은 값 — 이 이겼다.** 그리고 「k줄을 다 받았는가」(`decided`)도 이제 **서로 다른 수 k개**를 뜻한다.

### 안 한 것

- **이미 쌓인 행을 지우는 마이그레이션.** 읽는 자리 둘이 다 거르므로 값이 없고, 공유 DB에 되돌릴 수 없는 작업을 돌릴 이유가 아니다
- **퀴즈의 `Lines[0]` · `Lines[1]` 직접 읽기.** `quiz.score` 는 `Ranked` 를 안 쓴다. 중복이면 1위−2위 차가 0이 되어 그 문항이 조용히 빠질 뿐이라 틀린 것을 가르치지는 않지만, `Ranked` 를 쓰는 다른 자리들과 규약이 갈려 있다

## 88. 駒落ち는 上手가 먼저 둔다 — 手番 한 글자가 기준점 표를 옮겼다 (2026-08-20)

**手合割의 관례는 접어 준 上手가 先指다.** [§84](82-100.md)가 세운 판은 반대였다 — 표의 SFEN 일곱 줄이 전부 `b`(下手 차례)로 끝나 있었고, 주석·테스트·시작 화면의 문구까지 그 규약 위에 서 있었다.

**고친 것은 手番 칸 한 글자다.** 그런데 기준점이 곧 그 국면의 평가치라, **표가 통째로 다른 국면의 값이 됐다.**

### 실측 — 一手가 香車 한 장쯤이다

水匠5 · depth 14 · `FV_SCALE=24` · Threads=1 · Hash=128. **下手 관점 cp**이고, 0手目가 上手 차례라 엔진이 준 부호를 뒤집어 적는다(`baseline_measure_test.go`). 「발화선」은 기준점을 안 뺐을 때 입문 임계치(0.25)를 넘기는 최소 낙폭이다.

| 手合     | 옛(下手 先指) | 지금(上手 先指) | 차이 | 발화선(기준점 없이) |
| -------- | ------------: | --------------: | ---: | ------------------: |
| 平手     |            91 |      91(그대로) |    0 |                 635 |
| 香落ち   |           270 |          **97** | −173 |                 634 |
| 角落ち   |           756 |         **627** | −129 |                 652 |
| 飛車落ち |           741 |         **658** |  −83 |                 659 |
| 飛香落ち |           865 |         **726** | −139 |                 678 |
| 二枚落ち |          1490 |        **1386** | −104 |                 989 |
| 四枚落ち |          1834 |        **1561** | −273 |                1107 |
| 六枚落ち |          2011 |        **2003** |   −8 |                1450 |

**香落ち가 平手 실측(+91)에서 6cp다.** 一手의 값이 香車 한 장에 가깝다는 뜻이고, 手合割이 「香落ち는 平手에 가장 가깝다」고 말해 온 자리가 숫자로 그대로 나왔다.

**순서가 관례와 같아졌다.** 옛 값은 角落ち(756)가 飛車落ち(741)보다 커서 목록 순서와 거꾸로였고, `TestBaselineRisesWithTheHandicap` 이 그 한 줄을 건너뛰어야 했다. 627·658이 되면서 **예외가 없어졌다.**

발화선은 기준점을 빼면 어느 手合에서도 그대로 660cp 언저리다 — 바뀐 것은 「안 뺐을 때 얼마나 나쁜가」쪽이다. 二枚落ち가 1058 → 989로 내려와 銀 헌납(약 1000cp, [01-core.md §2](../01-core.md))에 간신히 닿지만, **그 「간신히」에 판정을 걸지 않는다**(四枚·六枚落ち는 여전히 1107·1450이다).

### 화면 값도 다시 쟀다 (depth 12)

검토와 가정 수순은 `game.DefaultDepth` = 12로 묻는다. 문서가 인용해 온 「二枚落ち 0手目 +1525」가 여기서 바뀐다.

| 手合     | depth 12 (下手 관점) | 기준점(depth 14) |
| -------- | -------------------: | ---------------: |
| 香落ち   |                  117 |               97 |
| 角落ち   |                  606 |              627 |
| 飛車落ち |                  636 |              658 |
| 飛香落ち |                  721 |              726 |
| 二枚落ち |             **1383** |         **1386** |
| 四枚落ち |                 1536 |             1561 |
| 六枚落ち |                 1894 |             2003 |

**二枚落ち는 화면 값이 기준점보다 3cp 낮다.** 화면이 값을 옮기지 않고 「二枚落ちの互角は +1386 あたりです」를 한 줄로 말하는 구조라([§84](82-100.md)) 그 3cp가 하는 일은 없다.

### 판이 열린 자리가 사람 차례가 아니게 됐다

**코드가 안 늘었다.** 세션은 「엔진이 선수면 시작하자마자 생각한다」를 `pos.Turn != HumanColor` 하나로 판단하므로(`game.Session.run`), SFEN의 手番이 바뀐 것만으로 첫 수가 엔진의 것이 된다 — 平手 後手 판이 이미 그 길을 쓰고 있었다.

바뀐 것은 **기다리는 자리**다. 실엔진 테스트(`TestWSKomaochiAgainstRealEngine`)가 上手의 1手目를 받은 뒤에 첫 착수를 보낸다 — 안 기다리면 「네 차례가 아니다」로 거절되고, 그 실패는 手番 규약이 뒤집힌 것과 구별되지 않는다.

검토의 뿌리도 「내 차례」가 아니다. 관점은 여전히 下手로 못박혀 있고(`exploreRoot`), 양쪽을 다 움직이는 화면이라 그것으로 끝난다.

### 옛 기록을 살리려고 `Of` 의 키에서 手番을 뺐다

手合을 되짚는 값이 `games.start_sfen` 하나인데([§84](82-100.md)) 뒤집기 전에 시작한 판은 그 칸에 `b` 로 남아 있다. 키가 手番까지 맞추면 그 판들이 되짚기에서 **手合割을 잃고 기준점 0으로 그려진다** — 二枚落ち면 「호각」 선이 1386cp 어긋난 자리에 간다.

**어느 駒를 뺐나가 이미 手合을 정하므로** 판과 持ち駒로만 맞춘다. 대가는 그 판들의 기준점이 一手만큼(83~273cp) 어긋난 값이 되는 것이고, 1386cp보다 훨씬 작다.

### 八枚·十枚落ち도 다시 쟀다 — 여전히 안 넣는다

+3014 · +3890(옛 +3258 · +4010). 뺀 이유가 기준점이 아니라 **上手에 攻め駒가 하나도 없어 판이 개입이 아니라 詰め 연습이 된다**는 것이라([§84](82-100.md)) 값이 옮겨간 것과 무관하다.

### 화면에서 갈린 것

| 자리      | 어떻게                                                                                                                       |
| --------- | ---------------------------------------------------------------------------------------------------------------------------- |
| 시작 화면 | 「あなたが下手（先手）から指します」가 거짓이 됐다 → **「あなたが下手です。駒を落とした上手（相手）から先に指す」**로 바꿨다 |
| 안내 화면 | 「上手의 駒가 빠진 상태로 시작한다」에 **「그 上手부터 둔다」**를 더했다. 先手/後手를 고르는 것은 平手에서만이라는 것도 같이 |
| 그 밖     | 手番 라벨(下手/上手)·기준점 배선·색 계산은 **한 줄도 안 바뀌었다** — 값이 서버에서 오고 사람의 색이 그대로 下手라서다        |

### 남은 것

- **香落ち의 97과 平手의 0이 계단을 만든다.** 平手는 실측 +91을 쓰지 않고 0으로 못박아 뒀는데([§84](82-100.md)), 上手 先指로 재니 香落ち가 그 +91에서 6cp다 — 사실상 같은 국면인 두 手合이 97cp 다른 좌표에서 판정된다. 발화선으로는 634 vs 635라 이번에는 안 건드렸다 `[미확정]`
- 발화선 660cp가 駒落ち 초심자에게 맞는 값인지는 그대로 못 잰다(K=600과 같은 벽, [§39](21-40.md))

## 89. 주석이 문서를 두 번 쓰고 있었다 — 마크다운을 걷고 수사를 줄였다 (2026-08-20)

기능은 안 건드렸다. 읽기 힘들다는 지적이 나온 자리를 재고, 규칙을 하나 못박고, 그 규칙으로 전부 다시 썼다.

### 실측 — 무엇이 길게 만들었나

| 무엇                         | 얼마                                       |
| ---------------------------- | ------------------------------------------ |

### 무엇을 정했나

- **「~것이 요점이다」로 끝내지 않는다.** 결론을 먼저 평서문으로 쓰고 이유를 `—` 뒤에 붙인다
- **한 문단은 세 줄까지.** 넘으면 대개 두 가지를 한 자리에서 말하고 있다 — 서버에서 5줄 넘는 문단이 17개였고 넷을 갈랐다
- 규칙은 [CLAUDE.md](../../CLAUDE.md) 「문서」 절에 넣었다. 안 넣으면 다음 회차에 그대로 돌아온다

### 문서를 두 번 쓰던 자리 — 26곳을 §NN으로 바꿨다

「20자 이상이 `docs/` 와 겹치면 지우고 §NN으로 가리킨다」를 전수로 돌렸다. 서브에이전트가 주석 블록 703개를 훑어 판정했고, 걸린 것이 26곳이다. 같은 실측이 **다섯 벌까지** 있었다 — 駒落ち 기준점의 989·1107·660cp가 `handicap.go` · `judge.go` · `baseline_measure_test.go` · `judge_test.go` · `handicap_test.go` 에 각각 적혀 있었고 원본은 [§88](82-100.md) 하나다.

「지우기 전에 옮길 곳을 확인한다」에 걸려 **남긴 것도 있다.** `blunder_mate_measure_test.go` 의 「중앙값이 대국의 88% 지점」은 `docs/` 에 없는 유일본인데, 같은 §40이 뒤에서 그 백분율 척도 자체를 폐기했다 — 결론은 참이고 숫자만 폐기된 자로 잰 것이라, 지우는 대신 그 사실을 한 줄로 적었다.

## 90. 관측이 0이었다 — 로그를 구조화하고 지표를 CloudWatch까지 보냈다 (2026-08-20)

**「장애를 어떻게 알아채나」에 답할 자료가 하나도 없었다.** 서버 Go 42,467줄에 관측 코드가 0줄이고, 프로덕션에서 보이는 것은 평문 로그 한 줄기뿐이다.

### 실측 — 붙이기 전에 있던 것

| 항목                                  | 값                                                   |
| ------------------------------------- | ---------------------------------------------------- |
| `log/slog` 사용                       | 0곳 — 전부 `log.Print*` 이고 108곳(api 가 지나는 것) |
| metrics · tracing                     | 0 — prometheus·otel·expvar·pprof 없음                |
| Container Insights                    | `disabled` (`infra/ecs.tf` — 요금)                   |
| 알람                                  | 0                                                    |
| 「엔진 풀이 언제 포화하나」에 답할 값 | 없음                                                 |

풀 대기가 이 앱에서 지연의 거의 전부인데(빌리는 자리가 여섯인데 프로덕션 풀이 탐색 2개다) 그 값을 아무도 안 재고 있었다.

### 표면을 둘로 갈랐다 — 요금이 그 이유다

EMF 는 **차원 조합 하나가 곧 과금 대상 지표 하나**다. `route` 를 차원으로 올리면 경로 수만큼 지표가 생겨 월 $7.5가 되고, 그 대부분은 아무도 안 보는 경로다.

|             | `/metrics`                        | CloudWatch EMF                    |
| ----------- | --------------------------------- | --------------------------------- |
| 형식        | Prometheus 텍스트                 | stdout 에 JSON 한 줄              |
| 라벨        | route·status·pool·result 전부     | 차원은 `Service`·`Environment` 둘 |
| 지표 수     | 계열만큼                          | **10개** (월 $3 정도)             |
| 어디서 보나 | 태스크 안(Caddy 가 안 프록시한다) | 콘솔·알람                         |

### EMF 가 받는 값은 숫자 아니면 100개 이하 배열뿐이다

스펙을 먼저 확인했다 — `Values`/`Counts` 같은 히스토그램 형식이 **없다.** 그래서 하나를 둘로 나눠 낸다.

- **개수는 카운터로** 낸다. 정확하다
- **분포는 표본 배열로** 낸다. 100개가 상한이라 넘으면 알고리즘 R로 자리를 바꾼다 — 앞의 100개만 남기면 회차 앞머리의 요청만 백분위에 들어간다
- **교체 확률의 분모는 회차 기준이어야 한다.** 표본은 회차마다 비우는데 분모를 누적 관측 수로 두면 확률이 회차가 지날수록 0으로 내려가, 배열이 결국 「그 회차 앞머리 100건」으로 굳는다. 셀프리뷰가 이걸 잡았다 — 20회차 × 500건으로 재 보니 느린 절반의 표본이 53개에서 0개로 말라갔고, 하필 바쁜 분에 p95 가 0.01초로 나온다

그래서 **CloudWatch 의 `Sum`·`SampleCount` 는 지연 지표에 쓰지 않는다.** 표본에서 나온 값이라 백분위·최대만 유효하다.

**카운터는 증분으로 낸다.** 누적값을 올리면 `Sum` 이 회차마다 지금까지의 전부를 다시 더해 단조증가하는 계단이 되고, 그 위에는 알람을 걸 수 없다.

### 계측하는 자리가 셋뿐이다

| 자리                    | 나오는 것                        |
| ----------------------- | -------------------------------- |
| `usi.Pool.Acquire`      | 풀 대기 시간 · 점유 수 · 풀 크기 |
| `archive.SearchMultiPV` | 탐색 시간 · **캐시가 답했나**    |
| HTTP 미들웨어           | 요청 수 · 상태 · 지연 · 요청 ID  |

`archive` 하나가 엔진을 부르는 여섯 자리를 다 덮는다 — 기록을 그 자리에 붙인 것과 같은 이유이고([§37](21-40.md)), 계측도 같은 이유로 한 곳이면 된다.

**안 기다린 탐색도 대기 0으로 넣는다.** 기다린 것만 재면 표본이 「밀린 회차」만 남아 백분위가 늘 나쁘게 보인다.

**탐색 시간에는 풀 대기가 들어 있다.** 재는 자리가 풀 바깥이라(`archive`) 부르는 쪽이 실제로 기다린 시간이고, 엔진 자체의 시간은 거기서 대기를 뺀 것이다 — 그 둘을 따로 내는 것이 「느린 것이 엔진이냐 줄이냐」를 가르는 유일한 방법이다.

### 깨질 수 있었던 자리 둘

- **`ResponseWriter` 를 감쌀 때 `Unwrap()` 이 없으면 대국이 통째로 안 열린다.** `coder/websocket` 이 감싼 것을 `Unwrap` 으로 되짚어 `Hijacker` 를 찾는다 — 없으면 업그레이드가 501이고, 그건 미들웨어를 붙인 순간 전부 깨지는 종류다. 기존 WS 테스트가 그물이 됐다
- **`r.Pattern` 은 `ServeMux` 가 요청에 직접 채운다.** 그래서 미들웨어가 mux 밖에 있어야 읽힌다 — 안쪽에 두면 빈 문자열이고, route 라벨이 통째로 `other` 가 된다

### 셀프리뷰가 잡은 것 셋

- **표본 교체 확률의 분모**(위 「EMF 가 받는 값」). 20회차 × 500건에서 느린 절반의 표본이 53개 → 0개로 말라갔다
- **핸들러 panic 이 지표에도 로그에도 안 남았다.** `net/http` 가 연결만 끊으므로 상태 코드조차 없다 — 가장 흔한 장애에 5xx 알람이 조용하다. 미들웨어가 잡아 500으로 답하고 스택을 `Error` 로 남긴다
- **정상 타깃 알람이 배포마다 울리는 값이었다**(1분 × 2회). 배포가 유일한 태스크를 먼저 내리는 구조라 그 창 안에 들어간다

**하나는 리뷰의 처방이 반대였다.** 「점유 게이지를 `select` 앞에서 내려라」를 그대로 따랐더니 이중 `Release` 에서 게이지가 **−1로 굳는다** — `default` 갈래는 풀이 이미 꽉 찬 자리라 점유가 0인 상태다. 원래 자리(돌아온 갈래)가 맞고, 테스트로 못 박았다.

### 무엇을 정했나

- **`slog.SetDefault` 가 `log` 패키지 출력까지 흡수한다.** 남은 `log.Print*` 들이(위 표) 그대로 JSON 한 줄로 나가므로 **옮겨 적지 않았다** — 옮겨서 얻는 것은 필드뿐이고, 필드가 필요한 자리(`cmd/api` 의 기동 로그)만 옮겼다
- **로그는 stderr, EMF 는 stdout.** 둘 다 같은 로그 그룹에 들어가지만 로컬에서 한쪽만 보는 편이 낫다
- **요청 ID 는 `ctx` 에 실어 로그 핸들러가 붙인다.** 핸들러가 직접 넘기게 두면 어느 줄에서든 빠지고, 빠진 줄이 되짚을 때 바로 그 없는 줄이 된다
- **업그레이드(101)는 지연 분포에서 뺀다.** 대국 한 판이 분 단위라 다른 경로의 백분위를 못 읽게 만든다. 세션의 길이는 `ws_sessions_active` 와 요청 로그가 든다
- **안 걸린 경로는 `other` 하나로 모은다.** 실제 경로를 라벨로 쓰면 스캐너 하나가 계열을 무한히 늘리고, 그 메모리는 프로세스가 사는 동안 안 돌아온다
- **`ENVIRONMENT` 하나가 EMF 를 켜고 끈다.** 비면 안 낸다 — 로컬 stdout 오염이 절반, 켠 줄 모르고 커스텀 지표가 쌓이는 것이 나머지 절반이다. 그때도 `/metrics` 는 그대로 있다
- **사람이 먼저 끊은 요청은 499로 센다.** 검토·가정 수순은 엔진을 기다리다 요청 ctx 가 죽으면 그 에러를 503으로 답하는데(`explore.go` 의 default 갈래), 탐색이 몇 초라 「눌러 놓고 다른 화면으로 가는」 것이 흔하다 — 그걸 5xx 로 세면 알람이 정상 사용에 울린다. 나간 상태 코드는 로그에 그대로 남기고 지표 라벨만 가른다
- **`Environment` 는 필드가 아니라 차원이다.** 루트 필드로만 두면 CloudWatch 가 메타데이터로 취급해서, 두 번째 배포(스테이징·디버그 태스크)가 프로덕션과 같은 계열에 값을 섞고 알람이 그걸 평가한다. 차원으로 올리면 개수는 배포 환경 수만큼만 늘어난다
- **알람 셋.** 「사이트가 떴나」는 ALB 의 `HealthyHostCount`(AWS 가 항상 낸다), 「무엇이 깨졌나」는 5xx와 panic 의 합, 「무엇이 느린가」는 풀 대기 p95
- **정상 타깃 알람의 창은 5분이다.** 인스턴스가 한 대라 배포가 유일한 태스크를 먼저 내리고(`deployment_minimum_healthy_percent = 0`) 기동 유예가 120초이며 스팟 회수도 2~3분이다 — 1분 두 회차로 두면 정상 배포마다 울리고, 그때부터 사람이 알람을 안 본다. 대신 지표를 「비정상 수」가 아니라 「정상 수가 0」으로 잡아 **타깃이 아예 없는 경우까지 같은 알람이 덮는다**
- **panic 을 따로 센다.** 업그레이드된 연결에서 panic 하면 그 요청의 상태가 이미 101이라 5xx 로 안 잡힌다 — 알람은 둘을 metric math 로 합쳐 본다

### 같이 나온 것

- **「선행 계산」을 막고 있던 것이 히트율 실측이었다**(06-status §1). 이제 `EngineSearchesCached / EngineSearches` 가 그 값이다 — 깊이 12 vs 14도 같은 지표에 걸려 있다
- **로그 보존 14일의 근거가 「대회 기간」이었다.** 해커톤은 2026-08-17에 끝났다 — 근거를 「원본 로그는 되짚기용 2주면 되고 지표는 CloudWatch 에 15개월 남는다」로 바꿨다
- **운영자 정책에 `cloudwatch`·`sns` 권한이 없었다.** 추가했고 5,818/6,144자다 — 관리형 정책 상한에 남은 것이 326자뿐이라, 다음에 권한을 늘릴 때는 정책을 갈라야 한다

- **정책 버전 게시는 끝났다**(2026-08-20). 그러면서 [§11](06-20.md)부터 열려 있던 부채도 같이 닫혔다 — 운영자가 이제 프로덕션 로그를 읽는다. 첫 조회에서 나온 것이 이 회차의 근거였다: **지금 뜬 태스크의 로그가 기동 5줄 전부**이고, 14일치 api 스트림 백여 개가 죄다 3~11줄이다
- **`cloudwatch:DescribeAlarmHistory` 도 게시했다**(2026-08-21). 「알람이 언제 울렸나」를 폴링이 아니라 이력으로 되짚는 자리이고, 위 확인 표의 마지막 줄이 그 첫 사용이다
- **`aws_launch_template` 도 같이 바뀌었다.** AMI를 SSM의 `recommended` 로 받는데 AWS가 새것을 퍼블리시해서 생긴 drift이고, 이 회차와 무관하다 — 도는 인스턴스는 안 건드리고 다음 인스턴스 교체부터 적용된다

### terraform 포맷을 아무도 안 보고 있었다

`.tf` 를 처음 새로 만든 회차라 드러났다. `pnpm lint` 는 oxfmt 인데 그것이 `.tf` 를 모르고, `pre-commit` 은 웹·Go 만 보고, 워크플로 다섯에 terraform 이 없었다 — `CLAUDE.md` 검증 절의 셋째 줄을 **사람이 직접 칠 때만** 맞는 상태였다. 실제로 이 회차에서도 한 번 어긋났고 손으로 돌린 `fmt` 가 고쳤다.

두 자리를 메웠다. `pre-commit` 이 스테이징된 `.tf` 를 정리하고(terraform CLI 가 없으면 건너뛴다), `Terraform` 워크플로가 `fmt -check -recursive` 와 `validate` 를 돌린다 — **자격증명이 없다**: `init -backend=false` 면 S3 백엔드에 안 붙고 프로바이더 스키마만 받아 validate 가 그대로 된다. 룰셋에 필수 체크로 넣는 것은 사람 몫이라 그때까지는 참고용이다.

### 프로덕션 확인 — 배포까지 끝냈다 (2026-08-21)

**apply 만으로는 지표가 안 올라온다.** 서비스가 `task_definition` 변경을 무시하므로(`ignore_changes`) `ENVIRONMENT` 가 든 리비전은 등록만 되고, 도는 태스크가 그것으로 바뀌는 것은 다음 배포다 — CI가 최신 리비전을 `describe` 해서 이미지만 갈아 끼우는 구조라 그때 따라온다. 그래서 PR을 머지해 배포까지 돌렸고, 세 가지를 실물로 봤다.

| 무엇                      | 결과                                                                                                                   |
| ------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| 배포가 알람을 울리나      | **안 울렸다.** `healthz` 가 503으로 두 번 잡혔는데 알람 셋은 계속 `OK` 였다                                            |

**엔진 지표 둘은 아직 비어 있다.** `EngineSearchSeconds`·`EnginePoolWaitSeconds` 는 관측이 없으면 빈 배열을 안 내는 쪽으로 정한 자리라 그렇고, **한 판이 두어지면 채워진다.** 그 판이 히트율도 같이 채운다. → **[§91](82-100.md)에서 채웠다.**

## 91. 엔진 지표를 처음 채웠다 — 풀 대기가 0이고 히트율은 초반 전용이다 (2026-08-21)

[§90](82-100.md)이 재는 자리를 만들었고 여기서 값이 들어왔다. 에이전트 셋이 프로덕션에서 동시에 뒀다 — 50분 · 184手 · 판 셋(`games` 71·72·73). 회차 기록은 [playtests/2026-08-21-01.md](../playtests/2026-08-21-01.md)다.

### 풀 대기가 0이라 지연의 주인이 갈렸다

세 판을 동시에 걸었고 프로덕션 탐색 풀이 2개다. 점유가 2에 닿은 회차가 있는데도 **269표본 전부 대기 0**이다.

**최댓값에 퀴즈 생성은 안 섞였다.** 판이 끝난 뒤(19:03 이후) 아홉 회차에서 탐색이 0건이라 되짚기 퀴즈([§53](41-60.md))가 안 돌았고, 25.82초는 18:40의 中盤 탐색이다. 표본 269는 상대 수와 개입 판정뿐이다. **안 돈 이유가 기제에 있다** — `generateQuiz` 는 `sendSummary` 안에서만 불리고 그 호출은 대국이 끝나는 갈래에만 있어, 연결이 끊겨 `abandoned` 로 닫히면 총평도 문항도 안 만들어진다. `EngineSearchSeconds` 에 대기가 포함돼 있으므로 그 값이 곧 엔진 시간이다 — **느린 쪽은 줄이 아니라 엔진이다.**

### 개입은 184手에 6건이고 두 판은 0건이다

`shallow_trap` 1 · `other` 5(83.3%). 판 하나에 몰렸고 나머지 두 판은 0이다. **분모가 6이라 이 비율은 추세를 못 말한다** — 회차 2의 87.5%와 같은 종류의 숫자다.

프로덕션 1,097행 전부 NULL이다. `INSERT INTO game_moves (game_id, ply, usi, eval_cp)` 에 그 컬럼이 없다 — `positions` 를 참조하는 FK가 달린 채로 비어 있다. 같은 표의 `eval_cp` 는 995/1,097로 차 있다.

### 끊긴 원인은 서버가 아니었다

세 세션이 71µs 안에 동시에 닫혔고 `took` 이 셋 다 3,025초다. 맥이 `Clamshell Sleep` 에 들어가 pong이 끊긴 것이고, 서버의 67번째 핑(45s × 67 = 3,015s)이 `writeTimeout` 10초를 넘겨 `writeLoop` 이 닫았다. 그 창에서 5xx·panic이 0이고 EMF 회차가 끊기지 않았다.

**서버는 이 상황을 정확히 닫았다** — 셋 다 `result=abandoned` 로 남았다. **클라이언트는 6분 12초 동안 몰랐다** — 핑이 한 방향이라 다음 쓰기까지 죽은 소켓을 붙든다.

### 무엇을 정했나

- **풀 대기 임계치 3초는 여전히 근거가 없다.** 세 판 병렬로도 분포가 0이라 실측이 임계치를 못 정했다 — 알람은 그대로 두고, 값은 부하를 실제로 거는 회차에서 정한다
- **「깊이 12 vs 14」는 선행 계산의 깊이였고, 답이 나왔다.** [§10](06-20.md)의 `[미확정]` 이 「`depth 14 × k≈10` 이 8.4초다 — 내릴지는 초반 캐시 히트율을 보고 정한다」였다. **초반이 65.7%다** — 세 건 중 둘을 캐시가 이미 답하는 자리에 8.4초를 쓸 근거가 없다. **선행 계산을 깊이 14로 붙이지 않는다.** 붙인다면 깊이 12이고, 겨냥할 곳은 초반이 아니라 히트율 2.3%인 中盤이다
- **실행 중인 탐색의 깊이는 건드리지 않는다.** `DefaultDepth`·`JudgeDepth` 가 이미 12이고, 이 회차의 p50 0.38초·p95 5.24초가 그 깊이의 값이다 — 줄일 자리가 아니라 이미 줄여 둔 자리다
- **프로덕션이 [§10](06-20.md) 벤치보다 느리다.** 같은 깊이 12에서 로컬 최장이 k=10에서 2.0초·k=20에서 3.3초였는데 프로덕션 p95가 5.24초·max 25.82초다(2 vCPU · 세 판 동시). 그래서 **깊이 14의 8.4초는 프로덕션에서 하한**이고, 그 방향은 더 볼 것이 없다
- **지금 있는 캐시로 中盤 지연을 덮는 것은 안 된다** — 히트율이 2.3%다. 캐시는 쌓인 것을 다시 꺼내는 쪽이라 새 국면에 답할 것이 없다. 그 자리를 메우려면 **선행 계산이 中盤 국면을 미리 채워야 하고, 그것이 이득인지는 같은 2 vCPU를 나눠 쓰는 문제**라 이 회차가 답하지 않았다
- **`sfen_key` 는 이번에 안 건드린다.** 쓰기를 붙이는 것과 컬럼을 걷는 것이 다른 결정이고, 어느 쪽도 이 회차가 답한 것이 아니다
- **플레이테스트 중에는 뚜껑을 열어 두거나 `caffeinate -s` 를 건다.** Caffeine 은 디스플레이 잠자기만 막는다
- **지연 지표는 관측이 0이면 계열이 아예 안 생긴다.** 그래서 「지표가 안 보인다」를 고장으로 읽지 않는다 — 가르는 것은 카운터 둘이다

### 하네스 버그 둘 — 셋이 독립적으로 물렸다

- **持ち駒 표시가 남의 개수를 내 쪽에 붙였다.** SFEN 持ち駒는 `[개수]駒` 의 나열(`S5P2n2p`)인데 대소문자만으로 정규식을 갈랐고, 개수는 뒤따르는 駒의 것이라 경계에서 섞인다. 재료 균형을 판에서 다시 세게 만들었다
- **개입이 2~3배로 세어졌다.** 같은 개입이 지워질 때까지 스냅샷 여러 장에 실려 온다 — 판 하나에서 스냅샷 16장에 개입 6건이 실려 요약이 16으로 나갔다. DB가 6이다

### 남은 것

- **엔진 자체와 CPU 경합을 가르는 계측이 없다.** `EnginePoolInUse` 는 회차 끝의 순간값이라 느린 탐색과의 상관을 못 본다. 탐색을 시작할 때의 **동시 탐색 수를 그 탐색의 라벨로** 붙이면(풀이 2라 값이 둘뿐이어서 계열이 안 늘어난다) 「두 번째 탐색이 붙으면 시간이 두 배가 되나」에 분포로 답한다 — 붙일 자리는 대기와 점유를 이미 내는 `usi.Pool.Acquire` 다. **부하를 거는 회차에 같이 넣는다**
- **부하를 걸어 본 것이 아니다.** 세 판은 풀 2개를 다 못 채웠다 — 「동시에 몇 판까지 되나」는 여전히 열려 있고, 그것이 임계치와 깊이를 같이 정한다
- **화면을 안 봤다.** 프록시로만 뒀으므로 카드 가독성과 카테고리 이름이 화면에 어떻게 나가는지는 브라우저로 확인해야 한다
- **개입 0건 두 판이 판정 문제인지 성향 문제인지 안 갈렸다.** 엔진 평가치를 안 보고 둔 회차라 「그 자리가 실제로 블런더였나」를 이 회차가 답하지 않는다

## 92. 대인전에 레이팅이 붙었다 — 낙폭과 갈라 둔 이유는 비교 가능성이다 (2026-08-21)

사람끼리 두는 판([§83](82-100.md))이 승패를 남기기 시작한 뒤로 그것을 쌓는 자리가 없었다. 붙였다. **화면에는 안 나간다** — 쓰는 쪽은 앞으로 붙는 대기열 하나다.

### 왜 `skill_loss` 를 그대로 못 쓰나

[§47](41-60.md)의 추정치가 이미 있는데 그것을 매칭에 쓰면 안 된다. `Loss` 가 **임계치로 나눈 비율**이라서다(`skill.moveLoss` — `DeltaWin / Level.Threshold()`).

지금은 `main.go` 가 전원을 `intervene.Beginner` 로 박아 둬서 분모가 0.25 하나다. 그래서 **우연히 비교 가능하다.** 그런데 `Beginner` 주석이 「실력 추정이 붙으면 좁혀진다」고 예고하고 있고, 그날 같은 실수가 이렇게 갈린다.

| 레벨         | 임계치 | 승률 0.06 손해의 정규화 Loss | `RankOf` |
| ------------ | ------ | ---------------------------- | -------- |
| Beginner     | 0.25   | 0.24                         | 4級      |
| Intermediate | 0.12   | 0.50                         | 8級      |

**네 계급이다.** 레벨이 사람마다 갈리는 순간 매칭이 틀리기 시작하고, 그것은 아무 테스트도 안 잡는다 — 두 값 다 멀쩡한 범위에 있다.

`RankOf` 자신이 이미 그 척도의 한계를 적어 뒀다: 「道場や将棋ウォーズの段級ではない (…) 절대 실력에 맞춰 본 적이 없다」. 사람끼리 비교 가능한 신호는 **승패뿐**이고, 그것은 `games.match_id` 와 `result` 로 이미 쌓이고 있었다([§83](82-100.md)).

### 칸은 이미 있었다

`001_init.sql` 이 `rating_est double precision NOT NULL DEFAULT 0` 과 `rating_sd double precision NOT NULL DEFAULT 350` 을 만들어 뒀고, `006` 이 그것을 **비워 둔 채 남겼다**(「지우는 것은 되돌릴 수 없고」). `350` 은 Glicko 의 「전혀 모른다」다 — 원래 스키마가 그 방향을 상정하고 있었다.

**§47의 결정은 뒤집히지 않았다.** 저쪽이 정한 것은 「낙폭을 점수로 바꾸지 않는다」이고 그건 그대로다. 새로 생긴 것은 그 옆의 다른 값이고, 입력이 승패라서 척도가 다르다.

### 정한 것

- **Glicko-1이다. Glicko-2로 안 간다** — 저쪽은 변동성 칸이 하나 더 필요한데 있는 것은 둘이고, 이만한 표본에서 변동성까지 추정해 얻을 것이 없다
- **`rating_games = 0` 이 「레이팅 없음」이다.** `rating_est` 로 그것을 못 말한다 — `NOT NULL DEFAULT 0` 이고 레이팅에서 0은 「모른다」가 아니라 「아주 약하다」다. `006` 이 `skill_loss` 에서 NULL 과 0을 가른 것과 **같은 함정**이라 칸을 하나 더 뒀다(`013`)
- **한 판도 안 둔 사람은 엔진 대국의 추정치에서 시작한다**(`rating.SeedFromLoss`). Elo 류의 콜드 스타트가 이 앱에는 없다 — 사람과 처음 만나는 사람에게도 이미 낙폭이 있다. **유저가 적은 동안 첫 매칭이 무작위가 아닌 것과 같은 말이다.** 표본 하한은 `skill.MinSamples` 를 그대로 쓴다: 여기서 따로 정하면 이름만 다른 두 하한이 생긴다
- **시드의 RD 는 상한(350) 그대로다.** 낙폭에서 나온 값을 믿을 근거가 없고(`RankOf` 의 그 문장), 그것을 RD 가 말한다
- **승부가 안 난 판은 안 센다.** 세면 탭을 닫는 것이 레이팅 수단이 된다
- **안 둔 시간만큼 RD 가 되돌아간다**(`rating.Inflate`, 90일에 상한까지). 값은 안 건드린다 — 안 두는 동안 세지지도 약해지지도 않았다는 것이 아는 전부다. `updated_at` 을 못 쓰는 이유는 그 칸이 판정 한 건마다 갱신되기 때문이고(`SaveSkillEstimate`), 그래서 `rating_updated_at` 이 따로 있다
- **두 사람을 한 문장으로 옮긴다**(`SaveMatchRatings`). 트랜잭션을 안 여는 이유는 원자적이면 열 것이 없기 때문이다 — 반쪽만 반영되면 그 뒤로 두 사람이 서로 다른 판 수 위에서 돈다
- **갱신은 갱신 전 값 둘로 한다.** 갱신된 값으로 상대를 보면 먼저 계산한 쪽이 이득을 본다 — 인자를 뒤집어도 같은 값이 나오는 것을 테스트가 잡는다
- **밖으로 안 나간다.** 어느 API 도 이 값을 안 돌려주고 段級도 안 붙인다 — 보여주면 사람이 그것을 지키려 두기 시작하고, 학습 앱에서 원하는 행동이 아니다

### 다음 — 대기열의 설계는 여기서 같이 정했다

레이팅을 먼저 넣은 이유가 이것이다: **쌓이는 데 시간이 걸린다.** 대인전은 이미 돌고 있으므로 오늘부터 쌓인다.

- **큐는 DB 행이다.** 방과 성질이 반대다 — 방은 초당 수십 번 바뀌는 상태머신이라 goroutine 소유가 맞고(`match.Table`), 큐는 행 몇 개가 몇 초에 한 번 바뀌는데 **모든 인스턴스가 같은 것을 봐야 한다.** 덤으로 큐는 처음부터 N대에서 돈다
- **짝짓기는 줄에 서는 그 요청이 한다.** `FOR UPDATE SKIP LOCKED` 한 줄이 「두 인스턴스가 같은 대기자를 두 번 집지 않는다」를 맡는다 — `ClaimGameForResume`([§51](41-60.md))과 같은 계열이고, 그래서 **리더도 sweeper 도 알림 채널도 안 생긴다.** 기다리는 쪽이 스스로 재시도하고 그 호출이 heartbeat 를 겸한다
- **고르는 규칙은 밴드 안에서 FIFO다.** 밴드가 품질을 보장하니 그 안의 후보는 정의상 받아들일 만하고, 그중에서는 오래 기다린 쪽이 먼저다. 최근접으로 고르면 가까운 짝을 가로채서 남은 둘이 최악으로 붙는다 — 큐 `0·11·21` 에 `10` 이 들어오면 최근접은 격차 합 22(그중 하나가 21), FIFO 는 20이다
- **밴드는 양쪽을 다 봐야 한다.** 찾는 쪽만 보면 30초 기다린 외곽 유저가 방금 온 사람을 끌어당기고, 그 사람은 동의한 적 없는 짝에 앉는다. 조건은 `abs(rA − rB) ≤ LEAST(band(tA), band(tB))` 이고 밴드에 두 사람의 RD 가 더해진다 — **모르는 사람에게 좁은 밴드는 뜻이 없다**
- **큐는 平手 확정 · 先手 랜덤이다.** 手合(駒落ち)을 큐에 안 붙인다 — 레이팅 차를 cp 로 환산하는 계수가 없고(`handicap.BaselineCp` 는 手合의 값만 안다), 그것을 재려면 사람끼리 둔 판이 먼저 쌓여야 한다. 手合은 미리 만드는 방에만 둔다. **덤으로 이 결정은 작업이 0이다** — `HubConfig` 에 `StartSFEN` 을 넘기는 자리가 없어서 대인전은 이미 平手 전용이다
- **동시 접속자가 없으면 안 잡히는 것을 받아들인다.** 엔진으로 떨어뜨리는 폴백도 안 붙인다 — 대기 중에 엔진과 두게 하면 짝이 잡혔을 때 두던 판을 어떻게 할지가 새 문제가 된다
- **큐가 만든 방은 손님을 지정해야 한다.** `Hub.Enter` 에 화이트리스트가 없어서 방 id 만 있으면 아무나 빈 자리에 앉는다 — 링크 방식에서는 그게 의도지만(링크가 열쇠다) 큐 방식은 상대가 이미 정해져 있다. **확인 화면도 건너뛴다**: `Join.tsx` 가 있는 이유가 「링크를 잘못 누른 사람이 모르는 사이에 자리를 태우는 것」인데, 스스로 줄에 선 사람에게는 그 이유가 없다

### 남은 것

- **상수 셋이 전부 초기값이다.** `SeedSpread` 400 · `MinDeviation` 50 · `InactivityToUnrated` 90일. 재려면 **사람끼리 둔 판이 쌓여야 한다** — [§39](21-40.md)의 벽과 같은 종류이고, 이번에는 표본이 사람이어야 한다는 조건까지 같다
- **시드의 환산비를 안 쟀다.** 낙폭 0.2가 레이팅 +240인 것에 근거가 없다. 판이 쌓이면 「시드가 첫 다섯 판의 승률을 맞혔나」로 잴 수 있고, 그것이 이 값의 유일한 검산이다
- **밴드 상수는 아직 없다.** 대기열이 붙는 자리에서 `band0`·확장 속도·상한이 새로 셋 생기고, 그것을 잴 지표(`MatchPairingSeconds`·`MatchRatingGap`)도 같이 붙어야 한다 — **EMF 는 지금 정확히 10개**이고([§90](82-100.md)의 「열 개로 묶는다」) 넷을 더하면 그 선을 넘는다. 무엇을 빼거나 선을 다시 정하는 결정이 그때 같이 온다
- **`WsSessionsActive` 에 큐 대기를 그냥 붙이면 안 된다.** 그 지표는 kind 라벨을 합쳐서 내므로(`emf.go` 의 `WSSessions.Total()`) 대기자가 「대국 세션」으로 세어져 조용히 부풀어 오른다
- ~~**두 축이 갈린 대가로 구멍이 하나 생겼다.**~~ 사람과만 두는 사람은 `skill_loss` 가 영원히 비어 있었다 — 그 사람이 나중에 엔진 대국을 열면 **레이팅이 1800이어도 상대가 기준선 8級에서 시작**했다. **[§95](82-100.md)에서 메웠다**: `internal/match` 는 그대로 `skill` 을 안 부르고(부정행위 경계, [02-architecture.md §7](../02-architecture.md)), 판이 끝난 뒤 분석기가 그 기보의 手 낙폭을 쌓는다. 예상대로 **거꾸로(승패 → `skill_loss`)가 아니다**

## 93. 한 사람이 들고 있는 방을 하나로 내렸다 (2026-08-21)

`openRoomsPerHost` 가 3이었고 주석에 `[미확정] 3은 감으로 잡은 값이다` 라고 적혀 있었다. 1로 내렸다.

### 3이 세고 있던 것은 「사람에게 허용한 개수」가 아니었다

정책이 「넘으면 거절이 아니라 오래된 것을 버린다」다([§83](82-100.md)). 방 만들기가 **절대 거절되지 않으므로** 이 상수가 정하는 것은 「몇 개까지 만들 수 있나」가 아니라 **「안 쓰는 방을 몇 개까지 살려 두나」** — 제품 허용량이 아니라 GC 상한이다.

그리고 그 살려 둔 방을 호스트가 볼 수 없다.

|              |                                                              |
| ------------ | ------------------------------------------------------------ |
| 방 목록 화면 | 없다. `screens/match/` 넷은 전부 방 **하나**를 보는 화면이다 |
| 방 취소 API  | 없다. `match.go` 는 `create`·`get` 둘뿐이다                  |
| 링크 수명    | `OpenTTL` 30분                                               |

그래서 두 번째 방을 만든 순간 **첫 링크는 30분간 살아 있고 호스트는 그것을 볼 수도 걷을 수도 없고 있는 줄도 모른다.**

두 번째 방은 클릭 한 번이면 만들어진다. `Setup.tsx` 가 성공해도 버튼을 되돌리는데(「이 화면은 방으로 옮겨 가도 언마운트되지 않는다」 — 탭 모델 때문에 맞는 판단이다) 결과가 「같은 방으로 돌아간다」가 아니라 **「새 방을 만든다」**다.

### 정한 것

- **1이라 「방을 만든다」가 사람마다 멱등이다.** 열린 링크가 언제나 최신 하나이고, 새로 만드는 순간 옛것이 죽는다 — 사람이 초대 링크에 갖는 심상(「내 링크」)과 맞는다
- **상수만 바꿔도 산수가 맞는다.** `dropSurplusLocked` 가 기존 열린 방 1개면 그 하나를 버리고, 0개면 아무것도 안 버린다
- **안전하다.** 필터가 `room.table == nil && room.guest == nil` 이라 **두는 중인 판도, 손님이 앉기만 한 방도 안 버린다** — 대국 중에 새 방을 만들어도 자기 판을 안 죽인다
- **잃는 것은 「A에게 보내고 답 없는 동안 B에게도 보내기」다.** 그건 상수로 얻을 기능이 아니라 로비가 필요한 기능이고, 지금은 **어느 링크가 살아 있는지 호스트가 모르는 상태로** 되는 것이라 잃는 쪽이 낫다
- **테스트가 상수를 심볼로 쓰고 있어서 1에서도 그대로 성립한다** — N개를 만들고 마지막 `openRoomsPerHost` 개만 남는지 본다

### 남은 것

- **근본 수정은 취소 버튼이다.** 상한이 보이지 않는 상태를 막는 대역이라면, 진짜 답은 호스트가 자기 방을 걷을 수 있게 하는 것이다 — `Waiting.tsx` 의 「やめる」 하나와 주인만 부를 수 있는 `DELETE /api/rooms/{id}` 하나. 그러면 링크가 죽는 시점이 사람의 손에 있고 상한은 사고 방지용으로 남는다
- **1이 대기열 쪽 설계를 줄인다**([§92](82-100.md)). 상한이 3이면 N대에서 3N개가 되어 전역 카운트를 세야 하는데, 1이면 규칙이 「방은 디렉터리에 행이 있을 때만 존재한다」 하나로 줄어든다

## 94. 段級을 실측으로 앵커했다 — 級은 갈리고 段은 안 갈렸다 (2026-08-22)

급수가 밖에서 정해진 사람끼리의 판 **15개**를 프로덕션 판정 경로로 다시 뒀다. [§39](21-40.md)가 「사람 표본을 기다린다」로 남긴 자리이고, 그 표본이 처음 왔다.

### 먼저 축을 옮겼다 — 옛 값 위에는 앵커를 놓을 수 없다

| 무엇                                           | 왜 앵커가 안 되나                                                                                                                  |
| ---------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| 분모가 임계치다 (`DeltaWin / Level.Threshold`) | 임계치가 좁아지는 날 같은 실수가 **네 계급** 움직인다([§92](82-100.md)의 표). 그날 앵커가 통째로 낡는다                            |
| 비대칭 EMA다 (rise 0.5 / fall 0.1)             | 순서 의존이라 끝이 무너진 판이 판 전체보다 훨씬 나쁘게 남는다([06-status.md §5](../06-status.md)의 ①). 「棋力」이 재는 값이 아니다 |

그래서 `skill.Estimate` 에 축을 하나 더 뒀다 — `AbsLoss`(임계치로 안 나눈 낙폭의 평균, 창은 `AbsWindow`)와 `AbsSamples`. 개수를 따로 세는 이유는 `014` 이전에 쌓인 행이 `skill_samples` 는 차 있는데 평균이 없기 때문이고, 그것을 0으로 메우면 「매 수 최선」이 되어 **가장 센 이름**이 붙는다(`006` 이 NULL과 0을 가른 것과 같은 함정).

### 자를 두 번 고쳐야 값이 나왔다

첫 표는 급수를 재지 못했다. **판 전체의 평균은 실력이 아니라 판 길이의 함수였다.**

|                | 무엇을 뺐나                  | 왜                                                                                                                                    |
| -------------- | ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| 이미 갈린 국면 | 최선수의 승률이 0.95 밖인 手 | 승률이 포화해 나쁜 수도 낙폭이 0에 가깝고, 무너지는 몇 수만 크게 잡혀 판 평균을 그 꼬리가 정한다. **15級 판의 39%가 이 구간이었다**   |
| 창 밖의 手     | 21手 이전과 60手 이후        | 초반은 定跡이라 그 사람의 급수가 아니라 책의 품질이다(15級의 1-20手 낙폭이 뒤 구간의 3분의 1이다). 뒤를 안 자르면 긴 판이 값을 정한다 |

이 둘이 결론을 실제로 뒤집었다. 같은 표본에서 15級↔三段이 **필터 없이 3.15σ(갈린다) → 필터만 걸면 0.78σ(아니다) → 창까지 걸면 3.08σ(갈린다)** 였다. 가운데 단계에서 갈림이 사라진 것은 차이가 줄어서가 아니라 **판간 분산이 드러나서**다(합성SE가 0.0060 → 0.0155).

**일곱 라벨이 전부 단조롭다.** 그런데 갈리는 것은 세 덩어리뿐이다.

```
{15級 0.1287 · 10級 0.1064}   서로 1.18σ — 안 갈린다
{5級 · 1級 · 初段 · 三段}       서로 0.07~0.94σ — 안 갈린다 (12계급이 한 덩어리)
{5段 0.0332}                   위 덩어리와 2.82~5.76σ — 갈린다

덩어리끼리는 갈린다: 10級↔5級 2.17σ · 10級↔三段 4.93σ · 10級↔5段 9.96σ
```

**SD가 평균에 비례한다**(비 0.13~0.43). 낙폭이 곱셈적이라는 뜻이고, 그래서 척도를 로그에서 잇는다.

**같은 판을 다시 재면 값이 갈린다.** 새 판을 안 넣고 다시 돌렸을 때 初段이 0.0673 → 0.0659(2%)로 움직였다 — [§39](21-40.md) ⑦의 치환표 잡음이 이 파이프라인에서 얼마인지를 그 두 숫자가 말한다.

### 정한 것

- **앵커는 두 점이다.** 15級 0.1287과 「初段 이상」 0.0662(初段 0.0659 · 三段 0.0651)이고, 사이는 로그 보간(계급당 ×1.046)이다. 10級·5級·1級도 쟀지만 앵커로 안 쓴다 — 그 구간이 평평해서 점을 박으면 **낙폭 1%가 계급 넷을 움직인다.** 검산으로 쓰고, 그 선에서 세 계급 안에 들어오는 것을 테스트가 잡는다(실제로는 10級 0.7 · 5級 1.6 · 1級 0.5계급이다)
- **段을 나누지 않는다.** 初段 0.0659와 三段 0.0651이 같은 자리이고 5段(0.0332)만 아래에 있다. 지시받은 「15級~三段 19칸」은 이 표본으로 지을 수 없다 — 段을 칸으로 세우면 **段 유저가 1級보다 약하게 표시된다.** `RankOf` 가 「初段에서 끊는다」고 적어 둔 결정이 그대로 지지됐고, 이번에는 근거가 실측이다
- **16級을 뺐다.** 척도의 아래 끝이 실측 앵커(15級)여야 하고, 그 밖은 근거가 없다
- **왜 段이 안 갈리나는 [미확정]이다.** 강한 사람이 날카로운 국면을 두어 한 수의 승률 값이 커지는 것과 정확도가 좋아지는 것이 상쇄된다는 설명이 표와 맞지만(三段 판이 143~156手로 길다) 그것을 따로 재지 않았다
- **런타임이 앵커와 같은 자를 쓴다.** `skill.Move` 가 `Ply`·`Decided` 를 받고, 段級은 창 안의 手만 센다(`inAnchorWindow`). 밴드는 그대로 전부 본다 — 조절은 매 수 일어나야 한다
- **`Ply` 가 0이면 창을 안 씌운다.** 手数를 안 실어 주는 배선에서 段級이 영원히 안 붙는 것이 조용한 고장이라, 그때는 전부 센다

### 해상도 — 이 척도로 계급 하나를 말할 수 있나

계급당 낙폭 차이가 4~~5%인데 **판 하나의 흔들림이 20~~40%**다.

| 원하는 정밀도 | 필요한 판 수 |
| ------------- | ------------ |
| ±5계급        | 2~3판        |
| ±3계급        | **7판**      |
| ±1계급        | 59판         |

그래서 화면의 이름은 판이 쌓이는 동안 **몇 계급씩 움직인다.** 그것을 줄이는 것이 `AbsWindow`(120手 ≈ 창으로 여섯 판)이고, 「±3계급이 7판」이 지금 이 값이 서 있는 근거다.

### 남은 것

- **이름 사이는 실측이 아니다.** 이 자가 가르는 것은 세 덩어리인데 화면은 16칸을 그린다. 앵커에서는 이름이 맞고 사이는 로그 보간이며, 그 한계를 「目安」이 말한다 — 칸을 덩어리 수에 맞춰 줄일지는 열려 있다
- **段 구간의 표본이 얇다.** 初段이 판 2개이고 二段·四段은 0이다. 段을 나눌지는 그 구간에 級 구간만큼의 판이 쌓여야 다시 볼 수 있다
- **교차 대국은 격차가 크면 못 쓴다.** 15級 vs 三段 한 판을 넣었는데 46手에 끝나 창(21~~60手)에 남은 手가 **0개**였다. 같은 국면에서 두 사람을 비교하려면 판이 끝까지 팽팽해야 하고, 그건 4~~5계급 차이까지다
- **엔진 대국의 표시는 인플레된다.** 상대가 추정치에 맞춰 약해지므로(`adaptive.go`) 국면이 쉽고 낙폭이 낮게 나온다. 앵커가 사람끼리의 판에서 왔으니 그 차이만큼 세게 나오고, 빼려면 **같은 사람의 두 종류 판**이 필요하다
- **`rating.SeedFromLoss` 는 여전히 정규화값을 본다.** 같은 종류의 낡음이 그쪽에 남아 있다([§92](82-100.md))
- **창의 두 끝(21·60)과 「이미 갈렸다」의 0.95는 [미확정]이다.** 구간 표를 보고 고른 값이고, 민감도는 `SHOWGI_RANK_FROM_PLY`·`SHOWGI_RANK_TO_PLY`·`SHOWGI_RANK_DECIDED` 로 다시 볼 수 있다
- **앵커 자체가 흔들린다.** 같은 판을 두 번 재면 값이 0.0284 → 0.0290으로 갈린다 — [§39](21-40.md) ⑦의 치환표 잡음이 그대로다

라벨별 표(평균·중앙값·SD·개입률·큰 실수 빈도·EMA·지금 척도가 붙이는 이름) · 手数 구간별 평균 · 라벨 쌍의 분리(세 축) · 교차 대국의 대응 비교를 낸다. **상수는 이 테스트가 안 고친다** — 재채점 측정과 같은 규약이다([§39](21-40.md)).

**잰 手가 0이면 초록으로 끝나지 않는다.** 엔진이 죽었거나 수순이 재현되지 않으면 표가 머리만 찍히는데, 사람이 이 표에서 상수를 옮겨 적는 자리라 그때는 실패로 세운다.

### 기보는 `/explore` 로 받았다

검토 화면은 **양쪽 수를 다 받고 서버가 한 수도 대신 두지 않는다**(`server/explore.go`). 그래서 주소 하나가 기보 하나이고, 그 화면이 지나간 국면은 `positions` 에 같은 깊이(12)로 남아 재생이 캐시로 맞는다.

**대국 화면으로는 이 측정이 안 된다.** 재려는 나쁜 수가 정확히 개입이 걸리는 수라 물러져서 판에 안 남고, 상대가 엔진이라 첫 수부터 기보와 갈린다.

**제3자 기보는 커밋하지 않는다.** 레포가 퍼블릭이라 「보는 것」과 「배포하는 것」을 가르고, 들어오는 것은 파생 상수뿐이다.

## 95. 대인전이 실력 추정에 들어온다 — 이미 잰 값을 줍는 것뿐이다 (2026-08-22)

[§92](82-100.md)가 마지막 줄에 남긴 구멍을 메웠다. 사람과만 두는 사람은 `skill_loss` 가 영원히 비어 있어서, 그 사람이 나중에 엔진 대국을 열면 **레이팅이 1800이어도 상대가 기준선(8級)에서 시작**했다.

### 재료가 계산돼서 버려지고 있었다

`matchAnalyzer.analyze` 는 끝난 대인전을 처음부터 다시 재서 `eval_cp` 를 채운다([§83](82-100.md)). 그 루프가 매 手 `analyst.Judge` 를 부르는데 **판정을 버렸다** — 주석이 「개입은 대인전에 없다」로 그 이유를 적어 뒀고, 맞는 말이지만 `skill.Move` 가 먹는 값이 정확히 그 자리에 다 있다.

| `skill.Move` | 어디서 오나                               |
| ------------ | ----------------------------------------- |
| `Blunder`    | `j.Verdict.Kind == intervene.KindBlunder` |
| `DeltaWin`   | `j.Verdict.DeltaWin`                      |
| `Threshold`  | `j.Threshold`                             |
| `Ply`        | 루프의 手数                               |
| `Decided`    | `j.Decided()`                             |

**추가 탐색이 0이다.** 마이그레이션도 없다 — `skill_profile` 의 칸을 그대로 쓴다.

### 정한 것

- **창 안의 手만 먹인다.** 段級 축은 `Move.Ply` 로 스스로 창을 씌우지만(`InAnchorWindow`) 밴드의 EMA 는 안 씌운다. 그 규약은 매 수 오는 신호를 상정한 것이라, 한 판을 한꺼번에 먹이는 이 자리에서는 **부르는 쪽이 두 축에 다 씌운다** — 비대칭 EWMA(rise 0.5 / fall 0.1)에 100手를 순서대로 먹이면 끝이 무너진 판이 판 전체보다 훨씬 나쁘게 남고, 그 편향이 다음 판의 시작 밴드로 굳는다([§94](82-100.md)의 그 표)
- **한 手마다 시한을 건다**(`game.DefaultMoveDeadline` 과 같은 60초). 없으면 한 手가 워커를 영영 붙잡는다 — 판정이 매 手 詰み solver 를 부르는데 그것이 `go mate infinite` 이라 스스로 안 끝나고 취소로만 풀린다(`usi.Engine.SearchMate`). 대국 쪽은 세션이 시한을 걸어서 그 자리가 없었다. **붙잡히는 것이 워커 하나로 안 끝난다**: solver 풀이 둘뿐이고 詰み 게이지·종반 판정·퀴즈와 공유라, 한 국면이 그 절반을 프로세스가 죽을 때까지 들고 있는다. 시한을 넘기면 끊긴 것으로 치고 아래 규칙을 그대로 태운다
- **규칙 하나로 가른다 — 잰 창이 그 판의 전부인가.** `analyze` 는 끊기면 멈춘다(엔진이 못 답했거나 판정이 국면을 못 되만든 것(`HasEvals`)이고, 둘 다 그 뒤가 전부 같이 실패한다). 창(60手) 전에 멈췄고 **판이 더 길었던 것을 알면** 통째로 버린다 — 남는 것이 더 긴 판의 앞부분뿐이고 그 구간이 체계적으로 쉬워서 낙폭이 낮게 나온다. 창 뒤에서 멈춘 것, 마지막 手에서 멈춘 것, **짧게 끝난 판**은 잰 창이 그 판의 전부이므로 남긴다(앵커도 그렇게 쟀다 — [§94](82-100.md)의 46手 판). 평가치는 어느 쪽이든 멈춘 자리까지 채운다: 그쪽은 手마다 독립이라 반쪽이어도 거짓이 아니다
- **잘린 행의 창과 짧은 판의 창은 판정이 똑같이 나온다.** 그래도 가르는 것은 위 규칙이 하나이기 때문이고, 안 가르면 같은 표본이 **끊긴 이유에 따라** 들어갔다 나갔다 한다. 대신 **두 행이 같은 자리에서 같이 잘리면 못 잡는다** — 그 값은 두 행을 비교해 알아내는 것이라 둘이 일치하면 짧게 끝난 판으로 남는다. 기록에 진짜 마지막 手数가 없어서 지금은 대조할 것이 없다. 같은 이유로 **두 행이 다 길이를 말해야 실력을 쌓는다**: 못 읽은 행과 통째로 빈 행은 둘 다 아무 말도 안 하고, 남은 한 행만으로는 그 행이 끝까지인지 잘렸는지를 가릴 수 없다
- **기보는 두 행 중 성한 쪽에서 읽는다.** 기록기는 큐가 차면 이벤트를 버리고 계속하고(`dbRecorder.send`) 두 행을 각자 쓰므로, 한쪽에만 手가 빌 수 있다. 색인을 手数로 쓰는 이상 구멍 난 행은 못 쓴다 — 한 칸이 비면 그 뒤가 전부 밀리고, 수순이 불법이 되는 것보다 **手番이 조용히 뒤집히는 쪽**이 나쁘다. 그래서 **구멍 없는 행 중 가장 긴 것**을 고르고, 둘 다 못 쓸 때만 그 판을 버린다. 「구멍이 없다」만으로 고르면 안 된다: 같은 유실이 끝에서 나면 절단이라 그 행도 빈틈없이 이어지고, 그대로 쓰면 **긴 판이 짧게 끝난 판으로 둔갑해** 앞부분만 실력에 들어간다. 버린 행이 더 긴 手数를 들고 있으면 고른 행이 잘렸다는 뜻이라, 그때는 평가치만 채우고 실력은 안 쌓는다
- **手番은 1手目를 둔 색에서 나온다.** `Judgement` 이 手番을 안 내놓는다. 대인전은 지금 平手 확정이라 `ply` 홀짝으로 갈라도 맞지만, **駒落ち는 上手가 먼저 둔다**([§88](82-100.md)) — 그 사실이 여기 박히면 手合이 붙는 날 실력이 반대 사람에게 쌓이고 아무 테스트도 안 잡는다. 시작 SFEN 을 읽어서 정하고, 못 읽으면 그 판을 추정에서 뺀다 — 평가치도 대개 같이 빠진다(판정 안의 replay 가 같은 문자열에서 같이 실패한다)
- **자리마다 저장한다.** 대인전 한 판은 `games` 행 둘이고(`012`) 자리마다 번호도 사람도 다르다. 곁장부만 그 짝을 아는데(`roomRecord.player`) 줄에 서는 것은 번호뿐이었다 — 색과 사람을 같이 실어 보낸다. `ids[0]` 하나에 쓰면 두 사람의 手가 한쪽에 쌓이고, **그 값도 멀쩡한 범위에 있다**
- **읽은 값이 그대로일 때만 덮는다.** 판정을 다 모은 뒤에 한 번에 읽고 쓰는데, 그 사이(수십 초)에 그 사람의 엔진 대국이 끝나 있을 수 있다. 그냥 덮으면 그 판이 통째로 사라진다 — 끝난 세션은 자기 트랙을 다시 안 쓴다. 그래서 표본 수를 조건에 달아 쓰고(`SaveSkillEstimateIfSamples`), 어긋나면 **다시 읽어 얹는다**(手는 손에 있으므로 엔진을 다시 안 부른다). 세 번 지면 그 판을 버린다: 상대가 대국 중인 세션이면 판정마다 쓰므로 몇 번을 해도 지고, 그때는 여기가 이겨도 그쪽 다음 판정이 도로 덮는다. **마지막 쓰기는 취소를 뗀다**(사람마다 10초 상한) — 판을 다 잰 뒤라 여기서 끊기면 재느라 쓴 탐색이 통째로 버려지고 그 판은 다시 재지지 않는다. **종료를 이겨내지는 못한다**: 이 워커를 기다려 주는 자리가 없어서 풀이 먼저 닫히면 그대로 실패한다
- **거꾸로는 여전히 안 한다.** 엔진 대국의 승패로 레이팅을 매기지 않는다 — 상대의 강함을 서버가 내 추정치에서 골라 주므로(`adaptive.go`) 나에 대한 정보가 아니다. 이번에 오는 것은 승패가 아니라 **그 판의 手 낙폭**이고, 그건 상대가 누구든 내가 둔 수다
- **기여가 간헐적인 것을 받아들인다.** 분석 진행 상태가 메모리라 배포하면 하던 판이 끊긴다. 고장으로 읽지 않도록 주석에 남겼다

### 남은 것

- **프로덕션에 대인전 판이 0건이다**([06-status.md §3](../06-status.md)). 확인은 로컬 DB 테스트뿐이고 **실물 판정으로는 한 번도 안 돌았다.** 사람끼리 몇 판을 두는 것이 이 항목의 다음 단계인 것은 그대로다
- **엔진 대국과 대인전이 같은 프로파일에 섞인다.** [§94](82-100.md)가 「엔진 대국의 표시는 인플레된다」(상대가 약해져 국면이 쉽다)고 남겼는데, 이제 한 사람의 `AbsLoss` 에 **인플레된 판과 안 된 판이 같이** 들어간다. 가르려면 칸이 하나 더 필요하고, 그 결정을 하려면 같은 사람의 두 종류 판이 먼저 쌓여야 한다 — 저쪽이 「빼려면 같은 사람의 두 종류 판이 필요하다」로 남긴 것과 같은 표본이다
- **한 판이 段級을 얼마나 움직이는지 안 쟀다.** 한 사람 몫이 창에서 최대 **20手**이고 `AbsWindow` 가 120이라 한 판이 6분의 1이다. 「±3계급이 7판」([§94](82-100.md))은 엔진 대국의 판 길이에서 나온 값이라 그대로 못 쓴다
- **시드를 스스로 낮출 수 있다.** 승부가 안 난 대인전은 레이팅을 안 움직이지만(`ratingOutcomeOf`) 실력 추정은 그 판도 먹으므로, 창 안에서 일부러 헤맨 뒤 판을 버리면 `Loss` 가 몇 手 만에 1로 붙고(RiseRate 0.5) 첫 레이팅 대국이 `Default - SeedSpread` = 1100에서 시작한다. **엔진 대국을 던져서 이미 열려 있던 길**이라 새로 생긴 구멍은 아니고, 사람과만 두는 계정에도 열렸을 뿐이다. 막는 자리는 낙폭이 아니라 시드다 — 「사람과 둔 판에서 나온 낙폭인가」를 가르려면 칸이 하나 더 필요하고, 그건 대기열이 붙어 레이팅이 실제로 쓰이는 날의 결정이다([§92](82-100.md))
- **詰み 탐색이 시한을 넘겨도 판정이 그것을 안 알린다.** `engineAnalyst.Judge` 는 `SearchMate` 의 에러를 삼키므로(`err == nil && r.Found()`) 시한 안에 답이 안 오면 `MateBefore` 가 0으로 남고, 詰み을 놓친 수가 **잘 둔 수로 들어간다** — 그 수는 승률이 포화한 구간에서 나와 낙폭이 0에 가깝고, `MateAbsLoss` 0.25가 정확히 그 자리를 메우려고 있는 값이다. **분석기만의 문제가 아니다**: 대국 쪽도 판정 하나를 60초로 묶고(`state.moveDeadline`) 그 안에 詰み 탐색이 들어가며, 같은 자리에서 같이 삼킨다. 여기만 따로 고치면 대인전과 엔진 대국이 **다른 자로 재진다** — 고치려면 `engineAnalyst` 안에서 詰み 탐색에 자기 예산을 주는 것이고, 그건 엔진 대국의 숫자와 [§94](82-100.md)의 앵커를 같이 움직인다
- **`Judgement.Decided()` 가 駒落ち의 기준점을 안 뺀다.** `intervene.Judge` 는 승률을 재기 전에 `BaselineCp` 를 빼는데(`judge.go` 의 `delta`) 이쪽은 안 뺀다. 四枚落ち의 기준점 1561cp 는 그 자체로 승률 0.93이라, 下手는 실제 +200cp쯤에서 이미 「갈렸다」가 되고 上手는 그 반대다 — 그러면 駒落ち의 手 대부분이 段級 축에서 빠진다. **이 절이 만든 것이 아니고**(엔진 대국의 `observeSkill` 이 같은 값을 쓴다) 대인전은 平手 확정이라 지금은 안 걸리지만, 手合이 큐에 붙는 날 같이 봐야 한다. 고치려면 `Judgement` 이 기준점을 실어야 하고, 그건 엔진 대국의 段級까지 움직이므로 [§94](82-100.md)의 앵커를 다시 볼 결정이다
- **레벨은 여전히 전원 `Beginner` 다.** 밴드 축이 우연히 비교 가능한 것은 [§92](82-100.md) 그대로이고, 段級 축은 분모가 없어서 안 걸린다
- **밴드 축에 자가 둘 섞인다.** 엔진 대국은 `skill_loss` 에 **모든 手**를 먹이는데 대인전은 창(21~~60手) 안의 手만 먹인다. 초반 20手는 定跡이라 낙폭이 뒤 구간의 3분의 1이고([§94](82-100.md)), 그 낮은 값이 빠지면 같은 실력이라도 대인전 뒤의 `skill_loss` 가 높게 남는다 — 다음 엔진 대국의 상대가 그만큼 약해지고(`adaptive.skillShift`), 승부가 안 난 대인전만 둔 사람은 `rating.SeedFromLoss` 의 시드까지 그 값에서 나온다. 段級 축은 원래 창만 보므로 안 걸린다. **한 판을 통째로 먹이는 쪽이 더 나쁘다고 봐서 이렇게 뒀다** — 가르려면 칸이 하나 더 필요하다
- **대국 중인 세션과 겹치면 대인전 쪽이 진다.** 엔진 대국은 **시작할 때의 값**에서 트랙을 만들고(`priorSkill`) 판정마다 프로파일 전체를 덮는다. 조건부 쓰기가 막는 것은 **끝난 판을 지우는 것**이고, 아직 돌고 있는 판은 못 막는다 — 그 세션이 자기 트랙을 들고 있어서 여기가 이겨도 다음 판정이 도로 덮는다. 판이 끝난 직후에 다음 판을 여는 것은 드문 경로가 아니므로, **대인전의 기여는 그만큼 자주 사라진다.** 없애려면 덮는 대신 더해야 하고(증분 갱신) 그건 `skill.Track` 이 순서 의존이라 칸이 더 필요하다 — **열어 둔다**

## 96. 검토에서 국면을 저장한다 — 판이 아니라 手合割과 수순을 든다 (2026-08-22)

[§85](82-100.md)가 세운 검토 화면은 20手를 걸어 들어간 자리를 **주소로만** 들고 있었다. 새로고침은 살아나지만 그 국면에 이름을 붙여 다시 찾아오는 길이 없어서, 어제 본 자리로 돌아가려면 링크를 어딘가에 스스로 적어 둬야 했다.

### 저장하는 것

| 칸         | 값                                         |
| ---------- | ------------------------------------------ |
| `handicap` | 手合割 id. 빈 값이 平手다                  |
| `moves`    | 0手目부터의 USI 한 줄. 빈 배열이 시작 국면 |
| `name`     | 사람이 붙인 이름. 비면 서버가 짓는다       |

**SFEN 칸이 없다.** 저장된 값이 곧 다음 요청의 본문이라(불러오기 = 그 두 칸을 주소에 실어 `/api/explore` 로 다시 묻는다) SFEN을 들면 [§37](../journal/21-40.md)이 닫아 둔 문이 저장·불러오기 쪽으로 다시 열린다 — 「아무 국면이나 깊이 12로 재 주는 공개 엔진」이고, 그 풀은 대국 세 판이 쓰는 것과 같다.

### 정한 것

- **개수 상한이 없다.** 상한을 걸면 「하나 지우고 다시 저장하라」가 되는데, 저장한 국면은 판 기록과 달리 사람이 손으로 만든 것이라 무엇을 버릴지 서버가 고를 수 없다. 목록 질의에 `LIMIT` 도 안 둔다 — 자르면 **지울 수 없는 행**이 생기고, 화면에서 사라진 국면은 이름으로도 못 찾는다
- **저장 전에 룰 엔진으로 한 수씩 되짚어 본다.** 엔진 탐색이 아니라 합법성 검사뿐이라 검토의 슬롯 벽을 안 지난다([§85](82-100.md)의 두 번째 벽). 안 하면 불러올 때마다 거절되는 행이 기록에 남고, 그건 화면에서 「고장난 국면」으로 보인다 — 실제로 二枚落ち에 下手의 수를 앞에 두고 저장해 봤더니 그 자리에서 걸렸다(上手가 먼저 둔다, [§88](82-100.md))
- **이름은 서버가 짓는다** — 비어 있거나 공백뿐이면 `N手目の局面`. 화면이 그 문구를 안 갖는다. **手合割을 이름에 안 넣는다**: 목록 줄이 그 이름을 이미 곁에 달고 있어서 넣으면 한 줄에 「二枚落ち」가 두 번 선다
- **이름에 UNIQUE 를 안 건다.** 같은 이름 둘이 서는 것보다 저장이 거절되는 것이 나쁘고, 줄이 手合割·手数·저장 시각을 같이 들어서 두 줄을 가를 수 있다
- **불러오기는 이력을 쌓는다**(`replace` 없이). 手合割을 고르는 것과 같은 자리다 — 걸어 보던 줄이 통째로 없어지지만 뒤로 가기 한 번으로 돌아오므로 「정말 버립니까」를 안 묻는다. 한 수 두는 쪽은 그 반대로 이력을 안 쌓는다(40手 줄에서 나가려고 뒤로 가기를 40번 누르게 두지 않는다)
- **없는 국면과 남의 국면이 같은 404다.** 갈라 주면 남이 몇 개 저장했는지를 번호로 훑어볼 수 있다(`GetGameForOwner` 와 같은 규약)
- **로그인 벽에서 닫히면 화면이 이 패널을 아예 안 그린다.** 검토 자체가 같은 벽 뒤에 있어서 그 문구가 이미 옆 패널에 서 있고, 여기서 한 번 더 말하면 같은 사실을 두 자리가 말한다
- **삭제는 두 번 눌러야 된다.** 불러오기 버튼 바로 옆이라 한 번에 지워지면 잘못 누른 것이 곧 잃는 것이 된다
- **`盤を反転` 을 판이 주는 손잡이 줄로 옮겼다**(`駒音`·`相手の利き` 옆). 셋이 다 「판을 어떻게 보나」라 자리가 같아야 하고, 뒤집기만 駒台 아래에 있으면 판을 보던 눈이 그것을 찾으러 화면 밖으로 나간다. 그래서 0手目의 그 줄은 이제 아예 안 선다 — 되돌릴 것이 없을 때 서 있는 버튼이 하나도 없다

### 남은 것

- **되짚기의 `盤を反転` 은 그대로 두었다.** 저쪽은 手数 슬라이더와 한 줄에 있어서(`.review-board-controls`) 옮기면 그 줄의 축이 갈린다
- **정렬도 검색도 없다.** 상한이 없는 목록이라 줄이 쌓이면 필요해지는데, 몇 줄부터 그런지를 아직 모른다 — 화면은 자체 스크롤(15rem)로만 막고 있다
- **되짚기에서 「이 국면을 검토로 보내기」가 없다.** 지금 저장할 수 있는 것은 검토에서 직접 놓은 자리뿐이고, 판 기록의 한 手를 저장하려면 그 수순을 검토에서 다시 놓아야 한다. 붙이려면 뿌리가 다른 두 화면을 잇는 일이라(手合割 표 ↔ 판 기록) 저장 칸에 「어느 판의 몇 手目인가」가 하나 더 필요하다
- **표는 프로덕션에 섰고 코드는 아직 안 갔다.** 마이그레이션 `015` 는 2026-08-23에 사람이 넣었다([06-status.md §3](../06-status.md)) — 컬럼·인덱스·`ON DELETE CASCADE` 를 직접 조회해 확인했고 0행이다. **먼저 넣어도 안 깨지는 파일이다**: 지금 떠 있는 이미지가 이 표를 안 읽으므로 코드가 오기 전까지 비어 있기만 하다([§94](82-100.md)의 `014` 와 갈리는 자리 — 저쪽은 새 이미지가 그 칸을 읽어서 배포보다 먼저여야 했다). 기능 확인은 여전히 로컬 DB와 브라우저 왕복까지다

## 97. 명세를 갈라 뒀다 — 「왜」 뒤에 「무엇이 어떻게 생겼나」가 없었다 (2026-08-23)

문서가 96절까지 「왜 이 결정을 했나」를 쌓았는데, **형태를 묻는 물음에 답하는 자리가 없었다.** API를 붙이려면 `internal/server/*.go` 의 구조체 `json:` 태그를 읽어야 하고, 표 사이의 관계를 보려면 마이그레이션 15개를 순서대로 열어야 했다. 라우트 표는 `apps/server/README.md` 에 있었지만 그 표가 드는 것은 **의존성**(무엇 없이 못 서나)이고 요청·응답·상태코드가 아니다.

### 갈라 둔 축

`docs/spec/` 을 새로 만들었다. **갈린 기준은 「왜/무엇」이 아니라 갱신 주기다.**

| 갱신되는 때                  | 어디                                          |
| ---------------------------- | --------------------------------------------- |
| 코드를 고칠 때마다           | `spec/` — 라우트·스키마·표·의존 방향          |
| 판단이 뒤집힐 때만           | `01-core` · `02-architecture` · `03-frontend` |
| 무엇을 재고 무엇을 정했을 때 | 이 저널                                       |

`spec/README.md` 에 「코드를 고치면 무엇을 따라 고치나」 표를 뒀다. 그것이 이 디렉터리가 낡지 않게 하는 유일한 장치다 — 갈라 두기만 하면 베낀 쪽이 조용히 뒤처진다.

### 대조에서 드러난 불일치 넷

**코드에서 명세를 끌어내니 문서가 자기 자신과 어긋난 자리가 넷 나왔다.** [§29](21-40.md)·[§36](21-40.md)와 같은 종류이고, 이번에는 **회차를 나눈 것도 아닌데** 나왔다 — 문서를 새 축으로 다시 읽는 것 자체가 같은 힘을 낸다.

| 어긋난 것                  | 문서                | 실제                                                                                                                                          |
| -------------------------- | ------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| `eval_by_depth` 의 깊이    | `d14`               | **12** — `game.JudgeDepth` · `game.DefaultDepth`. [§91](82-100.md)에서 14를 접었는데 §4의 세 곳과 [01-core §7.1](../01-core.md)이 안 따라왔다 |
| WebSocket 이 받는 것       | 넷 (`hint` 가 없다) | **다섯** — `hint` 는 [§78](61-81.md)에서 붙었다. `resign` 의 답도 `error` 가 아니라 `snapshot` 이고, 보내는 것에 `summary` 가 빠져 있었다     |
| 서버 패키지                | 15개 (배치 표)      | **18개** — `match`([§83](82-100.md)) · `handicap`([§84](82-100.md)) · `rating`([§92](82-100.md))가 표에 없었다                                |
| `games.result` 의 API 어휘 | 다섯                | **셋** — 질의가 `result IN ('win','loss','draw')` 로 거른다. `abandoned`·`declined` 는 DB에만 있고 목록·상세에 안 나온다                      |

셋째가 가장 값이 큰 종류다. **표에 없는 패키지는 「그런 것이 없다」로 읽히고**, 그건 이미 있는 것을 다시 만들게 만든다.

### 정한 것

- **OpenAPI 는 REST 만 든다.** WebSocket 프레임을 담는 규격이 아니라, `/ws/game` 과 `/ws/match` 의 프로토콜은 `spec/api.md` §5·§6 이 **유일한 명세**다. 핸드셰이크가 거절되는 경우(`503` · `401` · `404`)만 yaml 에 적었다
- **AsyncAPI 를 붙이지 않는다.** WebSocket 을 위한 규격이 있지만 스키마 정의를 한 벌 더 쓰게 되고, 지금 이 프로토콜은 받는 것 다섯·보내는 것 다섯이라 표 두 개로 끝난다
- **「없는 것」을 세 자리에 적었다** — API 에 없는 것([api.md §7](../spec/api.md)) · 없는 화살표 다섯([architecture.md §2](../spec/architecture.md)) · 무엇이 없으면 무엇이 꺼지나(§6). 있는 줄 알고 찾는 시간이 없는 것을 읽는 시간보다 비싸고, 특히 「`intervene` 이 `usi` 를 안 부른다」는 화살표가 없는 것으로만 말할 수 있다
- **관점(perspective)을 명세의 일부로 적었다.** cp 는 부호가 뒤집히는 값이라 DB(先手) · API(플레이어) · 검토(下手 고정)가 갈리는데, 그것을 안 적으면 화면이 뒤집는 코드를 한 번 더 쓴다
- **다이어그램은 mermaid 로만 쓴다.** GitHub 이 그대로 렌더하므로 이미지 파일을 커밋하지 않는다 — 그림을 고치려고 원본 도구를 찾아야 하는 순간 아무도 안 고친다. `erDiagram` 의 복합 키는 `PK, FK` 이고 `PK_FK` 는 파싱이 깨진다(실제로 깨졌다)

### 남은 것

- **명세와 코드를 기계가 대조하지 않는다.** 핸들러 테스트가 응답을 검사하지만 `openapi.yaml` 을 안 본다 — 스키마를 고치고 yaml 을 안 고쳐도 초록이다. 붙인다면 테스트가 응답을 yaml 로 검증하는 쪽이고, 그때 정본이 코드에서 yaml 로 넘어간다
- **표 하나(`edges.tags`)는 여전히 소비자가 없다.** ERD 에 칸으로 서 있고 「아직 아무도 안 채운다」가 그 칸의 주석이다
- **`spec/` 은 일본어가 아니다.** 개발 문서라 [CLAUDE.md](../../CLAUDE.md) 의 언어 표대로 한글인데, 그 안에 인용한 `message` 값은 화면에 나가는 일본어 그대로 적었다 — 옮기면 문구가 두 벌이 된다

## 98. 대기열이 붙었다 — 줄은 표이고 짝짓기는 그 요청이 한다 (2026-08-23)

[§92](82-100.md)가 레이팅을 넣으면서 대기열의 설계를 같이 정해 뒀다. 그대로 지었다. **사람끼리 두려면 링크를 보낼 상대가 있어야 했던 것**([§83](82-100.md))이 이 절에서 닫힌다.

### 설계는 §92 그대로다

큐가 표이고(`match_queue`, `016`) 짝짓기는 줄에 서는 그 요청이 하고, 고르는 규칙은 밴드 안에서 FIFO 이고 밴드는 양쪽을 다 본다. 리더도 sweeper 도 알림 채널도 안 생겼다 — 청소는 그 요청이 문장 하나로 하고(`SweepQueue`), heartbeat 는 재시도가 겸한다.

**WebSocket 을 안 쓴다.** 기다리는 동안 서버가 할 말이 없다 — 짝은 상대가 줄에 서는 순간 생기는데 그것을 아는 것은 그 사람의 요청이고, 알림을 붙이면 인스턴스 사이의 통로가 하나 필요해진다. 큐를 표로 둔 이유가 그것을 안 만드는 것이었다.

### 밴드 식을 SQL 에 안 적었다

§92는 짝짓기를 `FOR UPDATE SKIP LOCKED` **한 문장**으로 적어 뒀다. 실제로 짓다 보니 그 한 문장에 밴드 식이 들어가고, 그러면 같은 식이 `internal/queue` 와 `query/queue.sql` 에 두 벌 있게 된다 — 한쪽을 고칠 때 다른 쪽이 조용히 낡는 자리다.

그래서 **역할을 갈랐다.** 질의는 잠그고 오래된 순으로 주는 것까지, 고르는 것은 Go 다.

| 트랜잭션 안에서 | 무엇                                                          |
| --------------- | ------------------------------------------------------------- |
| ① 잠근다        | 내 행 하나 + 후보 20줄. 둘 다 `FOR UPDATE SKIP LOCKED`        |
| ② 고른다        | `queue.Pick` — 밴드 안에서 FIFO. DB를 안 만지고 즉시 돌아온다 |
| ③ 적는다        | 짝의 행에 방 쪽지(`room_id`·`color`), 내 행은 지운다          |

**잠금이 전부 SKIP LOCKED 인 것이 교착을 없앤다.** A가 B를, B가 A를 동시에 집을 때 서로의 행을 기다리면 그 자리에서 교착인데, 아무도 안 기다리므로 **한쪽만 성공한다** — 진 쪽은 자기 행을 못 잠가서 이번 회차를 포기하고, 다음 재시도에서 쪽지를 읽는다. 테스트가 그 둘을 동시에 걸어 「짝짓기가 정확히 한 번」을 확인한다.

**내 행도 잠가야 한다.** 안 잠그면 위 시나리오에서 둘 다 성공해 **방이 둘 생기고 두 사람이 각각 두 방에 앉는다.**

### 방은 표를 따라간다

짝짓기의 결과는 표에 적히는 방 id 하나다. 방 자체는 짝을 지은 인스턴스의 메모리에 선다(`Hub.CreatePaired`) — 그래서 순서가 **표 먼저, 방 나중**이다. 반대면 짝짓기가 어긋났을 때(내 행이 이미 남에게 잡혔다) 아무도 안 오는 방이 남는다.

**큐 방은 손님이 처음부터 앉아 있다.** `Hub.Enter` 에 화이트리스트가 없어서 방 id 만 있으면 아무나 빈 자리에 앉는데(링크 방식에서는 그게 의도다), 자리를 미리 채워 두면 `seatOfLocked` 가 그 둘만 통과시킨다. **확인 화면도 같이 없어진다** — 방이 `waiting` 이 아니면 화면이 「참가하시겠습니까」를 안 그린다(`MatchScreen.tsx`). 스스로 줄에 선 사람에게는 물을 이유가 없고, 코드를 한 줄도 안 더했다.

**상한(`openRoomsPerHost`)은 안 건다.** 손님이 있는 방은 그 필터에 애초에 안 걸리고, 부르면 그 사람이 따로 열어 둔 초대 링크가 조용히 죽는다.

### 정한 것

- **줄에 서는 것이 멱등이다.** 한 사람이 한 행(`user_id` PK)이고 두 번째 호출은 `seen_at` 만 옮긴다. **레이팅을 다시 안 쓴다** — 다시 쓰면 `joined_at` 을 지키는 뜻이 없어져서 밴드가 매 재시도마다 처음으로 돌아간다
- **레이팅은 줄에 설 때 한 번 읽는다.** 시드(`SeedFromLoss`)와 불확실성 복원(`Inflate`)이 그 자리에서 얹히고, 그것을 판이 끝나고 갱신하는 쪽과 **같은 함수**가 한다(`currentRating`) — 갈라 두면 대기열이 시드 없는 1500으로 짝을 짓고 그 판이 시드 위에서 채점된다
- **자리는 한 번만 나간다.** 읽는 것과 지우는 것이 한 문장이다(`TakeQueueSeat`) — 두 번 나가면 화면이 두 번 방으로 가고, 두 번째는 남의 자리를 노린다
- **낡은 대기자는 후보가 아니다.** 걷히기 전에도 이미 화면을 떠난 사람이라(`seen_at`), 그와 짝을 지으면 상대가 아무도 안 오는 방에서 60초를 기다린다
- **화면이 「줄에 몇 명인가」를 말한다.** 동시 접속자가 없으면 안 잡히는 것을 그대로 받아들이기로 정했으므로([§92](82-100.md)), 그 사실을 알려 줄 자리가 하나 필요하다 — 없으면 안 잡히는 것이 고장으로 읽힌다
- **상대에 대해 아무것도 안 나간다.** 짝이 잡힌 답에 이름조차 없다. 이름은 방에 붙으면 스냅샷이 주고, 레이팅은 여전히 어느 API 도 안 돌려준다
- **지표 셋은 EMF 에 안 올렸다.** 저쪽은 열 개로 묶여 있고([§90](82-100.md)) 그 선을 다시 정하는 결정은 밴드 상수를 실제로 재는 회차에 온다 — 그때까지 `/metrics` 로 읽는다. **대기자를 게이지로 세지 않는다**: 줄은 표에 있고 프로세스가 그것을 소유하지 않아서, 인스턴스마다 올렸다 내리면 탭을 닫은 사람이 영영 안 내려간다([§92](82-100.md)가 `WsSessionsActive` 에 대해 적어 둔 것과 같은 함정)

### 새 상수 여섯 — 전부 [미확정]

| 상수               | 값     | 무엇                                                     |
| ------------------ | ------ | -------------------------------------------------------- |
| `queue.Base0`      | 200    | 처음 섰을 때의 밴드 폭                                   |
| `queue.Expand`     | 20 / s | 기다린 1초마다 넓어지는 폭 (30초에 상한)                 |
| `queue.BaseMax`    | 800    | 밴드 상한. 두 사람의 RD 가 여기에 더해진다               |
| `queue.StaleAfter` | 12초   | 다시 안 물어보면 줄에서 빠지는 시간. 화면의 주기가 2초다 |
| `queue.PickupTTL`  | 2분    | 짝이 잡힌 자리를 들고 기다리는 시간                      |
| `queue.Candidates` | 20     | 한 번에 잠그고 훑어보는 후보 수                          |

**재려면 사람끼리 줄에 서 본 판이 쌓여야 한다** — [§92](82-100.md)의 벽과 같은 종류이고, `match_pairing_wait_seconds` 와 `match_pairing_rating_gap` 이 그것을 재려고 붙어 있다. **앞의 넷이 제품 행동을 정하고**(밴드 셋과 만료 하나), 뒤의 둘은 사고 방지용이다.

### 남은 것

- **N대에서 방이 안 따라간다.** 큐는 표라서 처음부터 N대에서 도는데, 방은 짝을 지은 인스턴스의 메모리에 선다 — 상대가 다른 인스턴스에 붙으면 그 방이 없다. **지금은 인스턴스가 하나라**(`infra/ecs.tf` 의 `desired_count = 1`) 실제로 안 마주치고, 늘리는 날 방을 표로 내리는 결정이 같이 온다
- **짝이 잡혔는데 안 나타나는 사람.** 상대는 그 방에서 기다리다 화면을 떠나야 한다 — 방이 걷히는 것은 `OpenTTL`(30분)이고 큐 방에 그것을 줄이지 않았다. 근본 수정은 [§93](82-100.md)이 적어 둔 「호스트가 자기 방을 걷는 버튼」과 같은 자리다
- **줄에 선 채로 엔진과 두는 것을 막지 않는다.** 폴백을 안 붙이기로 한 것([§92](82-100.md))과 다른 물음이다 — 사람이 스스로 그러면 짝이 잡히는 순간 두 판이 열린다. 화면이 대국 중에 이 자리를 감추는 것이 답이고, 아직 안 했다
- **연속 대국이 없다.** 판이 끝나면 되짚기로 가고, 「もう一局」은 줄에 다시 서는 것이다
- **실물로 안 돌았다.** 프로덕션에 대인전 판이 0건이고([§95](82-100.md)와 같은 벽), 확인은 DB 테스트와 핸들러 테스트뿐이다 — **사람 둘이 줄에 서 보는 것**이 남은 단계다
- **큐 테스트는 표를 비워서 격리할 수 없다.** CI 가 패키지들을 같은 DB 에 동시에 걸고 큐는 사람마다 한 행인 표 하나라, 「지금 줄에 서 있는 사람」에 남의 테스트가 섞인다. 비우면 그 순간 줄에 서 있던 남의 테스트가 깨지므로 **레이팅을 테스트마다 만 점씩 떨어뜨려 격리한다** — 밴드가 900을 못 넘으니 제품의 장치가 그대로 벽이 된다. 「줄에 몇 명인가」는 표 전체를 세는 제품 질의라 **정확한 수로 단정하지 않는다**(로컬에서는 통과하고 CI 에서만 빨개진 자리다)
