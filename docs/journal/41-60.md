## 41. 화면이 한 사실을 두 채널로 말하고 있었다 (2026-08-12)

되짚기 화면을 눌러 보며 나온 것들이다. **여덟 개가 같은 모양의 실패였다** — 한 사실을 두 곳이 말하거나, 한 채널이 두 뜻을 나른다. §31이 「내」를 두 뜻으로 쓰다 갈렸을 때 「말이 두 뜻으로 쓰이면 그 말을 버린다」로 닫은 그것의 **화면판**이고, 낱말이 아니라 **CSS 속성·화살표 색·버튼 라벨·커밋 경계**에서 났다.

| 무엇이 두 벌이었나           | 어떻게 드러났나                                                                                                   |
| ---------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| `transform`                  | 선택 표시가 `translateY` 로 들어올려 `rotate(180deg)` 를 덮었다 — **고른 상대 駒가 내 방향으로 섰다**             |
| 「指し直す」                 | 버튼은 「카드 닫고 다시 두기」, 카드의 한 줄은 「판을 만지면 가정 분기」. 카드를 읽다가 판을 만지면 분기로 빠졌다 |
| 초록 화살표                  | 회상에서는 **물러진 수**, 분기에서는 **최선수**. 뜻이 정반대인데 모양이 같다                                      |
| 「지금 어디인가」            | 슬라이더 손잡이 · `0 / 109 手` · 목록의 강조 줄, 셋                                                               |
| 「지금이 아니다」            | 판 탈색 + 되짚기 화면 그 자체. **되짚기는 전부가 과거라** 탈색이 아무것도 구별하지 못한다                         |
| 「갱신 중이다」              | 흐림 + `読んでいます…`. 手数마다 문구가 번쩍여 그것만 눈에 남았다                                                 |
| 물러진 수의 자리             | 출발 칸 테 + 도착 칸 동심원(2.4초 맥박) + 화살표, 셋                                                              |
| 최선수 목록 · 물러진 수 목록 | 같은 국면의 같은 종류의 사실이 두 목록으로 갈려 **견줄 수가 없었다**                                              |

### 두 커밋으로 나뉘면 두 번 보인다

`useEffect` 는 **페인트 뒤에** 돈다. 분기가 한 수 나아갈 때 미끄러짐을 거기서 붙이고 있었고, 그래서 순서가 이렇게 됐다.

```
커밋 1  판이 도착 칸의 駒로 바뀐다 → 페인트        ← 첫 번째 움직임
커밋 2  data-motion 이 붙어 駒가 출발 칸으로 돌아가 미끄러진다  ← 두 번째
```

`useLayoutEffect` 로 옮기면 판 변경과 미끄러짐이 **같은 그림**에 들어간다. 「말이 두 번 움직인다」가 그것이었다.

### 회상 장치를 없앴다 — 분기가 그것을 겸한다

되짚기에는 같은 물음에 답하는 장치가 둘 있었다. 「회상」(탈색·유령 駒·두 칸 표식)과 「もしも」(분기)다. 물러진 수를 고르면 **분기로 그 수를 둔다**로 합치니 셋이 같이 없어졌다.

- **打이 회상에서만 안 그려졌다.** 打은 출발 칸이 없어 화살표가 안 나가고, 그때 표식 하나에 전부가 걸린다. 분기에서는 그 수가 **실제로 놓여 있으므로** 짚을 것이 없다
- `この手を指してみる` 버튼이 **방금 한 일을 다시 하자고** 물었다
- 대국 화면에는 회상이 남는다 — 거기서는 살아 있는 판과 회상이 같은 자리를 쓰므로 탈색이 실제로 구별을 한다

### 한 목록 — 이 국면에서 지을 수 있던 수 전부

최선수 · **실제로 둔 수** · 물러진 수를 평가치 하나로 정렬하고 파랑→빨강으로 칠한다. 622번 77手째가 이렇게 선다. (**정렬과 색은 §60에서 고쳐졌다** — 詰み은 cp 밖으로 나가고 색은 플레이어 관점이 됐다. 위 예의 둔 수는 최선수를 겸해 값이 붙었지만, **후보 셋 밖이면 그 칸이 비어 있었다.**)

```
▲8六角  あなたが指した手  +41     ← 최선수 1위이면서 실제로 둔 수. 한 줄이다
▲4八金引                 +36
▲同角   タダ捨て ×2     −498     ← 같은 수를 두 번 물렸다. 낙폭은 −36%/−32% 로 달랐다
▲6六香  大きな形勢損     −777
▲7四金  大きな形勢損    −1397
```

- **값은 전부 지금 잰 것이다.** 같은 `▲8六角` 이 저장된 `eval_cp` 로는 **+100**, 리뷰가 다시 재면 **+41** 이었다(k=10 vs k=3). 한 줄에 두 자를 섞지 않는다
- **같은 수는 한 줄로 세고 횟수를 적는다.** 낙폭이 달랐던 것은 판정 당시의 흔들림이고, 나란히 적으면 없는 차이를 가르친다
- **실제로 둔 수를 누르면 진행한다.** 분기로 열면 같은 국면에 서면서 화면만 「もしも」가 된다 — 벌어진 일에 그 말을 붙이면 거짓이다
- 차례를 **양쪽 다** 적는다. 「相手の番」만 적으면 말이 없는 것이 「내 차례」인지 「아직 모른다」인지 갈리지 않는다

### 물러진 수에는 cp가 없었다 — `005`

`interventions` 에 낙폭만 있었다. 판정이 `WinRate(best) − WinRate(after)` 로 만들고 **두 원본을 버렸다.**

되돌릴 수 없다. 미지수가 둘인데 식이 하나이고, 같은 cp 차이가 위치에 따라 다른 낙폭이 된다.

```
   0 → 300cp    승률 0.500 → 0.622   낙폭 0.122
2000 → 2300cp   승률 0.965 → 0.973   낙폭 0.008
```

§26이 「판정이 이미 두 국면을 재고 있으니 공짜다」로 `game_moves.eval_cp` 를 붙일 때 **이 표를 안 봤다.** `best_cp`·`after_cp` 두 칸을 추가했다(`005_intervention_cp.sql`). 과거 행은 영원히 NULL이고, 화면은 그 자리를 **다시 재서** 채운다.

### 판정의 두 탐색은 지평이 한 수 다르다 — 새로 찾은 것

§39 ⑦이 「같은 국면·같은 깊이가 같은 값을 안 준다」를 치환표로 설명했다. 그것 말고 **방향이 있는 오차**가 하나 더 있다.

```go
before := moves[:len(moves)-1]
best  = SearchDepth(startSFEN, before, 12)   // 뿌리 = N−1手 뒤,  절대 지평 (N−1)+12
after = SearchDepth(startSFEN, moves,  12)   // 뿌리 = N手   뒤,  절대 지평 (N−1)+13
```

깊이는 같고 **뿌리가 한 수 다르다.** 엔진 점수는 깊이의 홀짝으로 수번 측에 치우치므로(depth parity), 한 쪽만 한 수 더 보면 **낙폭이 한 방향으로 기운다.** 정석은 **한 뿌리에서 MultiPV** 로 최선수 줄과 그 수의 줄을 함께 받는 것이다.

**크기는 안 쟀다. [미확정]** 재려면 622번 개입 24건을 한 뿌리 MultiPV로 다시 채점해 낙폭을 견주면 된다.

그리고 `bestCp` 와 `eval_cp[N-1]` 이 **같아야 하는데 다른** 이유는 이것과 별개다 — 뿌리도 깊이도 같고, `eval_cp[N-1]` 에 값이 들어오는 경로가 둘이다(N−1을 판정할 때의 `SenteCpAfter`, N을 판정할 때의 `SenteCpBefore`). 같은 칸을 두 탐색이 쓰고 나중에 쓴 쪽이 남는다. §39 ⑦이 「手数 연결을 세 가지로 확인해도 안 맞았다」고 적은 자리가 여기다.

### Tier 1 비율은 이 계기로 영원히 0이다

§38이 「5\~65% 사이이고 플레이테스트 한 판이면 나온다」고 적었다. 한 판 뒀더니 이렇다.

| 622번 개입 24건 |       |
| --------------- | ----- |
| Tier 0 (캐시)   | 13    |
| Tier 2 (실시간) | 11    |
| **Tier 1**      | **0** |
| 템플릿(NULL)    | 0     |

`Layered.Explain` 이 **캐시를 먼저 보고 맞으면 Tier 0으로 적는다.** `004` 로 넣은 Tier 1 문구 21개는 캐시에 있으므로 히트하고, `explain_tier` 에는 0이 남는다. **「Tier 1 비율」은 이 계기로 못 재고**, 물어야 하는 것은 **「캐시가 몇 %를 답했나」**다 — 54%이고, LLM 왕복이 절반 넘게 0회다. §38의 「그 절반이 0초가 된다」가 다른 경로로 맞았다.

### 그늘이 회상에서 강제로 켜지던 것을 뺐다

탈색된 판 위의 둥근 얼룩이 「상대가 손을 뻗은 칸」으로 안 읽히고 **판에 낀 흠**으로 읽혔다. 사람이 켤 때만 그린다(회상 중에도 토글을 잠그지 않는다).

**D6의 「three.js 2컷」이 1.5컷이 됐다.** 컷 2가 「회상에서 그 한 칸에 고이는 그늘」이었고, 이제 자동으로 안 켜진다. 데모에서 그늘을 보여줄 거면 토글을 눌러야 한다.

### 남은 것

- **[미확정] 판정의 지평 비대칭이 얼마인가.** 위의 새로 찾은 것. 방향이 있으므로 K를 잡는 데 치환표 잡음보다 나쁠 수 있다

- **새 판으로 A를 안 확인했다.** 622는 마이그레이션 이전 판이라 저장된 값이 없고, 화면이 재서 채우는 쪽으로만 확인됐다

## 42. 착수 **전**에 이름을 알린다 — 그리고 「이름은 맞는데 값이 없는」 형태 (2026-08-12)

§30이 연 태그의 세 소비자 중 **제안형 힌트**를 붙였다. §43이 RAG 검색 키를 이은 것과 같은 회차의 다른 갈래다.

### 두 축이 서로 다른 이유로 갈렸다

|                     | 무엇으로 정해지나          | 그래서                                      |
| ------------------- | -------------------------- | ------------------------------------------- |
| 囲い·전법·戦型 31개 | 판과 수순                  | 합법수마다 시뮬레이션. **엔진 0회, 동기**   |
| **手筋 10개**       | 「그래서 得인가」= 엔진 값 | 게이지와 같은 **비동기**(`maybeTesujiHint`) |

`computeTagHints` 가 「手筋은 엔진 평가치가 있어야 하므로 여기서 건너뛴다」로 비워 둔 자리다.

**게이트를 새로 쓰지 않았다.** 후보 스캔은 `freshTesuji`, 통과 여부는 `enginePaidOff`(`TesujiLossCp = 100`) — 착수 후에 이름을 붙이는 쪽과 **같은 두 함수**다. 갈리면 같은 수가 힌트에서는 手筋이고 착수 뒤에는 아니게 된다(§34 ⑦).

**엔진을 걸기 전에 룰로 거른다.** 새 이름이 생기는 수가 국면당 0\~2개라 대부분의 국면에서 탐색이 0회다. 안 거르면 사람 차례마다 1\~7회를 부른다.

### 실측 — 게이트가 실제로 무엇을 끄는가

실 기보 103수(`playtestUpTo103`), depth 12, 水匠5.

| ---- | ------- | ----------------- | --------- | ---- | ----------------------- |
| 19   | `8h2b+` | `kaku_ryodori`    | +440cp    | ✗    | —                       |
| 21   | `P*2c`  | `tataki_no_fu`    | +489cp    | ✗    | —                       |
| 27   | `B*5e`  | `kaku_ryodori`    | **+24cp** | ✅   | **딴다** — `5e4d`       |
| 43   | `4d5e`  | `kaku_ryodori`    | +196cp    | ✗    | —                       |
| 60   | `L*8c`  | `dengaku_zashi`   | +426cp    | ✗    | —                       |
| 77   | `S*4d`  | `wariuchi_no_gin` | **−72cp** | ✅   | **딴다** — `4d3c+`      |

**형태 6개 중 4개를 끄고, 통과한 2개는 둘 다 최선 수순이 대상을 딴다.** 이 판에서 위양성은 0이다.

### 무엇을 정했나

- **계단을 하나로 쓴다.** 갇힘 힌트와 手筋 힌트는 둘 다 「네가 무엇을 두면 되는가」이고 발동 조건(3회·5회)도 같다. 따로 두면 **같은 파랑(`--hint`)이 두 뜻**이 되고, 그게 §41이 여덟 번 잡은 실패다. `buildHint` 를 그대로 쓰고 **짚는 대상만** 手筋으로 바꾼다(`pointHintAtTesuji`)
- **바꿔도 되는 근거는 게이트다.** 후보는 전부 `TesujiLossCp` 안이라 최선수보다 100cp 넘게 나쁠 수 없고, 그 대신 **이름이 있다**
- **예산은 나눈다.** 상한·쿨다운 값(`TagHintMaxPerGame`·`TagHintCooldown`)은 그대로 쓰되 카운터를 나눈다 — 한 예산이면 囲い 힌트가 먼저 세 번 떠서 手筋이 한 번도 못 뜬다. 手筋은 그 국면에서만 성립하고 놓치면 사라진다
- **웹 변경이 0이다.** `TagHints`·`Hint` 두 채널과 `KIND_JA.tesuji` 가 이미 있었다
- **엔진을 부르는 자리가 다섯이 됐다.** 手筋 힌트가 `archive.Wrap` 의 다섯 번째 소비자다. 후보의 착수 후 국면은 **플레이어가 그 수를 두면 바로 다시 물어볼 국면**이라 캐시 적중이 저절로 따라온다(§37)

### 남은 것

- **[미확정] 판당 手筋 기회가 몇 번인가.** 위 표는 한 판이고 「형태」가 6개다. 게이트를 지난 2개가 판당 빈도의 전부인지는 표본이 하나라 말할 수 없다. **floodgate 기보로 넓혀 재는 것이 다음**이고, CSA 파서는 `kifu-import` 갈래에 있다
- **[미확정] 「최선 수순이 대상을 따나」를 자동으로 세지 않는다.** 지금은 로그로 찍고 눈으로 본다. 자동화하려면 대상 칸을 `tag` 밖으로 꺼내야 하는데, **무엇을 셀지 정하기 전에 그 API를 만들지 않는다**
- **2차·3차(강제 수순)를 안 만들었다.** 「A를 두면 상대가 B밖에 못 두고 그때 C가 手筋」이다. 대상은 `Fork` 4 + `Skewer` 1 = **5개뿐** — 腹銀·桂頭の銀·底歩·叩きの歩·垂れ歩는 강제와 무관하고 1차가 이미 덮는다
- **프로덕션에서 뜨는 것을 아직 안 봤다.** 로컬 테스트와 컨테이너 측정까지다

## 44. 종반에 떠돌던 飛가 「中飛車」가 되고 있었다 (2026-08-12)

실 기보로 태그를 넓게 처음 재봤다. [09-tags.md §4](../09-tags.md)가 「囲い·전법은 손으로 만든 국면에서만 재봤다」로 남겨 둔 자리다.

**표본은 floodgate 341판**(wdoor, 2020-03-14 하루 + 기존 25판). 엔진을 안 쓰므로 341판이 0.5초에 끝난다. 받는 절차와 돌리는 법은 [apps/server/README.md](../../apps/server/README.md).

### 정답 라벨 없이도 틀린 것이 확실한 자리가 있었다

### 실측 — 이름이 처음 붙는 手数 (341판)

**자른 것이 아니라 갈린 것이다.** 남은 것의 중앙값이 6\~16수 — 정석이 전법을 선언하는 그 구간이다. 四間·三間이 고치기 전에도 중앙 11\~12수였던 것이 「진짜는 원래 序盤에 있었다」는 증거이고, 中飛車(45수)·右四間飛車(59수)·相振り飛車(67수)의 늦은 중앙값이 그 이름은 거의 전부 잡음이었다는 뜻이다.

### 무엇을 정했나

- **`OpeningPlies = 24`** (양쪽 12수씩). 분포에 골짜기가 없어서 **이 수는 데이터가 아니라 정석 수순의 길이에서 왔다** — ▲7六歩△3四歩▲6六歩△8四歩▲6八飛 가 9수째다. **[미확정]**
- **경계를 「지금 몇 수째인가」가 아니라 「振った 것이 몇 수째였나」에 건다.** 그래야 12수에 얻은 四間飛車가 100수째에도 남는다. 지금 手数로 자르면 이름이 대국 도중에 꺼진다
- **角換わり만 예외로 「지금 手数」로 자른다.** 상태 술어라 교환 시점을 복원할 수 없다 — 수순에 무엇이 잡혔는지가 없다. 대가로 **角換わり는 序盤 동안만 뜬다**
- **囲い에는 경계를 안 건다.** 美濃는 70수째에 서도 美濃다. **이것은 그대로 산다** — 다만 「그래서 囲い는 아무것도 안 자른다」는 [§67](61-81.md#67-태그-오진-셋--하나는-오진이-아니었고-둘은-방향이-같았다-2026-08-14)에서 틀린 것이 됐다. 거기서 자른 것은 시간이 아니라 **打って 채운 좌표**다
- **자르는 방향이 안전한 쪽이다.** 이름이 안 뜨면 힌트가 없을 뿐이지만, 틀린 이름은 초심자가 검증할 수 없는 것을 가르친다

## 45. 手筋 태그 1국 검분 — 오진 3/8, 그리고 手筋 추천을 보류했다 (2026-08-12)

§42가 「이름은 맞는데 값이 없는」 형태를 예고했고, §44가 `sode_bisha` 를 341판에서 83개(대부분 의심)로 남겼다. floodgate 1국(108手, **실제 파이프라인** depth 12·k 10)을 DB에 임포트하고, 태그 달린 엣지 8건을 국면 복원으로 하나씩 판정했다. 게이트(`game.NamedTesuji`)를 통과한 것들이라 **「이득인가」는 이미 참**이고, 남은 질문은 **「이름이 맞는가」**였다.

### 실측 — 8건 중 3건이 오진

| 태그              | 수      | 판정 | 실체                                                    |
| ----------------- | ------- | ---- | ------------------------------------------------------- |
| `tataki_no_fu`    | `P*8e`  | ✅   | 8四 銀 머리를 두드림                                    |
| `tataki_no_fu`    | `P*7e`  | ✅   | 7四 金 머리를 두드림                                    |

| `keitou_no_gin`   | `S*3d`  | ✅   | 3三 桂 머리에 銀                                        |
| `wariuchi_no_gin` | `3d3c`  | ✗    | **王手銀取り** — 玉을 표적으로 셌다                     |

### 오진 셋의 뿌리는 버그 둘 — 고쳤다

- **`wariuchi_no_gin` (#6·#7)** — `targetSquares` 가 표적에서 歩만 빼고 **玉을 안 뺐다.** 手番을 뒤집힌 국면에서 `LegalMoves` 가 敵玉을 잡는 수를 내므로, 玉+駒 두 갈래(=王手○取り)가 両取り 2매로 化했다. 出典(手筋事典)이 割打ちの銀을 「**右斜め後ろ·左斜め後ろ**の飛車または金」로 정의한다 — 玉은 대상 밖이고 방향은 **뒤쪽 대각**이다. 玉을 표적에서 빼고(fork 계열 전체에 적용), `forkShape` 에 銀은 **뒤쪽 두 대각** 조건을 넣었다.
- **`sode_bisha` (#8)** — `DetectFormation` 이 飛의 筋 변경만 보고 段을 안 봤다. 振り飛車는 **자기 2段**(先手 八·後手 二)에 振る게 선언이라, 敵陣 3四로 뛰는 ▲3四飛(横歩取り)는 이제 걸러진다(`senteRank == 8`). §44가 남긴 `sode_bisha` 83개의 상당수가 이 유형이었을 것이다 — **재스캔은 아직 안 했다.**

### `kaku_ryodori`(#4)는 버그가 아니라 게이트의 빈자리 — §42가 예고한 그것

`9e7g+` 는 飛를 角으로 따는 엔진 최선수(+1030cp)라 게이트를 여유롭게 통과한다. 그런데 엔진의 최선 PV가 `9e7g+ 6h7g …` — **겨눠진 6八 角이 馬를 되잡아** 両取り는 실현되지 않는다. 값은 **飛 포획**에서 왔지 両取り에서 오지 않았다. 게이트가 「이 수가 이득인가」만 묻고 「**PV가 그 표적을 따는가**」를 안 물어서다. 판정 정보는 **저장된 PV에 이미 있다**(2수째가 手筋 駒를 되잡는가). 「좋은 수에 틀린 이름」이라 #6\~#8(형태가 틀림)과 결이 다르고, 더 잡기 어렵다.

### 무엇을 정했나

- **버그 둘은 고쳤다**(위). `internal/tag/tesuji.go`(玉 제외 + 銀 뒤 대각)·`tag.go`(`senteRank`). 유닛 테스트 4개 추가(뒤대각 양성·앞대각 음성·玉 음성·横歩取り 음성), 실제 세 국면(#6·#7·#8)으로 확인. 기존 `馬` 테스트가 玉을 fork 표적으로 쓰던 **잠재 결함**도 같이 고쳤다.
- **手筋 분류 방향은 보류한다.** 한 판에서도 8건 중 3건이 오진이었고, `kaku_ryodori` 유형(両取り 실현)은 게이트를 강화해야 닫힌다. **「좋은 수에 틀린 이름」이 학습 앱에서 가장 값비싼 실패**라(설명이 틀리면 초심자는 검증 못 한다), 이 정확도를 그대로 두고 이름을 늘리지 않는다. **제안형 힌트 자체는 §74에서 열었다** — 그쪽이 막혀 있던 것은 이름의 정확도가 아니라 게이트가 답하는 속도였고, 뜨는 이름은 여기서 이미 검분한 것들이다.
- **다음 최우선은 레이팅 기반 난이도다.** 회원가입 → 유저 착수 실시간 레이팅 분석 → 그 레이팅으로 컴퓨터 수 확정. 판단이 룰·엔진 값에만 매여 있어(설명 정확도에 안 걸린다) 난이도가 더 현실적이다. **§5 1순위를 이것으로 바꿨다.**

### 남은 것 (手筋 방향을 재개할 때 — **게이트 쪽은 §74에서 재개했다**)

- **게이트에 「PV가 手筋 駒를 되잡는가」 조건.** 프로덕션 비용 0(양쪽 호출부가 PV를 이미 들고 있다). `kaku_ryodori`·`juji_bisha`·`wariuchi_no_gin`·`fundoshi_no_kei` 네 両取り에 다 걸린다. §42가 「최선 수순이 대상을 따나」로 손으로 찍던 그 열을 자동화하는 것과 같은 일이다
- **341판 재스캔으로 `sode_bisha`·`wariuchi_no_gin` 감소를 실측한다.** 이번 수정 뒤 아직 안 했다
- **囲い 계열 라벨·2차 手筋** — §44·§42의 「남은 것」 그대로

## 46. 로그인 — 세션을 표로 만들지 않았다 (2026-08-12)

§45가 §5 1순위를 「레이팅 기반 난이도」로 바꿨고, 그 셋 중 첫째다. **판이 누구의 것으로 남는지가 정해진다** — 실시간 레이팅(2순위)이 사람을 가로질러 쌓이려면 그 이름이 먼저 있어야 한다.

`users`·`skill_profile` 은 `001_init.sql` 에 이미 있었다. **마이그레이션이 하나도 없다.**

| 무엇                                   |                                                             |
| -------------------------------------- | ----------------------------------------------------------- |
| `internal/auth`                        | 서명 쿠키(HMAC-SHA256)와 Google 왕복. HTTP 표면은 안 갖는다 |
| `internal/server/auth.go`              | `/api/me` · `start` · `callback` · `logout`                 |
| `ws.go` → `recorder.go` → `CreateGame` | 연결이 열릴 때 쿠키를 읽어 `games.user_id` 를 채운다        |
| `review.go` · `whatif.go`              | **자기 판만 읽힌다** — 아래                                 |
| `apps/web`                             | 헤더 오른쪽 끝 — `ログイン` 또는 이름 + `ログアウト`        |

### 되짚기를 같이 걸렀다 — §33이 이 PR에 맡겨 둔 것

§33의 「남은 것」이 **「로그인을 붙이는 PR이 같이 목록을 걸러야 한다」**고 적어 뒀다. 안 걸렀으면 `user_id` 가 채워지기 시작하는 바로 이 PR이 **남의 기보와 「그 사람이 어디서 막혔나」를 여는** PR이 된다([02-architecture.md §7](../02-architecture.md) 위협 2).

목록·상세·가정 수순 셋이 같은 함수 하나(`authHandler.owner`)로 걸린다 — 규칙이 두 벌이면 한쪽만 고쳐진 채 남고 그 한쪽이 곧 구멍이다. **남의 판은 403이 아니라 404다**: 403은 「그 번호의 판이 있다」를 알려주는 셈이라 그것만으로 남이 몇 판 뒀는지 세어 볼 수 있다.

거르는 쪽이 짧은 이름을 갖는다 — `ListGames`·`GameRecord` 가 주인을 보고, 주인을 안 보는 쪽은 `…AnyOwner` 로 길다. **측정만 그쪽을 쓴다**(§39의 상수 재채점). 나중에 손이 먼저 닿는 것이 안전한 쪽이어야 한다.

### 무엇을 정했나

- **세션을 DB에 두지 않는다.** 담을 것이 `user_id`·이름·만료 셋뿐이고, 표를 만들면 공유 DB에 마이그레이션이 하나 늘고 로그인마다 쓰기가 생긴다. 대가는 하나이고 크다 — **발급한 세션을 서버가 끊을 수 없다.** 그래서 `SESSION_SECRET` 을 바꾸는 것이 곧 전원 로그아웃이고, TTL 30일이 「기기를 잃었을 때 남의 손에 로그인이 살아 있는 시간」이다.
- **redirect URI의 스킴을 `X-Forwarded-Proto` 로 정하지 않는다.** 앞단이 ALB → Caddy 두 겹인데 Caddy는 신뢰 설정 없이 그 헤더를 자기 것(평문 http)으로 덮는다. 믿었다면 프로덕션에서 `http://show-gi.com/...` 이 되어 Google이 거부하고 쿠키에서 `Secure` 가 빠졌을 것이다. 대신 **Host로 정한다** — 배포된 자리는 전부 HTTPS이고 평문인 것은 로컬뿐이라 규칙이 「localhost면 http, 아니면 https」로 끝난다. `PUBLIC_ORIGIN` 이 있으면 그것이 정본이다.
- **ID 토큰의 서명을 검증하지 않는다.** 브라우저를 거치지 않고 우리가 TLS로 직접 부른 토큰 엔드포인트에서 온 것이라 가운데에 낄 것이 없다(Google 문서가 그 경우를 예외로 둔다). JWT 라이브러리가 안 들어오고, 대신 **`aud` 만 본다** — 서명이 아니라 설정 실수를 잡는 자리다.
- **`unset` 을 빈 값으로 본다.** SSM이 빈 문자열을 거부해 아직 발급 안 된 키가 그 문자열로 들어가 있다(§3). 그대로 켜면 로그인 버튼이 뜬 뒤 Google이 400을 준다.
- **`/api/me` 는 로그인이 꺼진 배포에도 있다.** 화면이 「로그인이 없는 배포」와 「서버 고장」을 갈라 그려야 하는데 404면 그 둘이 같아진다. 응답에 `skill_profile` 을 싣지 않는다 — 본인만 보는 값이고([02-architecture.md §7](../02-architecture.md)) 이 자리는 화면이 늘 부른다.
- **로그인은 대국의 전제가 아니다.** 키가 없어도, 사람이 안 눌러도 지금까지처럼 익명으로 둔다. 두는 중에 다른 탭에서 로그아웃해도 **그 판은 시작할 때의 주인으로 끝난다** — 주인이 연결이 열릴 때 한 번 정해진다.

### 물린 것 — Vite가 Host를 바꿔 보내고 있었다

첫 시도에서 Google이 `redirect_uri_mismatch` 를 줬고, 거부된 주소가 `http://localhost:8080/...` 이었다. **Vite 프록시의 기본값이 Host를 타깃(:8080)으로 바꾸는 것**이라, 서버가 되짚은 주소가 브라우저의 것(:5173)이 아니었다.

`changeOrigin: false` 로 껐다(`vite.config.ts`). **프로덕션은 ALB도 Caddy도 Host를 보존하므로 어긋나 있던 것은 개발 쪽이고**, 끄는 편이 양쪽을 같게 만든다 — `PUBLIC_ORIGIN` 을 로컬에서 채워 넘기는 것보다 낫다.

### 로컬에서 끝까지 돌렸다 (2026-08-12)

```
ログイン → 계정 선택 → 동의 → 헤더에 이름 + ログアウト
games.id 35  user_id 7  (조성현(Jovid))  moves 2
ログアウト → 헤더가 ログイン 으로 돌아가고 **두던 판은 그대로 이어졌다** (▲7六歩 △7二銀)
```

마지막 줄이 설계한 그것이다 — 로그아웃이 페이지를 새로 부르지 않는다. 부르면 WebSocket이 끊겨 그 판이 `abandoned` 로 닫힌다.

### 남은 것

- **프로덕션에서도 켜졌다** (2026-08-12). SSM의 `GOOGLE_CLIENT_ID`·`GOOGLE_CLIENT_SECRET` 를 실키(버전 2)로 덮고 ECS를 새로 띄웠다 — `https://show-gi.com/api/me` 가 `{"enabled":true,"user":null}` 를 준다. redirect URI가 https로 나가는 것과 쿠키의 `Secure` 도 실물로 확인했다.
- **새로고침하면 두던 판이 여전히 그 자리에서 끝난다** — 세션은 연결에 매여 있어(`ws.go`) ctx가 취소되면 goroutine과 함께 사라지고 `abandoned` 로 닫힌다. **바뀐 것은 그다음이다**(§51): 다시 오면 「이어하시겠습니까」를 묻고, 「はい」면 그 기보로 국면을 되만들어 **같은 행에 이어 쌓는다.** 로그인이 이 물음의 전제다 — 그 abandoned 판이 그 사람 것으로 남는 것이 여기서 값을 한다.
- **`skill_profile` 에 아직 아무것도 안 쓴다.** 표는 `001` 부터 있었다. 실시간 레이팅은 들어왔지만(§47) **판마다 초기화되고 이 표를 안 건드린다** — 사람을 가로질러 쌓는 것이 그다음이다.

### 이어하기 — 기록에서 다시 세운다 (§51에서 붙었다)

**세션을 살려 두는 쪽을 안 골랐다.** game id로 레지스트리에 담고 TTL을 걸면 「세션은 연결에 매여 있다」가 깨지고, ECS 태스크가 둘 이상이 되는 순간 sticky 라우팅이나 공유 상태를 요구한다.

**싼 쪽은 기록에서 국면을 되만드는 것이다.** 그 코드가 이미 있었다 — `review.go` 의 `detailOf` 와 `whatif.go` 의 뿌리 만들기가 `games.start_sfen` + `game_moves` 로 판을 다시 둔다(§33 · §37). 새 세션을 그 수순으로 시작시키므로 **세션 수명도 goroutine 소유권 규약도 안 건드린다.** 국면 캐시는 다시 데워지지만 §37 덕에 27ms다.

정할 것이 셋이었고 전부 「어느 판에 쌓느냐」였다. **답이 하나다 — 같은 행이다**(§51).

| 정할 것           |                                                                                                           |
| ----------------- | --------------------------------------------------------------------------------------------------------- |
| `games.result`    | **되연다.** 점유(`ClaimGameForResume`)가 `abandoned` → NULL 을 한 문장으로 하고, 그 한 문장이 곧 잠금이다 |
| `interventions`   | 같은 행이라 저절로 따라온다. 갈렸으면 「그 국면이 그 사람에게 얼마나 어려웠나」가 두 판에 흩어졌다(§18)   |
| 어디까지 이어받나 | 물러진 수는 기보에 없으므로(§18) 되만든 판에 안 온다. 그것이 맞다 — 롤백된 수다                           |

## 47. 실시간 레이팅 — 조절하는 것은 밴드 하나다 (2026-08-12)

§5 1순위의 남은 둘(실시간 레이팅 분석 · 그 레이팅으로 컴퓨터 수)을 같이 닫았다. **구조는 §21 ①이 적어 둔 그대로다** — `Recorder` 와 같은 이벤트 흐름의 두 번째 소비자이고, 세션은 값을 채널로 받는다.

| 무엇                                 |                                                                                                         |
| ------------------------------------ | ------------------------------------------------------------------------------------------------------- |
| `internal/skill`                     | 롤링 추정기(`Track`)와 그것을 소유하는 worker. **엔진도 DB도 판도 모른다** — 입력은 낙폭과 「걸렸나」뿐 |
| `game.Rater`                         | 넣는 쪽은 논블로킹(`Recorder` 규약), 받는 쪽은 채널 — **읽는 것을 세션이 소유한다**                     |
| `Opponent.Choose(…, skill.Estimate)` | 밴드를 매 수 옮긴다. `adaptive` 만 보고 `engineOpponent` 는 무시한다                                    |
| `intervene.Judge`                    | **통과한 수에도 낙폭을 담아 돌려준다** — 추정의 주 신호가 그 값이다                                     |
| `internal/server/ws.go`              | 판정이 있을 때만 worker를 만든다. 대국마다 새로                                                         |
| `apps/web`                           | 사이드바에 눈금 다섯 개 + 말 한 마디(`相手の強さ`)                                                      |

### 실측 ① — 밴드를 옮기면 실제로 다른 수가 나오는가

**여기서 0이면 이 기능은 도는 코드일 뿐이다.** 후보 10개가 20\~40cp에 몰리는 국면에서는 밴드를 어디로 옮겨도 갈 곳이 없다고 §21 ①이 미리 적어 뒀다.

약한 기보(늘 첫 합법수)의 상대 차례 12 국면. 국면마다 `depth 12 · k=10` 을 **한 번** 탐색하고 고르는 코드만 세 번 돌렸다 — 강함이 갈리는 자리는 선택이지 탐색이 아니다.

```
        후보폭(플레이어 관점)   loss=1        기준선        loss=0
 1수    +10 ~ +112cp          7a6b +112     7a6b +112     3c3d +10
 5수    -292 ~ +426cp         5b4b +426     6a7a +285     8c8d +36
 9수    -1398 ~ +114cp        P*9d +114     P*9d +114     P*9f -136
19수    -214 ~ +657cp         L*8e +484     L*4d +325     9i8i -214

고른 수가 갈린 국면      9/12
후보폭 200cp 이상        10/12
```

**너그러운 쪽이 덜 듣는다.** 기준선과 `loss=1` 이 갈린 곳은 12 중 2뿐이고(5수·19수), 세지는 쪽(`loss=0`)은 8이었다. 후보의 최대가 +112cp인 국면(1수·9수)에서는 밴드를 +400으로 올려도 같은 수가 뽑힌다 — **양보는 후보 목록이 허락하는 만큼만 된다.**

> **여기서 그 원인을 「기준선이 이미 후보 상한 근처를 겨냥한다」로 읽었고, 그게 틀렸다.** 실제 원인은 고르는 자였다(§55) — 두 방향 거리가 「양보 0」을 「초과 양보」보다 앞에 세운다. 자를 고친 뒤 같은 측정이 **11/12**다.

### 실측 ② — 20수 뒤 형세 (§16 표의 연장)

```
헤맴(loss=1)     플레이어 관점  +74cp
기준선(loss=.5)  플레이어 관점  +11cp
잘 둠(loss=0)    플레이어 관점 -407cp
```

**세 값의 순서가 이 표의 내용이고 절대값은 아니다.** §16이 같은 조립으로 +293cp를 적었는데 여기 기준선은 +11cp다 — 재 볼 때마다 흔들리는 폭 안이고(§39 ⑦), 그래서 이 표로 상수를 정하지 않는다.

**그래도 한 숫자는 남겨야 한다 — 레버가 한쪽으로 짧다.** 기준선에서 너그러운 쪽으로는 **+63cp**이고 세지는 쪽으로는 **−418cp**다. 밴드 폭이 200cp인데 너그러운 쪽 이동이 그 3분의 1이다. 위 ①의 「2/12 대 8/12」와 같은 사실을 다른 자로 잰 것이다.

> **원인을 후보 목록에서 찾았고 그게 틀렸다.** `HiCp` 도 k도 아니라 **고르는 자**였다(§55).

> **그래서 이 절을 「초심자가 통과할 수 있게 됐다」로 읽으면 안 된다.** 들어온 것은 **조절이 사람을 보기 시작했다**는 것까지다. 통과 여부는 §17이 이미 실측해 뒀다 — **+300에서도 초심자가 통과하는 수를 못 찾는 국면이 있다.** 그 자리를 움직이려면 밴드 안의 겨냥점이 아니라 `HiCp` 자체를 올려야 하고, 그것은 §21의 「밴드만으로는 안 되는 자리」와 같은 결론으로 간다.

### 화면까지 왔다

로컬에서 7수를 깨끗하게 두니 눈금이 `ふつう`(3) → `強め`(4)로 올라갔다. 반대쪽은 `TestRealEngineStrengthReachesTheClient` 가 잰다 — 같은 나쁜 수 3번이면 `かなり弱め`(1)까지 내려간다.

**내려갈 때는 `弱め`(2)를 건너뛴다.** 표본 셋까지 밴드가 안 움직이는데(`MinSamples`) EWMA는 그동안에도 값을 먹으므로, 연속 블런더 셋이면 세 번째 판정에서 낙폭이 이미 0.94이고 눈금이 3에서 1로 한 번에 간다. **눈금을 따로 부드럽게 만들지 않았다** — 그러면 화면이 말하는 강함과 상대가 겨냥하는 강함이 갈리고(§31), 반대로 밴드를 표본에 비례해 미리 움직이면 `MinSamples` 를 둔 이유가 없어진다. 연속으로 셋을 물러진 사람에게 도움이 한 번에 오는 것은 **틀린 그림이 아니다.**

**눈금은 판정 스냅샷보다 한 프레임 늦게 온다.** 추정이 세션 밖에서 돌기 때문이고, 그것이 「기다리지 않는다」의 실물이다.

### 무엇을 정했나

- **저장하는 값은 실력 점수가 아니라 낙폭이다.** `Estimate.Loss` 는 임계치에 대한 비율이라 뜻이 하나다. 「실력 0.7」은 무엇에 대한 0.7인지가 없다. **화면에 이름을 안 붙이기로 했던 것은 §62에서 뒤집혔다** — 段級은 뜻이 있는 척도라 「0.7」이 못 답하던 것에 답하고, 그래도 저장은 그대로 낙폭이다(段級은 파생값이다).
- **나빠지는 쪽이 빠르고 좋아지는 쪽이 느리다**(`RiseRate=0.5` · `FallRate=0.1`). 도움은 헤매는 그 자리에서 와야 하고, 조용한 국면에서는 아무 수나 둬도 낙폭이 0이라 빠르게 올리면 방금 통과한 사람이 곧바로 더 센 상대를 만난다.
- **조절하는 것은 밴드뿐이다.** 두 안전 필터도 후보 k도 안 건드린다 — 화면이 가르쳐 막은 종류의 수와 600cp 넘는 대형 악수를 난이도가 되살리지 않는다(§16 · §81).
- **개입 임계치(`Level`)는 안 건드린다.** 대국 중에 흔들면 같은 수가 같은 국면에서 걸리기도 안 걸리기도 하고, 문구 캐시 키까지 그 값으로 갈린다(`explain.Facts`).
- **표본 3개까지는 안 움직인다.** 첫 수 하나로 상대가 딴사람이 되면 사람이 알아차리기 전에 강함이 흔들린다.
- **눈금과 밴드가 같은 숫자에서 나온다**(`skillShift` → `strengthStep`). 따로 계산하면 화면이 말하는 강함과 상대가 겨냥하는 강함이 갈린다 — 게이지에서 手数를 따로 구했다가 한 수 낡았던 것과 같은 실패다(§31).
- **눈금은 추정기가 아니라 상대를 보고 그린다**(`game.SkillAdapter`). 추정기가 돌아도 상대가 그 값을 무시하는 조립이 있고(`engineOpponent`, 테스트가 쓴다), 추정기 유무로 갈랐더니 **강함이 내려가는데 상대는 최선수를 그대로 두는** 화면이 만들어질 수 있었다. 프로덕션이 adaptive 하나라 안 드러날 자리였다.
- **밴드 이동은 `PriorLoss` 의 위치를 몰래 못 박지 않는다.** `(loss - prior) × 2` 로 쓰면 그 식이 `prior = 0.5` 를 가정하는데 그 값도 [미확정]이다 — 0.3으로 옮기는 날 한쪽이 최대 폭을 넘고 다른 쪽이 잘린다. 양쪽을 따로 정규화해 prior 가 어디에 있어도 양 끝이 ±`SkillShiftCp` 가 되게 했다(`prior = 0.5` 에서는 옛 식과 같은 값이라 위 실측이 그대로 산다).
- **추정치는 국면 세대를 안 본다.** 게이지·手筋 이름은 특정 국면에 대한 답이라 판이 움직이면 거짓이 되지만, 이것은 사람에 대한 값이라 그대로 참이다.
- **착수 소요 시간은 안 넣었다.** 웹에서는 사람이 자리를 비운 시간과 생각한 시간이 같은 값으로 들어와, 그 신호가 실력이 아니라 자리 비움을 잰다. §5가 「아직 없다」고 적어 둔 그 칸은 **안 만들기로** 정했다.

### 물린 것 — 문구의 낱말을 고정한 테스트가 `main` 에서 깨져 있었다

`TestRealEngineHangingPiece` 가 개입 문구에 「利き」가 있어야 한다고 걸어 뒀는데, タダ捨て는 사실이 실리면 「その馬を取れる相手の駒が2枚あり…」로 나간다(`explain.Render`). 둘 다 「상대가 그 駒를 잡는다」는 같은 이야기이고 **사실이 실린 쪽이 더 나은 문구**다.

`8ff6074`(#54)에서도 똑같이 실패했다 — 즉 이 브랜치가 만든 것이 아니다. **CI 러너에 엔진이 없어 아무도 몰랐다.** 낱말 둘 중 하나면 통과하도록 고쳤다.

### 남은 것

- **상수 다섯이 전부 초기값이다**(`PriorLoss`·`RiseRate`·`FallRate`·`MinSamples`·`SkillShiftCp`). 실측으로 옮기려면 사람이 둔 판이 필요한데 표본이 아직 0이다 — §39가 상수 재채점에서 막힌 것과 **같은 벽이고 같은 한 걸음**이다.
- ~~**너그러운 쪽 도달이 2/12이고 실제 이동이 +63cp다.**~~ **막고 있던 것은 `HiCp` 도 k도 아니라 고르는 자였다**(§55). 그 자를 고치니 창 위 국면에서 실력별로 다른 수가 나온다. **초심자가 통과하느냐**는 여전히 사람이 둬 봐야 안다.
- ~~**`skill_profile` 에 아직 안 쓴다.**~~ **§48에서 붙었다.**
- **프로덕션에서 봤다**(2026-08-12). `wss://show-gi.com/ws/game` 의 첫 스냅샷이 `opponentStrength: 3` 이고 깨끗한 4수 뒤 **4**로 움직였다.

## 48. 판을 열기 전에 고른다 — 선후공과 상대의 진형 (2026-08-12)

시작 화면이 생겼다. **고르기 전에는 서버에 붙지 않는다** — 붙는 순간 판이 하나 열려 기록에 남고, 아무것도 고르지 않은 채로 先手 평수 대국이 시작된다.

### 서버는 거의 다 돼 있었다

| 이미 있던 것                     | 어디                             |
| -------------------------------- | -------------------------------- |
| `HumanColor` 가 세션에 꿰여 있다 | `game.Config` 외 12곳            |
| `games.my_color` 가 `'b'/'w'`    | `001_init.sql`                   |
| 복기·분기가 後手를 처리한다      | `whatif.rootOf` · `ReviewDetail` |

빠진 것은 셋이었다 — **연결마다 고르는 길**(프로세스 `Options` 였다), **스냅샷이 사람의 색을 안 실었다**, **북이 없었다**.

### 무엇을 정했나

- **설정은 WS URL 쿼리로 받는다**(`?color=&opening=`). `start` 메시지로 하면 세션이 첫 명령까지 기다려야 하고 「연결 하나 = 대국 하나」와 수명이 갈린다. 쿼리는 업그레이드 전에 읽히므로 그 규약을 안 건드린다.
- **오프닝은 랜덤이 아니라 사람이 고른다.** 원안(§6의 무작위)을 바꿨다 — 무엇을 상대하는지 모르면 그 형을 익히는 것이 아니라 매번 새 문제를 푸는 것이 된다.
- **정석 파일을 고르지 않는다.** 4종(四間飛車·中飛車·矢倉·棒銀)을 직접 적고 항목마다 위키백과 URL을 박았다. 이것이 §8의 「RAG 코퍼스 출처」 나머지 절반을 닫는다.
- **後手 수순은 돌려서 만든다.** 두 벌 적으면 한쪽만 고치는 버그가 나고 그 버그는 에러를 안 낸다 — §30의 「後手를 두 벌 적지 않는다」와 같은 자리다. 180° 회전이 정확히 先手/後手 대응이다.
- **북은 후보 생성이 아니라 선택만 한다.** 두 안전 필터도 k도 안 건드리고, 감싸기만 하므로 밴드 제어와 실력 추정이 그대로 돈다. `AdaptsToSkill` 을 안쪽에 물어보는 것이 중요하다 — 여기서 false를 답하면 진형을 고른 판에서 **강함 눈금이 조용히 사라진다**(§47).
- **북은 상태를 안 들고 있다.** 몇 수까지 뒀는지를 매번 `(startSFEN, moves)` 에서 다시 구한다. 개입이 수를 되무르는 이상 카운터를 들고 있으면 롤백된 수를 센 채로 남고, 그 어긋남은 「상대가 진형을 건너뛴다」로만 드러난다.
- **손을 놓는 조건 넷**: 駒를 한 번이라도 잡았다 · 王手를 받고 있다 · 그 수가 반칙이다 · 수순을 다 뒀다. 전부 룰 엔진과 좌표뿐이라 **엔진을 안 부른다.** 「한 번이라도 잡았다」로 세는 것이 되돌리기와 맞는 자리다 — 물러진 수는 `moves` 에서 사라지므로 그 잡기도 같이 없던 일이 된다.
- **판은 CSS로 돌리지 않는다.** 칸의 **자리 번호만** 뒤집는다(`80 - i`). `transform` 을 쓰면 打 화살표의 출발점을 재는 쪽이 어긋난다 — 그 값은 변형 **전**의 배치 좌표를 재고 있고(§35에서 판 기울기를 뺀 그 자리다), 판에서 유일하게 산수로 안 나오는 좌표다.
- **좌표 라벨에는 안 걸린다.** `7六` 은 판의 절대 좌표라 누가 어느 쪽에 앉아도 같다. 뒤집히는 것은 **줄의 순서**뿐이다.

### 뒤집으면서 드러난 버그 하나

`useBoardSurface` 의 그늘(`相手の利き`)이 **`black` 으로 박혀 있었다.** 後手로 두면 그 자리가 조용히 **상대가 받는 자리**를 그려서, 판이 정반대를 같은 그림으로 말한다. 사람의 색을 받아 고쳤고, 셰이더에 넘기는 배열도 같이 뒤집어야 그늘이 제 칸에 앉는다.

같은 가정이 대국 화면 네 자리에 흩어져 있었다 — 駒台 둘 · 힌트의 打 · 회상의 打.

### 실측 — 로컬, 뒤집힌 판(사람 後手 · 四間飛車)

| 手数 | 무엇                                    |
| ---- | --------------------------------------- |
| 1    | `▲7六歩` — 북의 첫 수                   |
| 2    | `△3四歩` — 사람                         |
| 3    | `▲6八飛` — 북의 두 번째 수. 四間에 振る |

`相手の強さ ●●●○○ ふつう` 가 그대로 떴고(눈금이 안 사라졌다), 그늘을 켜면 **7五**가 어두워졌다 — 배열을 안 뒤집었다면 3五에 떴을 자리다. 콘솔 오류 0.

先手 · 棒銀으로 한 번 더: `▲7六歩`(사람) → `△8四歩`. 미러 수순이 맞았다.

### 우리 개입이 우리 북의 버그를 잡았다

**矢倉으로 두는 중에 개입이 걸렸다.** 평범한 `△8四歩`에 Δ승률 **−51%**였고 처음에는 오진으로 보였다. 아니었다.

```
1 ▲7六歩   7七이 비어 2二의 角이 8八까지 닿는다
2 △3四歩   사람이 자기 角길을 연다
3 ▲6八銀   ← 8八을 받치던 銀이 7九를 떠난다. 角이 공짜다
4 △8四歩   그 角을 안 잡았다 → 개입
```

수순의 **모든 수가 합법인데 순서가 材料를 넘긴다.** 룰 엔진은 「합법이다」까지만 답하므로 `TestOpeningMovesAreLegal` 은 이것을 통과시킨다.

- **고친 것**: `▲6六歩`을 두 번째로 올려 **銀이 7九를 비우기 전에 대각선을 닫는다.** 四間飛車도 같은 창이 있었다 — `▲7八銀` 이 `▲6六歩` 보다 먼저였다.
- **막은 것**: `TestOpeningNeverHangsAPiece` — 사람이 **자기 角길을 먼저 여는** 선을 두고, 북의 매 수 뒤에 「상대가 노리는데 아무도 받치지 않는 駒」가 있으면 실패한다. 歩와 玉은 뺀다(마주 본 歩는 초반의 정상 상태이고, 王手는 합법성 검사가 이미 막는다). 옛 순서로 되돌려 **실제로 실패하는 것을 확인했다** — `8h의 駒(type 6)가 공짜다`.
- **런타임 가드로는 안 잡힌다.** `MoveFeatures.HangsPiece` 는 **움직인 駒**가 잡히는지를 보고, 이 버그는 **다른 駒의 받침을 거두는** 것이다. 그쪽을 넓히면 adaptive.go 의 후보 필터까지 성질이 바뀌므로 건드리지 않았다.

> **이 자리가 제품의 논거이기도 하다.** 판단이 엔진에 있으니, 사람이 손으로 적은 정석이 틀렸을 때 **그 틀림을 제품이 그 자리에서 말한다.** 북이 판단에 끼어드는 구조였다면 「정석이니까 맞다」로 조용히 지나갔을 것이다.

### 「もう一局」이 시작 화면으로 안 갔다

투료 뒤 `もう一局` 을 누르면 시작 화면이 아니라 **「接続が切れました」**가 떴다. 정리에서 부른 `socket.close()` 의 `close` 이벤트가 늦게 도착해 방금 정한 상태를 덮은 것이다 — **우리가 일부러 닫은 것을 사고로 보고하고 있었다.**

이 경합은 원래도 있었고 **새 연결이 곧바로 `open` 으로 덮어서 안 보였다.** 「고르기 전에는 안 붙는다」가 그 가림막을 걷어냈다. 효과마다 `current` 플래그를 두고 정리에서 내린다.

### 실력 추정이 판 사이로 이어진다

§47이 남긴 「`skill_profile` 이 비어 있다」를 닫았다. 정한 것만 적는다.

- **`rating_est` 를 안 쓴다.** §47이 레이팅 점수를 만들지 않기로 정했고(낙폭은 임계치에 대한 비율이라야 뜻이 하나다) 그 칸에 비율을 넣으면 이름이 거짓말을 한다. `006` 이 칸 둘을 더한다.
- **`NULL` 이 「모른다」다.** `0` 은 「매 수 최선」이라 뜻이 정반대이고, 기본값을 0으로 두면 **처음 로그인한 사람이 가장 센 상대를 만난다.**
- **판정 한 건마다 저장한다.** 대국이 끝날 때 한 번이 아니다 — 새로고침하면 판이 끝나므로(§46) 몰아 쓰면 끊긴 판의 추정이 통째로 사라진다.
- **이어 시작한 판은 첫 수 전에 한 번 올려보낸다.** 안 올리면 지난 값이 있는데도 첫 판정까지 상대가 기준선으로 둔다.
- **저장된 값을 자른다.** DB는 밖이라 1을 넘는 낙폭 하나가 밴드를 임의로 밀 수 있다.
- **콜백이 추정기 goroutine에서 돈다.** 「상태는 goroutine 하나가 소유한다」(§21 ①)와 어긋나지 않는 이유는 **대국 상태를 안 건드리기** 때문이다 — `dbRecorder` 가 자기 goroutine에서 기록을 쓰는 것과 같은 종류다.

### 남은 것

- **북이 `edges.tags` 를 안 채운다.** 상대가 둘 수순일 뿐이라 「정석 이탈」 카테고리는 그대로 비어 있다(§1의 카테고리 표).
- **복기 화면은 뒤집지 않는다.** 기보를 되짚는 자리라 先手가 아래인 것이 관례이고 駒台 라벨이 누구인지 이미 말한다. 그늘의 기준만 사람 쪽으로 고쳤다.
- **진형 4종의 「이 형이 맞나」는 여전히 실측 전이다.** 합법성은 룰 엔진이 보고 材料를 넘기지 않는 것은 위 테스트가 보는데, **형태가 정석인지는 사람이 봐야 한다.** 矢倉과 四間飛車는 그 확인이 한 번 물렸다(위). **[미확정]**
- **마이그레이션 `006` 은 들어갔다**(2026-08-14, §3). 「그 전까지 로그인한 사람의 추정 저장만 조용히 실패한다」던 구간이 끝났다. **프로덕션에서 눈으로 본 것은 아직 아니다** — 그건 사람이 다음 판을 둘 때다.

## 49. 대국 후 총평 — LLM이 사람을 요약하는 첫 자리 (2026-08-12)

판이 끝나면 그 자리에 한 문장이 뜬다. 로드맵 5번이고, **개입 문구와 다른 것은 재료뿐**이다.

### 무엇을 정했나

- **`explain` 안에 둔다.** 새 패키지로 빼면 캐시·검증(`Clean`)·결정적 폴백·라우터 호출 넷이 두 벌이 된다. `Summarize` 는 `Explain` 과 같은 순서로 내려가고 프롬프트와 길이 상한만 다르다.
- **세는 것은 기록이고 LLM은 문장만 쓴다.** 카테고리 분포·구간·전후반 추세를 `internal/server` 가 `GameRecord` 에서 결정적으로 뽑는다.
- **프롬프트에 숫자를 안 준다.** 手数와 횟수는 화면의 표가 그리고, 문장에는 **등급**(`一度だけ`·`数回`·`何度も`)만 준다. 같은 수를 두 곳에 두면 어긋났을 때 어느 쪽이 맞는지 알 수 없다 — `Facts` 가 Δ승률을 안 싣는 것과 같은 이유다.
- **기록이 다 쓰이기를 기다린 뒤 만든다.** 기록이 비동기라(`dbRecorder`) 끝난 스냅샷을 보고 곧바로 DB를 읽으면 **마지막 수와 그 수의 개입이 없다** — 하필 총평이 가장 말하고 싶은 수다. 기록자가 `FinishGame` 을 쓴 뒤 대국 id를 채널로 한 번 보낸다.
- **스냅샷을 먼저 보내고 총평을 뒤에 보낸다.** 결과 문구는 그 자리에서 떠야 하고 총평은 LLM을 기다린다. 화면은 그동안 「まとめています…」로 **자리를 잡아 둔다** — 자리가 없으면 문장이 도착할 때 아래 버튼이 밀려 내려간다.
- **문장은 「무엇을 연습하라」까지 말한다.** 개입 문구에는 없던 자리인데, 판이 이미 끝나서 답을 알려주는 것이 아니다.

### 실측 — 두 번 틀렸고 둘 다 화면에서 잡혔다

**① 3手째 개입이 「終盤で」로 나갔다.**

판을 手数로 삼등분했더니, 2手 확정 + 3手째 개입 하나인 판에서 그 개입이 마지막 삼분의 일에 떨어졌다. 화면이 그대로 **「終盤で駒をそのまま取られてしまった」**라고 말했다.

**判定을 手数의 절대값으로 바꿨다** — 序盤 ≤ 30手 · 中盤 31–80 · 終盤 81+. 20手에 끝난 판에는 종반이 없는 것이 맞고, 그때는 아무 구간도 말하지 않는 것이 맞다. **[미확정]** 두 경계는 초기값이고 109手 한 판(08-playtest.md)에서 눈으로 잡았다.

> 물러진 수는 기보에 없어서(`game.Recorder`) 개입의 手数가 마지막 확정 수보다 클 수 있다. 그 값을 안 보면 판이 실제보다 짧게 세어진다 — 같은 자리에서 같이 고쳤다.

**② 개입 1건을 「場面が多かった」로 불렀다.**

사실에 양이 없어서 모델이 과장했다. **등급을 넣었다**(위) — 정확한 횟수가 아니라 등급인 것이 요점이고, 등급이 횟수에서 나오므로 표와 어긋날 수 없다.

고친 뒤의 실측(로컬, `▲3三角成` 로 角을 던진 판):

```
序盤で、うっかり駒をそのまま取られてしまったのがもったいなかったですね。
次は置いた駒が取られないか、もう一度よく見てから指してみましょう。

あなたの手数 1 · 戻した回数 1 · タダ捨て 1
```

### 남은 것

- ~~**되짚기 화면에 안 붙였다.**~~ **§52에서 붙었다** — 라우트 하나와 카드 재사용이었다.
- **Tier 0이 자주 안 맞는다.** 키가 결과 × 카테고리 × 등급 × 구간 × 추세 × 레벨로 갈려 수백 가지다. 판마다 한 번이라 비용이 개입 문구와 비교가 안 되게 작아서 그대로 뒀다.
- **`skill_profile` 을 안 본다.** 총평이 이 판만 말한다 — 「지난 판보다 나아졌나」는 판을 가로지르는 이야기이고, 그 값은 §48에서 쌓기 시작했으므로 표본이 아직 없다.
- **구간 경계와 등급 경계, `trendMinSamples` 가 전부 초기값이다.** §47의 상수 다섯과 같은 벽이다 — 사람이 둔 판이 필요하다.

## 50. 셸을 밝은 쪽으로 뒤집었다 — 어두운 것은 판이 있는 방이다 (2026-08-13)

「강조는 색이 아니라 빛으로」는 **판 위의** 규칙이고([03-frontend.md §1](../03-frontend.md)), 그 빛이 실제로 사는 순간은 개입이 걸려 `.veil` 이 화면을 덮고 판만 남는 그때다. **그 둘은 그대로 두고 판 밖만 밝게 바꿨다.**

값이 있는 쪽은 대비다. 어두운 셸에서 조금 더 어두워지던 것이, 이제 **크림에서 검정으로 떨어진다** — 개입 연출은 한 줄도 안 고치고 세졌다.

### 무엇이 얼마나 있었나

| 무엇                                        |                                                                                    |
| ------------------------------------------- | ---------------------------------------------------------------------------------- |
| 크롬의 `rgb(빛 / 0.0x)` 반투명 흰 테두리·면 | 60군데. 「1px 반투명 흰 테두리 + hover에 알파 올리기」가 화면 전체의 층 문법이었다 |
| `box-shadow`                                | 2,501줄에 **13개**. 고도차가 없어 카드 스무 개가 전부 같은 무게였다                |
| 어두운 배경 전용으로 하드코딩된 색          | 3군데(`#cfc7ba` — 상대가 둔 수). 흰 면에서 거의 안 보였다                          |
| 평가치 그래프의 격자·축                     | `rgb(255 255 255 / 0.06)`·`0.18`. 흰 면에서 **아예 안 보였다**                     |

### 무엇을 정했나

- **판 토큰은 한 글자도 안 건드렸다.** `--board`·`--koma-*`·`--grid`·`--ray`·`--ray-check`·`--hint`·`--mate`·`--light`. three.js 판 표면이 `--board`·`--grid` 를 CSS에서 읽어 가므로(`libs/three/surface.ts`) 이 선을 지키는 것이 WebGL 쪽까지 같이 지킨다
- **브랜드색은 深緑다.** 판이 쓰는 넷과 부딪히지 않는 근거가 둘이다 — 표면이 다르고(판 안이 아니다, 詰み 불꽃이 테두리에서 색을 쓰는 것과 같은 근거), **개입이 걸리면 셸이 장막 아래로 들어가** 브랜드색과 판의 광선이 같은 세기로 같이 보이는 순간이 없다
- **어두운 자리는 자기 팔레트를 들고 있는다.** 개입 카드가 토큰을 통째로 덮어쓴다. **`color` 를 거기서 다시 선언해야 한다** — 토큰만 바꾸면 글자가 안 바뀐다(`color: var(--fg)` 를 선언한 곳이 `:root` 라서 계산이 거기서 끝나 있고, 내려오는 것은 이미 먹색이 된 값이다). 실제로 카드의 棋譜 표기와 설명문이 검정 위 검정이었다
- **駒台는 나무다.** 흰 카드에 두면 크림색 駒가 사라진다. 판보다 **어둡게** 둬서 판이 가운데 하나로 읽히게 했다 — 같은 밝기면 나무 슬래브가 셋이 된다
- **개입 중에는 駒台도 판과 같이 색을 잃는다.** 안 하면 어두워진 화면에서 나무 받침 둘이 가장 밝은 것이 되어 「판만 남는다」가 「駒台만 남는다」로 읽힌다. 어두운 셸에서는 駒台가 회색 면이라 없던 문제다. 판과 같은 수법(`backdrop-filter`)이라 打의 출발 駒는 그 위에 남는다
- **판 칸을 56px에서 62px로 키웠다.** 셸이 밝아지면서 판이 화면에서 가장 밝은 것이 아니게 됐고, 그 자리를 되찾는 것은 색이 아니라 크기다
- **탭의 「고른 쪽」을 빛에서 색으로 바꿨다.** 흰 바탕의 흰빛은 신호가 아니다

### 개입 장면을 확인한 줄

디자인이 성립하는지는 개입이 걸린 화면을 봐야 알 수 있어서, 3手에 걸리는 줄을 하나 써서 확인했다. **[로드맵 §3](../05-roadmap.md)의 「데모 영상 시나리오」가 이 줄이다.**

상대 진형 **矢倉**에 先手로 붙어 `▲7六歩` → (상대 `△3四歩`) → `▲3三角成`. `hangs_piece` 로 걸리고 「馬がそのまま取られてしまいます」가 뜨며 반박은 `△同角`(勝率 −53%)다. **로컬에서 재현했고 프로덕션은 아직 이 회차에서 안 걸어 봤다.**

### 남은 것

- **다크모드를 안 만들었다.** `color-scheme: light` 하나이고 `prefers-color-scheme` 을 안 본다. 두 벌을 유지하는 비용이 마감까지의 남은 시간보다 크다
- **`.review-iv`·`.review-iv[data-active]` 는 죽은 CSS다**(§41에서 개입 목록이 `この局面で指せた手` 안으로 들어갔다). 이 회차에서 토큰만 바꿨고 안 지웠다

## 51. 결과가 나온 판만 보이고, 중단된 판은 이어서 둔다 (2026-08-13)

§46이 남겨 둔 「이어하기 — 붙인다면 기록에서 다시 세운다」를 닫았다. 그리고 **같이 닫아야 하는 것이 하나 더 있었다** — 이어할 판을 감추는 일과 되짚기에서 감추는 일이 같은 판을 두고 서로 반대 방향을 본다.

| 무엇                                               |                                                                                             |
| -------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| `ListGamesForOwner` · `GetGameForOwner`            | **결과가 나온 판만**(`win`·`loss`·`draw`). 목록·상세·가정 수순 셋이 이 둘로 걸린다          |
| `ResumableGameForOwner`                            | 그 반대 — 중단된 판 하나. **전용 경로다**(`GET /api/resumable`)                             |
| `ClaimGameForResume`                               | 점유와 되열기가 한 문장. `result` 를 조건에 둬서 두 번째 요청이 0행이다                     |
| `DeclineResume`                                    | 「いいえ」. `result = 'declined'`                                                           |
| `game.Config.StartMoves`                           | 기보를 그대로 다시 둬서 끊긴 자리로 판을 되돌린다. **세션 수명은 안 건드렸다**              |
| `internal/server/{resume.go,ws.go}`                | 물음은 HTTP, 이어 두는 것은 `/ws/game?resume=<id>` — 설정을 쿼리로 받는 §48의 문법 그대로다 |
| `apps/web/{protocol,hooks}/resume*` · `Resume.tsx` | 시작 화면 **앞에** 뜨는 물음 카드                                                           |

### 실측 — 목록에서 무엇이 사라졌나

로컬 익명 판(한 수 이상 둔 것) **11줄 중 5줄이 빠졌다.**

```
loss        6     남는다
abandoned   4     중단 — 이어하기가 가져갈 몫이다
(두는 중)   1     result NULL
```

`abandoned` 4줄이 **전부 「연결만 열렸다 끊긴 판」이 아니다** — 2줄은 실제로 두다 끊긴 판이다. 그것들이 되짚기 목록 위쪽을 차지하고 있었고, 눌러도 보여 줄 것이 반쪽이었다.

### 무엇을 정했나

- **이어하는 판은 같은 행에 쌓는다.** §46이 남긴 「정할 것 셋」의 답이 하나다 — 새 id로 이어 붙이면 한 대국의 기보와 개입이 두 행으로 갈리고, 「그 국면이 그 사람에게 얼마나 어려웠나」(§17)가 흩어진다. `interventions` 도 저절로 따라온다
- **`declined` 를 `result` 의 새 값으로 넣었다. 마이그레이션이 없다.** 칸에 CHECK 가 없어서 어휘를 늘리는 데 DDL이 필요 없고, DB를 공유하는 이상 되돌릴 수 없는 마이그레이션을 안 만드는 쪽이 싸다. 대신 **어휘 목록은 `store.GameResult` 하나다** — `001_init.sql` 의 칸 주석은 이 값을 모른다(적용된 마이그레이션은 안 고친다)
- **진형은 `opening_tag` 에 적는다.** `001` 부터 있고 아무도 안 쓰던 칸이다. 북이 상태를 안 들고 매번 (start_sfen, moves)에서 다시 구하므로(`game.bookOpponent`) **id 하나면 끊긴 자리 그대로 이어진다** — 이 칸이 없었으면 이어한 판만 상대가 진형을 잊는다
- **점유가 곧 되열기다.** `UPDATE … WHERE result = 'abandoned'` 한 문장이라 탭 두 개가 같은 판을 이어하려 들면 뒤엣것이 0행을 받는다. 잠금을 따로 만들지 않은 이유가 이것이다 — 세션 goroutine 둘이 한 대국 행에 겹쳐 쓰는 것을 막는 자리가 **DB의 한 줄**이면 된다
- **되열어 놓고 세션이 못 서면 기록 쪽이 다시 닫는다.** `dbRecorder` 가 시작부터 그 id를 알게 해서(`recordTarget.resumeID`) ctx 취소 경로가 `abandoned` 로 되돌린다. 안 하면 그 판은 `result` 가 NULL인 채로 남아 **되짚기에도 이어하기에도 안 걸리는 유령**이 된다
- **한 수라도 안 맞으면 이어하지 않는다.** 기록은 큐가 넘치면 이벤트를 버리므로(`recorder.go`) 手数에 구멍이 날 수 있는데, 눈감고 이어 두면 한 칸 밀린 **없던 판**이 「그때 두던 판」의 얼굴로 선다 — 되짚기가 같은 자리에서 재현을 멈추는 것(§33)과 같은 판단이다
- **목록 질의를 나눠 쓰지 않는다.** 이어할 후보는 「내 것이고 `abandoned` 인 최신 판」인데 위쪽 규칙이 바로 그것을 감춘다. 한 질의에 조건을 얹어 겸하게 두면 두 목표가 서로를 지운다
- **로그인한 사람만이다.** 셋 다 주인을 `=` 로 받아 익명 판(`user_id` NULL)이 애초에 안 걸린다 — 익명끼리는 구별할 수단이 없어(`002`) 「누구의 중단된 판인가」에 답할 수가 없다
- **404다, 403이 아니다.** 없는 판·남의 판·이미 누가 점유한 판이 같은 답을 받는다(§46의 규칙이 그대로 걸린다)
- **물러진 수는 안 온다.** 기보에 애초에 없다([01-core.md §5](../01-core.md)). 그것이 맞다 — 롤백된 수다

### 남은 것

- **`/ws/game?resume=` 이 실패하면 화면이 「接続が切れました」로 간다.** 404가 업그레이드 전에 나가는데 브라우저는 그것을 연결 실패로만 알려준다. 실제로 도달하는 길은 「물음 카드를 띄워 둔 채 다른 탭이 그 판을 가져갔다」 하나뿐이라 이번에는 두지 않았다
- **총평은 이어한 판에도 한 번만 뜬다.** 판이 끝나는 자리에서 만들므로(§49) 이어한 뒤 끝내면 그때 나온다 — 끊기기 전 구간까지 포함한 기록 전체를 읽는다

## 52. 총평을 되짚기에도 붙였다 — 붙이자 문장 하나가 재지 않은 것을 말하고 있었다 (2026-08-13)

§49가 남긴 하나다. 라우트 하나와 카드 재사용인데, 붙이면서 총평이 **평가치 그래프 옆에** 서게 되자 어긋남이 한눈에 보였다.

### 무엇을 정했나

- **`GET /api/games/{id}/summary` 로 기보와 따로 준다.** 총평만 LLM을 기다리므로 `GET /api/games/{id}` 에 실으면 판이 그때까지 안 그려진다 — WS가 스냅샷을 먼저 보내고 총평을 뒤에 보내는 것(§49)과 같은 이유다.
- **id 파싱과 기록 읽기를 `detail` 과 한 함수로 묶었다**(`reviewHandler.record`). 주인 거르기(§46)와 「결과가 나온 판만」(§51)이 `GameRecord` 에 들어 있으므로, 갈라 두면 새 표면 하나가 그 둘을 안 지나는 길이 된다.
- **payload도 카드도 대국 화면의 것 그대로다.** `summarize` 가 이미 `GameRecord` 만 받고(§49) 화면은 `Summary` 가 `{ summary: GameSummary | null }` 하나만 받는다 — 같은 판이 두 화면에서 다른 문장을 말할 자리가 없다.
- **못 읽으면 카드를 아예 안 그린다.** `null` 은 「まとめています…」라, 실패에 그것을 넘기면 기다리면 온다는 거짓말이 된다. 이 화면의 본론은 기보이고 그쪽은 이미 왔다.
- **「大きな形勢損はなかった」를 지웠다.** 아래.

### 실측 — 개입 0건인 판에서 문장과 그래프가 어긋났다

| 판   | 사람의 手数 | 개입 | 평가치 궤적      | 고치기 전                        | 고친 뒤                            |
| ---- | ----------- | ---- | ---------------- | -------------------------------- | ---------------------------------- |
| #1   | 54          | 0    | 55% → 0% (108手) | 大きな形勢の損はありませんでした | 大きなミスなく最後まで指せましたね |
| #121 | 2           | 0    | —                | (같은 문장)                      | (같은 문장)                        |
| #122 | 0           | 0    | —                | (같은 문장)                      | (같은 문장)                        |

`summaryUserPrompt` 가 `len(Top) == 0` 일 때 **「大きな形勢損はなかった」를 사실로 적어 주고 있었다.** 잰 것은 「판정에 걸린 수가 하나도 없다」뿐이고 형세는 애초에 사실에 없다 — #1은 그동안 55%에서 0%까지 밀렸다.

**프롬프트와 결정적 문구를 둘 다 「手を戻す場面はなかった」로 바꾸고 `summaryPromptVersion` 을 2→3으로 올렸다.** 그 값이 캐시 키에 들어가므로(`GameFacts.Key`) 옛 문장이 그 자리에서 죽는다. 화면의 표가 `戻した回数 0` 을 그리고 있으므로 문장과 표가 같은 것을 말하게 됐다.

**대국 화면에서는 이것이 안 보였다.** 거기에는 평가치 그래프가 없다 — 같은 문장이 §49부터 그 자리에 있었다.

### 남은 것

- **한 수도 안 둔 판에도 총평이 나온다.** `factsOf` 가 「센 것이 없다」와 「깨끗한 판」을 안 가르고, 사실에 手数가 아예 없다(§49의 「프롬프트에 숫자를 안 준다」). #122가 그 판이다 — 이제 형세는 말하지 않지만 「最後まで指せましたね」까지는 간다. 手数를 등급으로 넣으면 사실 하나와 키 하나가 늘어난다.
- **모양이 같은 두 판은 문장이 글자 그대로 같다.** 키가 game id가 아니라 판의 모양이고(§49) **캐시를 꺼도 같다** — 같은 사실이 같은 프롬프트이고 `temperature=0` 이다. 목록에서 여러 판을 연달아 여는 화면이 지금까지 없어서 여기서 처음 눈에 띈다.

## 53. 되짚기 퀴즈 — 문제도 정답도 그 판에서 나온다 (2026-08-13)

로드맵이 「詰将棋 문제은행」을 이번 범위에서 잘라낸 이유와 `../shogi/src/data`(手筋 208문)를 금지한 이유는 같은 것이었다 — 출처와 저작권. **자기 기보에서 만들면 그 문제가 아예 없다.** 그리고 「내가 놓친 詰み」이라는 말이 성립한다.

**새로운 발상은 아니다.** lishogi 가 실전에서 「다음 한 수」를 자동 추출하고 棋神ラーニング 은 유료로 그것을 판다([00-product.md §4](../00-product.md)). 갈리는 것은 **개입 루프와 같은 판을 쓴다**는 것뿐이다 — 낙폭·평가치·詰み 거리가 이미 그 판에 다 있다.

문항은 둘이다. **詰み 하나**(사람 차례 국면을 手数 순으로 훑어 처음으로 7手 이하가 나온 자리)와 **「この局面の最善手は?」 최대 셋**(1위−2위 차가 큰 국면). 없으면 0문이고, 그것은 흔한 결과다.

### 실전 국면은 詰将棋 작품이 아니다 — 그것이 채점 규약을 정했다

작품의 규칙 셋이 실전에서 깨진다.

|             |                                                                                                 |
| ----------- | ----------------------------------------------------------------------------------------------- |
| 玉方の持駒  | 작품은 「나머지 전부」, 실전은 실제 持駒다 → **화면에서 「詰将棋」라고 부르지 않는다**          |
| 정답 유일성 | 같은 手数의 詰み筋이 여럿이다(余詰). **1手詰め 시험 국면에서 실제로 `G*5b`·`4c5b` 둘이 나왔다** |
| 無駄合い    | 玉方이 持駒를 들면 사람 눈의 3手가 合駒로 늘어난다. solver 는 그것도 手数로 센다                |

**그래서 「엔진이 준 수순과 다르면 오답」으로 채점할 수 없다** — 맞은 사람에게 틀렸다고 말하게 된다. 대신 **입력을 王手인 수로 닫았다**: 화면이 王手만 빛내고(`legalMoves` 가 王手만 담는다) 서버가 그 밖을 거절한다. 그러면 사람이 낼 수 있는 입력이 유한해서 미리 셀 수 있고, 玉方의 응수는 우리가 고르므로 **트리가 모든 경우를 덮는다 — 채점에 엔진이 아예 필요 없다.**

### 무엇을 정했나

- **판정은 등호다.** 뿌리가 `N`手면 정답의 조건은 「그 수와 玉方의 최장 방어 뒤에 `N-2`手가 남는다」다. `N-4` 이하는 **불가능하다** — 그러면 뿌리에서 `1+1+(N-4)`手 詰み이 성립해 뿌리가 최소라는 전제와 모순이다. 그래서 그 자리에 로그를 남겨 뒀다: 일어나면 버그이고, **그 수는 더 빠른 詰み이라 정답으로 둔다**(맞은 것을 틀렸다고 말하지 않는다).
- **`go mate` 는 「수번 측이 詰ます」만 답한다.** 그래서 사람 수 뒤(상대 차례)에 그대로 물으면 방향이 뒤집힌다 — 응수마다 한 번씩 물어 최댓값을 잡는다. 부호 뒤집기와 같은 종류의 함정이다.
- **최장 방어가 동률이면 USI 순서로 정한다.** 매번 다르게 응수하면 같은 문제가 열 때마다 다르게 흘러가고, 사람은 그것을 고장으로 읽는다. 手数가 같으니 문제의 성질은 안 변한다.
- **「모른다」를 「없다」로 쓰지 않는다.** `MateResult.Proven` 이 거짓이면 그 국면을 건너뛰고, 트리를 못 완성하면 **문항을 버린다.** 잘린 트리로 채점하면 정답이 오답이 된다.
- **王手가 아닌 수는 오답이 아니라 안내다**(「王手を続けてください」). 초심자의 첫 본능이 그것이고, 규약을 모른 채 오답 처리되는 것이 배움을 막는다. 판정이 `InCheck` 하나라 엔진 0회·즉시다.
- **오답 문구를 하나로 뭉치지 않는다.** 「この手では詰みません」은 詰み이 9手로 늘어질 뿐인 수에는 **거짓**이고, 초심자는 그것이 거짓인지 확인할 수단이 없다. 남는 手数를 이미 구했으므로 「詰みが○手に伸びます」와 「詰みを逃します」로 갈랐다.
- **gap 문항은 두 기준을 겹친다.** 낙폭으로 후보를 좁히고(기록만 보므로 엔진 0회) 그 후보에만 MultiPV를 건다. **낙폭은 「사람이 여기서 틀렸다」이고 gap은 「정답이 하나뿐이다」다** — 낙폭만 쓰면 정답이 여럿인 국면이 문항이 되어 좋은 수를 둔 사람이 「不正解」를 받고, gap만 쓰면 사람이 이미 맞게 둔 국면이 뽑힌다.
- **만드는 것은 판이 끝나는 자리에서 한 번이고 되짚기는 읽기만 한다.** 되짚기에서 만들면 그 탐색이 **진행 중인 다른 대국의** 착수를 기다리게 한다. 연결이 끊겨도 계속하도록 `context.WithoutCancel` 이다 — 사람은 판이 끝나면 곧 화면을 떠나고, 여기서 못 만들면 아무 데서도 못 만든다.
- **詰み 문항은 정석 구간도 훑는다.** `OpeningPlies` 는 「최선수는?」 문항의 것이고(둘 만한 수가 여럿인 자리를 안 내려는 값이다) 詰み에는 그 이유가 없다 — 棒銀·早石田의 함정으로 20手 안에 끝나는 판이 **이 기능이 겨냥하는 초심자 그 자체**다.
- **「최선수는?」은 詰み 문항의 국면 하나만 뺀다.** 한때 그 手数부터 뒤를 통째로 잘랐는데, 詰み 문항이 판에서 **가장 이른** 것이라 120手 판의 25手째에서 놓친 3手詰め 하나가 中盤과 終盤을 전부 지웠다 — 진짜 블런더가 있는 구간이 그쪽이다. 자르려던 이유는 국면마다 `IsMate` 가 이미 거른다.
- **「王手가 아니다」에는 정답을 안 준다.** 그쪽은 시도가 소진되지 않는 안내라, 답을 실어 보내면 아무 조용한 수나 한 번 눌러서 답을 꺼낼 수 있다 — 채점을 서버에 둔 이유가 사라진다.
- **정답의 표기는 그 수가 성립하는 국면에서 만든다.** 오답이면 판이 그 수만큼 나아가 있어서, 나아간 국면에서 만들려 하면 정답이 불법이라 표기가 빈다. **§61 뒤로 이 자리가 만드는 것은 정답이 아니라 세 번째 오답의 「무엇을 움직이나」다** — 비면 그 한 마디까지 사라진다. 打이 정답일 때는 더 나쁘다: 상대가 그 駒를 들고 있으면 합법으로 통과해 **상대 기호(`△`)로 렌더된다.**
- **「決めた」는 手数가 정확히 맞을 때만이다.** 이긴 것도 마지막이 詰み인 것도 모자란다 — 상대가 잘못 받아 빨리 끝나면 사람이 둔 것은 **이 문항의 수순이 아니다.** 길 수는 없다(solver 가 無駄合い까지 센다), 그래서 좁아지는 방향이 「놓쳤다」쪽이고 그쪽은 참이다. 아래는 그 앞에 있던 판단이다.
- **엔진의 승리만으로 정하지 않는다.** 엔진은 投了하기도 하고 못 두는 수를 내놓기도 하는데 둘 다 사람의 승리로 닫힌다(`applyEngineMove`). 手数만 보면 「あなたが決めた詰みです」가 **두어진 적 없는 詰み**을 두고 나간다 — 그래서 마지막 국면이 실제로 詰み인지를 함께 본다.
- **문항이 없어도 행을 남긴다.** 안 하면 「아직 만드는 중」과 「문항이 없는 판」이 화면에서 같은 그림이 되고, 만드는 데 수십 초가 걸려서 그 사이의 「問題はありません」이 거짓이 된다. `ready` 가 그 둘을 가른다.
- **아무것도 못 본 생성만, 그리고 비었을 때만 안 적는다.** 「못 봤다」가 참이어도 **나온 것은 사실이다** — 다 지어진 詰み 트리는 gap 후보 하나를 못 쟀다고 틀려지지 않는다. 그리고 **한 자리를 못 본 것은 「아무것도 못 봤다」가 아니다** — 중반의 무관한 국면에서 df-pn solver 가 timeout 하는 것은 흔하고, 그것으로 행을 안 남기면 그 판은 5분을 기다린 뒤 「안 왔다」에 서는데 사실은 「못 만들었다」다. 그래서 기준은 **엔진이 한 번이라도 답했는가** 하나다. 「못 봤다」가 참이어도 **나온 것은 사실이다** — 다 지어진 詰み 트리는 gap 후보 하나를 못 쟀다고 틀려지지 않는다. 둘을 한 깃발로 묶어 통째로 버리면 한쪽의 사소한 실패가 멀쩡한 다른 쪽을 지운다. 버리는 것은 **빈 결과**뿐이고, 그때만 「문항이 없다」와 「못 봤다」가 같은 그림이 된다. 그때 나온 것은 「이 판에 문항이 없다」가 아니라 **「끝까지 못 봤다」**인데, 빈 행을 남기면 화면이 그것을 「問題が作れませんでした」로 단정한다 — **詰み이 있었는데 없다고 말하는 자리**이고, 생성이 판이 끝날 때 한 번뿐이라 그 거짓이 영구히 남는다. **시한만 보면 모자란다** — 배포가 생성 도중에 끼면 엔진 풀이 DB보다 먼저 닫혀(`main` 의 defer 순서) 모든 탐색이 즉시 실패하는데, 그때 ctx는 멀쩡하고 결과만 비어 있다. 그래서 생성기가 「끝까지 봤는가」를 값으로 따로 말한다.
- **기다리기에 끝이 있다.** `ready:false` 는 **영영 참일 수 있다** — 이 코드 전에 끝난 판, 생성기가 없는 배포, 문항 판이 올라가 옛 행이 죽은 뒤가 전부 그렇다. 화면이 **서버가 스스로 자르는 시한과 같은 5분**까지만 묻고 그 뒤에는 **「안 왔다」만 말한다**(「없다」가 아니다 — 아는 것이 그만큼이다). 서버 쪽도 두 자리를 막았다: 생성기가 없어도 빈 행을 남기고, **저장에 시한을 따로 준다**(만드는 쪽이 시한에 걸리면 그 ctx로는 못 쓴다).
- **오답을 붉게 칠하지 않는다.** 진 판을 붉게 안 칠하기로 한 것과 같은 이유이고(`index.css` 의 `data-result`), 문제를 틀린 초심자에게 붉은 글씨를 내미는 자리가 그 규칙이 가장 걸리는 곳이다. 붉은 것은 **고장뿐이다.**
- **`mate` 풀을 1에서 2로 올렸다.** 아래.

### 실측 — 프로덕션과 같은 엔진으로 로컬에서

| 무엇                                            | 결과                                                                              |
| ----------------------------------------------- | --------------------------------------------------------------------------------- |
| `SearchMate(SFEN, nil)` — 手数 경로 없이 국면만 | **사람 차례 3국면 전부 증명됨**(미증명 0). 트리가 이 모양으로 부른다              |
| 6手 판의 생성 시간                              | 1초 미만 (사람 차례 3국면 · 詰み 없음)                                            |
| gap 문항 — 4手目 국면                           | 1위 `▲2五歩` +152 · 2위 +126 → **차 26**                                          |
| 그 탐색이 캐시에 남았나                         | `positions` 에 `computed_depth=12` · 후보 5 — **가정 수순의 k=3 요청을 받아친다** |
| 초반에서 임계치 200이 하는 일                   | **그 국면이 문항에서 빠진다** (차 26 < 200)                                       |
| 시험의 합성 국면 트리 (`3手詰め`)               | 노드 2 · 王手 판정 12개 · solver 호출 11회                                        |

**훑는 것과 짓는 것이 같은 예산을 쓴다.** 문항을 고르려면 사람 차례 국면마다 solver 를 한 번씩 부르므로(100手 판이면 50회쯤) 트리가 쓰기 전에 그만큼이 빠진다. **자르는 자리는 `quizTimeout`(5분) 하나로 뒀다** — 예산(2400 × 107ms ≈ 4.3분)을 그 아래로 잡아 먼저 걸리지 않게 했고, 남는 여유는 40초 남짓이다.

**마지막 줄은 바닥값이다** [미확정] — 그 국면은 駒가 거의 없다. 실전 종반은 持駒가 있어 王手 후보와 合駒가 둘 다 늘고 그 둘이 곱해지므로, `MateSearchBudget`(2400)이 실제로 얼마나 쓰이는지는 사람이 둔 판을 기다린다.

**세 번째 소비자가 전제를 깼다.** `startMateEngines` 의 주석이 「소비자가 둘이고 시간상 겹치지 않아 1로 족하다」였는데(종반 판정은 사람의 수 직후, 게이지는 상대의 수 직후) 퀴즈 생성이 판이 끝나는 자리에서 수십 초를 잡는다. `ENGINE_MATE_POOL_SIZE` 를 손잡이로 빼고 기본을 **2**로 뒀다.

**「대국 쪽에 늘 한 자리가 남는다」는 아니다.** 생성은 끝나는 판마다 하나씩 뜨고 수를 막는 자리가 없어서, 두 판이 동시에 끝나면 둘이 두 자리를 다 잡는다. 다만 탐색 하나마다 빌리고 돌려주므로(`Pool.Do`) **굶는 것이 아니라 줄을 서는 것**이고, 대국 쪽은 지연으로 겪는다 — 하나였을 때는 수십 초를 통째로 기다렸다.

### 남은 것

- **詰み 트리가 실제 solver로는 아직 한 번도 안 지어졌다** [미확정]. 확인한 것은 훑는 쪽(`SearchMate` 호출)까지이고, 트리를 짓는 `defend`·`expand` 는 룰 엔진 기준 solver로만 봤다 — 詰み이 있는 판이 필요하고 그것은 사람이 이겨야 나온다. **초심자 판에서 무엇이 먼저 나오는지도 여기서 갈린다**: 1手·3手가 흔하고 7手는 드물 것이라 봤지만 안 쟀다.
- **`BestMinGapCp=200` 은 감이다** [미확정]. 이 값이 곧 문항의 정의라(차가 작으면 정답이 사실상 여럿이다) 문항 수와 정답률을 같이 봐야 정해진다.
- **無駄合い이 「7手 이하」 게이트를 불균등하게 좁힌다.** 持駒가 많은 종반일수록 手数가 부풀어 게이트에서 떨어진다 — 방향이 한쪽이다. 화면에 적는 手数는 solver 가 준 값이라 거짓은 아니지만, **「7」은 난이도 상한이 아니라 필터다.**
  - 덤으로 나온 것: 부풀린 手数를 받는 것이 `JudgeMatePlies=5` 게이트도 마찬가지다(§29 ②). 그쪽은 이 회차에서 안 건드렸다.
- **`MateSearchBudget` 는 실전 종반에서 모자랄 수 있다** [미확정]. `expand` 가 王手 후보마다 `defend` 를 부르고 그쪽이 응수마다 solver 를 부르므로, 持駒가 있는 7手 뿌리 하나가 **40\~60 × 10\~30**이면 예산을 통째로 쓴다. 2400으로 올려 `quizTimeout`(5분)이 마지막에 걸리게 뒀지만 — 자르는 자리를 하나로 두려는 것이다 — 재 본 값이 아니다. 걸려도 이제 **詰み 문항만** 사라지고 「최선수는?」은 남는다.
- **1手 노드에서는 응수를 안 물어본다.** 정답 조건이 `2+rest <= plies` 이고 `rest >= 1` 이므로 `plies == 1` 에서 詰み이 아닌 王手는 **절대 정답이 될 수 없다** — 물어봐도 답이 안 바뀐다. 그런데 그 노드가 트리에서 가장 많아서(정답 하나마다 하나씩 달린다) **예산의 대부분을 거기서 쓰고 있었다.** 시험의 합성 국면에서 1手는 7→1회, 3手는 11→9회로 줄었고, 실전 종반에서는 그 노드마다 王手 수 × 응수 수가 빠지므로 절감이 그쪽에 몰린다.
- **정답이 하나도 없는 노드는 트리를 버린다.** 증명된 詰み이 있는 국면이면 어떤 王手 하나는 手数를 줄여야 하므로, 그런 수가 없다는 것은 **solver 가 최소 手数를 준다는 전제가 깨졌다**는 뜻이다(`go mate` 는 df-pn이라 최소를 보장하지 않는다). 그대로 내보내면 무엇을 둬도 오답이고 `Best` 가 비어 **세 번째 오답의 「무엇을 움직이나」까지 빈다**(§61) — **답이 없는 문제**다.
- **「詰みません」이라고 단정하지 않는다.** 남는 手数 0은 **두 가지**다 — solver 가 자기 한계(`ENGINE_MATE_PLIES`, 기본 11) 안에서 못 찾았거나, 애초에 안 물어봤다(위 1手 노드). 한계를 넘겨 늘어난 詰み은 여전히 강제되고(7手 뿌리에서 한 手 낭비하면 13手가 될 수 있다) 안 물어본 쪽은 말할 것이 없다. 그래서 **「この手では詰みになりません」** — 둘 다에서 참인 것만 말한다.
- **빈 화면은 이유를 말하지 않는다.** 「詰み이 없었고 뚜렷한 한 수도 없었다」는 서버가 모른다 — 생성기가 없는 배포는 아무것도 안 찾아보고 빈 행을 남기고, 트리가 깨져 詰み 문항이 빠진 판도 같은 자리로 온다. 초심자가 확인할 수 없는 것을 말하지 않는 규칙이 **가장 걸리는 자리가 빈 화면**이다.
- **기록이 늦게 쓰이면 그 판은 문항을 영구히 잃는다.** 생성을 띄우기 전에 `summaryWait`(5초)를 기다리는데, 그 시한을 넘기거나 기록 읽기가 실패하면 그대로 돌아간다 — 총평은 되짚기가 다시 청할 수 있어도(§52) 퀴즈에는 그 자리가 없다. 드문 길이라 이번에는 안 고쳤다.
- **한 갈래를 못 증명하면 詰み 문항이 통째로 사라진다** [미확정]. `defend` 가 첫 「모른다」에서 트리를 버리고 그 판은 다시 만들 자리가 없다. 반박된 갈래는 `nomate`(증명)로 오므로 안전하지만, **한계 밖으로 늘어난 갈래**는 `timeout` 으로 올 수 있다 — 7手 뿌리에서 한 手 낭비하면 13手이고 `ENGINE_MATE_PLIES` 는 11이다. 틀리게 채점하지는 않지만 **프로덕션에서 詰み 문항이 늘 안 나올 수** 있고, 그래서 버린 이유를 예산과 갈라 로그에 적어 뒀다 — 첫 실전 판이 어느 쪽인지 말해 준다.
- **채점 요청마다 기보를 통째로 읽는다.** 소유권과 「끝난 판만」을 `reviewHandler.record` 한 자리로 지나게 한 값이다(§52) — 7手 문항을 푸는 동안 네 번 넘게 그 질의가 돈다. 가벼운 소유권 질의를 따로 파면 줄지만, **거르는 규칙이 두 벌이 되는 값**과 맞바꾸는 것이라 이번에는 안 바꿨다.
- **옛 판에는 문항이 없다.** 생성이 판이 끝나는 자리에만 있으므로, 이 코드 전에 끝난 판은 영원히 `ready: false` 다. 채우려면 되짚기에서 만들거나 배치를 도는 자리가 필요하고, 둘 다 엔진 경합을 다시 부른다.

## 54. 개입 카드가 수순을 말하는 대신 판을 열었다 (2026-08-13)

「相手はこう咎めてきます」는 깊이 12 탐색의 PV를 잘라 보여주던 것이다. **자르는 자리를 국면이 정하는데**(`trimRefutation` — 손익이 바뀌는 첫 수에서 시작해 같은 칸의 주고받기가 끝날 때까지, §20) 그래서 두 수에서 끊기는 판이 흔했고, 넘겨 봐도 「그래서 어떻게 뒀어야 하나」가 안 남았다.

같은 물음의 답이 **되짚기 화면에 이미 있었다** — 국면 하나에 최선수 셋을 세우고 그 자리에서 직접 둬 보는 장치(§37). 대국 중에도 그 길은 열려 있었고(`ws.go` 의 `whatif`) 카드가 **cp만 꺼내 쓰고 후보 목록은 안 그리고** 있었다.

### 무엇을 정했나

- **PV 수순을 화면에서 뺐다. 남긴 것은 증명된 詰み 수순뿐이다.** 그것만이 자를 필요가 없어서(§40의 `full`) 「어디서 끊나」가 아예 없다. 나머지는 후보 셋이 맡는다.
- **`refutationLine` 은 그대로 돈다.** 그 첫 수가 `Facts.Threatened`(「무엇을 잡히는가」)이고, 그건 카테고리가 이유를 못 대는 자리의 유일한 사실이다(§25). 화면에 안 보낼 뿐이다.
- **개입 중에 판이 다시 살아난다 — 뜻은 하나로.** 판을 만지면 언제나 「그 수를 그대로 뒀다면」이고, 카드를 닫으면 대국의 판이다. §41이 이 길을 닫았던 이유는 판이 아니라 **자리 다툼**이었다(둬 보면 분기 패널이 개입 문구의 자리를 빼앗아 읽던 설명이 사라졌다). 설명·후보 목록·무르기를 **한 카드 안**에 두면 그 실패가 안 난다.
- **바닥이 둘이다.** 분기는 물러진 수 위에서만 자란다 — 그 앞은 곧 지금 다시 둘 국면이라, 거기서 후보 셋을 그리면 대국 중에 답을 알려주는 것이 된다([01-core.md §7](../01-core.md)). 화면은 버튼을 안 그리고(`useWhatIf` 의 `floor`) **서버는 요청을 거절한다**(`ws.go` 의 `branchRoot`). §37 ②는 이 벽을 「후보 목록을 안 켠다」로 지켰는데, 그쪽은 목록을 켜면 무너지고 이쪽은 안 무너진다.
  - 그전까지 그 표면은 **살아 있는 국면의 최선수 셋을 답해 줬다.** 화면이 안 물어봤을 뿐이다.
- **값은 「그 수를 둔 쪽 관점」이다.** 되짚기의 `MoveOptions` 와 같은 자를 쓴다 — 상대의 수는 상대에게 좋을수록 위다. 사람이 둬 본 수도 같은 자로 뒤집어 한 줄에 세운다(노드의 cp는 플레이어 관점이라 부호를 여기서 돌린다).
- **사람이 둬 본 수는 화면만 들고 있다.** 새로고침하면 사라진다 — 대국의 사실이 아니라 그 사람이 무엇을 궁금해했는가다. 잰 값 자체는 서버가 이미 남겼고(`positions`), **레이팅에는 안 닿는다**: 판정을 지나지 않는 수다.
- **`other` 가 이유 대신 결말을 말한다.** 「形勢を大きく損ねます」 하나로 16회를 버티던 자리다(§27). 이제 상대의 최선수 하나와 **내가 둘 수 있는 갈래 셋**(내 수 → 상대의 응수 → 결말 cp)을 문장이 든다.
- ~~**추가 탐색은 한 번이다.**~~ 상대의 최선수를 「판정이 이미 손에 든 PV의 첫 수라 공짜」로 잡았던 자리다. **그 공짜가 이 절의 값이었다** — 판정은 k=1로 묻고 카드는 같은 국면을 k=3으로 다시 물어서, 화면이 한 국면의 최선수를 둘로 말했다(**[§58](#58-문장과-카드가-한-국면의-최선수를-둘로-말했다-2026-08-14)**). 지금은 그 수도 카드와 같은 질문으로 구하므로 **`other` 개입의 추가 탐색은 두 번**이다. **A+B 국면의 MultiPV 하나**가 내 후보 셋과 각 줄의 PV(=상대의 응수)와 결말 cp를 함께 준다는 것은 그대로다.
- **「指し手は書かない」를 「우리가 준 수만」으로 좁혔다.** 푼 것이 아니다 — `Clean` 이 棋譜 표기를 전부 버리던 자리에서, 준 표기를 먼저 지우고 남은 것에 같은 정규식을 건다(`CleanBranches`). 목록이 비면 규칙이 예전 그대로다.
- **막지 못하는 것이 하나 있다** [미확정] — 준 수와 준 숫자를 **틀리게 짝지어** 쓰는 것. 토큰이 목록 안에 있는지는 기계가 보지만 대응까지는 못 본다. 그래서 갈래 목록 자체는 카드가 판 옆에서 따로 그리고, 문장은 그 위의 이야기다.
- **결정적 문구도 같은 갈래를 같은 순서로 적는다**(`renderBranches`). 라우터가 죽은 날에 잃는 것은 문장의 결이지 사실이 아니다.

### 실측 — 로컬, 프로덕션과 같은 엔진

▲7六歩 △3四歩 ▲3三角成(§50의 그 줄)으로 개입을 걸어 카드를 열었다.

## 55. 밴드가 절대 좌표였다 — 이기기 시작하면 조절이 꺼졌다 (2026-08-13)

사람이 한 판을 끝까지 뒀다(`games.id=397` · 先手 · 棒銀 · **298手**). 그 판이 밴드의 좌표계를 드러냈다.

### 실측 — 그 판에서 무슨 일이 있었나

| 手数 | 평가치(플레이어=先手 관점) |
| ---- | -------------------------- |
| 40   | +160                       |
| 80   | +498                       |
| 120  | **+1233**                  |
| 200  | +665                       |
| 295  | **+1782**                  |

| 무엇                           | 값                         |
| ------------------------------ | -------------------------- |
| 사람이 둔 수                   | 149手                      |
| 물러진 수                      | **65회** (시도 214 중 30%) |
| 200\~240手 구간의 개입         | **29회**                   |
| 手筋 힌트                      | **0회**                    |
| 창 상한(+395)을 처음 넘은 手数 | **54手**                   |
| 창 위에 있던 手数              | 111 / 297                  |
| **80手 이후 평가치 평균**      | **+391**                   |

**상한이 +395인데 220手 동안 평균이 +391이다.** 사람은 54手부터 끝까지 이기고 있었고, 그 우세가 그 선에 묶여 있었다. 결과는 `loss` 인데 **투료를 사람이 눌렀다** — 종반에 탐색 하나가 5분 넘게 안 돌아왔고, 그 판정 경로에는 시한이 없다.

### 원인 — 같은 숫자가 두 뜻이었다

`Band{100,300}` 은 「플레이어가 조금 이기고 있게 둔다」는 **양보 폭**으로 쓰려던 것인데 **절대 좌표**로 적혀 있었다. 플레이어가 0 근처일 때만 그 뜻이 맞고, 창 위에서는 「+300으로 **되돌려라**」가 된다.

되돌리는 방향의 실행자가 `distance` 였다. **기준점이 후보의 최솟값**이라(수를 두는 쪽이 상대이므로 플레이어 관점 cp는 그 아래로 안 내려간다) 「양보 0」이 곧 최선수이고, 두 방향 거리는 후보 간격이 밴드 폭보다 넓을 때 그쪽을 고른다.

**실력 추정은 처음부터 결백했다** — `skill.Track.Observe` 는 낙폭 하나만 먹고 형세도 결과도 안 본다. 「이기면 상대가 세진다」는 추정이 아니라 이 좌표계에서 나왔다.

### 무엇을 정했나

- **밴드가 정하는 것은 「어느 좌표로 읽을지」다.** 지금 형세가 구간 안이나 아래면 절대 좌표, 위면 **지금 + 밴드**다.
- **§81 이후 밴드는 닫힌 구간이다.** 안에서는 최소 양보를 고르고, 안전한 후보가 하나도 없으면 구간에 가장 가까운 안전한 수를 고른다. 하한을 넘겼다는 이유로 상한 밖의 수를 우선하지 않는다.
- **난이도보다 안전이 먼저다.** タダ捨て를 뺀 뒤 최선의 안전한 후보보다 600cp 넘게 나쁜 수도 뺀다. 밴드를 맞추려고 이 후보를 되살리지 않는다.
- **`SkillShiftCp` 는 밴드의 위치를 옮긴다.** 잘 두면 최선수 쪽으로, 헤매면 더 양보하는 쪽으로 움직이되 안전 상한은 움직이지 않는다.
- **詰み 줄을 후보에서 뺀다.** `ScoreCp` 가 환산값(`usi.MateCp`)이라 기준점을 판 밖으로 끌고 간다. 빼도 지금까지와 같게 돈다 — 詰み 줄은 어느 쪽이든 가장 먼 후보였다.
- **엔진 投了는 넣지 않았다.** 판을 끝내는 가장 짧은 길이지만 이 제품의 상대가 스스로 지는 것을 인정하는 순간 「지지만 던지지 않는다」가 무슨 뜻인지가 흐려진다.

### 실측 — 같은 자리를 옛 자와 새 자로

아래는 **§55 당시 하한만 쓰던 선택자의 실측**이다. §81에서 닫힌 밴드와 안전 상한으로
선택자를 바꿨으므로 현재 결과로 읽지 않는다. 새 규칙의 실제 한 판 길이는 아직 못 쟀다 [미확정].

`TestMeasureSkillBandReach`(depth 12 · k=10). **국면 집합이 두 실행에서 다르다** — 국면을 만드는 게임이 이 상대를 쓰므로 자를 고치면 국면도 갈린다. 그래서 개수로 견주지 않고 **같은 종류의 자리**로 견준다.

| 창 위 국면 | 옛 자                                        | 새 자                                      |
| ---------- | -------------------------------------------- | ------------------------------------------ |
| 몇 줄      | 1 (17수)                                     | 3 (17·19·21수)                             |
| 고른 수    | **헤맴·기준선·잘 둠이 전부 같다** (`+742cp`) | **셋이 갈린다**                            |
| 헤맴       | +742 (= 최선수)                              | +1407 · +1210 · +814                       |

새 자의 12줄 전부에서 **헤맴 ≥ 기준선 ≥ 잘 둠**이다. 「고른 수가 갈린 국면」은 9/12 → 11/12 인데, 위 이유로 이 두 숫자는 나란히 놓지 않는다.

### 남은 것

> **그 판에서 사람이 남긴 것은 18항목이고 이 절은 그중 둘만 고쳤다.** 나머지는 항목별 근거·상태와 손대야 할 순서까지 [playtests/2026-08-13-human-1.md](../playtests/2026-08-13-human-1.md)에 있다 — **몇 개가 남았는지는 그 문서와 위 §5가 정본이다**(여기 세어 두면 다음 회차마다 낡는다). **이어받는 사람은 그 문서의 §8부터 읽는다.**

- **사람이 다시 둬 봐야 안다** [미확정]. 위 실측은 「자가 다른 수를 고르는가」까지고, 「298手가 짧아지는가」는 다음 판이 답한다.
- **양보 폭 상수를 실측으로 안 잡았다.** `DefaultBand{100,300}` 이 이제 「한 수에 얼마나 양보하나」를 뜻하는데, 그 뜻으로 재 본 적이 없다 — §39·§47이 남긴 벽과 같은 자리이고 이제 표본이 한 판 생겼다.

## 56. 대국 탐색에 시한을 걸었다 — 그리고 시한만으로는 안 됐다 (2026-08-13)

§55의 그 판이 종반에 멈춘 자리다. 탐색 하나가 5분 넘게 안 돌아왔고 화면은 그동안 아무 말도 안 했다([playtests §6 #2 · #9](../playtests/2026-08-13-human-1.md)).

### 무엇에 시한이 없었나

`context.WithTimeout` 이 걸린 곳은 whatif·퀴즈·LLM뿐이었다. **대국 자체가 쓰는 네 경로에는 없었다.**

| 경로                          | 안 돌아오면                          | 시한     |
| ----------------------------- | ------------------------------------ | -------- |
| 상대 수 (`maybeThink`)        | 판이 안 넘어간다                     | **60초** |
| 개입 판정 (`startJudging`)    | `judging` 이 입력을 잠근 채로 남는다 | **60초** |
| 詰み 게이지 (`maybeGauge`)    | 테두리가 안 켜진다                   | **20초** |
| 手筋 힌트 (`maybeTesujiHint`) | 힌트가 안 뜬다                       | **20초** |

### 실측 — 시한만으로는 안 됐다

그 판의 기보 298手를 그대로 다시 두면서 잰 것이다(`TestMeasureTagHintLoad`). **엔진도 DB도 안 쓴다** — 룰 엔진만 돈다.

|                    | 옛 자                                                      | 새 자     |
| ------------------ | ---------------------------------------------------------- | --------- |
| 사람 차례          | 149회                                                      | 149회     |
| 게이트가 열린 手数 | **117**                                                    | **26**    |
| 엔진 탐색          | **586회**                                                  | **131회** |
| 룰 필터 한 번      | 평균 **133ms** · 최장 **2.46초**(276手目, 합법수 273)      | 같다      |
| 열린 手数당 후보   | 평균 **4.8개** · 최다 **20개** · 상한 6에 걸린 手数 **25** | 같다      |

**룰 필터가 걸러 주는 양이 적다.** 사람 차례 149회 중 117회에 후보가 있었으니 32회만 없앤 것이고, 게이트를 실제로 아끼는 것은 필터가 아니라 쿨다운이다. `TesujiHintMaxCandidates=6` 도 「실측으로는 안 걸린다」고 적어 뒀는데 **25手数가 걸렸다** — §34 ④의 「102수에서 6개」를 근거로 삼았던 것인데, 저것은 **실제로 둬진 수** 중 형태가 생긴 수이고 이쪽은 그 국면의 **합법수 전부**를 훑은 수다. 분모가 다르다.

엔진 풀은 **셋**이고 그 옆에서 상대의 수와 개입 판정이 자리를 다툰다(`cmd/api/main.go`). 그리고 저 룰 필터는 **세션 goroutine 안에서** 돌고 있었다 — 종반 한 수에 2.46초 동안 스냅샷도 投了도 못 받았다.

「초기 국면 90µs라 80수를 훑어도 10ms 안쪽」이라고 적어 두고 그 자리에 놓은 것이었다. **합법수가 273개까지 간다는 것을 안 셌다.**

### 무엇을 정했나

- **시한은 자를 시간이 아니라 버릴 시점이다.** 넘기면 결과를 통째로 버린다 — 깊이 기반이라 중간 결과는 depth N 결과가 아니고, 그것을 `computed_depth = N` 으로 캐시에 적으면 거짓말이 된다([01-core.md §4](../01-core.md)). **넘겼다고 얕게 다시 묻지도 않는다** — 그러면 상대의 강함이 서버 사정에 따라 달라진다.
- **값이 두 개인 것은 「무엇을 먼저 포기하나」다.** 판이 그 자리에서 멈추는 둘(상대 수·판정)이 60초, 없어도 판이 도는 둘(게이지·手筋)이 20초. 넷이 같은 풀을 다투므로 부가 기능이 먼저 자리를 내놓는다. `Config.MoveDeadline`·`ExtraDeadline` 로 흔들 수 있고 0이면 기본값이다.
- **상대의 수를 못 얻으면 中断이다** — `StatusAborted`, 승자 없음. 투료로 적으면 지고 있던 판이 기록에서 이긴 판이 된다. §55의 그 판이 반대 방향으로 겪은 실패이고(이긴 판을 진 판으로 적었다) 같은 종류다. 기록에서는 `abandoned` 로 떨어져 **이어하기 목록에 그대로 올라온다**(로그인한 사람). 엔진이 스스로 `resign` 이라고 답한 것은 그대로 사람의 승리다 — 갈리는 자리가 거기다.
- **판정을 못 하면 사람에게 말한다**(`Snapshot.Notice`). 수는 그대로 서지만 조용히 넘기지 않는다 — 개입이 없는 화면은 「이 수는 괜찮았다」와 똑같이 생겼고, 초심자는 아무 말이 없으면 통과한 것으로 읽는다. 개입 카드와 갈라 둔다: 저쪽은 판에 대한 판단이고 이쪽은 우리 쪽 사정이다.
- **手筋 게이트의 쿨다운을 「띄운 자리」가 아니라 「물어본 자리」에서 잰다.** 뜬 자리에서만 재면 게이트가 한 번도 안 열리는 판에서 쿨다운이 영영 안 걸린다 — 그 판이 정확히 그랬다(0회, §45). 상한(`TagHintMaxPerGame`)은 그대로 **뜬 횟수**를 센다.
- **룰 필터를 goroutine 안으로 옮겼다.** 「상태를 소유한 goroutine은 오래 막히면 안 된다」가 이 패키지의 규약인데 종반 한 수에 2.46초를 막고 있었다. 시한 안에 두지만 이 함수는 ctx를 안 보므로 중간에 안 끊긴다 — 오래 걸린 만큼 게이트의 몫이 줄어들 뿐이다.
- **시한을 넘겨 못 물어본 후보는 센다**(`dropped`). 조용히 넘기면 「手筋이 없었다」와 「못 물어봤다」가 같은 결과가 된다.

### 남은 것

- **60초·20초가 실측이 아니다** [미확정]. 「사람이 화면 앞에서 기다리는 한계」로 잡았다. 실측으로는 상대 수 2.0초·판정 0.8초·게이지 0.12초라(§10 · §12) 정상적인 판이면 어느 것도 안 닿는다 — **닿는 자리를 아직 못 쟀다.**
- **5분이 어디서 났는지는 여전히 모른다.** 위 표가 말하는 것은 「한 판에 얼마를 걸었나」이지 「그 한 번이 왜 5분이었나」가 아니다. 서버가 대국 중에 로그를 거의 안 써서 남은 길은 다음 판에서 시한이 실제로 걸리는지를 보는 것이다.
- **퀴즈 생성이 같은 풀을 5분 예산으로 잡는다**(`quizTimeout`, §53). 판이 끝나는 자리마다 뜨고 수를 막는 자리가 없어서, **다른 대국**의 상대 수가 그 뒤에 줄을 설 수 있다. 이 절은 대국 쪽에만 시한을 걸었다 [미확정]
- ~~**手筋 힌트가 뜨는지는 이 절이 답하지 않는다.**~~ **§74가 답했다.** 후보는 24회에 있었고 게이트를 통과한 것이 122분의 2였으며, 그 둘조차 4초 뒤에 왔다. 이 절이 「비용만 내던 것」이라고 부른 그 비용이 곧 이유였다.

## 57. 퀴즈가 「네가 낸 수」를 한 번도 말하지 않았다 (2026-08-14)

「정답대로 뒀는데 不正解이라고 한다」의 자리다([playtests §6 #17 · #18](../playtests/2026-08-13-human-1.md)). **회차 문서가 적어 둔 원인은 틀렸다** — 표기 구분은 이미 있었다. 그 행을 이 PR에서 고쳤다.

### 실측 — 110手 국면에서 3五로 가는 수 셋

| 수     | 棋譜 표기    |                            |
| ------ | ------------ | -------------------------- |
| `4f3e` | ▲3五金       | 정답 (cp 910 · 2위 548)    |
| `G*3e` | **▲3五金打** | 사람이 낸 것으로 보이는 수 |
| `P*3e` | ▲3五歩       |                            |

`shogi.MoveJa` 가 打을 이미 붙이고, 반상의 수가 여럿이면 上·寄·引까지 붙인다. **구멍은 채점 응답에 낸 수가 없다는 것이었다** — `Played` 는 **그 판에서 실제로 둔 수**(`G*3h`)이지 퀴즈에서 낸 수가 아니다. 그래서 오답 문구가 「正解は▲3五金でした。この対局では▲3八金を指しています」로 끝나고, ▲3五金打를 낸 사람에게는 **자기가 낸 수가 문장 어디에도 없다.**

그리고 「최선수는?」 문항의 판은 채점 뒤에도 그대로 서 있었다(#18). **무엇이 등록됐는지 확인할 길이 화면에 하나도 없었다** — 둘은 같은 상처의 양쪽이라 한 자리에서 닫았다.

### 무엇을 정했나

- **낸 수를 응답에 싣는다** — `move`(정본 USI)·`moveJa`. `played` 와 **다른 칸이다**: 하나는 지금 이 문항에 낸 수, 하나는 그 판에서 둔 수다. 뭉쳐 두었던 것이 이 절의 원인 전부다.
- **문구가 낸 수부터 말한다.** 낸 수가 그 판에서 둔 수와 같으면 뒤 문장은 붙이지 않는다. **정답을 나란히 두는 부분은 §61에서 없어졌다** — 오답 문구는 정답을 말하지 않는다. 그래서 「한 글자 차이」를 갈라 줘야 하는 쌍도 그때 **낸 수와 그 판에서 둔 수**로 옮겨 갔다.
- **「어디서 오는가」는 두 수가 같은 칸으로 갈 때만 붙인다**(`moveOriginJa`). 반상 이동은 「4六の金」, 打은 「持ち駒の金」. 칸이 다르면 표기가 이미 갈려 있어 문장만 길어진다. **詰み 문구도 같은 자리를 지난다** — 같은 종류의 오답이 그쪽에도 있다.
- **괄호는 문장에만 넣고 표기는 棋譜 그대로 둔다**(`answerJa`·`bestJa`). 화면이 그 값을 cp 표에 그대로 적는다.
- **판을 그 수 뒤 국면으로 옮긴다.** 서버가 SFEN과 王手 칸을 주고 화면은 수를 두지 않는다 — 화면은 규칙을 모른다. 짚는 두 칸이 打과 반상 이동을 가른다: **출발 칸이 빛나면 반상, 안 빛나면 持ち駒에서 온 수다.**
- **표기나 국면을 못 만들어도 500이 아니다.** 채점은 그 앞에서 끝나 있고, 여기서 오류로 올리면 **맞은 답이 오류가 된다.**

### 확인 — 그 판의 그 문항을 다시 풀었다

로컬 DB의 `games.id=397` · 110手 문항. 브라우저로 두 수를 실제로 냈다.

| 낸 수  | 문구                                                                                                                                                             | 판                                                                               |
| ------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------- |
| `G*3e` | 不正解です。あなたが指したのは▲3五金打、正解は▲3五金（4六の金）でした。この対局では▲3八金を指しています。<br>**이 문구는 §61에서 바뀌었다** — 정답 부분이 빠진다 | 3五에 金이 서고 **4六 金은 그대로**, 持ち駒의 金이 사라진다. 짚는 칸은 도착 하나 |
| `4f3e` | ▲3五金で正解です。この局面はこの一手で、次善手とは362の差があります。                                                                                            | 4六이 비고 **두 칸을 짚는다**                                                    |

### 남은 것

- **詰み 문항의 문구는 낸 수를 여전히 말하지 않는다.** 그쪽은 판이 채점마다 움직여서 낸 수가 눈에 보인다 — 붙인 것은 정답 표기의 괄호뿐이다.
- **詰み 채점 경로는 브라우저로 못 봤다.** 그 판에 詰み 문항이 없다. 실제 solver로 트리가 한 번도 안 지어진 것과 같은 벽이다(§53).
- **`BestMinGapCp=200` 은 그대로 감이다**(§53). 이 판의 두 문항은 362차·356차로 둘 다 그 선을 넉넉히 넘었고, **200 근처의 문항이 어떻게 읽히는지는 표본이 없다** [미확정].

## 58. 문장과 카드가 한 국면의 최선수를 둘로 말했다 (2026-08-14)

사람이 남긴 그림 그대로다([playtests §6 #8](../playtests/2026-08-13-human-1.md)) — 카드 후보 1위는 `△2五玉` 인데 그 위의 문장은 「相手の最善手は△7七歩」라고 한다.

**어느 쪽도 버그가 아니었다.** 두 값이 서로 다른 탐색에서 나온다.

| 화면의 어디 | 무엇을 물었나                          | 어디서                         |
| ----------- | -------------------------------------- | ------------------------------ |
| 문장        | 물러진 수 뒤 국면 · depth 12 · **k=1** | 판정이 이미 손에 든 `after.PV` |
| 카드 후보   | 같은 국면 · depth 12 · **k=3**         | 화면이 whatif로 다시 물은 것   |

깊이가 같아서 「같은 기준」인 줄 알았던 자리다([§37](21-40.md#37-そのときこう指していたら--두-화면이-한-장치를-쓴다-그리고-모든-탐색이-데이터가-된다-2026-08-11)이 이미 「갈리는 것은 MultiPV뿐」이라고 적어 뒀다). **k가 다르면 1위가 갈린다** — MultiPV는 형제 줄을 함께 유지해야 해서 가지치기가 달라진다([§34 ②](21-40.md#34-이름은-룰이-이득은-엔진이--그리고-실측이-셋을-뒤집었다-2026-08-11)).

### 실측 — 같은 국면을 k=1과 k=3으로

`internal/game/card_pv_measure_test.go`. 재는 국면은 **사람이 둔 첫 판에서 사람이 두고 난 뒤**의 자리들이다(8手마다). 개입 카드가 서는 것과 같은 모양(상대 차례)이고, 물러진 수 자체는 롤백돼 기보에 없어서 그 국면을 그대로는 못 되만든다.

|                     |                                                            |
| ------------------- | ---------------------------------------------------------- |
| 잰 국면             | **34개** (8手마다)                                         |
| **1위가 갈린 국면** | **7개 — 21%**                                              |
| k=1 평균 소요       | 569ms                                                      |
| k=3 평균 소요       | **1.96s** (같은 국면을 이어서 재므로 치환표가 더워져 있다) |

갈린 일곱은 序盤 하나와 中終盤 여섯이다.

| 手数 | k=1 (문장이 말하던 것) | k=3 (카드가 짚는 것) |
| ---- | ---------------------- | -------------------- |
| 9    | `8c8d` (−21)           | `3a3b` (+62)         |
| 121  | `1e4h` (−1146)         | `1e2d` (−1120)       |
| 145  | `8a2a` (−75)           | `8a3a` (−127)        |
| 185  | `1g2h` (−54)           | `1g1h` (−148)        |
| 209  | `P*2h` (+38)           | `3h2h` (+72)         |
| 225  | `1f2g+` (−671)         | `3h2g` (−967)        |
| 233  | `5b4d` (−182)          | `5h4g` (−107)        |

**갈릴 때 점수도 함께 갈린다.** 225手는 k=1이 −671로 본 국면을 k=3이 −967로 본다 — 같은 국면·같은 깊이다. 화면에서 두 수가 다르게 보이는 것보다 이쪽이 큰 값이고, 그것이 「어느 하나를 정본으로 정한다」의 이유다.

**그 판의 `other` 개입은 30건이었다**([playtests §4](../playtests/2026-08-13-human-1.md)). 21%면 **한 판에 여섯 번쯤** 화면이 한 국면의 최선수를 둘로 말한 셈이다.

### 무엇을 정했나

- **정본은 카드가 묻는 질문이다** — 같은 국면·같은 깊이·`k=OtherBranches`. 문장이 그 답을 쓴다(`engineAnalyst.cardPV`). 카드 쪽을 k=1로 내릴 수는 없다: 후보 셋이 그 화면의 내용 자체다([§54](#54-개입-카드가-수순을-말하는-대신-판을-열었다-2026-08-13)).
- **판정 자체는 안 건드린다.** 착수 후 탐색을 k=3으로 올리면 한 줄로 끝나지만, 그것은 **착수 직후에 도는 유일한 탐색**이라 개입이 안 걸린 수까지 1.4초씩 느려진다(위 표의 569ms → 1.96s). 물러진 수는 시도의 30%였으니 나머지 70%가 값을 내는 셈이다.
  > **§10의 표로 넘겨짚으면 안 된다.** 저기서는 depth 12·k=1이 400ms인데 이 판에서는 569ms이고, k의 배수도 저 표(k=5가 k=1의 2.4배)보다 크다(k=3이 3.4배). 저 여섯 국면은 8급 대국의 것이고 이 판의 종반은 持ち駒가 양쪽에 쌓인 국면이다 — **자를 바꿀 때는 그 판의 국면으로 다시 잰다.**
- **`other` 에서만 다시 묻는다.** 문장에 수를 적는 카테고리가 그것뿐이라(`explain.Facts.used`) 다른 카테고리에는 갈릴 자리가 없다. 이름으로 이유를 대는 문장에 탐색을 하나 더 물릴 이유도 없다.
- **탐색 총수는 그대로다.** 새로 거는 그 탐색이 **화면이 곧 물을 그 탐색**이다 — 결과가 `positions` 에 남아 카드의 요청이 캐시에서 답한다(`server.evalOf`). 옮겨진 것은 순서이고, 그래서 **기다리는 자리가 둘에서 하나로 바뀐다**: 지금까지는 카드가 빈 목록과 「読んでいます…」를 들고 먼저 떠서 그 2초를 사람이 봤고, **그 자리에서 사람이 `指し直す` 를 눌렀다**([playtests §6 #2](../playtests/2026-08-13-human-1.md)). 이제는 카드가 목록을 채운 채로 뜨고, 그만큼(위 표의 1.96초) 늦게 뜬다.
- **「무엇을 취할 수 있는가」도 같은 수의 것이다.** `Facts.Threatened` 는 반박 수순의 첫 수로 따이는 駒인데 그 수순이 k=1 PV였다 — **한 문장 안에서 최선수와 따이는 駒가 서로 다른 수의 사실**일 수 있었다(`TestThreatenedPieceComesFromTheSameMove`).
- **후보 순서의 정의를 한 자리로 모았다**(`usi.SearchResult.Ranked`). 캐시에 쌓는 목록과 문장이 보는 1위가 각자 세면 이 절의 버그가 다시 산다. **`Lines[0]` 이 1위가 아닐 수 있다** — 순위 자리를 미리 채우므로 아직 안 온 순위가 빈 줄로 남는다.
- **`explain_cache` 키가 갈리는 것은 의도한 것이다.** 키에 `|best=` 로 그 수가 들어가므로(`Facts.keyMaterial`) 정본이 바뀌면 옛 키를 못 찾는다. 그 키들은 국면마다 다른 Tier 2라 히트가 애초에 드물고, **사전 생성해 둔 21행은 Tier 1이라 `|best=` 가 없다** — `promptVersion` 은 올리지 않는다.
- **카드 후보에 낙폭을 적는다**(#11). 값은 서버가 이미 보내고 있었다(`WhatIfCandidate.lossCp`). **1위 줄의 「最善」이 그 칸의 이름표다** — 열 제목을 얹지 않고, 아래 줄의 숫자가 무엇에 대한 값인지를 그 한 단어가 말한다. 1위를 색으로만 표시하던 자리이기도 해서 **색을 못 보는 사람에게도 1위가 남는다.**
- **詰み이 섞인 줄에는 낙폭을 안 적는다.** 그 줄의 cp는 환산값(±30000)이라 뺄셈이 29900을 내놓는다. 서버가 그 자리를 비우고(`candidatesOf`) 0을 안 내보낸다 — 화면이 「낙폭 0」과 「낙폭을 모른다」를 갈라야 한다.

### 확인 — 브라우저에서 `other` 개입을 하나 만들었다

로컬에서 새로 한 판(`games.id=547`). 5六歩을 밀어 5五를 **공격받지만 지켜지는 칸**으로 만든 뒤 거기에 角을 던졌다 — 그러면 `hangs_piece` 가 아니라(`LandsDefended` 가 그 분기를 막는다) `other` 로 떨어진다. `interventions` 에 `ply=9 · retracted_usi=7g5e · category=other · explain_tier=2`(LLM 실호출)로 남았다.

| 카드의 어디 | 나온 것                                                         |
| ----------- | --------------------------------------------------------------- |
| 문장        | 「相手は角を取ることができます。**相手の最善手は△同歩です。**」 |
| 후보 1위    | **△同歩** +1932 · 「最善」                                      |
| 2위 · 3위   | △6二銀 +118 · **−1814** / △3二金 +106 · **−1826**               |

**한 수를 두 번 말하지 않는다.** 문장의 최선수와 초록 화살표가 짚는 후보가 같은 수이고, 「角を取ることができます」도 그 수가 따는 駒다. 낙폭 칸은 1위가 「最善」, 아래가 −1814·−1826으로 서고 **세 줄의 오른쪽 끝이 같은 자리**다(폭을 고정한 이유).

같은 판의 직전 개입(`ply=7` · `hangs_piece`)에서는 카드가 후보 목록만 갖고 문장은 수를 안 적었다 — **그 카테고리에서 탐색을 더 걸지 않는다**가 화면에서도 그 모양이다.

### 남은 것

- **한 카드 안의 두 숫자는 아직 다른 탐색의 것이다.** 「勝率 −N%」는 판정의 k=1이 만든 값이고 물러진 수 옆의 형세는 카드의 k=3이 만든 값이다. 뜻이 다른 두 값이라 화면에서 모순으로 읽히지는 않지만, **같은 국면을 두 번 재고 있는 것은 그대로다**.
- **詰まされる 카드는 첫 수가 갈릴 수 있다.** 「このあと詰まされます」의 수순은 증명된 詰み이고 후보 목록의 1위는 탐색의 것이라, 같은 手数의 다른 詰め手가 나란히 설 수 있다 — 둘 다 참이므로 이 절에서는 안 건드렸다 [미확정].
- **캐시 쓰기가 goroutine이라 경합 창이 있다.** 판정의 그 탐색이 `positions` 에 닿기 전에 카드의 요청이 오면 엔진을 한 번 더 부른다. 답은 거의 같지만 **같은 국면·같은 깊이·같은 k도 치환표 상태에 따라 갈린다**(§34 ②) — 그때만 이 절의 그림이 다시 나올 수 있다.
- **`other` 개입 하나가 도는 데 탐색이 셋이 됐다** — 착수 후 k=1(0.57s) · 카드 국면 k=3(1.96s) · 갈래 국면 k=3. **그 셋이 전부 카드가 뜨기 전에 돈다**(판정이 끝나야 문구가 나가고, 문구 뒤에 LLM이 한 번 더 붙는다). 총 시간은 안 늘었지만 **카드가 뜨는 시점은 늦어졌고, 그 크기를 안 쟀다** [미확정]. 다음 판에서 「待った가 늦다」가 나오면 되돌릴 자리는 이 절이다.
- **그 셋이 시한 하나를 나눠 쓴다.** `MoveDeadline`(60초)은 `Judge` **호출 전체**에 걸리므로(session.go) 셋의 합이 그 안이어야 한다 — 넘기면 판정이 실패하고 **그 수는 그대로 선다**(사람에게는 `Snapshot.Notice` 로 말한다, §56). 정상적인 국면에서는 4.5초쯤이라 멀지만, **위에서 엔진이 죽은 그 종반**에서는 여유가 그만큼 줄었다 [미확정].
- **273手 국면에서 엔진이 죽었다** — 위 실측이 거기서 멈췄다(`engine exited during search`, 풀이 재기동했다). §56이 「5분이 어디서 났는지는 여전히 모른다」로 남긴 자리에 붙는 데이터 하나다: **그 판의 종반은 엔진이 실제로 죽는 국면들이다.** 시한(60초)은 죽음을 대신 잡아 주지만, 왜 죽는지는 여전히 모른다 [미확정].
- **사람이 다시 둬 봐야 안다** [미확정]. 위 「확인」은 국면 하나이고, 「이 카드가 이제 앞뒤가 맞는가」는 다음 판이 답한다.

## 59. 사람이 두 번째로 뒀다 — 판은 닫혔고 남은 것은 화면이다 (2026-08-14)

두 번째 사람 판(`games.id=580` · 105手 · `win`). 항목별 근거는 [playtests/2026-08-14-human-2.md](../playtests/2026-08-14-human-2.md)에 있고, 여기에는 다른 절의 [미확정]을 닫은 것만 적는다.

### 실측 — 두 판 대조

### 무엇을 정했나

- **§55·§56의 [미확정] 둘이 닫혔다.** 「298手가 짧아지는가」는 105手 · `win` 으로, 「판이 종반에 멈추지 않는가」는 `StatusAborted` 없이 끝난 것으로. **다만 비교 축이 하나 어긋났다** — 회차 1은 상대가 `棒銀` 이고 이 판은 진형을 안 골랐다. 手数 감소를 전부 §55의 몫으로 읽지 않는다.
- **§58의 카드 지연을 되돌리지 않는다.** 「다음 판에서 「待った가 늦다」가 나오면 되돌릴 자리」라고 적어 뒀는데, 사람이 남긴 12항목에 그 말이 없다. **되돌릴 근거가 없으므로 그대로 둔다.**

- **`skill_loss` 는 실력의 누적이 아니라 블런더율의 평형값이다.** 위 표가 두 점이고 둘 다 맞았다. `RiseRate`·`FallRate` 를 실측으로 고르는 것은 곧 **「블런더율 몇 %를 어느 눈금으로 볼 것인가」**를 고르는 일이고, 그 관계식이 자다.
- **표본 수를 신뢰도로 쓰지 않는 것이 실제로 물렸다.** `skillShift` 는 `Ready()`(표본 ≥3)만 확인하므로 표본 3개짜리와 246개짜리를 똑같이 믿는다. 그래서 **다른 세션의 확인용 착수 22개가 회차 1의 0.658을 0.250으로 끌어내렸고**(정석 구간의 조용한 수는 낙폭 ≈0이라 「매 수 최선」으로 셈된다), 그대로 두면 이 판이 −150cp 센 상대에서 출발했다. 판 시작 전에 손으로 비웠다 — **사람이 두는 판마다 그럴 수는 없다.**
- **詰み 트리가 실제 solver로 처음 지어졌다**(§53). 사람이 이겨야 나오는 국면이었고, `payload.mate` 가 98手 7手詰み · 노드 7개다. `converted: false` 이므로 환산값이 아니라 증명된 詰み이다.
- **手筋 게이트는 두 판 연속 0건이다.** §45가 정확도 때문에 방향을 보류한 결과이고, 이 판도 그 결정을 뒤집을 근거를 주지 않았다.

### 남은 것

- **사람이 남긴 12항목은 거의 전부 대국 밖이다** — 리뷰 화면의 표기(#6 · #7 · #8), 퀴즈 진행(#9 · #10 · #11 · #12), 총평과 실력 표시(#2 · #3), 대국 흐름(#1 · #5). **대국 자체에 대한 지적이 하나도 없었다.** 순서는 회차 문서 §8.
- **`other` 비율이 87.5%로 올랐다** (회차 1은 46.2%). **표본이 8건이라 추세로 못 읽는다.** 그리고 그중 하나는 문구가 스스로 「理由は特定できていません」이라고 말한다.
- **`cost_yen` 이 두 판 73건 전부 0이다** [미확정]. 계측이 안 읽는지 모델이 정말 0인지 여전히 모른다 — 「절감 2단계」를 아직 숫자로 못 말한다.

## 60. 되짚기 목록이 「같은 자를 쓴다」고 적혀 있었지만 아니었다 (2026-08-14)

회차 2가 남긴 리뷰 화면 셋을 고쳤다([playtests §6 #6 · #7 · #8](../playtests/2026-08-14-human-2.md)) — 그 셋의 상태는 이 절로 ✅다.

**§54가 이미 「되짚기의 `MoveOptions` 와 같은 자를 쓴다」고 단언해 뒀다.** 숫자는 그랬고 **색과 詰み은 아니었다** — 미리 참이라고 적힌 문장이 코드가 따라오지 않은 자리를 덮고 있었다.

### 실측 — 그 셋이 무엇을 그리고 있었나

`games.id=580` · 로컬 · `93d3550`. 브라우저로 짚었다.

| 자리                             | 고치기 전                   | 고친 뒤            |
| -------------------------------- | --------------------------- | ------------------ |
| 105手 `▲同馬`(#8)                | **+29990**                  | **1手で詰み**      |
| 12手 `△1四歩`(#7 · 상대가 둔 수) | **빈칸** · 맨 아래          | **−220**           |
| 13手 `▲1六歩`(#7 · 내가 둔 수)   | **빈칸** · 맨 아래          | **+86**            |
| 12手 세 후보의 색                | 빨강(`--ray-check`)         | **파랑(`--hint`)** |
| 그래프를 마우스로 누를 때(#6)    | `rgb(0, 95, 204) auto 5px`  | **링 없음**        |
| 그래프를 `Tab` 으로 잡을 때(#6)  | `rgb(47, 93, 69) solid 2px` | 그대로             |

색 줄만 `evalTone` 에서 나온 것이고(음수 cp면 `--ray-check` 다) 나머지는 화면에서 읽은 값이다. **`Tab` 은 원래도 深緑이었다** — 그쪽은 `:focus-visible` 이 붙어 우리 규칙이 걸렸고, 바뀐 것은 마우스 쪽뿐이다.

**같은 화면이 한 국면을 두 말로 부르고 있었다** — 옆의 「もしも」 카드는 105手를 이미 「1手で詰み」이라 적고 목록은 `+29990` 이라 적었다(§58과 같은 종류의 어긋남이다).

**파란 테는 우리 색이 아니었다.** recharts 3.10.1의 `accessibilityLayer` 가 기본 켜짐이라 `<svg>` 에 `tabindex="0"` 이 붙고(`RootSurface.js`), 마우스로 누르면 포커스가 간다. 그런데 **위젯이 아니라서 `:focus-visible` 이 안 붙어** 우리 深緑 규칙이 아예 안 걸리고 Chrome 기본 링이 그려졌다.

### 무엇을 정했나

- **부호 규칙을 한 벌로 모았다** — `rowScoreJa`·`playerCp` 가 `libs/whatif/branch.ts` 로 갔다. 대국 중의 블런더 목록과 되짚기 목록은 **같은 목록**인데 그 규칙이 두 벌이었고, 되짚기 쪽만 뒤집기 없이 자라 있었다. 서버의 `playerCp`(branch.go)와 같은 일이라 이름을 맞췄다.
- **열의 자는 「둔 쪽 관점」으로 남긴다.** 후보끼리 견주는 자라 그래야 위가 「그 쪽에게 좋은 수」다. 뒤집는 것은 **색과 詰み의 주어**뿐이다 — 색은 어디서나 「나에게 좋은가」이고, 手数는 세는 값이라 관점을 바꿔도 자가 안 갈린다.
- **다시 잰 값이 詰み도 들고 온다**(`useMoveEvals` → `MoveEval`). cp만 받으면 #7로 채운 칸에서 #8이 그 자리에서 다시 터진다.
- **후보 안에 있으면 다시 묻지 않는다.** 둔 수의 값은 후보 셋 밖일 때만 없어서, 그때만 한 번 더 잰다 — 手数를 옮길 때마다 깊이 12 탐색을 하나 더 거는 것은 대국과 나눠 쓰는 풀에서 할 일이 아니다.
- **`accessibilityLayer` 를 끄지 않는다.** 끄면 `tabindex` 가 사라져 **키보드로 그래프에 닿을 길이 없어진다** — 여기가 手数를 고르는 장치다. 마우스일 때만 링을 지웠다(`:focus:not(:focus-visible)`).

### 남은 것

- **저장된 cp에는 아직 `mateIn` 이 옆에 없다.** 그래서 두 자리가 詰み을 환산값으로 말할 수 있다 — 기보 목록의 cp 칸(`review-kifu-eval` · `ReviewMove.evalCp`)과, `afterCp` 가 남아 있는 물러진 수의 줄(`ReviewIntervention.afterCp`)이다. **`eval_cp` 에서 되짚지 않는다** — `usi.MateCp` 를 웹에 한 벌 더 두는 일이고, `EvalGraph` 의 `K = 600` 이 이미 그 후회다. **서버가 `mateIn` 을 함께 보내야 닫힌다.**

  회차 문서가 예로 든 `-29940` 은 **이 판의 값이 아니다** — `games.id=580` 의 `interventions.after_cp` 는 여덟 건 전부 −1701\~+113이고, 그 숫자는 실엔진 테스트 로그의 것이다(§55). 이 판에서 실제로 화면에 나간 환산값은 위 표의 `+29990`(후보 줄)이고 그쪽은 닫혔다.

- **끝난 국면(詰み·手詰まり)으로 가는 수는 값이 없다.** 서버가 탐색 없이 돌아오므로(`branch.go`) 그 줄은 빈칸으로 남는다. 그 자리를 0으로 채우면 호각으로 읽힌다.
- **대국 중의 블런더 목록은 브라우저로 다시 안 봤다.** 위 통합은 함수 두 개를 그대로 옮긴 것이고 타입·테스트로만 확인했다 [미확정].
