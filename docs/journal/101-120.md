# 저널 §101–

## 101. 사후 분석 층에 눈을 붙였다 — 밀린 것을 手로 센다 (2026-08-23)

대인전이 끝나면 기보를 手마다 다시 재는 층이 돈다([§95](82-100.md)). 그 층이 지금까지 **로그 한 줄로만 보였다** — 줄이 넘쳐 판을 버릴 때 `analysis queue is full` 이 남는 것이 전부이고, 얼마나 밀렸는지도 판 하나를 재는 데 얼마나 걸리는지도 그래프가 없었다.

부하 회차를 걸기 전에 이 자리를 열었다. 회차가 답해야 할 물음이 「동시에 몇 판까지 되나」인데([06-status.md](../06-status.md) §5), 이 층이 안 보이면 그 물음의 절반이 안 보인다.

### 붙인 것

| 지표                                 | 뜻                                                           |
| ------------------------------------ | ------------------------------------------------------------ |
| `analysis_backlog_games`             | 줄에서 기다리는 판 수                                        |
| `analysis_backlog_plies`             | **그 판들의 手 합**                                          |
| `analysis_games_total{result}`       | `done` · `dropped`(줄이 넘침) · `failed`(판정이 중간에 끊김) |
| `analysis_game_duration_seconds`     | 판 하나를 처음부터 끝까지 재는 데 걸린 시간                  |
| `engine_pool_wait_seconds{borrower}` | 풀 대기를 **누가 빌렸나**로 가른다                           |

### 정한 것 넷

**① 밀린 양은 手로 센다.** 판 수는 밀린 일의 크기를 못 말한다 — 회차 4의 세 판이 **27手 · 34手 · 123手**였다([§91](82-100.md)). 「밀린 판 3개」가 같은 값인데 실제 일은 4.5배 다르다.

**手도 균일하지는 않다.** 초반 手는 캐시가 답하고(히트율 65.7% · 27ms) 中盤은 아니다(2.3% · p95 5.24초). 그러니 궁극의 지표는 「예상 잔여 시간」이고 手는 그 근사다 — 手당 비용 곡선이 나오면 그때 환산을 얹는다.

**② 그래도 큐의 작업 단위는 판이다.** 手 단위로 쪼개면 셋이 무너진다.

- **부분 수용** — 100手 판이 남은 자리 40개에 반만 들어간다. 그러면 「창(21~60手) 안에서 끊긴 판은 실력 표본을 통째로 버린다」([§95](82-100.md))를 판단할 자리가 없어지고, 편향된 부분집합이 조용히 쌓인다
- **실패 전파** — 지금은 한 手가 실패하면 뒤도 전부 같은 이유로 실패할 것이 확실해 루프를 끊는다. 手가 이미 줄에 들어가 있으면 못 끊고, 남은 手마다 시한 60초를 태운다
- **완료 시점** — 실력 추정은 판 끝에 한 번 커밋한다(`saveMoves`). 手 단위면 「마지막 手가 끝났다」를 아는 쪽이 없고, 버려진 手가 하나라도 있으면 그 판이 영영 「분석 중」으로 남는다

**지표 단위와 작업 단위는 같을 필요가 없다.** 줄에 서는 항목이 手数를 같이 들면(`analysisJob.plies`) 판 단위 큐에서 手 지표가 그대로 나온다.

**③ 手数는 곁장부에서 센다.** 줄에 세우는 자리에서 기보를 되읽으면 판이 끝나는 경로에 질의가 하나 는다. 기록기가 지나가는 `Moved` 를 세어 두고 그 값을 쓴다 — 두 자리가 같은 수를 다 적으므로 큰 쪽을 든다.

**④ 풀 대기를 빌린 쪽으로 가른다.** 이 라벨 하나가 **「사후 분석이 대국을 굶히는가」를 직접 답한다** — 분석이 도는 동안 `borrower=game` 의 대기가 튀는지로 갈린다. 분석기를 별도 서비스로 떼는 판단이 그 숫자에 걸려 있고, 지금은 그것을 대신할 값이 없다.

이름은 컨텍스트로 나른다(`usi.WithBorrower`). 부르는 자리와 빌리는 자리 사이에 탐색부가 끼어 있어서, 인자로 받으면 그 사이 함수들이 전부 「누가 왜 부르는지」를 알아야 한다. 안 붙인 것은 `game` 이다 — 대국 중의 경로가 세션에서 곧장 부른다.

### EMF 에는 셋만 올린다

`/metrics` 는 라벨을 다 들지만 CloudWatch 로 나가는 것은 추린 것이다([§90](82-100.md)). 이번에 더한 셋:

- `AnalysisBacklogPlies` — 이 층의 부하 지표
- `AnalysisGamesDropped` — 0이 아니면 그 자체가 사고다. 버려진 판은 평가치도 실력도 없이 남는다
- `EnginePoolWaitGameSeconds` — 위 ④의 증거

**표본통을 두 번 비울 수 없어서 자르는 방식을 바꿨다.** `DrainSamples` 는 고르지 않은 계열까지 비우므로, 같은 지표를 합친 것과 가른 것 두 벌로 내려면 한 번에 나눠 받아야 한다(`DrainSamplesSplit`). 두 번 부르면 두 번째가 늘 빈 배열이다.

### 남은 것 — 이 값은 아직 인스턴스별이다

큐가 프로세스 안의 채널이라 게이지도 그 프로세스의 것이다. 태스크가 둘이 되면 **합이 어디에도 없다.** 그리고 지금은 배포·스케일인·크래시에 밀린 판이 **그대로 사라진다** — 워커가 채널을 안 비우고 나가고(`run` 의 `ctx.Done`), 다시 잴 장치도 없다.

그래서 다음 한 걸음은 큐를 표로 내리는 것이다. `SUM(plies)` 가 전역 값이 되고, 재시도와 크래시 복구가 같이 온다. **다만 그 전에 회차를 한 번 돌린다** — 지금 t4g.small 한 대에서 이 층이 실제로 밀리는지를 먼저 보고, 밀리는 모양을 보고 표의 모양을 정한다.

## 102. 보는 자리를 정했다 — CloudWatch 대시보드 한 장 (2026-08-24)

[§101](101-120.md)이 지표를 붙였는데 볼 화면이 없었다. 콘솔에서 그때그때 위젯을 고르면 축도 기간도 회차마다 달라져서 **「지난번보다 나아졌나」를 말할 수 없다** — 부하 회차가 여러 번 돌 것이라 그 물음이 성립하는 것이 화면의 첫 조건이다.

그래서 `infra/dashboard.tf` 한 장을 코드로 뒀다. 위젯 여섯이고 읽는 순서를 텍스트 위젯이 맨 위에서 말한다.

| 위젯                         | 답하는 물음                                             |
| ---------------------------- | ------------------------------------------------------- |
| 풀 대기 — **대국만 vs 전부** | 사람이 기다렸나. 갈라서 봐야 원인이 분석인지 알 수 있다 |
| 분석 백로그(手) · 버려진 판  | 이 층이 어디서 꺾이나                                   |
| 탐색 시간 · 점유             | 원인이 줄인가 CPU인가                                   |
| 캐시 히트율                  | 회차가 中盤에 들어간 지점                               |
| 세션 · 요청                  | 부하의 크기                                             |
| 5xx · panic                  | 사고                                                    |

### 그라파나를 안 쓰기로 한 이유

**해상도와 분위수는 그라파나 쪽이 낫다.** EMF 는 1분에 한 줄이고 표본 배열을 100개로 솎아 보내므로 p95 가 근사값인데, `/metrics` 텍스트 표면은 히스토그램 버킷을 온전히 들고 있다(`_bucket{le=…}`). 프로메테우스로 15초마다 긁으면 그 버킷을 그대로 쓴다.

그런데 지금 그것을 붙이면 **관측 스택이 측정 대상의 CPU를 먹는다.** 태스크가 2 vCPU 인데 엔진이 최대 셋 돌고, 같은 박스에 Prometheus·Grafana 를 얹으면 회차의 결론이 「엔진이 느리다」인지 「관측이 가져갔다」인지 갈리지 않는다. `network_mode = host` 라 포트도 손으로 갈라야 하고, `/metrics` 에는 인증이 없어서 밖에 열 수도 없다.

|           | CloudWatch                                   | 그라파나 + 프로메테우스     |
| --------- | -------------------------------------------- | --------------------------- |
| 만드는 데 | 파일 하나                                    | 스크랩 경로·저장소·인증까지 |
| 해상도    | **1분 고정**                                 | 15초                        |
| 분위수    | 솎은 표본의 근사                             | 버킷 기반                   |
| 보존      | 15개월 롤업 — 회차 비교가 공짜               | 디스크가 내 일              |
| 비용      | 대시보드 3개 무료 · 커스텀 지표 13개 월 $4쯤 | 박스 하나 월 $12+           |

**정한 것: 1분으로 시작한다.** 백로그가 밀리는 것은 판 하나가 수십 초~몇 분인 현상이라 1분 평균에 보인다. 안 보이는 것으로 판명되면 — 백로그가 30초 만에 치솟았다 꺼져서 평균에 안 잡히면 — 그때 붙일 모양은 **부하 발생기 박스에 프로메테우스를 두고 회차 동안만 보안 그룹으로 `/metrics` 를 그 박스에만 여는 것**이다. 어차피 회차에 띄울 박스라 그릇이 공짜이고, 관측이 측정 대상과 CPU 를 안 나눈다.

즉 **CloudWatch 가 상시 표면이고 프로메테우스는 회차용 확대경**이다. 둘이 경쟁하지 않는다.

### 뒤늦게 걸린 것 — 정책에 대시보드 권한이 없었다

`show-gi-operator` 의 cloudwatch 권한이 알람용으로만 짜여 있어서(`PutMetricAlarm`·`DescribeAlarms`·`GetMetricData`·`ListMetrics`) apply 가 `AccessDenied` 로 막혔다. 파일에 넷을 더했고 **게시는 사람이 한다** — 정책을 스스로 넓힐 수 없는 것이 이 사용자의 설계다.

**정책이 상한에 가깝다.** 공백을 뺀 6,144자 상한에 지금 5,962자다 — 남은 182자면 액션 다섯쯤이다. 다음에 막히면 정책을 둘로 쪼갠다(사용자당 관리형 정책 10개까지).

**`GetMetricStatistics` 는 안 넣는다.** 없어서 CLI 조회가 한 번 막혔는데, 콘솔과 대시보드가 쓰는 것은 `GetMetricData` 이고 그쪽은 이미 있다 — 회차 중에 값을 읽을 때 `aws cloudwatch get-metric-data` 를 쓰면 되고, 182자를 옛 API 에 쓸 이유가 없다.

**게시하고 apply 했다**(2026-08-24). 대시보드가 실물로 섰고(3,780바이트) 값이 들어온다 — 배포 직후 20분에 `AnalysisBacklogPlies` 와 `WsSessionsActive` 가 둘 다 0이다. `EnginePoolWaitGameSeconds` 는 아직 계열이 없다: 표본이 0인 회차는 EMF 가 배열을 아예 안 내므로(빈 배열은 줄을 통째로 버리게 한다) **대국이 한 판 돌아야 그 위젯이 그려진다.**

apply 는 `-target=aws_cloudwatch_dashboard.main` 으로 겨냥해서 돌렸다. 전체 apply 는 태스크 정의를 새 리비전으로 바꾸려 하는데(CI 가 등록한 것과 테라폼이 그리는 것이 `hostPort`·빈 배열에서 어긋나 있다) 서비스가 `ignore_changes = [task_definition]` 라 배포로는 안 이어진다 — 그래도 회차 직전에 건드릴 이유가 없다.

## 103. 부하 도구가 생겼다 — 규칙을 모르는 k6 스크립트 (2026-08-24)

「동시에 몇 판까지 되나」가 [§91](82-100.md) 이후로 열려 있었다. 세 판을 동시에 걸었더니 풀 대기가 269표본 전부 0이라, 곡선이 무너지는 지점이 **네 판 이상**에 있다는 것만 알고 그 위를 못 재 봤다. → **이 「네 판 이상」은 틀렸다. 프로덕션에서는 세 판째가 이미 기다린다([§104](101-120.md)).**

`tools/loadtest/` 에 k6 스크립트를 뒀다. 셋을 한 입구에서 고른다 — `MODE=engine` · `match` · `both`.

### 정한 것 넷

**① k6 로 간다.** 처음에는 Go 도구를 생각했는데 이유 하나가 틀렸다 — 「합법수를 스스로 골라야 하니 `internal/shogi` 가 필요하다」고 봤지만, **서버가 스냅샷마다 `legalMoves` 를 통째로 준다**(api.md §5). 그러면 규칙 엔진이 필요 없고, k6 가 이미 갖고 있는 것(시나리오·ramping·백분위·태그·공식 컨테이너 이미지)이 우리가 안 짜도 되는 것이 된다. 쿠키 서명도 `k6/crypto` 로 다섯 줄이다.

**② 부하 단위는 동시 판수다.** `constant-vus` 로 두고 **VU 하나가 판 하나**다. 초당 도착률로 말하면 이 앱에서는 아무것도 안 보인다 — 판 하나가 연결 하나를 몇 분 잡는다.

**③ 手数 상한을 우리가 정한다**(`MAX_PLIES`, 넘으면 投了). 무작위로 두면 판이 잘 안 끝나서, 분석에 들어가는 手数 분포가 실제 대국과 달라진다.

**④ 사람은 만들고 로그인은 안 한다.** `provider='loadtest'` 로 시딩하고 쿠키는 도구가 굽는다. 정리가 한 줄이다(`DELETE FROM users WHERE provider='loadtest'` — FK 가 전부 CASCADE 다).

### 도구를 짜면서 물린 것 둘

**같은 手에 두 번 보내면 거절된다.** 내 차례인 스냅샷이 한 手에 여러 번 온다 — 힌트가 도착하거나 상대의 세기가 바뀌면 전체 상태가 다시 나가기 때문이다(부분 갱신이 없다). 두 번째 착수는 판정 중에 도착해 `not_your_turn` 이다. 手数로 걸러 닫았다.

**물러진 수를 다시 고르면 판이 그 자리에 선다.** 개입은 手数를 되돌리므로 도구가 「다시 둬야 하는 자리」로 알아야 하는데, 같은 수를 또 고르면 같은 카드가 다시 오고 그것을 「이미 답한 카드」로 보고 넘긴다 — 서버의 60초 시한이 풀어 줄 때까지 멈춘다. **후보에서 물러진 수를 빼는 것**으로 닫았다. 멈춘 판을 세는 지표(`showgi_stalls`)와 우리 쪽 시한도 같이 뒀다.

### 로컬 실측 — 도구가 실제로 판을 끌고 간다

`MODE=both` · VU 2+2 · 75초 · `MAX_PLIES=24` (맥, 로컬 api 컨테이너):

|                       | 값                                |
| --------------------- | --------------------------------- |
| 판 · 手               | **72판 · 886手**                  |
| 개입                  | 38건                              |
| 거절 · 멈춘 판        | **0 · 0**                         |
| 착수 왕복 (대인전)    | 중앙값 **2ms**                    |
| 착수 왕복 (엔진 대국) | 중앙값 **633ms** · p95 1.54s      |
| 짝 잡히기까지         | 중앙값 **2s** (폴링 간격이 2초다) |

**대인전의 2ms 가 「두는 동안 엔진이 0」을 숫자로 확인한다.** 같은 판을 두는데 엔진 대국은 그 300배다. → **그 0은 [§105](101-120.md)에서 의도적으로 깨졌다** — 판이 끝나는 순간의 봉우리를 없애려고 手마다 미리 재기 시작했다. 착수 경로는 여전히 엔진을 안 지난다.

그리고 [§101](101-120.md)의 지표가 실제로 움직였다.

| 지표                                 | 값                                     |
| ------------------------------------ | -------------------------------------- |
| `analysis_backlog_games` · `_plies`  | **19판 · 456手** 밀렸다                |
| `analysis_game_duration_seconds`     | 10판 82.6초 → **판당 8.3초**(24手)     |
| `engine_pool_wait_seconds{borrower}` | game 402 · **analysis 333** · quiz 120 |

**밀린다는 것은 로컬에서도 보였다.** 대인전 판이 몇 초에 하나씩 끝나는데 분석은 판당 8초를 쓰니, 75초 회차가 끝난 뒤에도 19판이 줄에 남아 있었다.

**그런데 대국은 안 굶었다** — `borrower=game` 의 풀 대기가 402표본 전부 1초 이내이고 평균 29ms 다. 맥의 코어가 많아서 그렇다. **그래서 이 물음은 프로덕션에서만 답이 난다**: 2 vCPU 를 엔진 최대 셋이 나눠 쓰는 곳에서 같은 회차를 걸어야 `borrower=game` 이 튀는지 알 수 있다.

### 곁다리 — 주소 조각을 못 믿기로 했다

CodeQL 이 열어 둔 알림 셋이 같은 자리였다(`js/client-side-unvalidated-url-redirection`, 2026-08-17~19). 되짚기 링크 셋이 **서버가 준 판 번호를 그대로 `href` 에 이어 붙인다** — 타입은 `number` 인데 실제 값은 JSON 이라, 문자열이 오면 `/reviews///example.com` 이 만들어지고 그건 내부 링크가 아니라 외부 이동이다.

세 자리가 `routeReview` 하나를 지나므로 거기서 못 박았다. **판 번호는 1 이상 정수**(`games.id` 가 bigserial 이라 0이 없다 — 그래서 `Number('')` 이 0인 함정도 같이 닫힌다), **手数는 0 이상**, 아니면 목록으로 떨어뜨린다. 방 id 도 같은 성질이라 영숫자만 통과시킨다(서버의 `roomIDAlphabet` 과 같은 글자).

**실제로 도달하는 경로는 아니었다** — 오염원이 우리 서버다. 고친 이유는 그 보장이 타입에만 있었다는 것이고, 타입은 런타임에 없다.

## 104. 프로덕션에 처음 부하를 걸었다 — 벽은 2 vCPU 이고 §91은 재현되지 않았다 (2026-08-24)

[§103](101-120.md)이 도구를 남기고 「아직 프로덕션에서 안 걸었다」를 열어 뒀다. 2026-08-23 20:14 부터 20:45 (UTC) 까지 계단으로 걸었다 — `MODE=engine` · `MAX_PLIES=60`, 클라이언트는 도쿄라 같은 리전이다(TCP connect 13~24ms).

### 실측 — 계단 다섯

풀 대기와 탐색은 1분 창 p95 의 범위다. 알람이 보는 5분 창은 아래 ④에 따로 있다.

| 동시 판수 | 판 · 手  | `move_cycle` 중앙값 | p95         | 풀 대기(대국) p95 | 탐색 p95        | 멈춘 판 |
| --------- | -------- | ------------------- | ----------- | ----------------- | --------------- | ------- |
| 1         | 3 · 96   | **1.84초**          | 4.62초      | **0.0**           | 2.0~3.9초       | 0       |
| 3         | 4 · 296  | 3.12초              | 7.80초      | **1.40~2.36**     | 2.8~5.1초       | 0       |

| 8         | 10 · 541 | **1.00초**          | **16.50초** | 3.14~**8.79**     | 3.8~**10.94초** | 4       |

**거절 0 · 5xx 0 · panic 0** — 끝까지 그랬다. 즉 **깨지는 지점에는 닿지 못했다.** 8판에서 멈춘 것은 미리 그렇게 정했기 때문이고, 아래 표가 보여주는 것은 **대기가 시작되는 곳**(세 판째)과 그 뒤의 곡선이다. 「동시 몇 판에서 무너지나」는 여전히 안 쟀다 — 계단을 더 얹어야 한다.

**VU 수는 사람 수보다 크게 읽어야 한다.** 도구는 자기 차례가 된 그 순간 두므로 생각 시간이 0이다. 사람이 한 수에 T초를 쓰면 엔진 수요가 `2.15/(2.15+T)` 로 줄고(2.15초는 동시 1판의 착수 왕복 평균), **T=3초면 8판이 사람 20명쯤**이다. 이 회차는 그 보수적 쪽을 의도해서 골랐다 — 8판에서 버티면 사람 8명에서는 확실히 버틴다. 다만 평균 수요 얘기라 **사람 20명이 순간적으로 동시 8판을 넘는 일은 생긴다.** 판은 45판 · 2,216手이고 개입 645건이다. 끝난 판은 24판(전부 사람 패)이고 21판은 도구의 시한이 끊어 `abandoned` 로 남았다.

**규칙으로 끝난 판이 하나도 없다.** 완주한 24판이 **전부 정확히 60手**이고, 나머지 21판은 우리 시한이 자른 것이다(12~56手, 평균 37). 상대에 밴드 제어가 걸려 있어 판을 벌리지 않으므로 `MAX_PLIES` 가 닿기 전에는 안 끝난다 — 그래서 **詰み도 終盤도 이 회차에서 한 번도 안 돌았고**, mate 풀은 사실상 유휴였다. 분석 층이 본 것도 초반·中盤뿐이다. 다음 회차는 상한을 **100手** 로 올린다.

**엔진이 시한을 넘긴 판은 DB로 셀 수 없다.** `internal/game` 은 상대 수를 60초 안에 못 얻으면 판을 `StatusAborted` 로 접고 화면에 `相手の思考が終わりませんでした` 를 낸다 — 승패를 지어내지 않는 자리다. 그런데 `recorder.go` 의 `resultOf` 가 **승자로만 분기**해서 그 판이 `abandoned` 로 저장된다. **「엔진이 멈췄다」와 「사람이 탭을 닫았다」가 DB에서 같은 값이다.** 이 회차에서 그 로그는 안 나왔지만, 「깨질 때까지」 올리는 회차에서는 그것이 가장 깨끗한 깨짐 신호다.

**그래서 DB 가 아니라 지표로 세기로 했다.** `games.result` 에 값을 하나 더하는 길도 있었는데, `abandoned` 가 「이어할 수 있다」를 뜻해서 질의 셋이 그 값을 조건으로 쓴다(`ResumableGame`·`ClaimGameForResume`·거절) — 값을 가르면 **엔진이 멈춰서 끊긴 판을 사람이 못 잇게 된다.** 우리 잘못으로 끊긴 판에 그건 틀린 처분이다. `game_finished_total{status}` 를 새로 두고 EMF 가 `GamesAborted` 로 내보낸다(대시보드에도 얹었다). 대인전은 `FinishedWith` 로 결과를 적어 이 자리를 안 지나므로 엔진 대국만 세어진다.

**「엔진이 멈춘 판」과 「창을 닫은 판」이 이어하기에서 여전히 같이 취급되는 것**은 남았다 — 그건 사용자에게 뭐라고 말할지의 문제라 지표로 닫히지 않는다(§5).

**계단을 연달아 돌리면 앞 회차가 뒤를 오염시킨다.** 알람이 8판 회차 시작 1분 뒤에 울렸는데 그것은 6판 회차의 5분 창이 절반을 채워서였다. 분석 백로그도 같은 성질이다 — **계단 사이에 백로그와 세션 수가 0으로 돌아오는 것을 확인하고 다음으로 간다.**

**캐시 히트율 42.0%(탐색 5,563 · 적중 2,336)는 좋은 소식으로 읽으면 틀린다.** 45판이 전부 같은 0手目에서 시작하니 초반 手가 판마다 겹친다 — [§91](82-100.md)이 갈라 둔 「초반 65.7% · 中盤 2.3%」의 초반 쪽을 회차 구성이 부풀린 것이다. **이 숫자로 中盤 선행 계산의 필요를 판단하지 않는다.**

### 알게 된 것

**① §91이 재현되지 않는다. 벽은 세 판째다.** [§91](82-100.md)은 3판 동시에서 풀 대기 269표본이 전부 0이었고, [§103](101-120.md)은 그래서 곡선이 무너지는 지점을 「네 판 이상」에 뒀다. 프로덕션에서는 **3판에서 이미 p95 1.4~2.4초**다. `pool_inuse` 가 내내 2에 붙어 있었으니 이유는 하나다 — `ENGINE_POOL_SIZE=2` 라 세 번째 판에는 빈 엔진이 없다.

**② 풀을 올리는 것이 답이 아니다. CPU다.** 탐색 p95 가 동시 1판 2.0초에서 8판 **10.94초**로 5배가 됐고, 그동안 풀은 2에 고정이었다. `ENGINE_POOL_SIZE=2` + mate 1 + 사후 분석이 **2 vCPU 에 엔진 셋**을 얹는다. 풀을 4로 올리면 대기가 탐색 시간으로 옮겨갈 뿐이다 — **남은 것은 수직 스케일이다.**

**③ 균등하게 느려지지 않는다. 일부가 굶는다.** 8판 동시에서 `move_cycle` 중앙값이 **1초**인데 p95 가 16.5초다(4판은 중앙값 4.4초 · p95 8.3초). 중앙값이 내려가면서 p95 가 오르는 것이 줄서기의 모양이고, 멈춘 판이 0→1→2→4로 늘었다.

**④ 알람이 5분 창으로는 못 잡았다.** 5분 창 p95 를 순서대로 보면 `0.54 → 2.16 → 2.22 → 3.28 → 4.29 → 7.43` 이고, 알람은 8판 회차 시작 1분 뒤에 울렸다 — **6판 5분과 8판 5분이 연달아 돌아서** 두 회차가 채워진 것이다. **6판에서 멈췄으면 1분 p95 가 5초였는데도 메일이 안 갔다.**

그래서 `period=60` · `evaluation_periods=5` · `datapoints_to_alarm=3`(최근 5분 중 3분)으로 바꾸고, 보는 계열을 합친 값에서 **`EnginePoolWaitGameSeconds`** 로 옮겼다. 합친 값은 분석·검토가 섞여서 튀어도 사람이 기다린 것인지 알 수 없다. **표본이 적을 때 1분 p95 가 튀는 함정은 이 지표에 없다** — 풀이 2라 한두 판이 겹칠 때 대기가 구조적으로 0이고, 동시 1판 실측이 0.0 이었다. 임계 3초는 그대로 뒀고 이제 실측 근거가 있다 — 3판이 2.4초, 4판이 3.5초라 3초는 네 판째를 잡고 세 판째를 넘긴다.

**⑤ 엔진 대국 쿠키가 프로덕션에서 동작한다.** 45판 전부 `games.user_id` 가 채워지고 익명은 0이다. 회차 전에 프로덕션에는 **익명 판이 이미 68개** 있었으므로(전체 74판), 이것이 없었으면 회차가 만든 판을 골라낼 수 없었다.

**⑥ 사후 분석은 이 완주율에서 안 굶겼다.** 백로그가 내내 0이고 버린 판도 0이며, 2,216手 중 **2,183手(98.5%)** 에 평가치가 채워졌다 — 백로그 0이 「안 돌았다」가 아니라 「밀리지 않았다」다.

다만 공짜는 아니다. `EnginePoolWaitSeconds`(전부, 8.46초)와 `EnginePoolWaitGameSeconds`(대국만, 8.77초)가 거의 같아서 **분석도 같은 8초를 기다렸다.** 그리고 **완주율을 올리면 어떻게 되는지는 안 쟀다** — 31분에 45판이라 판당 3~4분이고, [§103](101-120.md)의 로컬 회차(75초에 72판)와 두 자릿수로 다르다. `MAX_PLIES=24` 회차가 남았다.

### 곁다리 — 커넥션 풀이 4이고 재는 눈이 없다

`internal/store/store.go` 가 `pgxpool.New(ctx, url)` 뿐이고 `DATABASE_URL` 에도 `pool_max_conns` 가 없어서, pgx 기본값 `max(4, NumCPU)` 가 그대로 산다. 2 vCPU 라 **4**이고 태스크가 한 대라 그것이 전부다. 프로덕션 `max_connections` 는 **79** 라 DB 쪽은 남는다.

착수 경로에 동기 질의가 없어서(기록은 대국마다 goroutine 하나가 버퍼 256 채널로 받는다) 이 회차에서 4는 안 걸렸다. **그런데 걸렸는지를 지표로 볼 수 없다** — `pool.Stat()` 호출부가 레포에 없어서 대기가 커넥션 때문인지 엔진 때문인지 못 가른다. 포화되면 기록 큐가 차서 이벤트를 버리고 로그에 남는데(`game record: queue full`), 이번 회차에는 그 줄이 없었다.

## 105. 대인전에 처음 부하를 걸었다 — 부하가 쌓이는 방식이 엔진전과 다르다 (2026-08-24)

[§104](101-120.md)가 엔진 대국 계단을 끝내고 「대인전은 프로덕션에서 한 번도 안 돌았다」를 남겼다(`games.match_id IS NOT NULL` 이 0). 2026-08-23 22:01 부터 22:24 (UTC) 까지 걸었다 — `MODE=match` · `MAX_PLIES=100` · VU 4.

### 실측 — 회차 둘

VU 하나가 사람 하나이므로 **사람 넷 · 동시 2방**이다.

| 회차 | 길이     | 완주한 판 | 도착        | `move_cycle` 중앙값 | 큐 대기 중앙값 | 백로그 최고        | 버린 판  | 5xx · panic |
| ---- | -------- | --------- | ----------- | ------------------- | -------------- | ------------------ | -------- | ----------- |
| A    | **93초** | 54판      | 36판/분     | **23ms**            | 2.02초         | 5,223手            | 0        | 0           |
| A′   | **3분**  | 112판     | **37판/분** | 22ms                | 2.02초         | **6,317手 ≈ 63판** | **44판** | 0           |

**착수에 엔진이 안 들어간다.** `move_cycle` 중앙값 22~~23ms 는 순수 왕복이고(클라이언트가 도쿄, TCP 13~~24ms), p95 도 28~30ms 다. 엔진 대국의 같은 값이 동시 1판에서 1.84초 · 8판에서 p95 16.5초였다([§104](101-120.md)) — **세 자릿수 차이**다. 대인전 프로토콜에 개입도 힌트도 없어서(`api.md` §6) 착수 경로가 판정을 안 지난다.

**그래서 100手 판이 2초에 끝난다.** 판당 3.4초(큐 대기 1.2초 + 대국 2.2초)이고, 그것이 도착률 37판/분을 만든다.

### 알게 된 것

**① 부하가 쌓이는 방식이 엔진전과 다르다.** 엔진 대국은 착수마다 2 vCPU 를 물어 판이 느려지고, 그래서 부하가 판 길이에 퍼진다. 대인전은 착수가 공짜라 판이 초 단위로 끝나면서 **끝나는 순간 100手를 한꺼번에 사후 분석 큐에 던진다.** 같은 手数인데 한쪽은 실시간 경합이고 한쪽은 후불 부채다.

**② 배수구가 0.64판/분이다.** 백로그가 5,223手 에서 4,523手 로 내려가는 데 11분 걸렸다 — **64手/분**이고 100手 판 하나에 1.5~2분이다. → **이 값을 용량 상한으로 읽으면 틀린다**([§106](101-120.md)): 워커가 하나라 엔진 둘 중 하나만 쓰므로, 이것은 박스의 절반을 잰 값이다. 워커가 하나이고(`go a.run(ctx)`) `EnginePoolInUse` 가 내내 1이라 엔진도 하나다. 매 手가 탐색 하나가 아니라 詰み solver 까지 부르는 것이 이 값의 이유다.

**도착이 배수구의 58배다.** 사람 넷이 1분 33초 두면 엔진이 100분을 갚는다 — A 회차가 남긴 5,223手 가 그것이다.

**③ 지속 한계는 동시 6쌍이다.** 사람 둘이 100手를 10분에 두면 쌍당 0.1판/분이니 0.64판/분을 나눠 **약 6쌍(12명)** 에서 도착이 배수구를 따라잡는다. → **사람 속도로 재 보니 4판(8명)에서 버티고 6판(12명)에서 포화였다**([§106](101-120.md)) — 계산과 자리는 비슷한데 근거가 다르다: 여기는 일괄 배수 속도로 나눈 값이고 저기는 실측 계단이다. 그 위에서는 백로그가 영구히 자란다. **A·A′의 도착률 자체는 인공물이다** — 사람이 100手를 2초에 둘 수 없다. 인공물이 아닌 것은 배수구 쪽이고, 그것이 이 한계를 정한다.

**④ 부채 창 동안 라이브 대국이 엔진 하나로 돈다.** 갚는 내내 `EnginePoolInUse` 가 1이고 풀은 2다. [§104](101-120.md)의 「3판째부터 기다린다」가 그 창 안에서는 **1판째부터**가 된다 — 백로그는 조용한 백그라운드가 아니라 사람의 대국이 느려지는 창이다.

**⑤ 큐 상한 64판에 2분 안에 닿는다.** A′의 백로그 최고가 6,317手 ≈ 63판으로 `analysisQueue = 64` 에 붙었고, 넘친 44판을 버렸다. 계산값이 64 ÷ (37 − 0.64) ≈ 1분 46초이고, 버린 판이 회차의 두 번째 분에 처음 올랐다. **5xx·panic 은 0이다** — 설계대로 판이 끝나는 자리를 막지 않고 흘려보냈다(`enqueue` 의 `default`).

**⑥ 버리는 두 경로 중 하나가 지표에 안 잡혔다.** 큐가 꽉 차서 버린 44판은 `AnalysisGamesDropped` 에 올랐다. 그런데 **재배포로 잃은 46판은 안 올랐다** — 백로그 4,523手 가 0으로 사라지는 동안 그 카운터는 0이었다. 종료 자리에서 세는 코드가 없었고, 되짚기는 두 경우를 구별하지 못하므로(`analyzing` 이 false 라 「남지 않았다」로 굳는다) **그 지표가 유일한 눈이다.** 이번에 `abandonOnStop` 을 붙여 세운다.

**세는 자리를 워커에서 뗐다.** 워커는 한 판을 몇 분씩 재고 있어서, 그 판이 풀린 뒤에 세면 `main` 이 이미 마지막 EMF 줄을 낸 뒤다(`startEmitter`).

**재적재는 없다.** `enqueue` 호출부가 판 끝나는 자리 하나뿐이고(`match_records.go`) 시작 시 되채우는 질의가 없다 — 그 46판은 영구히 평가치가 없다(56판 중 분석 완료가 10판에서 멈췄다).

**⑦ 레이팅과 실력 추정이 실물로 돈다.** [§95](82-100.md)가 「실물로는 안 돌았다」로 남겼던 자리다. VU 넷이 쓴 id 5~8 만 움직이고 나머지 여덟은 그대로다.

| id  | `rating_est`      | `rating_sd`   | `rating_games` |
| --- | ----------------- | ------------- | -------------- |
| 5   | 1200 → **1259.7** | 80 → **53.1** | 10 → 38        |
| 6   | 1300 → **1335.7** | 80 → 53.5     | 10 → 37        |
| 7   | 1400 → **1350.0** | 80 → 52.9     | 10 → 38        |
| 8   | 1500 → **1454.5** | 80 → 53.1     | 10 → 39        |

넷이 서로를 향해 수렴하고 RD 가 80→53 으로 줄었다 — 무작위 수를 두는 실력이 같은 넷에게 Glicko 가 내야 하는 답이 그것이다. 짝은 중앙값 2.02초에 잡혔다(밴드 실측이 아니다 — 심긴 레이팅의 최소 쌍거리가 100 이라 처음 밴드 360 안에 전부 들어간다).

**⑧ 대인전은 `GamesAborted` 를 안 지난다.** 그 계열은 [§104](101-120.md) 뒤로 값이 오고 있고(차원까지 확인했다) 내내 0이다. 대인전이 `FinishedWith` 로 결과를 적어 그 자리를 비껴가므로 **엔진 대국 회차만 그 계열을 0 아닌 값으로 만들 수 있다.**

### 정한 것 — 도구에 생각 시간을 넣는다

`THINK_MS` 를 뒀고 기본은 0이다(지금까지의 회차와 그대로 견줄 수 있다). **대인전 회차는 이것을 켜고 돌린다** — 3초면 100手 판이 5분이 되어 쌍당 0.4판/분이고, 배수구 0.64판/분 아래라 사람의 도착률이 된다.

**VU 수를 낮추는 것으로는 안 된다.** 도착률이 250배 어긋나 있어서 배수로 줄일 값이 아니다.

**켜면 VU 수가 곧 사람 수다.** [§104](101-120.md)의 「VU 하나는 사람 하나보다 크다 · T=3초면 8판이 사람 20명」 환산이 그때 없어진다 — 환산을 없애는 쪽이 재는 눈으로 낫다.

**엔진 대국에는 없어도 된다.** 엔진의 탐색 시간(2~11초)이 저절로 페이서가 되어 도구가 상대를 기다린다. 대인전만 양쪽이 다 도구라서 기다릴 것이 없다.

### 정한 것 — 사후 분석을 手 단위로 미리 잰다

**봉우리가 판 단위 큐에서 온다.** 100手 판이 끝나는 순간 100手가 한 칸에 들어가고 칸이 64개라 최악이 6,400手인데, 위 ⑤가 그 6,317手다. 그런데 **대인전을 두는 동안 엔진은 완전히 유휴다** — 착수가 왕복 22ms 라 그 시간을 그대로 버린다.

그래서 **手마다 미리 재고 판이 끝날 때 그 결과로 채운다.** `matchRecorder.Moved` 가 手를 미리 재는 줄에 세우고(논블로킹이라 착수를 안 막는다), 판이 끝나면 미리 잰 것을 꺼내 평가치를 쓰고 실력을 커밋한다.

**총 처리량은 안 늘어난다.** 판당 엔진 일이 94초로 고정이라 언제 하든 같고 지속 한계 0.64판/분도 그대로다. 얻는 것 셋:

|     |                                                                           |
| --- | ------------------------------------------------------------------------- |
| 1   | **봉우리가 사라진다.** 판이 동시에 끝나도 일이 이미 대국 시간에 퍼져 있다 |
| 2   | **되짚기가 판이 끝나는 순간 준비된다.** 지금은 최소 1.6분, 밀리면 몇 시간 |
| 3   | **종료로 잃는 것이 판 전체가 아니라 남은 몇 手가 된다** (⑥)               |

**버려도 잃는 것이 없는 것이 이 설계의 핵이다.** 미리 재는 줄이 차면 그 手를 그냥 버리고, 판이 끝날 때 그 자리에서 잰다 — 즉 **미리 재는 쪽은 캐시이고 판이 끝나는 쪽이 정본이다.** 그래서 `whole` 판정·실력 창(21~60手)·`Before`/`After` 덮어쓰기 순서를 하나도 안 건드렸다.

**한 手가 실패하면 그 판은 그만둔다.** 뒤의 手도 전부 같은 자리에서 실패하므로(`analyze` 의 같은 판단) 안 그만두면 남은 手数만큼 탐색을 버린다.

**`AnalysisBacklogPlies` 의 뜻이 바뀌었다.** 이제 **미리 재는 줄의 길이 + 판이 끝날 때 아직 안 잰 手数**다. 그래서 **이 값이 0 근처인 것이 「미리 재는 쪽이 따라가고 있다」**이고, [§101](101-120.md)~[§104](101-120.md)의 같은 이름 숫자와 직접 견줄 수 없다.

**그 대신 대인전이 대국 중에도 엔진을 쓴다.** 지금까지 착수 경로가 2 vCPU 를 안 썼는데([§83](82-100.md)의 표가 그것을 규약으로 적어 뒀다) 이제 같은 시간대의 엔진 대국과 다툰다. 총량은 같지만 **부하가 사람이 두는 시간과 반드시 겹친다** — 밤에 갚을 수도 있던 것을 안 그러게 만든 것이고, `borrower` 라벨이 그것을 갈라 볼 자리다([§101](101-120.md)).

**`THINK_MS=0` 짜리 부하 회차에서는 이 변경이 안 듣는다.** 판이 2초에 끝나면 미리 잴 시간이 없다 — 그래서 위 `THINK_MS` 와 한 벌이다: 도구가 사람 속도로 두면 미리 재는 쪽이 따라갈 시간이 생긴다.

### 곁다리 — 재기동이 40초짜리 백로그 리셋이다

계단 사이에 백로그를 0으로 돌려야 하는데([§104](101-120.md)) 스스로 마르는 데 100분이 걸렸다. `aws ecs update-service --force-new-deployment` 가 그것을 즉시 비운다 — `desiredCount=1` · `maximumPercent=100` 이라 낡은 태스크를 먼저 세우므로 **단절이 생긴다** — healthz 가 503 인 창이 약 50초였다.

부하 회차에서는 쓸 만한 손잡이다. 잃는 것이 회차가 만든 판의 평가치뿐이다. **다만 그것이 위 ⑥의 사고와 같은 동작이다** — 실사용자의 판에 대해서는 같은 재배포가 같은 것을 잃는다.

## 106. 대인전을 사람 속도로 걸었다 — 병목이 워커 하나이고 신호가 §104의 것이 아니다 (2026-08-24)

[§105](101-120.md)가 `THINK_MS` 를 두고 「대인전 회차는 이것을 켜고 돌린다」를 남겼다. 2026-08-23 23:18 부터 2026-08-24 00:50 (UTC) 까지 계단으로 걸었다 — `MODE=match` · `THINK_MS=3000` · `MAX_PLIES=100`, 계단마다 8분, 태스크 정의 116(手 단위로 미리 재는 코드가 든 첫 배포).

**4판 계단과 그 위 사이가 26분 비어 있다.** 그 사이에 스팟이 두 번 인스턴스를 가져갔다(아래 곁다리). 6·8·12판 계단은 회수 뒤에 새로 뜬 인스턴스에서 잰 것이라 **크레딧 이력이 4판 계단과 다르다** — 아래 ④를 그 사실과 같이 읽는다.

**VU 하나가 사람 하나다.** 생각 시간을 넣었으므로 [§104](101-120.md)의 환산이 없다 — 2 VU 가 판 하나다.

### 알게 된 것

**① 병목이 CPU 가 아니라 워커 하나다.** 백로그가 443까지 쌓인 포화 상태에서 `EnginePoolInUse` 가 **끝까지 1**이었고 풀은 2다. 워커가 하나라 동시에 탐색 하나뿐이고, **남은 엔진 하나가 그 내내 놀았다.** 풀 대기도 계단 넷 전부 마이크로초다.

**그래서 위 표의 용량은 박스의 절반만 쓴 값이다.** t4g.small 의 진짜 천장은 워커 수를 손잡이로 뺀 뒤에야 알 수 있다.

**② [§104](101-120.md)가 세운 알람은 이 포화를 못 본다.** 그 알람이 보는 계열이 `EnginePoolWaitGameSeconds` 인데 계단 넷에서 내내 마이크로초였다 — 병목이 풀이 아니라서다. **엔진 대국의 신호와 대인전의 신호가 다른 계열이다.**

**③ 신호가 둘로 갈린다.** 이른 신호는 **`EngineSearchSeconds`** 다 — 8판 계단에서 백로그가 아직 0인데 이미 3.25→6.48초로 두 배가 됐다. 확정 신호는 **`AnalysisBacklogPlies` 의 단조 증가**다. 12판 계단에서 36→47→108→301→339→443 이고, 같은 구간에 탐색 처리량이 237→143→127/분으로 **떨어졌다** — 처리량이 내려가면서 줄이 쌓이는 것이 포화의 모양이다.

**④ CPU 크레딧이 12판 계단에서 마른다.** `CPUUtilization` 평균이 31.6→**44.0**→21% 인데 t4g.small 의 baseline 이 20% 다. 크레딧 잔량이 3.61→2.08→**0.011** 로 내려갔다.

**그래서 T 계열 `standard` 에서 「용량」은 시간 제한이 붙은 값이다** — 「N판 버틴다」가 아니라 「N판을 몇 분 버틴다」다. 클래스별 용량표를 만들려면 이 축을 벗어나야 한다.

**⑤ 대기열 밴드가 처음으로 실제로 움직였다.** 6판 계단의 큐 대기가 중앙값 2.22초인데 **p90 30.06초 · 최대 34.76초**다. [§105](101-120.md)가 「밴드는 안 쟀다」로 남긴 자리인데, 재려고 만든 것이 아니라 **시드가 회차를 거치며 수렴해서** 생겼다 — id 5~~8 이 1318~~1396 으로 모였고 id 9·10 이 1600·1700 이라 그 사이가 밴드보다 멀다. 8판 계단에서 최대가 6.13초로 내려간 것은 후보가 늘어 밴드 안에서 빨리 붙었기 때문이다.

**밴드 실측으로 쓸 수 없다.** 시드를 의도한 폭으로 심은 것이 아니라 흘러간 값이라, 「밴드가 대기로 얼마나 넓어지나」는 여전히 `seed.sql` 을 사람 둘 · 폭 700 으로 심는 회차가 답한다.

**⑥ 같은 판 안의 手 순서는 `analyze` 가 보장한다.** `setEval` 호출부가 레포에 그 순차 루프(`for ply := 1; ply <= len(moves); ply++`) 안 두 곳뿐이다. 미리 재는 쪽은 DB 를 안 만지고 手数를 키로 한 맵에만 쓰므로 **계산이 어떤 순서로 끝나든 결과가 같다.**

순서가 필요한 이유가 그 루프에 있다 — ply N 이 자기 칸에 `afterCp` 를 쓰고 ply N+1 이 그 칸을 `beforeCp` 로 덮는다. 오름차순이어야 최종값이 맞다.

**워커를 늘려도 이 보장은 안 깨진다.** 다만 그때 같은 판의 `analyze` 와 늦은 미리 재기가 동시에 돌 수 있고, `discard` 뒤에 도착한 쪽이 맵 항목을 다시 만들어 **판마다 하나씩 샌다.** 워커를 손잡이로 빼는 회차에서 같이 막는다.

### 곁다리 — 스팟이 두 번 가져갔고 26분 내려갔다

계단 도중에 프로덕션이 두 번 죽었고 두 번째는 **26분** 내려가 있었다. 부하 때문이 아니다.

**종료 이유는 `StateReason.Code` 에만 있다.** `Server.SpotInstanceTermination` 이다. `StateTransitionReason` 은 둘 다 `Service initiated` 라서 **그것만 보면 스팟 회수인지 알 수 없다** — 이 회차에서 한 번 그렇게 오진했다.

순서가 두 번 다 같았다.

|     |                                                |
| --- | ---------------------------------------------- |
| 1   | 스팟 2분 예고 → ECS 가 태스크를 뺀다(드레이닝) |
| 2   | ALB 에 정상 타깃이 0 → 들어오는 요청이 **503** |
| 3   | 도구가 그 503 으로 회차를 중단                 |
| 4   | 그로부터 90초쯤 뒤 인스턴스가 실제로 종료      |

**그 503 은 앱 지표에 안 남는다.** 요청이 앱에 닿지 않으므로 `HttpServerErrors` 가 0이다 — 「도구는 5xx 를 봤는데 서버는 0」이면 앞단을 봐야 한다는 뜻이고, 이번에 그것을 앱의 문제로 한 번 오진했다.

**26분은 대체가 안 됐기 때문이다.** ASG 가 2분마다 재시도했고 전부 `There is no Spot capacity available` 이었다 — `ap-northeast-1a`·`1c` 둘 다 t4g.small 스팟 재고가 없었다. **회수가 일어난 이유와 대체가 안 되는 이유가 같은 것이다**: 그 시각 그 리전에 그 타입이 말랐다.

**ASG 의 health check 가 `EC2` 라 앱 상태를 아무도 안 본다.** 앱이 느려지거나 죽어도 인스턴스는 교체되지 않고, 종료된 것을 뒤늦게 치우는 것이 이 설정의 전부다. 부하로 박스가 교체될 걱정은 없다는 뜻이기도 하다.

### 정한 것 — 회차의 목적을 오토스케일로 못 박는다

**목표는 사용자 수를 키우는 것이 아니라, 늘어난 것을 자동으로 감지해 스케일하는 구조와 「어느 수준에 어떤 클래스 몇 대」 표다.** 그 관점에서 오늘 막힌 것이 셋이고, 셋 다 수치보다 먼저다.

|     |                                                                                                                                                                                                                   |
| --- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | **대수를 늘리면 대인전이 깨진다.** 방이 짝지은 인스턴스의 프로세스 메모리에 선다([§98](82-100.md)) — 태스크가 둘이면 서로 다른 태스크가 지은 짝이 같은 방에 못 들어간다. 「몇 대」는 이걸 고치기 전에는 값이 없다 |
| 2   | **정책이 읽을 지표가 인스턴스별이다.** 분석 큐가 프로세스 안의 채널이라 `AnalysisBacklogPlies` 가 합이 안 된다([§101](101-120.md)) — 그 값으로 정책을 걸면 한 대의 줄을 전체로 읽는다                             |
| 3   | **알람이 이 포화를 못 본다**(위 ②). 스케일 신호를 `EngineSearchSeconds` + 백로그로 다시 정해야 한다                                                                                                               |

**수직도 필요하다.** 표의 기울기를 얻으려면 클래스가 둘 이상이어야 하고, 위 ④ 때문에 **두 번째 줄은 비버스터블이어야 한다.**

**그 전에 워커 수를 손잡이로 뺐다**(이 회차에서 같이). 손잡이는 `ANALYSIS_WORKERS` 이고 **기본값이 풀 크기와 같다** — 위 ①이 「올려도 안 빨라진다」였고 그 자리를 닫는다.

**「풀보다 하나 적게」를 먼저 지었다가 걷었다.** 라이브 대국이 빌릴 엔진을 남긴다는 뜻이었는데, 풀에 예약 기능이 없어서 그것이 **상한일 뿐 예약이 아니다** — 남긴 하나를 라이브끼리 서로 기다리므로 지연은 안 막고 분석 처리량만 깎는다.

**대신 풀이 우선순위로 빌려주게 고쳤다.** 그것이 「다 가져가도 된다」를 정당하게 만드는 자리다.

| 대기줄 | borrower                      | 왜                                                   |
| ------ | ----------------------------- | ---------------------------------------------------- |
| 먼저   | `game` · `explore` · `whatif` | 사람이 화면 앞에서 그 응답을 기다린다                |
| 나중   | `analysis` · `quiz`           | 아무도 안 기다린다 — 되짚기가 나중에 폴링해서 받는다 |

**대국 안에서 판정과 상대 수를 더 가르지 않는다.** 둘이 같은 사람의 대기 안에서 차례로 일어나므로(사람이 두면 → 판정 → 탐색 → 스냅샷) 순서를 바꿔도 그 사람이 기다리는 총 시간이 같다. 라벨도 이미 하나다(`BorrowerGame`).

**교착은 구조로 없다.** 판정이 엔진을 한 번에 하나만 쥔다 — `SearchDepth` 두 번이 각각 빌리고 즉시 반납하고, 詰み solver 는 다른 풀이다. hold-and-wait 이 없으니 워커가 풀보다 많아도 안 선다.

**줄을 채널에서 손으로 바꿨다.** 채널은 먼저 기다린 쪽에 주므로 우선순위를 못 얹는다. 바꾸면서 닫은 함정이 하나다 — **넘겨주는 쪽이 골랐는데 받는 쪽이 그 사이에 포기하면** 그 엔진이 아무 줄에도 없게 된다. 포기하는 자리가 버퍼를 비워 돌려준다(`giveUpWaiting`).

**워커가 여럿일 때 새는 자리도 같이 막았다.** 같은 판의 `analyze` 와 늦은 미리 재기가 겹칠 때 뒤엣것이 방 자리를 다시 만들면 아무도 안 지운다 — 그래서 **자리를 만드는 것은 `prefetch` 하나로 못 박았다.** 그쪽은 판이 살아 있는 동안에만 불리므로 `analyze` 보다 반드시 먼저다.

**`MODE=both` 은 이제 전보다 값이 있다.** 오늘 대인전 계단에서 풀 대기가 끝까지 마이크로초였으므로 `borrower` 라벨은 아직 한 번도 갈려 본 적이 없다. 그런데 [§105](101-120.md)의 변경으로 대인전이 대국 중에 엔진을 쓰기 시작했으니, 그 회차가 [§101](101-120.md)이 물으려던 「분석과 대국이 서로를 굶히나」를 처음으로 실제로 답한다.

## 107. 우선순위 풀을 배포하고 다시 쟀다 — 12판 계단이 뚫렸다 (2026-08-24)

[§106](101-120.md)이 「병목은 워커 하나」를 남기고 손잡이와 우선순위를 같이 넣었다. 태스크 정의 117로 배포한 뒤 같은 계단을 다시 걸었다 — `MODE=match` · `THINK_MS=3000` · `MAX_PLIES=100` · VU 12, 2026-08-24 01:58 부터 02:05 (UTC).

**널널히 통과한 4·6판 계단은 뺐다.** 워커 하나로도 백로그가 0이었으므로 둘에서 다시 볼 것이 없다.

### 실측 — 같은 계단, 같은 박스

| 12 VU (6판)                 | 워커 1 ([§106](101-120.md)) | 워커 2 + 우선순위            |
| --------------------------- | --------------------------- | ---------------------------- |
| `EnginePoolInUse` 최대      | **1**                       | **2**                        |
| `AnalysisBacklogPlies`      | **36→443 단조**             | **최대 13, 0으로 복귀**      |
| 탐색 처리량                 | 237→143→127/분 (하락)       | **217~319/분** (안 떨어진다) |
| `EnginePoolWaitGameSeconds` | 마이크로초                  | **표본 0**                   |
| 버린 판 · 5xx · panic       | 0                           | 0                            |

**세 가지가 같이 움직였다.** 풀을 다 쓰고(1→2), 줄이 안 쌓이고(443→13), 처리량이 포화에서 떨어지지 않는다. **그래서 12판은 이제 이 박스의 포화가 아니다.**

**탐색 시간에 42.45초 한 점이 있다.** 스팟이 태스크를 뺀 그 분의 값이고 — 엔진이 죽는 중이었다 — 그 앞 여섯 분은 2.9~6.5초다. 같은 창을 다시 조회하는 사람이 이 점을 부하로 읽지 않게 적어 둔다.

**사람은 한 번도 안 기다렸다.** `EnginePoolWaitGameSeconds` 에 표본이 아예 없다 — 대국·검토·가정 수순이 우선줄이라 빈 엔진을 늘 즉시 받았다는 뜻이다. 분석이 풀을 다 쓰는 것과 착수가 안 밀리는 것이 같이 성립한다는 것이 이 회차의 확인이다.

**16판 계단은 못 걸었다.** 아래 곁다리의 이유다. → **[§108](101-120.md)에서 걸었고 그 계단이 포화다** — 천장은 6판과 8판 사이이고, 그 위에서 재는 것은 박스가 아니라 크레딧 절벽이었다.

### 곁다리 — 스팟이 하루에 네 번 가져갔다

인스턴스 수명이 **12분·46분** 수준이었다. 오늘 뜬 것이 다섯이고, 종료 이유를 읽을 수 있었던 **넷이 전부 `Server.SpotInstanceTermination`** 이다(하나는 이미 조회에서 사라졌다).

**이유는 `StateReason.Code` 에만 있다.** `StateTransitionReason` 은 `Service initiated` 라서 그것만 보면 스팟인지 알 수 없다 — [§106](101-120.md)에서 한 번 그렇게 오진했다.

**계단 하나가 8분인데 박스가 12분을 산다.** [§106](101-120.md)의 곁다리는 이것을 「26분 장애」로 적었는데, 반복되면 성질이 다르다 — **회차를 끝까지 돌릴 수 없다.** 12판은 7분을 벌어 답을 얻었고 16판은 운에 맡기는 자리가 됐다.

**대체가 안 되는 이유도 같다.** `ap-northeast-1a`·`1c` 둘 다 t4g.small 스팟 재고가 없어서 ASG 재시도가 전부 실패한다. **회수와 대체 실패가 한 원인이다.**

### 곁다리 — 「사이트가 죽었다」 알람이 12분 늦다

`show-gi-no-healthy-target` 은 울렸다. 다만 늦었다 — 태스크가 빠진 것이 02:05:22 인데 메일이 **02:17:08** 이다.

늦는 이유가 구조에 있다. 타깃이 사라지면 `HealthyHostCount` 가 0이 아니라 **결측**이 되고, 그것을 위반으로 세는 데 5주기가 필요하며(`evaluation_periods = 5`), CloudWatch 가 「결측이다」를 선언하는 데 다시 몇 분이 걸린다.

**`evaluation_periods` 를 줄이는 것은 답이 아니다.** 그 5분은 정상 배포를 거르기 위한 값이다 — 태스크가 한 대라 배포가 유일한 태스크를 먼저 내리고 기동 유예 120초가 붙는다. 줄이면 배포마다 울리고, 그러면 사람이 알람을 무시하기 시작한다.

**그래서 회수 전에 오는 신호를 따로 받게 했다.** AWS 가 EventBridge 로 두 가지를 준다 — `EC2 Instance Rebalance Recommendation`(위험이 높아졌다)과 `EC2 Spot Instance Interruption Warning`(2분 전). 지표가 아니라 이벤트라 알람으로는 못 받는다.

**2분으로 용량을 구해 오지는 못한다.** 값은 둘이다 — 「왜 내려갔나」를 나중에 추측하지 않는 것, 그리고 부하 회차 도중이면 **그 회차가 곧 무효가 되는 것을 그 자리에서 아는 것**이다.

**알람 토픽에 얹지 않았다.** 그쪽은 정책 리소스가 없어서 AWS 기본 정책으로 도는데, EventBridge 를 붙이려면 정책을 명시해야 하고 그 순간 기본 정책이 대체되어 **지금 오는 알람 메일이 조용히 끊길 수 있다.** 스팟 이벤트가 시끄러운 것도 이유다(하루 다섯 번) — 갈라 두면 이쪽만 끌 수 있다.

### 곁다리 — 도구가 죽은 서버를 초당 40번 두드렸다

회차 요약이 「96.9% 실패」였는데, 실패 2,383건이 **한 분 안에 다 있었다**(스팟이 태스크를 뺀 직후). 그 앞 7분은 전부 200이다.

`match.js` 가 거절을 받으면 즉시 물러나서 k6 가 곧바로 다음 이터레이션을 시작한다 — 백오프가 없어서 VU 12개가 초당 40번을 보냈다. **1분짜리 장애가 회차 전체의 실패로 읽힌다.** 물러나기 전에 한 박자 쉬게 고쳤다.

**엔진 대국 쪽도 같은 모양이다**(WS 가 안 열리면 이터레이션이 그 자리에서 끝난다). 그쪽은 이번에 안 물렸으므로 안 건드렸다. → **[§109](101-120.md)에서 물렸다** — 스팟 회수 중에 엔진 회차를 걸었더니 1분 18초에 이터레이션이 1282번 돌았다. 같은 처치를 넣었다.

## 108. 8판 계단을 걸었고 포화를 봤다 — 그런데 잰 것은 박스가 아니라 크레딧 절벽이다 (2026-08-24)

[§107](101-120.md)이 12판을 뚫고 「그 위를 못 걸었다」로 끝났다. 같은 박스·같은 설정으로 16 VU 를 걸었다 — `MODE=match` · `THINK_MS=3000` · `MAX_PLIES=100` · 8분, 2026-08-24 02:51:45 부터 02:59:45 (UTC), 태스크 정의 118.

**이번에는 스팟이 안 가져갔다.** 인스턴스가 02:29 에 떠서 회차 내내 살아 있었다 — 계단을 끝까지 돌린 것이 [§107](101-120.md) 이후 처음이다.

### 알게 된 것

**① 8판이 포화다.** 백로그가 **1 → 3 → 66 → 140 → 267 → 453 → 533 → 691 → 756** 으로 계단 내내 단조 증가했다 — 시작 전에 적어 둔 깨짐 정의의 확정 신호다. 6판은 최고 13에 0으로 돌아왔으므로([§107](101-120.md)) **천장은 6판과 8판 사이**다. 7판은 안 걸었다.

산수가 맞는다. 8판 × 20手/분 × 手당 2.5탐색([§104](101-120.md))이면 **필요 ≈ 400탐색/분**인데 박스가 낸 것이 216~389/분이다. 모자란 만큼이 줄에 쌓였다.

**② 그런데 마지막 2분에 성질이 바뀐다.** 탐색 평균이 0.7초에서 **8.52초**로 뛰고 처리량이 389 → 18/분으로 무너졌다. 부하가 는 것이 아니다 — **CPU 크레딧이 말랐다.**

| 5분 구간 (UTC) | 크레딧 잔량 | 크레딧 사용 | CPU 평균  |
| -------------- | ----------- | ----------- | --------- |
| 02:50          | 8.11        | 0.10        | 31.4%     |
| 02:55          | 3.59        | 6.53        | **78.8%** |
| 03:00          | **0.248**   | 5.35        | **19.9%** |

`t4g.small` 의 baseline 이 20% 인데 CPU 가 19.9% 에 붙었다. **박스가 느려진 것이 아니라 AWS 가 조인 것이다.**

**③ 그래서 T 계열에서는 용량표 행을 적을 수 없다.** [§106](101-120.md) ④가 「용량이 시간 제한이 붙은 값」이라고 적은 자리인데, 이번에 그 벽을 정면으로 봤다 — 8판의 답이 「된다/안 된다」가 아니라 **「7분 된다」**다. 그 7분은 회차를 시작할 때 쌓여 있던 크레딧(8.11)이 정한 값이라, 어제의 부하가 오늘의 용량을 바꾼다. **재현되지 않는 축 위에서는 「어느 클래스 몇 대」를 못 적는다.**

**④ 워커 둘의 이득이 크레딧이 마르면 사라진다.** 회차가 끝난 뒤 백로그가 03:01 의 1177 에서 03:16 에 0 이 됐다. 그 사이 **크레딧은 한 번도 안 돌아왔다** — 잔량이 내내 0.25 이고 CPU 가 19.9% 에 붙어 있었다.

앞 11분(03:03 의 1120 → 03:14 의 616)의 배수가 **약 46手/분**이다. [§105](101-120.md)가 워커 하나로 잰 값이 **64手/분**이다 — 워커를 둘로 올렸는데 **더 느리다.** 통제된 비교는 아니지만(그쪽은 크레딧이 있었다) 방향이 분명하다: **손잡이가 둘이어도 vCPU 가 0.4개면 둘 다 못 돌린다.**

**마지막 2분은 갑자기 빨랐다** — 616 → 124 → 0 이고 한 분에 탐색이 1034회다. **[미확정]**: 크레딧도 CPU 도 안 올랐으므로(그 구간 CPU 평균이 오히려 12.2% 다) 남은 手가 `positions` 캐시에 이미 있어서 탐색이 즉시 끝난 것으로 보이는데, 확인하지 않았다. 미리 재는 층이 대국 중에 그 자리를 채웠다면 그 모양이 맞다([§105](101-120.md)).

**⑤ 봉우리가 판이 끝난 뒤에 온다.** 백로그 최고가 회차 종료(02:59:45) 뒤인 **03:01 의 1177**이다. 16 VU 가 두 번째 판을 두던 중에 끊겨서, 그 판들이 닫히며 아직 안 잰 手를 한꺼번에 넣었다. [§105](101-120.md)가 없앤 봉우리와 다른 것이다 — 저쪽은 정상 종료의 봉우리이고 이쪽은 **중단**의 봉우리다.

### 정한 것 — 박스를 비버스터블로 옮긴다

`instance_type` 을 **`c6g.large`**(2 vCPU / 4 GiB, 비버스터블)로 바꿨다. 고른 근거는 값이 아니라 **지속 vCPU 당 값**이다.

| 타입             | 지속 vCPU                | 스팟 $/hr | 지속 vCPU 당 |
| ---------------- | ------------------------ | --------- | ------------ |
| `t4g.small` (전) | **0.4** (크레딧 마른 뒤) | 0.0094    | $0.0235      |
| `c6g.large`      | **2.0**                  | 0.0366    | **$0.0183**  |

지금 싼 것은 「대부분 놀 것」을 전제로 산 값이고 부하 회차가 그 전제를 깼다. `m6g.large` 는 같은 2 vCPU 에 8 GiB 라 안 쓰는 RAM 값을 더 낸다 — 엔진이 쓰는 양은 `ENGINE_HASH_MB` 가 정하므로 `task_memory` 도 1536 그대로 둔다.

**`credit_specification` 을 조건부로 바꿨다.** 크레딧은 T 계열에만 있는 개념이라 다른 계열에 그 블록을 주면 기동이 거절된다.

**apply 만으로는 도는 박스가 안 바뀐다.** ASG 가 `$Latest` 를 보지만 이미 떠 있는 인스턴스는 그대로라, 새 타입은 다음 교체 때 뜬다. 그래서 그 자리에서 한 번 내렸다 — **03:27:01 종료 → 03:28 healthz 200 으로 약 1분 단절**이고, `ap-northeast-1c` 에서 `c6g.large` 스팟을 즉시 받았다. **재고를 미리 못 재고 띄워 봤다** — operator 에 `ec2:GetSpotPlacementScores` 가 없다.

### 정한 것 — 대인전 포화에 알람을 세운다

[§104](101-120.md)가 세운 `EnginePoolWaitGameSeconds` 알람은 이 회차에서도 **표본이 0**이라 아무것도 못 본다. 병목이 풀이 아니라 「엔진이 낼 수 있는 탐색 수」라서, 대국은 우선줄이라 안 밀리고 분석만 줄을 선다.

그래서 `show-gi-analysis-backlog` 을 세웠다 — **`AnalysisBacklogPlies` 가 5분 내내 100手를 넘으면** 운다.

- **임계 100 은 실측 사이에 둔다.** 6판이 최고 13이고 8판이 4분째에 140을 넘긴다
- **5분을 다 요구하는 것은 봉우리를 거르기 위해서다.** 판이 끝나는 순간 아직 안 잰 手가 한꺼번에 들어오므로(위 ⑤) 단발로 넘는 것은 정상이다
- **이른 신호는 알람으로 안 만든다.** `EngineSearchSeconds` 가 0.24초에서 8.52초로 갈리지만 국면 난이도에도 흔들리므로 대시보드가 맡는다

**태스크가 둘이 되면 이 알람이 틀린다.** 큐가 프로세스 안의 채널이라 값이 합이 아니라 한 대의 줄이다([§101](101-120.md)) — 스케일아웃보다 그것이 먼저다.

### 곁다리 — 대기열 밴드가 또 넓어졌다

큐 대기가 중앙값 2.05초인데 **p95 18.25초 · 최대 35.09초**다. [§106](101-120.md) ⑤와 같은 이유이고 같은 한계다 — 시드가 회차를 거치며 흘러간 값이라 **밴드 실측으로 쓸 수 없다.** 그 회차는 여전히 `seed.sql` 을 사람 둘 · 폭 700 으로 심어야 답한다.

### 곁다리 — `seed.sql` 이 DataGrip 에서 다르게 돈다

psql 전용 문법(`:n`·`\if`)을 썼는데 프로덕션 DB 는 사람이 DataGrip 으로 도는 자리다. 한 번은 `n=16` 이 `spread` 로 들어가 사용자가 안 늘었다. **`n` 과 `spread` 가 서로 다른 statement 에서 한 번씩만 쓰이므로 변수 자체가 필요 없었다** — 숫자 둘을 파일에서 고치는 것으로 바꿨다.

## 109. 비버스터블 박스에서 다시 쟀다 — 절벽은 없어졌고 천장은 그대로다 (2026-08-24)

[§108](101-120.md)이 박스를 `c6g.large` 로 옮겼다. 같은 계단을 그 위에서 다시 걸었다 — `MODE=match` · `THINK_MS=3000` · `MAX_PLIES=100` · 8분, 태스크 정의 120.

### 실측 — 대인전 계단 둘

| 분  | 8판 백로그 / 탐색·분 / 탐색 평균 | 6판 백로그 / 탐색·분 / 탐색 평균 |
| --- | -------------------------------- | -------------------------------- |
| 1   | 0 / 267 / 0.19초                 | 0 / 202 / 0.19초                 |
| 2   | 30 / 342 / 0.46초                | 3 / 312 / 0.29초                 |
| 3   | 80 / 283 / 0.59초                | 9 / 295 / 0.58초                 |
| 4   | 153 / 210 / 0.81초               | 47 / 195 / 0.74초                |
| 5   | 199 / 270 / 0.71초               | 140 / 74 / 2.65초                |
| 6   | 455 / 204 / 0.80초               | **313** / 241 / 1.22초           |
| 7   | **498** / 305 / 0.53초           | **220** / 557 / 0.56초           |
| 8   | 325 / 817 / 0.42초               | **51** / 645 / 0.38초            |

**둘 다 거절 0 · 5xx 0 · panic 0 · 버린 판 0 이고 `cut=stall` 이 없다.** 사람의 풀 대기는 두 계단 다 **표본 0**이다.

**갈리는 것은 「스스로 따라잡았나」다.** 6판은 부하가 도는 중에 313 → 220 → 51 로 내려왔고, 8판은 계단이 끝날 때가 정점이었다. **그래서 지속 가능선이 6판이고 포화가 8판이다.**

**절벽이 없어졌다.** [§108](101-120.md)의 `t4g.small` 은 8분째에 탐색이 26회/분 · 평균 8.52초로 무너졌는데, 같은 계단에서 `c6g.large` 는 305회/분 · 0.53초를 유지했다. 회차 뒤 배수도 **4분**이다(t4g 는 16분).

**그런데 천장은 안 올라갔다.** 8판이 여전히 포화다 — 두 박스가 같은 Graviton2 코어 2 vCPU 라서다. `c6g.large` 가 산 것은 속도가 아니라 **재현성**이다. 어제 부하가 오늘 용량을 바꾸지 않는다.

**CPU 가 71.7%(최대 92.1%)로 안 찼다.** 천장을 정하는 것이 vCPU 가 아니라 `ENGINE_POOL_SIZE=2` 일 수 있다. **이 회차에서 확인 못 했다** — 그 값이 `ecs.tf` 에 있어 배포가 필요하다.

> **이 숫자는 이 대인전 계단의 것이고, 엔진 계단은 같은 pool 2 에서 이미 99% 였다**([§110](101-120.md)). 그래서 위의 「천장이 풀일 수 있다」는 대인전 층에만 걸리는 말이었고, 4로 올려 재 보니 그쪽도 풀은 경합조차 안 하고 있었다.

### 알게 된 것 — 판 길이를 100手로 고정하면 축이 하나로 남는다

[§107](101-120.md)이 같은 12 VU 에서 **백로그 최고 13**을 적었는데 이번 6판은 **313**이다. CloudWatch 원본을 다시 읽어 보니 §107 의 기록이 맞다 — 그 회차는 WS 12로 8분 돌았고 백로그가 0·4·13·3·0·7·2·0 이며 처리량도 217~319/분으로 이번과 같다.

**처리 쪽이 같으니 도착 쪽이 다르다.** 이번 6판은 판이 짧아서(게임쪽당 40手, 8판 회차는 83手) **8분에 12판이 끝났다.** 끝나는 판 하나가 최종 `analyze` · 총평 · 퀴즈를 다 부르므로, 짧은 판이 두 배로 자주 끝나면 종료 처리도 두 배다.

**그래도 축을 하나 더 세우지 않는다.** 완주율로 정렬해 보면 단조롭지가 않다 — §107 이 0.75판/분에 백로그 13, 이번 6판이 1.5판/분에 313, 8판이 1.0판/분에 498 이다. 완주 하나로 설명되지 않으므로 축이 아니다.

**대신 판 길이를 100手로 고정해 읽는다.** 그러면 판 하나가 5분(3초 × 100手)이고 동시 N판이 분당 N/5 판을 끝내므로, **완주율이 동시 판수에서 유도되는 값이 되어 축이 하나로 남는다.** 100手 는 임의 가정이 아니다 — 실제 대국 평균이 그 언저리이고 도구가 60을 안 쓰는 이유도 그것이다(`tools/loadtest/README.md`).

**그 모델에서 이번 6판은 벗어나 있다.** 판이 100手까지 안 가고 詰み로 일찍 끝난 것이 섞였다 — 그래서 이 회차의 313 은 축의 증거가 아니라 **모델을 벗어난 측정**으로 적는다.

**단서 하나만 남긴다** — 초심자가 일찍 投了하는 인구에서는 이 행이 낙관적일 수 있다. 실사용 판이 쌓이면 그때 본다.

### 실측 — `MODE=both`, 우선순위 풀이 처음 다퉜다

엔진 4판 + 대인전 6판 · 6분. [§101](101-120.md)이 지으려던 회차이고, `borrower` 라벨과 우선순위 줄이 배포 뒤 처음으로 실제로 부딪힌 자리다.

| 분    | 풀 대기 표본 / p95 | 백로그  | 탐색/분 |
| ----- | ------------------ | ------- | ------- |
| 04:13 | 100 / 0.42초       | 7       | 312     |
| 04:14 | 100 / 1.33초       | 72      | 268     |
| 04:15 | 87 / 1.99초        | 150     | 195     |
| 04:16 | 72 / **3.95초**    | 239     | 154     |
| 04:17 | 64 / **3.39초**    | 352     | 107     |
| 04:19 | 57 / 1.80초        | **727** | 202     |

**우선순위가 듣는다.** 같은 6분 동안 `move_cycle` 을 시나리오별로 가르면 답이 분명하다.

| 시나리오  | 표본 | 중앙값 | p95        | 최대        |
| --------- | ---- | ------ | ---------- | ----------- |
| 대인전    | 745  | 3.04초 | **3.06초** | **3.08초**  |
| 엔진 대국 | 208  | 3.71초 | **9.10초** | **26.52초** |

대인전은 `THINK_MS` 3초를 빼면 서버 몫이 **40~80ms** 이고 포화 내내 안 변했다. 분석은 뒤로 밀려 백로그가 727까지 갔다 — **줄 둘이 설계대로 갈렸다.**

**다만 대국끼리는 서로 기다린다.** 풀이 2인데 엔진 대국이 4판이라 `game` 이 `game` 뒤에 선다 — 우선순위는 분석을 상대로만 듣고 엔진을 만들어 주지는 않는다. [§104](101-120.md)의 「3판째부터 기다린다」가 그 자리다.

**[§107](101-120.md)의 「사람은 한 번도 안 기다렸다」는 대인전만 잰 값이다.** 컴퓨터와 두는 사람은 여기서 p95 9.1초를 기다렸다.

**오늘 세운 알람이 처음 울렸다** — `show-gi-analysis-backlog` 이 이 회차에서 ALARM 이 됐다. `show-gi-engine-pool-wait` 은 안 울렸다: p95 가 3초를 넘긴 것이 2분이라 「5분 중 3분」에 못 미친다.

### 실측 — 엔진 대국 계단, 그리고 워크로드마다 다른 판정선

엔진 대국은 착수마다 엔진을 빌리므로 **`EnginePoolWaitGameSeconds` 가 곧 사람의 대기**다. 그래서 판정선이 대인전과 다르다 — 대인전은 백로그가 스스로 내려오는가이고, 엔진 대국은 **풀 대기 p95 ≤ 3초**다([§104](101-120.md)가 실측으로 잡은 값이자 알람 임계).

`MODE=engine` · VU 8 · 12분, 2026-08-24 04:27~04:39.

|                    | 값                                                 |
| ------------------ | -------------------------------------------------- |
| 풀 대기 p95 (분당) | **5~15.4초** (최저 1.28 · 최고 15.44)              |
| `move_cycle`       | 중앙값 **1.40초** · p95 **17.44초** · 최대 52.79초 |
| 완주 · 手 · 개입   | 5판 · 1111手 · 689건                               |
| 백로그             | **내내 0**                                         |
| 거절 · 5xx · panic | 0                                                  |

**판정선의 다섯 배라 8판은 포화다.** [§104](101-120.md)가 `t4g.small` 8판에서 잰 `move_cycle` p95 16.5초와 거의 같다 — 같은 2 vCPU 라서 크레딧이 있는 동안의 값과 겹치는 것이 맞다.

**아래로 내려가며 선을 찾았다.** 4판과 6판을 같은 설정으로 걸었다.

| 판 수 | 정착 구간의 풀 대기 p95 (분당)                 | `move_cycle` p95 | 판정          |
| ----- | ---------------------------------------------- | ---------------- | ------------- |
| **4** | 1.51 · 2.14 · 2.47 · 2.99 · (3.29)             | 7.92초           | **지속 가능** |
| **6** | 3.66 · 3.68 · 4.59 · 4.82 · 5.55 · 7.39 · 8.52 | 12.45초          | **포화**      |
| 8     | 5.74 ~ 15.44                                   | 17.44초          | 포화          |

4판은 5분 중 1분만 선을 넘고 6판은 매분 넘는다. **엔진 대국의 선은 4판이다.**

**두 회차 다 앞 2~3분이 마이크로초다.** `positions` 캐시가 데워져 있어서 탐색이 0.14초에 끝나고, 캐시가 마르는 분에 p95 가 14.47초(4판)·5.55초(6판)로 튄 뒤 정착한다. **앞 2분만 보고 「여유 있다」로 읽으면 두 자릿수 배로 틀린다** — 엔진 대국 회차는 정착 구간으로만 판정한다.

### 실측 — 섞으면 단순 합이 아니다

엔진 2판 + 대인전 6판 · 8분. 각각 단독으로는 4판·6판까지 되는데, [위](101-120.md)에서 엔진 4판 + 대인전 6판은 포화였다.

| 시나리오  | 표본 | 중앙값 | p95        | 최대    |
| --------- | ---- | ------ | ---------- | ------- |
| 대인전    | 981  | 3.03초 | **3.05초** | 3.09초  |
| 엔진 대국 | 293  | 0.14초 | **2.19초** | 10.61초 |

풀 대기 p95 가 **0.31~0.50초**(표본이 두 분에만 잡혔다), 백로그가 **0~6**, 거절·5xx·드롭 0. **두 기준을 다 넉넉히 통과한다.**

**그래서 섞인 부하는 각 워크로드의 선을 더해서 못 구한다.** 엔진 4판(단독 통과) + 대인전 6판(단독 통과)이 포화이고 엔진을 둘로 줄여야 선다 — **엔진 대국 한 판이 대인전보다 훨씬 비싸다**는 뜻이다. 대인전 착수는 엔진을 안 부르고 사후 분석만 남기는데, 엔진 대국은 착수마다 부른다.

**백로그가 0인 것이 대인전과의 차이다.** 엔진 판은 길어서 회차 안에 다섯 개만 끝났고, 사후 분석은 판이 끝날 때 오므로 줄이 설 일이 없었다. **엔진 대국의 병목은 착수 경로이고 대인전의 병목은 사후 분석이다** — 같은 박스인데 아픈 곳이 다르다.

### 알게 된 것 — 풀 대기 알람이 두 가지 이유로 안 운다

`show-gi-engine-pool-wait`(p95 3초 · 5분 중 3분)이 오늘 두 회차에서 다 안 울렸다. 이유가 서로 다르다.

|               |                                                                                                                                                 |
| ------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| `MODE=both`   | p95 가 3초를 넘긴 분이 **둘**뿐이었다(3.95 · 3.39). 임계 설계대로다                                                                             |
| `MODE=engine` | p95 가 내내 5~15초인데도 안 울렸다 — **표본이 매분 안 나와 결측이 섞이고**, `treat_missing_data` 가 `notBreaching` 이라 그 분이 위반에서 빠진다 |

두 번째가 함정이다. 상태 이유가 그대로 적혀 있다 — `1 datapoint was received for 2 periods and 1 missing datapoint was treated as [NonBreaching]`. **가장 아픈 회차에서 가장 조용한 알람**이고, 조용한 이유가 「부하가 없다」가 아니라 「표본이 드문드문하다」다. **[미확정]**: 고치는 방향이 `treat_missing_data` 인지 창 길이인지 아직 안 정했다.

### 곁다리 — 엔진 시나리오가 죽은 서버를 1분에 1282번 두드렸다

### 정한 것 — 스팟 풀을 넓힌다

풀은 「타입 × AZ」다. 타입 하나에 AZ 둘이면 풀이 둘이고, **회수와 대체 실패가 같은 원인에서 온다** — 그 풀이 마른 것.

`mixed_instances_policy` 로 후보를 여섯으로 늘렸다(`c6g` · `c7g` · `m6g` · `m7g` · `r6g` · `c6gn` 의 `.large`). **전부 비버스터블 2 vCPU arm64 다** — T 계열을 섞으면 [§108](101-120.md)의 크레딧 절벽이 돌아와 용량표가 다시 「몇 분 버티나」가 된다.

**`capacity-optimized-prioritized` 를 쓴다.** 재고가 깊은 풀을 고르되 순서를 힌트로 본다 — 회차가 어느 클래스에서 돌았는지 알아야 표를 적을 수 있어서다. Graviton3(`c7g`·`m7g`)는 코어가 더 빠르므로 표의 값은 하한으로 읽는다.

**온디맨드로 안 떨어뜨린다.** 그러려면 `on_demand_base_capacity` 를 1로 둬야 하는데 한 대뿐이라 늘 온디맨드이고 값이 네 배가 된다.

**ALB 는 AZ 둘 그대로다.** AZ 수만큼 퍼블릭 IPv4 가 과금된다(`alb.tf`) — 셋째 AZ 는 풀을 1.5배로 늘리는 대신 월 $4 쯤이라 아직 안 한다.

### 남긴 것 — 사이트가 죽은 것을 결측이 아닌 값으로 보는 수단 **[미확정]**

Route53 헬스 체크가 후보다. 30초마다 `HealthCheckStatus` 를 무조건 내므로 타깃이 사라져도 값이 0으로 남고, 그러면 **12분이 1~2분이 된다.** 위 곁다리 1번처럼 **인스턴스가 멀쩡한데 앱이 없는 상태**도 잡는다 — ALB 타깃 지표는 그때도 결측이다.

**안 지은 이유는 리전이다.** 그 지표는 `us-east-1` 에만 있어서 알람도 거기 세워야 하고, 알람은 같은 리전의 SNS 에만 보낼 수 있다 — 토픽과 이메일 구독이 한 벌 더 생기고 **구독 확인 메일을 사람이 다시 눌러야 한다.** 지금 알람 넷이 도는 경로를 건드리지 않는 값이 그 복잡도보다 큰지는 아직 안 정했다.

**어느 쪽이든 `show-gi-no-healthy-target` 은 남긴다.** 둘이 보는 것이 다르다 — 이쪽은 ALB 안쪽, 저쪽은 밖에서 본 사이트다.

## 110. 풀을 4로 올려 봤고 되돌렸다 — 대기가 탐색 시간으로 옮겨갔을 뿐이다 (2026-08-24)

[§109](101-120.md)가 「포화에서 CPU 가 71.7% 밖에 안 찼으니 천장이 `ENGINE_POOL_SIZE=2` 일 수 있다」로 끝났다. 4로 올려 배포하고 다시 쟀다.

### 정한 것 — 풀은 레버가 아니다. 2로 되돌린다

**빌린 구간이 탐색 하나뿐이라 그렇다.** `usi.Pool.Do` 가 Acquire·탐색·Release 를 붙여 두고, DB 는 그 밖이다 — 캐시 조회는 `archive.Searcher` 가 풀을 부르기 전에 하고 기록은 goroutine 으로 던진다. 슬롯을 잡은 채 CPU 를 안 쓰는 구간이 없으므로, 슬롯을 코어보다 많이 줘도 같은 CPU 를 잘게 쪼개는 것뿐이다.

`task_memory` 도 1536 으로 되돌린다. 탐색 2 + mate 1 이면 ~380 MB 다.

### 알게 된 것 — 종료 분석은 판 하나당 한 줄이다

병렬은 판 사이에만 있다. 판이 도는 중에는 `prefetch` 가 手마다 job 을 넣어 워커 여럿이 서로 다른 手를 잡지만, 판이 끝날 때의 `analyze` 는 job 하나가 한 워커를 잡고 `for ply := 1..N` 을 순차로 돈다.

**그래서 되먹임이 하나 있다.** 종료 분석은 `recall` 로 미리 잰 값을 재사용하는데, 선행 계산이 밀린 판은 그만큼 그 자리에서 엔진을 부른다 — 비싸진 종료 분석이 워커를 오래 잡아 백로그를 더 밀린다. [§109](101-120.md)의 8판이 단조로 자라고 6판이 313 → 51 로 내려온 차이가 그 문턱이다.

순서는 안 보장해도 된다. 手 하나의 판정이 `moves[:ply]` 로 시작 국면부터 다시 만들어 독립이고, 결과가 `plies[ply]` 맵에 들어가고, 쓰는 쪽이 1→N 순서다. **같은 국면이 같은 값을 준다는 것에 기대고 있다** — `setEval` 이 한 국면의 평가치를 두 번 쓰는데(手 N-1 의 after, 手 N 의 before) 그 둘이 다른 워커의 다른 탐색에서 나온다.

### 알게 된 것 — 詰み 풀은 프로덕션에서 안 보인다

EMF 의 풀 지표 전부가 `searchPool` 필터를 지난다(`metrics/emf.go`). `EnginePoolInUse` · `EnginePoolWaitSeconds` · `EnginePoolWaitGameSeconds` 가 `pool == "search"` 만 센다. 詰み 풀은 `reg.Pool(metrics.PoolMate)` 로 계측이 붙어 있는데 컨테이너 안 `/metrics` 에만 남고, Caddy 가 그 경로를 프록시하지 않는다.

**그래서 위의 「풀 대기 0」은 탐색부 풀만이다.** 詰み 풀이 줄을 섰는지는 프로덕션 데이터로 알 수 없다.

빌리는 자리가 넷인데 `startMateEngines` 의 주석은 셋으로 적어 뒀다 — 종반 판정 · 詰み 게이지 · 되짚기 퀴즈에 **대인전 사후 분석**이 빠져 있다. 그쪽은 `analyst.go` 의 `SearchMate` 가 게이트 없이 手마다 불리므로, 대인전 8판 회차면 분당 200~300회다. → **실측은 분당 153회다**([§113](101-120.md)).

### 알게 된 것 — 詰み 결과에는 캐시 층이 없다

탐색부는 `archive.Wrap` 이 `positions` 로 감싸서 같은 국면을 두 번 안 잰다(위 표의 캐시율 37~80%). 詰み 풀에는 그 층이 없고, 캐시가 퀴즈 빌드 안의 `mateSolver.memo` 하나뿐이라 빌드 하나 동안만 산다.

**그래서 게이지와 퀴즈가 같은 질문을 두 번 한다.** 둘 다 「사람 차례 국면에서 몇 手로 詰ますか」이고 국면 집합이 같다 — 게이지가 판이 도는 동안 사람 차례 국면을 전부 묻고(`session.go` 의 `maybeGauge`), 퀴즈가 판이 끝난 뒤 그 전부를 다시 묻는다(`quiz/mate.go` 의 `mateItem`). 게이지가 구한 手数는 세션 메모리에만 있고 다음 手에 덮인다.

**그리고 詰み 없는 국면이 제일 비싼 답이다.** `DepthLimit` 11까지 다 뒤진 뒤에야 `nomate` 로 답하므로, 훑기 구간의 거의 모든 국면이 가장 오래 걸리는 종류다. 퀴즈 생성이 판 끝에서 수십 초를 잡는 이유가 이것이다([§53](41-60.md)).

### 곁다리 — 스팟이 대체까지 막아 프로덕션이 내려갔고, 온디맨드로 옮겼다

14:54 에 회수로 태스크가 드레이닝된 뒤 **기동이 8번 연속 실패했다.** `c6g.large` 재고가 `1a` · `1c` 둘 다 말라서다. [§109](101-120.md)가 정한 `mixed_instances_policy` 가 **아직 apply 되지 않은 상태**였다 — 후보가 여전히 타입 하나였다.

apply 로 그 정책과 함께 `on_demand_base_capacity = 1` 을 넣었다. 회차가 8~15분인데 회수 하나가 약 9분 장애라, 회수를 밟으면 잰 것이 용량이 아니라 복구 시간이 된다. `c6g.large` 온디맨드가 하루 $2.15 이므로 이틀 회차의 차액이 $3 쯤이고, 그것이 회차를 다시 도는 값보다 싸다. **회차가 끝나면 0으로 되돌린다.**

`on_demand_allocation_strategy` 를 `prioritized` 로 못 박았다. 온디맨드는 override 순서대로 고르므로 `c6g.large` 에 확실히 앉고, 그래야 [§109](101-120.md)와 같은 클래스에서 잰 값이 된다.

**이 회차가 온디맨드에서 돈 첫 회차다.**

### 남긴 것 — 다음 레버는 vCPU 다

`06-status.md` §1 에 [§104](101-120.md)가 적어 둔 문장이 있었다 — 「풀을 올리면 대기가 탐색 시간으로 옮겨갈 뿐이고 수직 스케일(2→4 vCPU)이 답이다」. **그것이 추측에서 확인으로 바뀌었다.** 엔진 층은 pool 2 에서 이미 CPU 99% 였고, 대인전 층은 88% 인데 그 여유가 백로그를 못 따라잡는다.

`c6g.xlarge`(4 vCPU) 가 다음 회차다. 그때 `ENGINE_POOL_SIZE` 를 같이 올린다 — 코어가 늘면 슬롯을 늘릴 이유가 생긴다. 이번 회차가 말한 것은 **코어를 안 늘린 채 슬롯만 늘리는 것이 이득이 없다**는 것뿐이다.

## 111. 詰み 결과에 캐시 층을 붙였다 — 표를 갈랐고 timeout 은 안 쌓는다 (2026-08-25)

[§110](101-120.md)이 「詰み 결과에는 캐시 층이 없다」로 남긴 자리다. 탐색부는 `archive.Wrap` 이 `positions` 로 감싸는데 詰み 풀에는 그 층이 없어서, 빌리는 넷이 같은 질문을 겹쳐서 하고 있었다.

### 정한 것 — 표를 갈랐다. `positions` 에 컬럼을 더하지 않는다

`mate_positions`(`017`) 하나다. 컬럼 셋 + `created_at` 이고 `positions` 를 FK로 참조하지 않는다.

| 이유                      |                                                                                                                                                   |
| ------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| 「깊은 것이 이긴다」가 둘 | 탐색은 `computed_depth` 와 후보 수로, 詰み은 `depth_limit` 으로 갈린다. `ON CONFLICT` 하나에 두 규칙을 넣으면 한쪽 사실이 다른 쪽 갱신에 지워진다 |
| FK 를 안 거는 이유        | 詰み 답은 그 국면을 탐색한 적이 있는지와 무관하게 참이다. 참조를 걸면 퀴즈가 훑는 국면마다 후보 없는 `positions` 행을 먼저 만들어야 한다          |

### 정한 것 — 「행이 없다」가 곧 「모른다」다

`checkmate timeout` 은 행을 만들지 않는다. 증명된 것만 쌓으므로 `moves` 가 빈 배열이면 증명된 「詰み이 없다」이고, 행이 아예 없으면 「아직 안 물어봤다」다.

**규칙을 주석이 아니라 스키마가 든다.** 「timeout 만 캐시 금지」는 [01-core.md §2](../01-core.md)가 이미 적어 둔 것인데, 그것을 `proven` 불리언으로 표현하면 그 칸을 안 보는 질의 하나가 규칙을 깬다. 행의 유무로 두면 깨질 자리가 없다.

### 정한 것 — 읽는 조건이 둘이다

`archive.Mate.lookup` 이 견주는 것이 둘이고, 어느 하나를 빠뜨리면 증명 안 된 답이 증명된 답으로 나간다.

| 조건                   | 없으면                                                                       |
| ---------------------- | ---------------------------------------------------------------------------- |
| `depth_limit >= plies` | 한계 9의 「詰み이 없다」를 한계 11의 답으로 쓴다                             |
| `len(moves) <= plies`  | 한계 15가 찾은 13手詰을 한계 11로 물은 쪽에 준다 — 그 한계로는 증명이 아니다 |

그래서 `ENGINE_MATE_PLIES` 를 읽는 자리를 `matePlies()` 하나로 모았다. 풀에 주는 `DepthLimit` 과 캐시가 견주는 값이 같아야 하고, 파서가 둘이면 한쪽만 고쳐졌을 때 위 두 줄이 조용히 거짓말을 한다.

### 겹쳐 있던 질문 셋

키가 手数를 뺀 SFEN(`shogi.PositionKey`)이라 전치가 합쳐지고, 그 덕에 셋이 한 행으로 만난다.

| 부르는 쪽        | 언제                | 무엇을                                                  |
| ---------------- | ------------------- | ------------------------------------------------------- |
| 詰み 게이지      | 사람 차례마다       | 그 국면                                                 |
| 종반 판정        | 사람이 둔 직후      | **착수 전 국면 — 게이지가 한 手 전에 물은 그 국면이다** |
| 되짚기 퀴즈      | 판이 끝난 뒤        | 사람 차례 국면 전부 — 게이지가 이미 물은 그 전부다      |
| 대인전 사후 분석 | 착수마다(미리 재기) | 착수 전 국면. 게이트가 없다                             |

게이지와 판정이 같은 국면인 것은 `Config.Mate` 의 주석이 「묻는 국면이 다르다」로 적어 둔 자리다. **그 문장이 한 방향으로만 맞았다** — 판정이 게이지보다 나중이라 게이지가 판정을 기다릴 수는 없지만, 반대 방향은 성립한다. 주석을 고쳤다.

**대인전의 호출도 이제 표를 채운다.** 8판 회차면 분당 200~300행이다. → **「낭비였다」로 적었던 것이 틀렸다**([§113](101-120.md)) — `judged` 가 버리는 것은 `explain.Facts` 뿐이고, 詰み 판정은 `Verdict.LostMate` 로 `skill.Move` 에 남아 실력 추정에 들어간다.

### 예약통을 비우는 자리가 두 축이 됐다

`DrainSamplesSplit(pick, by)` 을 `DrainSamplesAll()` 로 바꿨다. 라벨을 그대로 주고 부르는 쪽이 묶는다.

이유는 **예약통을 비우는 것이 `pick` 과 무관**하다는 것이다 — 두 번 부르면 두 번째가 늘 빈 배열이라, 같은 지표를 여러 벌로 내려면 한 호출에서 다 갈라야 한다. 풀 대기는 축이 `pool`·`borrower` 둘인데 옛 함수는 하나만 갈랐고, 그래서 詰み 쪽 표본이 비워진 채 버려지고 있었다. 축 하나를 더 넣는 대신 라벨을 넘기는 쪽으로 바꾼 것은 세 번째 축이 필요해지는 날 이 함수를 또 고치지 않기 위해서다.

### 보는 자리

`engine_mate_searches_total{result}` 와 같은 이름의 히스토그램이다. 탐색부와 갈라 센다 — 詰み 쪽은 한계까지 다 뒤진 `nomate` 가 가장 비싸서 분포의 모양이 아예 다르고, `engine_search_duration_seconds` 는 [§106](101-120.md)이 정한 부하 신호다.

`result` 가 셋이다. `unproven` 이 따로 있는 것은 **캐시가 영원히 안 채워지는 구간**을 보기 위해서다 — timeout 은 부르고도 안 쌓이므로 나머지 둘로는 안 보인다.

EMF 에 셋이 올라간다. 대시보드는 위젯 하나가 새로 붙고 풀 대기 위젯에 선 둘이 더해진다.

| 지표                                  | 답하는 것                                                            |
| ------------------------------------- | -------------------------------------------------------------------- |
| `MateSearches` · `MateSearchesCached` | **양** — 몇 번 부르고 몇 번 캐시가 답했나. 비율이라 둘이 다 필요하다 |
| `MatePoolWaitSeconds`                 | **경합** — 슬롯을 빌리려고 줄을 섰나                                 |

**둘이 다른 질문이라 하나로 다른 하나를 못 대체한다.** [§110](101-120.md)이 잰 것이 정확히 그 실패였다 — 풀 대기가 내내 마이크로초인데 백로그는 498까지 자랐다. 캐시가 히트율을 내도 남은 미스가 슬롯에서 줄을 서면 양 지표에는 안 보인다.

`MatePoolWaitSeconds` 를 borrower 로 안 가른다. 탐색 풀은 크기가 2~4라 「대국이 굶었나」를 갈라 볼 값이 있는데(`EnginePoolWaitGameSeconds`), 詰み 풀은 크기가 2라 **대기가 0보다 큰 것 자체가 포화**다.

**값이 이 판단의 근거가 아니었다.** 차원이 `Service`·`Environment` 둘뿐이라 이름 하나가 과금 지표 하나이고([§90](82-100.md)), 개당 월 $0.30 이다([§102](101-120.md)의 「13개 월 $4쯤」). 로그는 EMF 가 1분에 한 줄이라 트래픽과 무관하게 월 ~$0.03 늘 뿐이다. 인프라가 월 ~$42 인데 셋을 더해 ~$0.9 다 — 「열 개로 묶는다」의 근거가 요금이었으므로, 요금이 이 값이면 그 선이 이것을 막을 이유가 없다. **EMF 는 이제 열두 개 + 분포 다섯이다.**

### 남은 것 · 안 본 것

- **히트율은 [§112](101-120.md)에서 쟀다** — 엔진 6판 73.1%(콜드 포함) · 8판 90.8%. 이 절을 쓸 때는 solver 가 로컬에서 안 돌아(arm64 Debian 바이너리) 확인한 것이 감싸는 층과 `017` 의 `ON CONFLICT` 뿐이었다
- **`EnginePoolInUse` 는 여전히 탐색 풀만이다.** 대기는 위에서 갈랐지만 점유 게이지는 `searchPool` 필터를 그대로 지난다 — 안 가른 이유는 詰み 풀 크기가 2라 「몇 중 몇」이 정보를 거의 안 준다는 것이다(대기가 그 답을 이미 한다). 크기를 올리는 날 같이 본다
- **`017` 은 들어갔고 대시보드도 apply 됐다**(2026-08-25). 표는 인덱스가 PK 하나·FK 0개다(`06-status.md` §3). 대시보드는 위젯 여덟(4,192바이트)이고, **값은 [§112](101-120.md)의 회차에서 채워졌다** — 그 전까지는 계열이 namespace 에 없었다
- **게이지의 답을 판정에 직접 넘기는 것은 안 했다.** 캐시가 그 자리를 덮으므로 배선을 늘릴 이유가 없어졌다 — 세션이 手数를 들고 다니면 그 값의 세대를 판정 쪽에서도 견줘야 하고, 그건 캐시가 공짜로 하는 일이다
- **퀴즈는 빨라지지만 깊어지지는 않는다.** `mateSolver.distance` 가 예산(`MateSearchBudget=2400`)을 부르기 **전에** 깎고, 감싼 층이 히트를 숨기므로 캐시가 답해도 한 칸이 빠진다. 그래서 훑는 국면 수는 그대로다 — 예산을 히트에서 안 깎게 고치면 퀴즈가 더 멀리 훑지만, 그건 바깥 `quizTimeout` 과 같이 봐야 하는 값이라 이 PR 밖이다
- **한계를 올리면 캐시가 통째로 비워진다.** `ENGINE_MATE_PLIES` 를 11→13 으로 올리면 쌓인 행 전부가 조건 ①에 걸려 다시 재진다. 맞는 동작이지만 그 배포의 첫 회차는 캐시가 없는 것과 같다. 내리는 방향은 안 비워진다
- **지운 적이 없다.** `positions` 와 같은 성질이라 행이 계속 쌓인다. 지금 그것을 줄이는 장치가 레포에 없고, 이 표도 같은 자리에 놓는다

## 112. 詰み 캐시를 프로덕션에서 쟀다 — 풀 경합은 사라졌고 용량표는 그대로다 (2026-08-25)

[§111](101-120.md)이 붙인 캐시를 실물로 쟀다. 계단 둘이고 같은 인스턴스(`i-02f45b0ec0fc84297`, `c6g.large` 온디맨드)에서 돌았다 — [§109](101-120.md)·[§110](101-120.md)이 돌았던 그 인스턴스라 **바뀐 변수가 코드 하나**다.

`MODE=engine` · `THINK_MS=0` · `MAX_PLIES=100` · 15분, `ENGINE_POOL_SIZE=2` · `ENGINE_MATE_POOL_SIZE=1`.

### 실측

|                               | ① 6판 (표가 0행에서 시작)                                  | ③ 8판 (889행에서 시작)      |
| ----------------------------- | ---------------------------------------------------------- | --------------------------- |
| 츠미 호출 / 캐시              | 5,262 / 3,848                                              | 4,617 / 4,190               |
| **히트율**                    | **73.1%**                                                  | **90.8%**                   |
| **츠미 풀 대기 p95**          | 1.09 · 1.08 → 0.16 · 0.06 · 0.16 · 0.09 → **0.00 아홉 분** | 0.53 → **사실상 0.00 내내** |
| 탐색 대기 p95 (borrower=game) | 2.83 ~ 15.05                                               | 1.96 ~ 11.67                |
| 탐색 p95                      | 4.94 ~ 17.74                                               | 3.23 ~ 15.20                |
| CPU                           | —                                                          | 94 · 99 · 99                |
| 분석 백로그                   | 0 내내                                                     | 0 내내                      |
| 완주 / 手数                   | 13판 / 2,282                                               | 14판 / 1,987                |
| `showgi_rejects` · 5xx        | 0 · 0                                                      | 0 · 0                       |
| 표 행                         | 0 → 889                                                    | 889 → 1,279                 |

①의 분당 히트율은 **11.2 → 76.5 → 73.5 → 75.5 → 60.6 → 72.5 → 86.0 → 85.7 → 77.2 → 85.8 → 84.8 → 86.1 → 83.2 → 81.7 → 72.8 → 67.3** 이다. 첫 분이 표가 빈 구간이고, 정착 구간은 80% 언저리다.

**쌓인 것의 94% 가 「詰み 없음」이다**(1,279행 중 1,212). 캐시가 아끼는 것이 가장 비싼 답에 쏠려 있다는 §111의 근거가 이것이다 — 한계 11까지 다 뒤진 뒤에야 `nomate` 로 답한다.

### 정한 것 — 이 캐시가 산 것은 용량이 아니라 츠미 층의 응답성이다

**츠미 풀 경합이 사라졌다.** 풀 크기가 1인데 8판에서도 대기가 0.00 이다. [§110](101-120.md)이 「詰み 풀이 줄을 섰는지는 프로덕션 데이터로 알 수 없다」로 남긴 자리에 답이 둘 다 왔다 — 줄을 섰던 것도(①의 첫 두 분 1.09·1.08) 없어진 것도 사실이다.

**그런데 용량표는 한 칸도 안 옮겼다.** 엔진 대국의 「지속 가능 4판 · 포화 6판」(`06-status.md` §5)이 그대로다 — ①의 6판에서 풀 대기 p95 가 판정선 3초를 열다섯 분 중 열 분 넘었고, CPU 는 ③에서 99% 다.

**병목이 츠미가 아니었기 때문이다.** 벽은 탐색부가 쓰는 2 vCPU 이고, 츠미에서 푼 CPU 를 탐색이 그대로 흡수한다. [§110](101-120.md)의 「다음 레버는 vCPU」가 이 회차로도 유효하다.

### 정한 것 — single-flight 는 만들지 않는다

같은 국면을 두 goroutine 이 동시에 미스하면 둘 다 계산하고 행은 하나만 남는다(같은 한계면 `ON CONFLICT` 가 갱신하지 않는다). 그 몫을 `computed − 신규 행` 으로 셌다.

|        | computed | 신규 행 | 중복 | 비율     |
| ------ | -------- | ------- | ---- | -------- |
| ① 콜드 | 1,414    | 889     | 525  | **37%**  |
| ③ 웜   | 427      | 390     | 37   | **8.7%** |

**중복은 콜드 현상이다.** 웜 상태에서는 미스가 드물고 국면이 흩어져 있어 충돌이 안 난다. → **대인전은 축이 다르다**([§113](101-120.md)) — 웜에서 출발했는데도 포화에서 17.7% 이고 지속 구간에서 0.06% 다. 만들지 않는다는 판단은 같고 근거가 바뀐다. ①만 보고 정했으면 37% 를 근거로 층을 하나 더 만들었을 것이고, 정착 상태에서 그것이 사는 값은 9% 다.

### 알게 된 것 — `unproven` 이 0 이다

`checkmate timeout` 이 두 회차 합쳐 **한 건도 없다.** [01-core.md §2](../01-core.md)의 「162국면 전부 미증명 0」이 표본 1만 건에서도 유지된다 — 캐시가 채워지지 않는 구간이 없다는 뜻이고, 그래서 히트율의 상한이 겹침의 양으로만 정해진다.

**읽는 방법이 하나 있다.** 그 라벨은 `/metrics` 에만 있고 Caddy 가 그 경로를 프록시하지 않는데, ECS Exec 으로 컨테이너 안에서 읽힌다. `curl`·`wget` 이 없으므로 bash 의 `/dev/tcp` 를 쓴다.

```sh
aws ecs execute-command --cluster show-gi --task <id> --container api --interactive \
  --command "/bin/bash -c 'exec 3<>/dev/tcp/127.0.0.1/8080; printf \"GET /metrics HTTP/1.0\r\n\r\n\" >&3; grep engine_mate <&3'"
```

`--command "/bin/sh"` 는 `EOF` 로 끊긴다 — 대화형 입력을 기다리는데 stdin 이 바로 닫혀서다. 일회성 명령을 줘야 한다.

> **`unproven` 을 계산으로 구할 수 있다고 적으려던 것을 접었다.** `(호출 − 캐시) − Δ행` 은 위 표의 중복까지 세므로 ①에서 525 를 내놓는데 실제 값은 0 이다. 상한이기는 하지만 그 정도로 느슨하면 쓸 수 없다.

### 남은 것 · 안 본 것

- **`cut=capped` 가 섞였다.** `GAME_TIMEOUT_MS`(기본 900초)를 `DURATION`(15분)과 같게 두어서, 이 README 가 경고한 자리를 그대로 밟았다. ③의 `showgi_stalls` 2건은 `iteration_duration` p95·max 가 정확히 15분이고 `move_cycle` 최대가 45.67초(`STALL_TIMEOUT_MS` 90초의 절반)라 **`capped` 로 본다 — 라벨을 직접 못 봤으므로 추론이다.** 다음 회차는 `GAME_TIMEOUT_MS` 를 넉넉히 키운다
- **`THINK_MS=3000` 계단을 안 걸었다.** 중복 계산의 도구 몫을 가르려던 것인데, ③의 8.7% 가 그 질문을 대체로 닫았다
- **대인전 계단은 [§113](101-120.md)에서 걸었다** — 정상 구간 히트율 8.0%(6판) · 포화에서 20.2%(8판)이고, 용량표는 그쪽에서도 안 움직였다. 이 자리에 「결과를 버리므로 히트율이 표 채우기다」로 적으려던 것은 틀렸다 — 詰み 판정은 `Verdict.LostMate` 로 실력 추정에 들어간다
- **`EnginePoolInUse` 는 여전히 탐색 풀만이다**([§111](101-120.md)). 츠미 풀 크기를 올리는 날 같이 본다

## 113. 詰み 캐시를 대인전에서 쟀다 — 히트율은 소비자 수가 정하고, 용량표는 여기서도 안 움직였다 (2026-08-25)

[§112](101-120.md)가 엔진 계단 둘을 재고 「대인전 계단을 안 걸었다」로 남겼다. 같은 인스턴스(`i-02f45b0ec0fc84297`, `c6g.large` 온디맨드)에서 계단 둘을 걸었다 — `MODE=match` · `THINK_MS=3000` · `MAX_PLIES=100` · 15분, `ENGINE_POOL_SIZE=2` · `ENGINE_MATE_POOL_SIZE=1`. 표가 1,279행(엔진 회차가 채운 것)에서 출발했다.

①의 백로그는 최고 **37**(회차 끝)이고 즉시 0이다. ②는 **0 · 12 · 16 · 48 · 92 · 209 · 199 · 84 · 161 · 174 · 420 · 524 · 628 · 465 · 428** 이다.

**②의 골은 회복이 아니라 톱니다.** 골이 둘(84 · 428) 있는데 봉우리가 **209 → 628**로 커지고 부하가 끝날 때 428이다. 골이 난 두 분(18:17 · 18:24)이 히트율 **68.7% · 69.5%** 인 그 분이다 — 판 여덟이 한꺼번에 끝나 종료 분석이 手 1..N 을 다시 훑는데, 선행 계산이 이미 쌓아 둔 국면이라 詰み 몫을 안 갚는다. [§110](101-120.md)이 적은 되먹임 고리의 츠미 쪽을 캐시가 끊는다. 그것만으로 도착을 못 이긴다.

회차 뒤 배수는 **771 → 0 이 5분**이다(≈154手/분). 771은 판이 잘리며 안 잰 手가 들어간 중단 봉우리다([§108](101-120.md) ⑤). 마지막 1분이 433手를 한꺼번에 비우는데 그 분의 히트율이 **91.3%** 다.

### 정한 것 — 히트율은 국면이 아니라 소비자 수가 정한다

엔진 계단이 73.1%·90.8% 인데([§112](101-120.md)) 대인전은 정상 구간 8.0% 다. 국면 성질이 아니라 **한 국면을 몇 번 묻느냐**의 차이다.

| 소비자         | 엔진 대국                        | 대인전               |
| -------------- | -------------------------------- | -------------------- |
| 詰み 게이지    | 사람 차례마다                    | 없다                 |
| 종반 판정      | 게이지가 한 手 전에 물은 그 국면 | 手마다 (게이트 없음) |
| 되짚기 퀴즈    | 판 끝에 전부 다시                | 없다                 |
| `opponentMate` | 게이트됨                         | 게이트됨             |

엔진 대국은 한 국면을 셋이 묻고 대인전은 하나가 한 번 묻는다. **겹침이 없는 곳에는 캐시가 안 걸린다** — 8%는 판들 사이에서 序盤이 겹치는 몫이다. 도구가 무작위로 두므로 그 8%는 하한이고, 定跡을 두는 인구에서는 序盤 겹침만 오른다. 소비자가 하나인 구조는 그대로다.

**포화에서는 다르다.** ②의 20.2% 와 배수 구간의 45.7% 가 그 자리다 — 선행 계산이 밀리면 종료 분석이 같은 국면을 다시 묻게 되어, **캐시가 값을 하는 구간이 정상 구간이 아니라 포화 구간**이다.

### 정한 것 — 용량표는 대인전에서도 안 움직였다

`06-status.md` §5 의 「대인전 6판 지속 · 8판 포화」([§109](101-120.md))가 그대로다. 그래서 [§112](101-120.md)의 「캐시가 산 것은 용량이 아니라 츠미 층의 응답성」이 **두 워크로드에서 확정**된다.

**이번 회차가 그 행을 처음으로 100手 모델 위에서 확인했다.** [§109](101-120.md)의 6판은 판이 40手라 스스로 「모델을 벗어난 측정」으로 적어 둔 것인데, 이번은 판이 100手·5분이고 완주가 6판 1.2판/분 · 8판 1.6판/분으로 모델(N/5)과 정확히 맞는다.

**왜 안 움직이는지가 숫자에 가까워졌다.** `/metrics` 의 히스토그램에서 계산된 詰み 탐색이 **평균 0.113초**이고 4,256건 중 4,255건이 0.25초 이하다(캐시 히트는 0.0055초). ②의 詰み 엔진 시간은 배수까지 합쳐 **약 271초**다.

**같은 구간의 탐색 시간은 이 회차에서 안 쟀다.** [§109](101-120.md)의 대인전 계단 평균(0.19~~0.8초)을 7,912회에 쓰면 1,500~~6,300초이므로 **詰み 층은 엔진 부하의 4~15%** 다 — 폭이 넓지만 어느 끝에서도 소수다. 그 20%를 캐시가 걷어도 표가 안 옮겨지는 이유가 여기 있다. **[미확정]**: 탐색 시간을 같이 재면 이 비율이 한 값으로 좁혀진다.

### 알게 된 것 — 중복 계산은 콜드 현상이 아니라 포화 현상이다

`계산 − 신규 행` 으로 셌다. `unproven` 이 0 이므로(아래) 이 차이가 전부 중복이다.

|              | 계산  | 신규 행 | 중복 | 비율      |
| ------------ | ----- | ------- | ---- | --------- |
| ① 6판 (지속) | 1,808 | 1,807   | 1    | **0.06%** |
| ② 8판 (포화) | 2,398 | 1,974   | 424  | **17.7%** |

[§112](101-120.md)가 엔진에서 「콜드 37% → 웜 8.7%」를 보고 **콜드 현상**으로 적었다. 대인전은 축이 다르다 — 웜에서 출발했는데도 포화에서 18%이고 지속 구간에서 0이다. 백로그가 쌓이면 선행 계산과 종료 분석이 같은 국면을 동시에 미스하기 때문이다.

**그래도 single-flight 는 만들지 않는다.** 424건 × 0.113초 = **48초**이고, 15분 계단에서 2 vCPU 의 3% 다. 판단은 §112와 같고 근거가 바뀐다 — 「중복이 정착하면 사라진다」가 아니라 **「중복이 남는 구간에서도 그 값이 작다」**다.

### 알게 된 것 — `unproven` 이 두 계단에서도 0 이다

`/metrics` 를 ECS Exec 으로 읽었다. `engine_mate_searches_total` 에 `cached` 1,101 · `computed` 4,256 뿐이고 **`unproven` 라벨이 아예 없다.** `cached` 가 EMF 합계(4 + 157 + 940)와 정확히 맞아 계열이 같은 것을 확인했다. [01-core.md §2](../01-core.md)의 「미증명 0」이 표본 1.5만 건으로 늘어난 뒤에도 유지된다.

### 고친 것 — 「대인전은 詰み 결과를 버린다」가 틀렸다

[§111](101-120.md)과 [§112](101-120.md)가 그렇게 적었는데 코드가 그렇지 않다. `judged` 가 버리는 것은 `explain.Facts`(개입 문구 재료)뿐이고, 詰み 판정은 이 경로로 살아남는다.

```
analyst.Judge        SearchMate → in.MateBefore
intervene.Decide     MateBefore > 0 → LostMate 블런더 분기
skillMoveOf          Verdict.Kind → skill.Move.Blunder
updateSkill          → 두 사람의 실력 추정
```

**대인전 실력 추정이 終盤을 보는 유일한 눈이다.** 그 구간은 승률이 포화해 낙폭 판정이 詰み 놓침을 못 잡는다. 그래서 手마다 게이트 없이 부르는 것이 낭비가 아니고, 「히트율이 제품 개선이 아니라 표 채우기」도 틀렸다 — 그 호출은 원래 제품 기능이다. 두 절의 그 문장을 고쳤다.

### 남은 것 · 안 본 것

- **7판을 안 걸었다.** 천장이 6판과 8판 사이라는 것까지다([§109](101-120.md)와 같은 자리)
- **캐시 없는 100手 6판 회차가 없다.** ①의 백로그 0과 [§109](101-120.md)의 313을 직접 못 견준다 — 그쪽이 40手 판이라서다. 그래서 「캐시가 6판을 편하게 했다」를 이 회차로 주장하지 않는다
- **`showgi_move_cycle` 이 시나리오별로 안 갈렸다.** `main.js` 가 `scenario` 태그를 붙이는데 k6 요약이 합친 값 하나만 냈다. → **갈라 찍게 고쳤다** — 태그가 붙은 하위 지표를 임계치로 선언하면 요약이 그것을 넣으므로, `handleSummary` 없이 `MODE=both` 에서만 선언용 임계치를 붙인다
- **알람.** `show-gi-analysis-backlog`(5분 내내 100手 초과)이 ②에서 울릴 조건이다. 회차 시각은 위 표에 있다

③의 백로그는 **0 · 0 · 32 · 85 · 138 · 313 · 247 · 307 · 367 · 497 · 757 · 814 · 800 · 860 · 819 · 866** 이다. 회차 뒤 최고 900(19:54)에서 0까지 **7분**이다.

②를 경계로 적는 이유는 마지막 3분에 풀 대기가 2.02 · 1.21 · **3.87** 로 올라온 것이다. [§104](101-120.md)의 알람 조건(5분 중 3분)에는 안 걸린다.

### 정한 것 — 대인전 착수는 어느 계단에서도 안 굶는다

`move_cycle` 이 3.03 · 3.03 · 3.03초이고 p95 가 3.04 · 3.05 · 3.06 이다(`THINK_MS` 3초를 빼면 서버 몫 30~60ms). 같은 회차에서 엔진이 1.05 → 5.20 → **13.82초** 로 간다.

**우선순위가 지켜 준 것이 아니라 구조다.** 대인전 착수 경로가 엔진을 안 지난다([§105](101-120.md)). 굶는 것은 **엔진 대국의 착수**와 **대인전의 사후 분석** 둘이고, 그 둘이 같은 2 vCPU 를 나눠 쓴다. [§109](101-120.md)가 「우선순위가 듣는다」로 적은 자리를 계단 셋으로 다시 보면, 우선순위가 가르는 것은 대국과 분석이고 **대인전이 안전한 이유는 그것과 별개**다.

### 정한 것 — 엔진이 포화하면 대인전 분석이 같이 무너진다. 반대는 아니다

③의 대인전은 **3판**인데 백로그가 866까지 자란다. 단독 지속선이 6판이고([§109](101-120.md) · [§113](101-120.md)) 3판의 도착이 약 60手/분인데 [§113](101-120.md)이 잰 배수가 154手/분이다 — **대인전 혼자서는 이 백로그를 만들 수 없다.** 엔진 6판이 엔진을 가져가서 분석이 줄을 선 것이다.

**반대 방향은 안 보인다.** ②의 엔진은 4판이고 판정이 단독 4판과 같은 「지속 가능」이다 — 대인전 2판을 얹은 것이 그 선을 못 넘겼다. 다만 같은 `THINK_MS` 의 단독 계단이 없어 **얼마나 못 넘겼는지는 못 잰다.**

**그래서 섞인 부하는 각 선을 더해서 못 구한다.** [§109](101-120.md)가 판 단위로 적은 그 문장이 사람 단위 계단에서도 성립하고, 이번에는 **어느 쪽이 어느 쪽을 무너뜨리는지**까지 갈렸다.

### 정한 것 — 용량표에 「섞어서 (사람 반반)」 행을 적는다

`c6g.large` 1대 · 2 vCPU 에서 **8명 지속 가능 · 12명 포화**다. 판으로 옮기면 엔진 4판 + 대인전 2판이 서고, 엔진 6판 + 대인전 3판이 무너진다.

**깨지는 자리가 엔진의 단독 선과 같다.** 엔진은 단독으로도 4판 지속 · 6판 포화다([§109](101-120.md) · [§112](101-120.md)) — 사람 반반으로 섞어도 그 선이 안 움직인다. 대인전이 얹히는 것은 그 선을 넘긴 뒤에 **분석 층까지 같이 무너뜨리는 것**이지, 선을 앞당기지 않는다.

### 알게 된 것 — ③은 부하를 올렸는데 처리량이 줄었다

엔진 판을 4에서 6으로 늘렸는데 탐색이 **4,800 → 2,825** 다. CPU 는 70% 에서 99% 로 올랐다. 일을 더 시켰는데 더 적게 했다.

**[미확정]**: 탐색 하나가 비싸진 것으로 보이는데 `EngineSearchSeconds` 를 이 회차에서 안 읽었다. 츠미 히트율이 80.8% 에서 67.9% 로 같이 떨어진 것이 「국면이 새로워졌다」쪽을 가리키지만, 그것만으로 41% 감소를 설명하지 못한다.

**`showgi_plies` 로는 이 물음에 답할 수 없다.** 그 지표는 도구가 **보낸 수**를 세고 개입 뒤 재착수도 다시 센다(`engine.js:159`) — ②의 개입이 1,062건이라 手数가 그만큼 부푼다. 처리량은 서버 쪽 `EngineSearches` 로 읽는다.

### 알게 된 것 — 히트율이 섞인 비율을 따라간다

①·②가 80% 인데 [§113](101-120.md)의 대인전 단독이 8.0% 였다. 엔진 대국이 섞이면 소비자 셋(게이지 · 판정 · 퀴즈)이 다시 겹쳐서다. ③에서 67.9% 로 내려가는 것도 같은 축이다 — 그 계단은 대인전 手가 엔진 手보다 많아져 **한 번만 묻는 쪽의 비중이 커진다.**

[§113](101-120.md)의 「히트율은 국면이 아니라 소비자 수가 정한다」가 세 번째 워크로드에서도 맞는다. 중복 계산은 세 계단 다 사실상 0이다.

### 도구 — 요약을 시나리오별로 가른다

[§113](101-120.md)이 남긴 자리다. 태그가 붙은 하위 지표를 **늘 통과하는 임계치로 선언**하면 k6 요약이 그것을 부모 지표 아래에 찍는다 — `handleSummary` 도 외부 import 도 필요 없다. `MODE=both` 에서만 붙인다.

이것이 없었으면 위 표의 첫 두 줄이 `move_cycle` 하나로 합쳐져서, ③의 「엔진 13.82초 · 대인전 3.06초」가 **p95 10.3초 하나**로 보인다. 그 값으로는 무엇이 굶었는지 못 가른다.

### 남은 것 · 안 본 것

- **같은 `THINK_MS` 의 엔진 단독 계단이 없다.** [§104](101-120.md) · [§109](101-120.md) · [§112](101-120.md)의 엔진 계단은 전부 `THINK_MS=0` 이라 엔진 축을 그쪽과 직접 못 견준다. 위의 「엔진 선이 안 움직인다」는 **이 계단 셋 안에서만** 읽는다
- **10명을 안 걸었다.** 8명과 12명 사이다
- **판 수를 반반으로 맞춘 회차는 안 걸었다.** 사람 반반이면 판이 엔진 2 대 대인전 1 이라, 「판이 반반일 때」는 다른 회차다
- **`EngineSearchSeconds` 를 안 읽었다.** ③의 처리량 감소를 가르는 값이다

## 115. 미리 재는 줄을 표로 내렸다 — 그 자리에서 버그가 둘 나왔다 (2026-08-25)

백로그로 오토스케일하려면 **새로 뜬 대가 이미 쌓인 일을 집어 갈 수 있어야 한다.** 지금은 그 줄이 프로세스 메모리라(`matchAnalyzer.plies`) 대수를 늘려도 각자 자기 몫만 먹는다 — 그건 스케일아웃이 아니라 샤딩이고, 그래프에 백로그가 안 내려온다.

그래서 手 단위 줄을 표로 내렸다(`analysis_plies`, `018`). 소비자는 아직 같은 프로세스이고 대수도 1대다 — **이 회차에서 재는 것은 「같은 자리에서 값이 안 움직이는가」다.**

### 단위를 手로 한 이유

手 하나는 서로를 안 본다. `engineAnalyst.Judge` 가 받는 것이 `startSFEN + moves[:ply]` 뿐이라 순서 의존이 없다.

|        | 병렬성 천장     |
| ------ | --------------- |
| **手** | 없다            |
| **판** | 동시 진행 판 수 |

판 단위면 워커를 늘려도 진행 중인 판 수에서 막힌다. 오토스케일 그림에 천장이 생기는 자리이고, 백로그 지표가 이미 手로 세어지는 것과도 어긋난다([§101](101-120.md)).

### 표가 든 것 — 재는 데 필요한 입력과 잰 결과가 한 행이다

수순을 행에 싣는다. `game_moves` 에서 읽지 않는 이유는 그쪽에 구멍이 날 수 있어서다(`dbRecorder.send` 가 큐가 차면 버린다) — 세우는 쪽은 테이블 goroutine 이 들고 있는 수순이라 구멍이 없다.

결과 일곱 칸도 같은 행이다. **`blunder` 를 평가치에서 되구할 수 없다** — 종반 판정으로 걸린 手는 승률이 포화해 낙폭이 0에 가깝고(`skill.Move`), 그 사실은 solver 가 준 것이라 `game_moves.eval_cp` 에 안 남는다.

### 착수 경로가 DB 를 안 기다린다

`prefetch` 는 테이블 goroutine 이 부른다(`match.Recorder`). 거기서 INSERT 를 치면 착수가 그만큼 늦는다. 그래서 작은 배수구 하나를 앞에 두고 별도 goroutine 이 적는다 — **채널이 없어진 것이 아니라 줄에서 배수구로 성질이 바뀌었다.** 길이가 밀린 양이 아니라 「아직 못 적은 것」이다.

### 버그 ① — 집는 문장이 돌려주는 것보다 많은 행을 잠갔다

`IN (SELECT … LIMIT 1 FOR UPDATE SKIP LOCKED)` 로 썼더니 계획에 따라 서브쿼리가 바깥 행마다 다시 돌았다. 돌려받는 것은 한 행이고 나머지는 **아무도 재지 않은 채 「집힌」 상태로 리스(3분)를 앉아 있는다.**

워커를 1개로 고정하고 잰 값이다. 1이어야 한다.

| 집는 문장                | 도는 중인 手 |
| ------------------------ | ------------ |
| `IN (SELECT … LIMIT 1)`  | **3 ~ 8**    |
| `WITH … AS MATERIALIZED` | **0 ~ 1**    |

**워커를 늘릴수록 낭비가 커지는 종류다.** 이대로 대수를 늘렸으면 「2대인데 처리량이 안 는다」가 나왔고, 원인이 대수가 아니라 이 문장이라는 것을 그 회차로는 못 갈랐다.

`ANALYZE` 를 돌린 300행짜리 표에서는 계획이 제대로 나왔다. **작은 표에서만 어긋난다** — 그래서 SQL 을 단독으로 확인하는 것으로는 안 잡히고, 부하 회차가 잡았다.

### 버그 ② — 종료를 판의 실패로 읽었다

`lookAhead` 는 판정이 끊기면 그 판을 그만둔다(`dead`). 한 手가 실패하면 뒤도 전부 같은 자리에서 실패하기 때문인데, **ctx 취소를 같은 값으로 읽고 있었다.**

프로세스가 멈추는 중에 끊긴 것은 판의 성질이 아니라 우리 사정이다. 배포 한 번이 그때 두고 있던 판들의 미리 재기를 통째로 끄고, 그 판들은 手数만큼을 끝날 때 몰아서 재게 된다 — [§105](101-120.md)가 잰 봉우리를 배포마다 만드는 셈이다.

`ctx.Err() == nil` 일 때만 그만둔다. **手 하나의 시한은 여기 안 걸린다** — 그쪽은 `judge` 가 자기 ctx 를 따로 두르므로 바깥 ctx 가 멀쩡하고, 그때는 그만두는 것이 맞다.

### 덤 — 주석이 인정하던 흠 셋이 닫혔다

- **버려지는 판이 없어졌다.** 줄이 차면 판을 통째로 버리던 자리가 표에는 없다
- **메모리가 안 자란다.** `prefetchQueue = 2048` 이 「밀렸다를 알아차리기 전에 메모리가 먼저 자란다」로 묶여 있던 값이다([§105](101-120.md))
- **배포를 이겨낸다.** 리스가 낡으면 다음 워커가 도로 집는다. 판 단위 줄은 아직 메모리라 그쪽은 그대로 끊긴다

### 실측 — 로컬 엔진, 대인전 회차

`MODE=match VUS_MATCH=4 THINK_MS=800 MAX_PLIES=40`.

|                          |                            |
| ------------------------ | -------------------------- |
| 완주한 판                | **6판 (games 행 12개)**    |
| 평가치                   | **80/80 手 전부** (판마다) |
| 실력 프로파일            | 16건 갱신                  |
| 회차 뒤 `analysis_plies` | **0행**                    |
| 거절 · 오류 로그         | **0**                      |

회차 중에 표를 보면 **세운다 → 집는다 → 잰다 → 판이 끝나면 걷는다**가 그대로 보인다. ① 고치기 전에는 「도는 중인 手」가 워커 수를 넘었고, 고친 뒤로는 안 넘는다.

### 도구 — `ANALYSIS_WORKERS` 를 compose 에 뚫었다

코드는 원래 읽고 있었는데(`cmd/api` 의 `analysisWorkers`) 컨테이너로 넘길 길이 없었다. **워커 수를 1로 고정해 보는 것이 ①을 가른 유일한 방법이었다** — 3개일 때는 「느린 手가 셋」과 구별이 안 된다.

### 정한 것 — 큐는 표로 간다. MQ 로 안 바꾼다

이번에 어려웠던 둘은 MQ 에서 이름만 바뀐다 — ①은 가시성 타임아웃, ②는 nack 과 DLQ 다. **갈린 자리는 관측이다**: 표라서 질의 한 줄로 「3개 집혔는데 워커는 1개」와 「전부 dead」를 그 자리에서 읽었고, 큐 뒤에 있었으면 둘 다 「백로그가 늦게 준다」로만 보였다.

그리고 원래 이유가 그대로다 — **평가치 쓰기와 잡 완료가 한 커밋에 들어간다.** 갈라지면 멱등 방어를 따로 짠다. 도착률도 아직 초당 두어 개다.

**나가는 길은 열어 둔다.** 잡 큐가 `store` 뒤에 있으므로 초당 단위가 되는 날 표면 하나를 갈면 된다.

### 테스트 — 줄이 프로세스 공용이 되면서 갈린 것

집는 질의가 판을 안 가린다. 그래서 **앞 테스트의 워커가 뒤 테스트의 手를 집어 간다.** 셋을 고쳤다.

- 판이 끝난 뒤의 분석만 보는 자리는 **워커를 안 띄운다**(`analyzerFor`). 열일곱 자리가 `newMatchAnalyzer` 를 그것 하나 때문에 부르고 있었다
- 「워커 수가 지켜진다」는 **판 단위 줄로 잰다.** 手 쪽은 무엇이 언제 집히는지가 테스트의 손 밖이고, 재려는 사실은 두 줄에서 같다
- 미리 재는 것을 확인하는 자리는 **횟수가 아니라 목표치로 돈다**(`measureAhead`)

### 남은 것 · 안 본 것

- **판 단위 줄은 아직 메모리다.** 소비자를 다른 프로세스로 가르는 회차에서 같이 내린다
- **프로덕션에서 안 쟀다.** 위 표는 로컬 엔진(풀 3 · 워커 3)이고, [§113](101-120.md)의 6판·8판 선을 다시 밟는 회차가 아직이다 — **그것이 이 변경의 통과 조건이다**
- **`enqueue` 가 판의 남은 手를 dead 로 안 만든다.** 판이 끝난 뒤 `analyze` 가 인라인으로 재는 手를 다른 워커가 동시에 집을 수 있다. 낭비이고 값은 안 틀어지는데, 재 보지 않았다
- **리스 3분·폴링 2초·TTL 6시간은 실측이 아니다.** 手 하나가 시한 60초 안에 끝난다는 것에서 잡은 초기값이다
